## Theory (1h)

### A. What "full app" means for the milestone (15 min)
- By end of today the incremental project must run end-to-end on the kind
  cluster as ONE Helm release: app Deployment (Day 64), a database
  StatefulSet or Deployment+PVC (Day 68), a Service (Day 65), an Ingress
  (Day 66) exposing it, and the CronJob (Day 72) for reporting — all as
  templates in `fresher-project/`, all parameterized through one
  `values.yaml`.
- This is the payoff of Days 61–77: nothing new to learn here, this is
  INTEGRATION — the hardest and most realistic skill in the whole phase.

### B. CI driving a Helm deploy — the missing piece from Phase 2 (20 min)
- Recall Day 57's end-to-end thread (commit → Actions → build+scan →
  Ansible deploys to a VM). Today's version: commit → Actions → build+scan
  image → **Actions runs `helm upgrade --install` against a kind cluster
  spun up IN the CI runner itself** (using `helm/kind-action` or manually
  installing kind inside the GitHub Actions job) → smoke test.
- `helm upgrade --install <release> <chart> -f values.yaml --wait
  --timeout 5m` — `--install` makes it idempotent (creates if absent,
  upgrades if present — the Ansible idempotency principle, again),
  `--wait` blocks until resources are Ready (not just applied) so CI
  actually verifies success, not just submission.
- CI needs the freshly-built image tag injected into the Helm values —
  typically `--set image.tag=${{ github.sha }}` (or the CI's build
  number/tag), so every CI run deploys the EXACT image it just built and
  scanned, closing the traceability loop from Day 48.

### C. Ephemeral CI clusters vs persistent dev clusters (15 min)
- A CI-spun kind cluster is torn down every run — this is fine and
  intentional: CI proves "this chart deploys cleanly from zero," which is
  a stronger test than upgrading a long-lived cluster that's accumulated
  drift.
- Your LOCAL kind cluster (used through Days 61–77) stays as your everyday
  dev/lab environment — don't confuse the two; today's CI job creates its
  OWN throwaway cluster.

### D. Smoke-testing after deploy (10 min)
- After `--wait` succeeds, CI should still verify the app actually
  answers — reuse the `helm test` hook from Day 75, or a simple `kubectl
  run --rm -it curltest --image=curlimages/curl -- curl -sf
  http://<svc>` step that fails the job (non-zero exit) if the app doesn't
  respond correctly.

## Lab (2h)

### Part 1 — Extend the chart to "full app" (45 min)
1. Add a database component to `fresher-project/templates/` — a
   Deployment+PVC (simplest) or StatefulSet (recall Day 68) for a
   lightweight DB (postgres or sqlite-backed, whatever the project
   actually needs), parameterized in `values.yaml`
   (`database.enabled`, `database.image`, `database.persistence.size`).
2. Add an Ingress template (recall Day 66) exposing the app Service,
   parameterized (`ingress.enabled`, `ingress.host`).
3. Confirm the CronJob template from Day 75/72 is present and
   parameterized (`cronjob.schedule`).
4. `helm lint .` then `helm template . | kubectl apply --dry-run=server
   -f -` — fix everything before touching the live cluster.

### Part 2 — Full local deploy and verification (30 min)
5. `helm upgrade --install fresher-project . -f values.yaml --wait
   --timeout 5m` on your LOCAL kind cluster (with ingress-nginx already
   installed from Day 66).
6. `kubectl get all,ingress,pvc,cronjob -l app.kubernetes.io/instance=
   fresher-project` — confirm every piece is up: app, db, service,
   ingress, cronjob.
7. `curl <ingress-host>` (per your `/etc/hosts` entry from Day 66) — confirm
   the full path works end to end: Ingress → Service → app Pod → (app
   talks to db Pod via its Service DNS name).

### Part 3 — Wire it into CI (35 min)
8. Add a new job (or extend the existing pipeline) in
   `.github/workflows/` that: builds+pushes the image (reuse Day 48's
   steps), spins up a kind cluster in the runner (`helm/kind-action` is
   the simplest path, or manual `kind create cluster` steps), installs
   ingress-nginx, then runs `helm upgrade --install fresher-project ./
   fresher-project --set image.tag=${{ github.sha }} --wait --timeout 5m`.
9. Add a smoke-test step after the Helm step (curl-based check inside the
   runner's cluster, per Theory D) that fails the job if the app doesn't
   respond.
10. Push and watch the Actions run end to end — this is the ★ milestone:
    the FULL pipeline (build → scan → deploy to a k8s cluster → smoke
    test) is now automated and reproducible from zero on every commit.

### Part 4 — Document and reflect (10 min)
11. Update the project README with an architecture diagram (even ASCII is
    fine) showing: GitHub → Actions (build/scan/deploy) → kind cluster
    (app+db+ingress+cronjob), and a "how to run this locally" section
    matching Part 2's steps exactly.

## Definition of done
Helm chart now deploys the FULL app (app+db+ingress+CronJob) as one
release, verified locally end-to-end via curl · CI pipeline builds, scans,
spins up a fresh kind cluster, and deploys the chart automatically with a
passing smoke test · README updated with architecture + local-run
instructions · this is a milestone — do not move on until CI is green.
