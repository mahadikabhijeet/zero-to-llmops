## Theory (1h)

### A. RBAC — who can do what (20 min)
- Role-Based Access Control governs every `kubectl`/API call: "can this
  identity perform this verb on this resource, in this scope?"
- **Role**: namespaced permission set (verbs like `get/list/watch/create/
  update/delete` on resources like `pods`, `configmaps`).
- **ClusterRole**: same idea, but cluster-scoped (covers cluster-wide
  resources like `nodes`, or is reused across namespaces via bindings).
- **RoleBinding**: grants a Role (or ClusterRole) to a subject (User, Group,
  or ServiceAccount) **within one namespace**.
- **ClusterRoleBinding**: grants a ClusterRole cluster-wide.
- Golden rule: **least privilege** — grant only the verbs/resources actually
  needed; avoid `cluster-admin` bindings for anything but true break-glass
  access.

### B. ServiceAccounts — identity for workloads (15 min)
- Every Pod runs AS a ServiceAccount (default: the `default` SA in its
  namespace if none specified) — this is how a Pod authenticates to the API
  server (e.g., an app that needs to `list pods` or read a ConfigMap it
  doesn't own).
- Token is auto-mounted at
  `/var/run/secrets/kubernetes.io/serviceaccount/token` unless
  `automountServiceAccountToken: false` is set — a real hardening step for
  Pods that never call the API.
- Create a dedicated SA per app that needs API access; bind it to a
  narrowly-scoped Role — never grant broad permissions to the `default` SA.

### C. Security contexts — hardening the container itself (15 min)
- `securityContext` at Pod level (applies to all containers) or container
  level (overrides): `runAsNonRoot: true`, `runAsUser`/`runAsGroup`,
  `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`,
  `capabilities.drop: ["ALL"]` (drop all Linux capabilities, add back only
  what's needed).
- This is the k8s-native continuation of Day 48's "non-root image" hygiene —
  the image CAN run as non-root, but the Pod spec is what enforces it at
  runtime even if the image forgot.

### D. Pod Security Standards (10 min)
- Three levels replacing the deprecated PodSecurityPolicy: **Privileged**
  (no restrictions), **Baseline** (blocks known privilege escalations),
  **Restricted** (heavily hardened — non-root, no host access, dropped
  capabilities). Enforced via namespace labels
  (`pod-security.kubernetes.io/enforce: restricted`), checked natively by
  the API server (built-in admission controller, no extra install needed).

## Lab (2h)

### Part 1 — RBAC from scratch (40 min)
1. Create a namespace `rbac-lab`. Create a ServiceAccount `reader-sa` in it.
2. Write a Role `pod-reader` allowing `get/list/watch` on `pods` in
   `rbac-lab`. Write a RoleBinding granting it to `reader-sa`.
3. Run a debug pod AS that ServiceAccount (`spec.serviceAccountName:
   reader-sa`) with `kubectl` installed (use an image with kubectl, or
   `curl` the API directly using the mounted token + `kubectl proxy`
   alternative: exec `curl -sk -H "Authorization: Bearer $(cat
   /var/run/secrets/kubernetes.io/serviceaccount/token)"
   https://kubernetes.default.svc/api/v1/namespaces/rbac-lab/pods`).
4. Confirm it CAN list pods but CANNOT list secrets or delete anything —
   try `kubectl delete pod <name>` from inside using that SA's
   kubeconfig/token and confirm a `Forbidden` error, reading the exact
   RBAC denial message.

### Part 2 — ClusterRole and cross-namespace scope (25 min)
5. Write a ClusterRole `node-reader` allowing `get/list` on `nodes`
   (cluster-scoped resource, can't be namespaced). Bind it via
   ClusterRoleBinding to `reader-sa`.
6. From the same debug pod, confirm it can now list nodes but its pod-read
   access is still scoped to `rbac-lab` only (per the original RoleBinding).

### Part 3 — Security contexts (30 min)
7. Deploy a Pod with NO securityContext — `kubectl exec -it <pod> -- id`
   confirms it's running as root (default for many images).
8. Add `securityContext: {runAsNonRoot: true, runAsUser: 1000,
   readOnlyRootFilesystem: true, capabilities: {drop: ["ALL"]}}`. Reapply —
   note if the image breaks (many default images assume root/writable
   filesystem); if it CrashLoops, add an `emptyDir` volume mounted at
   whatever path the app needs to write, keeping the root FS read-only.
9. `kubectl exec -it <pod> -- id` and `kubectl exec -it <pod> -- touch
   /test` (expect Permission denied on root FS) to prove enforcement.

### Part 4 — Pod Security Standards at the namespace level (25 min)
10. Label the `rbac-lab` namespace `pod-security.kubernetes.io/enforce=
    restricted`.
11. Try to apply a Pod with no securityContext (running as root) into that
    namespace — confirm the API server REJECTS it outright with a policy
    violation message, without your app even needing an admission
    controller add-on.
12. Fix the Pod spec to satisfy `restricted` (non-root, dropped
    capabilities, etc.) and confirm it's now accepted.

## Definition of done
Created least-privilege RBAC (Role+RoleBinding, ClusterRole+
ClusterRoleBinding) and proved denial on out-of-scope actions · hardened a
Pod with a securityContext and proved the read-only filesystem enforcement ·
enforced Pod Security Standards at the namespace level and saw the API
server reject a non-compliant Pod.
