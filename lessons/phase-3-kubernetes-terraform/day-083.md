## Theory (1h)

### A. The provision/configure boundary, precisely (20 min)
- **Terraform provisions**: creates/destroys/tracks the EXISTENCE of
  infrastructure resources (a VM, a network, a kind cluster, a cloud
  bucket) — it does not care what's installed or running inside them
  beyond initial bootstrap.
- **Ansible configures**: takes an EXISTING target (a VM Terraform just
  created, or a fleet of pre-existing servers) and ensures its internal
  state (packages, users, files, services) matches a desired
  configuration — recall Day 54's "playbook that fully configures a
  fresh VM."
- The clean handoff pattern: Terraform creates a VM and OUTPUTS its IP
  (recall Day 80's `output` blocks) → that IP feeds into an Ansible
  dynamic inventory (or is written to a static inventory file by a script)
  → Ansible takes over from there. Neither tool should try to do the
  other's job — using Terraform's `provisioner "remote-exec"` to run
  shell commands post-creation is a known ANTI-PATTERN (fragile, no
  idempotency guarantees, poor error handling) — mention it explicitly as
  "avoid this, use Ansible instead."
- k8s-layer tools (Helm/Kustomize, Days 74–76) sit ABOVE both: Terraform
  can provision the cluster itself (Day 79's kind_cluster resource), but
  what runs INSIDE the cluster is Helm/Kustomize's job, not Terraform's
  (yes, a `helm` Terraform provider exists — used sparingly in the field,
  and mixing concerns this way is itself a tradeoff worth naming rather
  than defaulting to).

### B. `terraform fmt` and `validate` (15 min)
- `terraform fmt` — canonical formatting (like `gofmt`/`black`,
  opinionated, no debate) — `terraform fmt -check -recursive` in CI fails
  the build if anyone forgot to run it locally (same spirit as Day 24's
  shellcheck-in-CI habit).
- `terraform validate` — syntax and internal-consistency check WITHOUT
  needing provider credentials or touching real infrastructure (unlike
  `plan`, which needs provider access) — the fastest possible CI gate.

### C. tflint and policy checks (15 min)
- `tflint` — a linter catching provider-specific mistakes `validate`
  doesn't (deprecated arguments, invalid instance types, unused
  declared variables) — plugin-based per provider.
- Briefly named for awareness (not lab depth today): `checkov`/`tfsec` —
  security/policy scanners for Terraform (analogous to Day 48's `trivy`
  for images) — flag hardcoded secrets, overly permissive configs; Phase
  4's cloud work will make these more concretely useful.

### D. CI pipeline shape for Terraform (10 min)
- Standard gate order: `fmt -check` → `validate` → `tflint` → `plan`
  (posted as a PR comment for human review, NEVER auto-applied on a PR)
  → `apply` (only on merge to main, ideally with manual approval for
  anything touching real/shared infra) — mirrors the build→scan→deploy
  gating discipline from Day 48, applied to infrastructure changes
  instead of application code.

## Lab (2h)

### Part 1 — fmt and validate discipline (25 min)
1. Take any `terraform/` config from Days 79–82; deliberately mangle its
   formatting (bad indentation, inconsistent spacing). `terraform fmt
   -diff -recursive` — observe the exact diff it would apply; run it for
   real, confirm the diff disappears.
2. Introduce a deliberate syntax error (unclosed brace, wrong argument
   name) — `terraform validate` — read the precise error location and
   message, fix it, re-validate clean.

### Part 2 — tflint (25 min)
3. Install `tflint`; `tflint --init` (installs provider plugin rulesets).
4. Run `tflint` against your Day 80–82 configs; read whatever warnings
   surface (unused variables are a common one from lab iteration) and fix
   at least 2 real findings.

### Part 3 — Wire fmt/validate/tflint into CI (40 min)
5. Add a new GitHub Actions workflow (or job) `terraform-ci.yml` running,
   on every push touching `terraform/`: `terraform fmt -check -recursive`,
   `terraform init -backend=false` (skip backend for a credential-free CI
   check), `terraform validate`, and `tflint`.
6. Push a change with intentionally bad formatting — confirm the Action
   fails at the `fmt -check` step with a clear message. Fix it, push
   again, confirm green.

### Part 4 — Codify the provision/configure boundary in the project (30 min)
7. Write (or update) a short `terraform/README.md` in the project repo
   explicitly documenting: what Terraform manages (the kind cluster
   resource, going into Day 90's capstone), what Ansible/Helm manage
   (VM configuration from Phase 2, k8s workloads from Days 61–78), and
   the explicit handoff point (Terraform output → next tool's input).
8. Cross-reference this document from the main project README so the
   full stack's division of responsibility is discoverable in one place
   before Day 90's capstone brings it all together.

## Definition of done
`fmt`/`validate`/`tflint` all run clean locally and are enforced in CI,
proven by a deliberately-broken push failing the pipeline · project repo
has an explicit, documented Terraform/Ansible/Helm boundary statement
cross-linked from the main README.
