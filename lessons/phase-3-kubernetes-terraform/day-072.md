## Theory (1h)

### A. Influencing where Pods land (20 min)
- `nodeSelector`: simplest form — match Pod to nodes by a single label
  (`disktype: ssd`).
- **Node affinity**: richer version — `requiredDuringSchedulingIgnored
  DuringExecution` (hard constraint) vs `preferredDuringScheduling...`
  (soft preference, scheduler tries but won't fail); supports operators
  (`In`, `NotIn`, `Exists`).
- **Pod affinity/anti-affinity**: schedule relative to OTHER pods, not
  nodes — e.g., "spread replicas across different nodes"
  (anti-affinity on `app` label with `topologyKey: kubernetes.io/hostname`)
  for resilience, or "co-locate cache with app" (affinity) for latency.
- On a single-node kind cluster these constraints can only be
  DEMONSTRATED conceptually via `preferred` (soft) rules or `dry-run`,
  since `required` anti-affinity across hosts has nowhere to go with one
  node — call this out explicitly as a lab limitation.

### B. Taints and tolerations (15 min)
- A **taint** on a node repels Pods unless they have a matching
  **toleration** — inverse of affinity (affinity is Pod choosing nodes;
  taints are nodes rejecting Pods by default).
- `kubectl taint nodes <node> key=value:NoSchedule` (or `NoExecute` — evicts
  already-running pods without the toleration, or `PreferNoSchedule` —
  soft). Real-world use: dedicating nodes to specific workloads (GPU
  nodes, control-plane nodes tainted so regular workloads don't land there).
- Toleration in a Pod spec must match the taint's key/value/effect to be
  allowed to schedule there — it doesn't FORCE placement, only permits it
  (combine with affinity for that).

### C. DaemonSets (10 min)
- Ensures exactly one Pod per node (or per matching subset via
  nodeSelector) — used for node-level agents: log shippers, monitoring
  agents (Prometheus's node_exporter — Phase 5), CNI plugins. New nodes
  joining the cluster automatically get the DaemonSet's Pod.
- No `replicas` field — replica count is implicitly "one per eligible node."

### D. Jobs and CronJobs (15 min)
- **Job**: runs a Pod to COMPLETION (not forever) — `restartPolicy` must be
  `OnFailure` or `Never`. `completions`/`parallelism` control how many runs
  and how many concurrently. Use for one-off or batch tasks (migrations,
  reports, backups).
- **CronJob**: schedules Jobs on a cron-syntax schedule
  (`schedule: "*/5 * * * *"`) — same 5-field cron syntax from Day 12's
  systemd-timers-vs-cron discussion, now expressed as a k8s object.
- `concurrencyPolicy`: `Allow` (default, overlapping runs OK),
  `Forbid` (skip new run if previous still active), `Replace` (kill old,
  start new). `successfulJobsHistoryLimit`/`failedJobsHistoryLimit` control
  cleanup of completed Job objects (otherwise they accumulate forever).

## Lab (2h)

### Part 1 — nodeSelector and soft affinity (25 min)
1. `kubectl label node <node-name> disktype=ssd` (label the single kind
   node). Deploy a Pod with `nodeSelector: {disktype: ssd}` — confirm it
   schedules; remove the label and reapply, confirm it now stays `Pending`
   (`kubectl describe pod` shows `0/1 nodes are available: node(s) didn't
   match Node Selector`).
2. Rewrite the same constraint as a `preferredDuringScheduling...` node
   affinity rule instead — confirm it schedules successfully even WITHOUT
   the label present (soft = scheduler tries, doesn't block).

### Part 2 — Taints and tolerations (25 min)
3. `kubectl taint nodes <node-name> dedicated=batch:NoSchedule`.
4. Try to schedule a plain Pod with no toleration — confirm it stays
   `Pending`. Add a matching toleration to the Pod spec, reapply, confirm it
   schedules.
5. `kubectl taint nodes <node-name> dedicated=batch:NoSchedule-` to remove
   the taint when done (note the trailing `-` syntax for removal).

### Part 3 — DaemonSet (20 min)
6. Write a DaemonSet running a simple busybox sleep-loop container. Apply;
   `kubectl get daemonset,pods -o wide` — confirm exactly one Pod on the
   (single) node.
7. `kubectl describe daemonset` — note the "Desired/Current/Ready" counts
   tied to node count, not a `replicas` field.

### Part 4 — Jobs and the CronJob project migration (50 min)
8. Write a Job running your project's report-generation logic once
   (e.g., a container running `sys_report.py` from Phase 1/2, or a stand-in
   script) with `restartPolicy: OnFailure`, `backoffLimit: 3`. Apply,
   `kubectl get job -w`, confirm it reaches `Completions: 1/1`, then
   `kubectl logs job/<name>` to see its output.
9. **Project step**: convert this into a CronJob. Write
   `report-cronjob.yaml`: `schedule: "*/5 * * * *"` (5-minute interval for
   lab visibility), `concurrencyPolicy: Forbid`,
   `successfulJobsHistoryLimit: 3`, `failedJobsHistoryLimit: 1`, same Pod
   template as the Job above (mount the ConfigMap from Day 67 for its
   config).
10. Apply; wait for at least 2 scheduled runs; `kubectl get cronjob,jobs,pods`
    — confirm new Job objects appear on schedule and old ones get pruned
    per the history limits. `kubectl logs job/<latest-job-name>` to confirm
    output each run.
11. Commit `report-cronjob.yaml` to the project repo under `k8s/`, replacing
    (or alongside) the Day 67 plain Deployment if the report logic was
    previously running as a long-lived service — document in the repo
    README which workload type the report component now uses and why
    (batch vs long-running).
