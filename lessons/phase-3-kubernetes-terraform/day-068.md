## Theory (1h)

### A. The storage problem for stateful apps (10 min)
- Pods are ephemeral — anything written to a container's filesystem (or an
  `emptyDir` volume from Day 62) is lost when the Pod dies/reschedules.
  Databases and any app holding real data need storage that outlives the Pod.
- k8s solves this with a layer of abstraction, same pattern as Service→
  Endpoints: **declare what you need, k8s finds/provisions the actual
  storage.**

### B. PV, PVC, StorageClass — the three pieces (25 min)
- **PersistentVolume (PV)**: a piece of real storage in the cluster (a disk,
  an NFS share, a cloud volume) — represented as a k8s object, usually
  created by a provisioner, rarely by hand.
- **PersistentVolumeClaim (PVC)**: a Pod's request for storage ("give me
  10Gi, ReadWriteOnce") — this is what application manifests actually
  reference.
- **StorageClass**: a template for dynamic provisioning — defines WHICH
  provisioner creates PVs on demand when a PVC asks for one, and with what
  parameters. `kubectl get storageclass` — kind ships `standard` backed by
  `rancher.io/local-path`, dynamically provisioning host-path-backed
  volumes. `kubectl get storageclass` also shows which is marked
  `(default)`.
- Binding: PVC references a StorageClass (or uses the default) → provisioner
  creates a PV matching the request → PVC binds to that PV → Pod mounts the
  PVC via `volumes[].persistentVolumeClaim.claimName`.
- Access modes: `ReadWriteOnce` (one node read-write — most common, what
  local-path supports), `ReadOnlyMany`, `ReadWriteMany` (needs
  NFS-like backends, not local-path).

### C. Reclaim policy and PVC lifecycle (10 min)
- `persistentVolumeReclaimPolicy`: `Delete` (PV+underlying storage destroyed
  when PVC is deleted — common for dynamic provisioning) vs `Retain`
  (storage kept, PV goes to `Released` state, requires manual cleanup —
  used when data must survive accidental PVC deletion).
- PVCs are namespaced; deleting a namespace can cascade-delete PVCs and
  therefore data — a real production footgun worth calling out explicitly.

### D. StatefulSets — identity-stable Pods (15 min)
- A **StatefulSet** is like a Deployment but for workloads needing **stable
  network identity and stable storage per replica** (databases, clustered
  systems): Pods get predictable names (`db-0`, `db-1`, `db-2`, not random
  hashes), stable DNS via a **headless Service** (`clusterIP: None`), and
  each replica gets its OWN PVC from a `volumeClaimTemplates` block (not one
  shared PVC).
- Ordering guarantees: Pods created/deleted/scaled in order (0, then 1,
  then 2...) — matters for clustered databases with leader-election
  dependencies. Deployments give none of these guarantees (deliberately, for
  stateless scale-out).

## Lab (2h)

### Part 1 — PVC and dynamic provisioning (25 min)
1. `kubectl get storageclass` — confirm `standard` is default on kind.
2. Write `data-pvc.yaml` requesting 1Gi, `ReadWriteOnce`. Apply; `kubectl get
   pvc,pv` — watch the PVC go `Bound` and a PV appear automatically
   (dynamic provisioning in action).

### Part 2 — Mount it in a Pod, verify persistence across Pod death (30 min)
3. Write a Pod (or single-replica Deployment) mounting `data-pvc` at
   `/data`, running a simple image (busybox sleep loop is fine).
4. `kubectl exec -it <pod> -- sh -c "echo hello > /data/testfile.txt"`.
5. Delete the Pod (`kubectl delete pod ...`) and let it (if Deployment-owned)
   or manually recreate it (if bare Pod) — `kubectl exec -it <new-pod> -- cat
   /data/testfile.txt` — confirm the file survived the Pod's death because it
   lived in the PVC, not the container filesystem.

### Part 3 — StatefulSet with per-replica storage (45 min)
6. Write a headless Service `db-headless` (`clusterIP: None`, selector
   `app=db`).
7. Write a StatefulSet `db` (3 replicas, image `busybox:1.36` with a sleep
   loop is fine for the exercise, or use a real lightweight DB image like
   `postgres:16` if comfortable), `serviceName: db-headless`, and
   `volumeClaimTemplates` requesting 1Gi each.
8. Apply; `kubectl get pods -w` — observe strict ordering (`db-0` Running
   before `db-1` starts creating). `kubectl get pvc` — confirm 3 SEPARATE
   PVCs (`data-db-0`, `data-db-1`, `data-db-2`).
9. `kubectl exec -it db-0 -- sh` (or psql if using postgres) — write unique
   data per pod under its own mount, confirm `db-1`'s data is NOT visible
   from `db-0` (separate volumes, unlike a Deployment which would share one
   PVC across replicas if misconfigured).
10. `kubectl run tmp --rm -it --image=busybox:1.36 -- nslookup db-0.db-headless`
    — confirm the stable per-pod DNS name from the headless Service.

### Part 4 — Reclaim policy and cleanup discipline (20 min)
11. `kubectl get pv -o custom-columns=NAME:.metadata.name,RECLAIM:.spec.
    persistentVolumeReclaimPolicy` — note the default policy on kind's
    provisioner.
12. Delete the StatefulSet (`kubectl delete statefulset db`) — confirm PVCs
    are NOT auto-deleted (StatefulSet PVCs survive by design, for data
    safety); then explicitly `kubectl delete pvc -l app=db` to fully clean
    up, and confirm the PVs disappear per the reclaim policy.

## Definition of done
Explained PV/PVC/StorageClass relationship and dynamic provisioning · proved
data survives Pod death via a PVC · deployed a StatefulSet with per-replica
PVCs and stable DNS, confirmed replicas don't share storage · understands why
StatefulSet PVCs survive StatefulSet deletion.
