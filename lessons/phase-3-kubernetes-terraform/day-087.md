## Theory (1h)

### A. kubeadm upgrade concepts (20 min)
- Cluster upgrades happen ONE minor version at a time
  (1.29→1.30, never 1.29→1.31 directly) — skipping versions is
  unsupported and risks incompatible API changes.
- Order matters: upgrade the CONTROL PLANE first
  (`kubeadm upgrade plan` → `kubeadm upgrade apply vX.Y.Z` on the first
  control-plane node, then `kubeadm upgrade node` on any additional
  control-plane nodes), THEN worker nodes one at a time — never all nodes
  simultaneously, to keep the cluster serving traffic throughout.
- Per-node sequence: `kubectl drain <node>` (evict workloads safely) →
  `apt-get update && apt-get install kubeadm=<version>` (or dnf
  equivalent) → `kubeadm upgrade node` → upgrade `kubelet`+`kubectl` →
  restart kubelet → `kubectl uncordon <node>` to return it to service.

### B. Drain vs cordon, precisely (15 min)
- `kubectl cordon <node>`: marks the node `Unschedulable` — NEW pods won't
  land there, but EXISTING pods keep running (recall Day 85's task 10).
- `kubectl drain <node>`: cordons AND evicts existing pods gracefully
  (respecting PodDisruptionBudgets — a preview of Phase 5's reliability
  patterns), moving them to other nodes. `--ignore-daemonsets` is required
  because DaemonSet pods (recall Day 72) are meant to run on every node
  and can't be "moved" — drain would otherwise refuse to proceed.
  `--delete-emptydir-data` is required if any pod uses local `emptyDir`
  storage that would be lost (an explicit acknowledgment, not silent
  data loss).
- After maintenance: `kubectl uncordon <node>` — does NOT automatically
  move pods back (no "rebalancing" happens); workloads simply schedule
  there again going forward.

### C. Ongoing etcd backup as practice, not a one-off (10 min)
- Day 86 drilled the mechanics; in practice, etcd snapshots should be
  taken on a SCHEDULE (cron/systemd timer on the control-plane node,
  recall Day 12) and stored OFF the node itself (a backup that lives on
  the machine it's protecting against isn't a real backup — same
  principle as Day 17's rsync backup-to-a-second-VM lab).

### D. Resource pruning (15 min)
- Completed Jobs, old ReplicaSets (kept by Deployments per
  `revisionHistoryLimit`, default 10), evicted/completed Pods, and
  unused ConfigMaps/Secrets accumulate over time and bloat etcd.
- `kubectl delete pods --field-selector=status.phase==Succeeded -A`,
  `kubectl get replicasets -A` (audit for ones with 0 desired/current
  hanging around beyond `revisionHistoryLimit`), and setting
  `successfulJobsHistoryLimit`/`failedJobsHistoryLimit` on CronJobs
  (recall Day 72) are the standard levers — a "garden-cleaning" mindset
  is a genuine ongoing cluster-admin responsibility, not a one-time task.

## Lab (2h)

### Part 1 — Drain and cordon in practice (30 min)
1. `kind create cluster --name fresher` (or reuse an existing dev
   cluster). Deploy a 3-replica Deployment.
2. `kubectl drain <node> --ignore-daemonsets --delete-emptydir-data` on
   the single kind node — watch it evict the app pods and confirm they
   go `Pending` (nowhere else to schedule, since there's only one node) —
   this demonstrates WHY multi-node clusters matter for real maintenance,
   even though single-node kind can't fully complete the drain's promise.
3. `kubectl uncordon <node>` — confirm pending pods schedule and recover.

### Part 2 — Simulated upgrade sequence (30 min)
4. Without actually changing k8s versions (kind's version is fixed per
   image), walk through and DOCUMENT the exact command sequence you would
   run for a real minor-version upgrade of a worker node, using `kubeadm
   upgrade plan`'s dry-run output format as a reference if available, or
   the official kubeadm upgrade docs structure — write this as a runbook
   file `docs/k8s-upgrade-runbook.md` in the project repo.

### Part 3 — Scheduled etcd backups (35 min)
5. On the kind control-plane node (via `docker exec`), write a small
   shell script performing `etcdctl snapshot save` with a timestamped
   filename, following Day 86's exact flag pattern.
6. Wrap it as a cron entry (recall Day 12) inside the node container
   running every few minutes for lab visibility, OR document it as a
   systemd timer definition (write the actual unit files) since kind
   nodes are containers and cron/systemd availability varies — pick
   whichever is available in your kind node image and get at least one
   automated snapshot to actually run and land in a directory.
7. Copy at least one snapshot OFF the kind node (`docker cp` to your host)
   — this enforces the "backup off the machine it protects" principle
   from Theory C.

### Part 4 — Resource pruning (25 min)
8. Create and let complete 5 Jobs (reuse Day 72's report Job pattern, run
   it 5 times or via a CronJob with a tight schedule and let a few runs
   accumulate).
9. `kubectl get pods --field-selector=status.phase==Succeeded -A` — count
   them, then prune: `kubectl delete pods --field-selector=status.phase==
   Succeeded -n <ns>`.
10. `kubectl get rs -A` — check `DESIRED`/`CURRENT` columns for any at 0
    beyond what `revisionHistoryLimit` should retain; clean up manually if
    found. Commit the upgrade runbook and backup script/unit files to the
    project repo under `docs/` and `scripts/` respectively.

## Definition of done
Drained and uncordoned a node, understanding the single-node kind
limitation · wrote a documented upgrade runbook · got at least one
automated etcd snapshot running on a schedule and copied off-node ·
pruned completed Jobs/Pods and audited stale ReplicaSets.
