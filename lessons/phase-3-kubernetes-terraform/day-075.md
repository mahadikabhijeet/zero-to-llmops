## Theory (1h)

### A. Chart scaffolding (10 min)
- `helm create <chart-name>` scaffolds a working starter chart (Deployment,
  Service, ingress, HPA, serviceaccount templates + `values.yaml` +
  `Chart.yaml` + a `_helpers.tpl` and `tests/`) — the fastest way to get a
  correct skeleton instead of writing one from a blank file.
- `Chart.yaml` fields worth understanding: `apiVersion: v2`, `name`,
  `version` (chart's own version, SemVer — recall Day 55), `appVersion`
  (the app's version, informational).

### B. Go templating essentials (20 min)
- `{{ .Values.foo }}` pulls from `values.yaml`; `{{ .Release.Name }}`,
  `{{ .Chart.Name }}` are built-in objects.
- `{{- if .Values.ingress.enabled }} ... {{- end }}` — conditional blocks
  (the `-` trims whitespace, keeping rendered YAML clean).
- `{{ include "chartname.fullname" . }}` — calling a named template
  (defined in `_helpers.tpl`) for consistent resource naming/labeling
  across all templates — avoids repeating the same naming logic
  everywhere.
- `{{ range .Values.list }} ... {{ end }}` — loops, e.g., for generating
  multiple env vars or ingress hosts from a values list.
- `toYaml`/`nindent` idiom: `{{- toYaml .Values.resources | nindent 12 }}`
  — how arbitrary nested values (like a whole `resources` block) get
  dropped into templates with correct indentation.

### C. Helpers, labels, and chart conventions (15 min)
- `_helpers.tpl` centralizes: fullname generation, common labels
  (`app.kubernetes.io/name`, `/instance`, `/version`, `/managed-by: Helm`)
  — the same standard labels you saw applied automatically by
  bitnami/nginx on Day 74. Consistency here is what makes `kubectl get
  all -l app.kubernetes.io/instance=<release>` work for ANY chart.
- Files starting with `_` (like `_helpers.tpl`) are NOT rendered as
  standalone manifests — they're template libraries only.

### D. Linting and testing a chart (15 min)
- `helm lint <chart-dir>` — static checks for common chart mistakes
  (missing required values, malformed YAML after templating).
- `helm template <chart-dir> -f values.yaml | kubectl apply --dry-run=
  server -f -` — a two-stage validation: render, then have the API server
  itself validate the resulting objects without actually creating them.
- `helm test` — runs Pods defined under `templates/tests/` with a
  `helm.sh/hook: test` annotation AFTER install, asserting the release
  actually works (e.g., a curl-based smoke test against the Service).

## Lab (2h)

### Part 1 — Scaffold the chart (20 min)
1. `cd` into the project repo; `helm create fresher-project`. Inspect the
   generated `templates/` directory and `values.yaml` in full before
   changing anything.
2. Delete/trim what you don't need yet (e.g., HPA template if not wiring
   autoscaling into the chart today) — keep the chart focused on what the
   project actually uses: Deployment, Service, ConfigMap, and (recall
   Day 72) the CronJob for reports.

### Part 2 — Wire in your real manifests (50 min)
3. Convert the project's Day 67 Deployment+ConfigMap and Day 72 CronJob
   into templated versions under `templates/`, pulling image repo/tag,
   replica count, resource requests/limits, and CronJob schedule from
   `values.yaml` instead of hardcoding them.
4. Use `{{ include "fresher-project.fullname" . }}` (or whatever the
   scaffolded helper is named) consistently for all resource names, and
   `{{- include "fresher-project.labels" . | nindent 4 }}` for labels —
   confirm every template uses the SAME helper, not ad hoc naming.
5. `helm lint .` — fix every warning before moving on.

### Part 3 — Render, validate, and install (30 min)
6. `helm template . | less` — read through the FULL rendered output;
   confirm it matches what you'd expect from the raw manifests written on
   Days 67/72.
7. `helm template . | kubectl apply --dry-run=server -f -` — confirm the
   API server accepts every object with no validation errors.
8. `helm install fresher-project . -f values.yaml` onto the kind cluster.
   `kubectl get all,configmap,cronjob -l app.kubernetes.io/instance=
   fresher-project` — confirm everything came up correctly.

### Part 4 — A basic Helm test and an upgrade cycle (20 min)
9. Add a minimal test under `templates/tests/test-connection.yaml`
   (`helm.sh/hook: test` annotation, a Pod that curls the Service and
   exits 0/1 accordingly). `helm test fresher-project` — confirm it
   passes.
10. Bump `Chart.yaml`'s `version` and change one value (e.g., replica
    count) in `values.yaml`; `helm upgrade fresher-project .`; `helm
    history fresher-project` to see the new revision. Commit the entire
    `fresher-project/` chart directory to the project repo.

## Definition of done
Own Helm chart authored from `helm create` scaffold, using helpers/labels
consistently · `helm lint` clean · rendered output validated via
`--dry-run=server` · chart installed on kind, upgraded, and a `helm test`
smoke test passes · chart committed to the project repo.
