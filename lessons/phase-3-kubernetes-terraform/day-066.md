## Theory (1h)

### A. Why Ingress exists (10 min)
- NodePort/LoadBalancer give you one Service = one exposed endpoint. Real
  apps need host-based (`api.example.com` vs `app.example.com`) and
  path-based (`/api` vs `/`) routing to MANY services behind a single entry
  point — that's what a reverse proxy (nginx, HAProxy) does at the edge.
- **Ingress** is a k8s API object describing routing rules; it does nothing
  by itself — you need an **Ingress Controller** (a Pod running an actual
  proxy, e.g. ingress-nginx) that watches Ingress objects and configures
  itself accordingly. This split (spec vs implementation) is the same
  pattern as Service vs kube-proxy.

### B. Installing and using ingress-nginx on kind (20 min)
- kind needs a special node config (`extraPortMappings` for 80/443 +
  `kubeadmConfigPatches` labeling the node `ingress-ready=true`) — kind's
  docs ship a specific manifest for this; without it, ingress-nginx's Pod
  can't bind host ports.
- `kubectl apply -f <kind-specific ingress-nginx manifest>` installs the
  controller into `ingress-nginx` namespace as a Deployment (or DaemonSet)
  + Service (NodePort in kind's case, since LoadBalancer isn't available).
- `kubectl get pods -n ingress-nginx -w` until the controller pod is Running
  and Ready — the readiness gate matters here (ties to Day 69).

### C. Ingress resource anatomy (20 min)
- `apiVersion: networking.k8s.io/v1`, `kind: Ingress`.
- `spec.ingressClassName: nginx` — tells k8s which controller should handle
  this Ingress (clusters can run multiple controllers).
- `spec.rules[].host` + `.http.paths[].path` + `.pathType` (`Prefix` vs
  `Exact`) + `.backend.service.name/.port.number` — the routing table.
- Path-based example: `/app` → app-svc:80, `/api` → api-svc:8080, same host.
- Host-based example: `app.local` → app-svc, `api.local` → api-svc.

### D. TLS termination at the Ingress (10 min)
- `spec.tls[].hosts` + `.secretName` — the controller terminates TLS using a
  cert/key stored in a `kubernetes.io/tls` Secret, then proxies plaintext to
  the backend Pod.
- For local labs: self-signed certs (recall Day 20's TLS concepts) generated
  with `openssl req -x509 ...`, loaded via `kubectl create secret tls`.
  Real certs (Let's Encrypt/ACM) come later with cert-manager (Day 88) and
  cloud DNS (Phase 4).

## Lab (2h)

### Part 1 — kind cluster configured for Ingress (25 min)
1. Recreate the kind cluster using a config file with `extraPortMappings`
   for containerPort 80→hostPort 80 and 443→443, and the
   `ingress-ready=true` node label patch (follow kind's official
   "Ingress" guide structure for the exact YAML).
2. Install ingress-nginx's kind-specific manifest; `kubectl get pods -n
   ingress-nginx -w` until Ready; `kubectl get ingressclass` — confirm
   `nginx` is listed.

### Part 2 — Path-based routing (35 min)
3. Deploy two simple apps: `app-deploy`/`app-svc` (nginx serving default
   page) and `api-deploy`/`api-svc` (httpd or a different nginx image with a
   custom index.html via ConfigMap, so you can visually tell them apart).
4. Write `path-ingress.yaml` routing `/app` → app-svc, `/api` → api-svc, both
   under a single host (or no host — matches any). Apply.
5. `curl localhost/app` and `curl localhost/api` from your host — confirm
   each hits the right backend. `kubectl describe ingress path-ingress` and
   read the Rules/Backends table.

### Part 3 — Host-based routing (30 min)
6. Write `host-ingress.yaml` routing `app.local` and `api.local` to the same
   two services (root path `/`).
7. Add both hostnames to `/etc/hosts` pointing at `127.0.0.1`.
8. `curl app.local` and `curl api.local` — confirm host-based routing works
   distinctly from path-based.

### Part 4 — TLS termination (30 min)
9. `openssl req -x509 -nodes -newkey rsa:2048 -keyout tls.key -out tls.crt
   -days 30 -subj "/CN=app.local"`.
10. `kubectl create secret tls app-tls --cert=tls.crt --key=tls.key`.
11. Add `spec.tls` to `host-ingress.yaml` referencing `app-tls` for host
    `app.local`; apply. `curl -k https://app.local` — confirm TLS
    termination (self-signed, hence `-k` to skip verification) and that
    `curl app.local` (plain HTTP) still works or redirects per default
    ingress-nginx behavior — check `kubectl describe ingress` for what
    changed.
12. Clean up host-file entries you don't want to keep; leave the cluster up
    for Day 67.

## Definition of done
Understand Ingress-object vs Ingress-controller split · path-based and
host-based routing both working through curl · TLS termination configured
and validated with `curl -k` · can read `kubectl describe ingress` output.
