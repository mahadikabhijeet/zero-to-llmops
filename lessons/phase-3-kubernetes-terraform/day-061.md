## Theory (1h)

### A. Why orchestration — the problem Ansible+Docker can't fully solve (15 min)
- Manual VM + Ansible + Docker gets you ONE server. Real systems need: many
  containers, self-healing on crash, rolling updates without downtime, scaling
  up/down with load, service discovery when IPs change constantly.
- Orchestration = a system that watches "desired state" and continuously
  reconciles actual state to match it — the **declarative model**: you say
  "I want 3 replicas of this container," not "start container, then container,
  then container."
- Kubernetes (k8s) is the industry-standard orchestrator; born from Google's
  internal Borg. CNCF-governed, huge ecosystem (Helm, ArgoCD, Prometheus — all
  coming later in this curriculum).

### B. Control plane components (20 min)
- **kube-apiserver**: the front door — every kubectl command, every controller,
  every kubelet talks to it via REST. Nothing touches etcd directly except this.
- **etcd**: distributed key-value store — the cluster's single source of truth
  (all objects: pods, secrets, configmaps live here as serialized state).
- **kube-scheduler**: watches for unscheduled pods, decides which node they run
  on (based on resource requests, constraints — deep dive Day 72).
- **kube-controller-manager**: runs controllers (Deployment controller, Node
  controller, etc.) — each is a reconciliation loop: observe → compare to
  desired state → act.
- **cloud-controller-manager**: mentioned for completeness (cloud-specific
  integrations — not relevant on our local kind cluster).

### C. Node components and the declarative reconciliation loop (15 min)
- **kubelet**: agent on every node — talks to the API server, ensures
  containers described in PodSpecs are running and healthy.
- **kube-proxy**: maintains network rules on nodes for Service abstraction
  (deep dive Day 65).
- **Container runtime**: containerd (or CRI-O) — actually runs the containers;
  Docker Engine itself is no longer the k8s runtime (Docker Desktop still uses
  containerd under the hood for this).
- The reconciliation loop, concretely: you `kubectl apply` a Deployment saying
  "3 replicas" → API server stores it in etcd → Deployment controller notices
  desired=3, actual=0 → creates 3 Pod objects → scheduler assigns nodes →
  kubelets on those nodes pull images and start containers → each controller
  keeps watching forever, so if a pod dies, actual drops to 2, and the loop
  fires again automatically. This self-healing loop is the single biggest
  mental model shift from Phase 2.

### D. Objects vs the API, and the anatomy of a manifest (10 min)
- Everything in k8s is an "object" defined in YAML/JSON with 4 required top
  fields: `apiVersion`, `kind`, `metadata`, `spec`. `apps/v1` for
  Deployments/ReplicaSets/StatefulSets/DaemonSets, `v1` for core objects
  (Pod, Service, ConfigMap, Secret, Namespace).
- `kubectl apply -f file.yaml` is declarative (diff+patch); `kubectl create`
  is imperative (fails if it already exists) — always prefer `apply` from here
  on, matching the IaC mindset from Phase 2's Ansible/CI work.

## Lab (2h)

### Part 1 — Install tooling (20 min)
1. Install `kubectl`, `kind`, and (if not already) `docker` — verify each with
   `kubectl version --client`, `kind version`, `docker version`.
2. Read `kind --help` and `kind create cluster --help` briefly — note the
   `--name` and `--config` flags we'll use going forward.

### Part 2 — Stand up your first cluster (30 min)
3. `kind create cluster --name fresher` — watch the output; it pulls a node
   image and configures kubectl context automatically.
4. `kubectl cluster-info` and `kubectl get nodes -o wide` — note there's one
   node acting as both control-plane and worker (kind's default single-node
   layout).
5. `kubectl get pods -A` — explore the `kube-system` namespace: find etcd,
   kube-apiserver, kube-scheduler, kube-controller-manager, coredns, and
   kube-proxy pods running as **static pods** on the node. This is the control
   plane you just read about, made concrete.
6. `kubectl describe pod -n kube-system <etcd-pod-name>` — read the container
   command/args; spot the etcd data directory flag.

### Part 3 — First declarative object (30 min)
7. Write a minimal Pod manifest `nginx-pod.yaml` (apiVersion: v1, kind: Pod,
   one container `nginx:1.27`). `kubectl apply -f nginx-pod.yaml`.
8. `kubectl get pods -o wide`, `kubectl describe pod nginx-pod` — walk through
   every field of the describe output: Node, IP, Events (Scheduled → Pulling
   → Pulled → Created → Started).
9. Delete the pod (`kubectl delete -f nginx-pod.yaml`) — watch the Events on
   `kubectl get events --sort-by=.lastTimestamp` show Killing/graceful
   shutdown.

### Part 4 — See the reconciliation loop directly (30 min)
10. Re-apply the pod, then in another terminal `kubectl delete pod nginx-pod
    --grace-period=0 --force` while watching `kubectl get pods -w` — because
    this is a bare Pod (no controller), it does NOT come back. Note this down;
    Day 64 introduces Deployments, which DO self-heal via a controller.
11. `kubectl get all -A` and `kubectl api-resources | head -30` — survey the
    breadth of object kinds available.
12. Tear down: `kind delete cluster --name fresher` then recreate it fresh —
    confirm the whole environment is disposable and scriptable (this matters
    for CI later — Day 78).

## Definition of done
Can explain the 6 control-plane/node components and what each does · created
and deleted a bare Pod via a YAML manifest · watched `kubectl get events`
narrate the pod lifecycle · explained why a bare Pod didn't self-heal but knows
Deployments will.
