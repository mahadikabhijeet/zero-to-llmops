## Theory (1h)

### A. Why local state doesn't scale past one person (15 min)
- Local `terraform.tfstate` works for solo labs (Days 79–80) but breaks
  the moment more than one person/process runs Terraform against the same
  infrastructure: two people apply concurrently, state gets overwritten
  or corrupted, and nobody has a shared source of truth.
- **Remote backends** (S3+DynamoDB, Terraform Cloud, Consul, etc.) store
  state centrally AND provide **locking** — while one `apply` is running,
  a second one is blocked until the first finishes, preventing concurrent
  corruption. (Phase 4's Day 107 sets up a real S3+lock backend on AWS;
  today's lab uses a local-but-shared-pattern stand-in since no cloud
  account exists yet.)

### B. Backend configuration mechanics (15 min)
- `terraform { backend "local" { path = "..." } }` (the default,
  implicit) vs `backend "s3" { bucket = "..." key = "..." region = "..."
  dynamodb_table = "..." }` (real remote example, referenced not yet run).
- Changing backends requires `terraform init -migrate-state` — Terraform
  detects the backend change and offers to copy existing state into the
  new location; this is a deliberate, confirmed operation, never silent.
- Backend config CANNOT use variables (chicken-and-egg problem — backend
  must be known before variables are resolved) — a common early confusion
  worth flagging explicitly.

### C. Workspaces (15 min)
- `terraform workspace new dev` / `terraform workspace select prod` —
  multiple named state files under ONE backend/config, useful for
  spinning up parallel environments (dev/staging/prod) from identical
  code with different variable values (`terraform.workspace` is a builtin
  you can reference inside HCL to branch behavior per workspace).
- Caveat: workspaces share the same backend config and provider
  credentials — for genuinely separate environments with different
  access boundaries (e.g., separate AWS accounts), separate root
  configs/directories are usually safer than workspaces; call this out as
  a real-world tradeoff, not a universal recommendation.

### D. Import and drift reconciliation (15 min)
- `terraform import <resource_address> <real_resource_id>` — brings
  EXISTING infrastructure (created outside Terraform, or before Terraform
  existed) under Terraform's management by writing an entry into state —
  you still must hand-write the matching `resource` block in HCL first;
  import only populates state, not config.
- After import, `terraform plan` will likely show a diff (your HCL
  doesn't perfectly match every real attribute yet) — iteratively adjust
  HCL until `plan` shows no changes, confirming your config now
  accurately describes reality.
- Drift review discipline: run `terraform plan` regularly (even without
  intending to apply) as a detection mechanism — CI can run `plan` on a
  schedule and alert if it's non-empty, catching manual/out-of-band
  changes early (a preview of Day 83's CI integration).

## Lab (2h)

### Part 1 — Local "remote-pattern" backend practice (30 min)
1. Take a Day 80 config (the kind-cluster module usage). Explicitly
   declare `backend "local" { path = "state/terraform.tfstate" }` (moving
   state to a subdirectory simulates the "backend is a deliberate
   choice" mental model even without real remote infra).
2. `terraform init -migrate-state` — confirm it prompts to copy existing
   state, and the new path is used afterward (`ls state/`).
3. Read (don't yet set up) an example S3 backend block for AWS — write it
   into a comment or a separate `backend-aws-example.tf.txt` (non-active)
   referencing bucket/key/region/dynamodb_table, to have ready for Day
   107.

### Part 2 — Workspaces (30 min)
4. `terraform workspace new dev` then `terraform workspace new staging` —
   `terraform workspace list` to confirm both plus `default`.
5. Reference `terraform.workspace` in a `locals` block to derive a
   cluster-name suffix (e.g., `local.cluster_name =
   "fresher-${terraform.workspace}"`), feed it into the kind-cluster
   module call from Day 80.
6. `terraform workspace select dev` → `terraform apply` → confirm a
   `fresher-dev` kind cluster exists. `terraform workspace select staging`
   → `terraform apply` → confirm a SEPARATE `fresher-staging` cluster
   exists alongside it, each tracked in its own state.
7. `terraform workspace select dev` → `terraform destroy` → confirm ONLY
   the dev cluster is torn down; staging remains untouched (prove state
   isolation is real, not cosmetic).

### Part 3 — Import (35 min)
8. Manually create a Docker container OUTSIDE Terraform: `docker run -d
   --name manual-web -p 8081:80 nginx:1.27`.
9. Write a matching (initially minimal) `resource "docker_container"
   "manual_web" {}` block in a new config. `terraform import
   docker_container.manual_web manual-web` (or the real ID depending on
   provider syntax) — confirm `terraform state show docker_container.
   manual_web` now reflects the real container's attributes.
10. `terraform plan` — read the diff; it will likely propose changes
    because your HCL block is still mostly empty. Iteratively fill in
    `image`, `ports`, etc. from the state-show output until `terraform
    plan` reports "No changes."

### Part 4 — Cleanup (25 min)
11. `terraform workspace select staging`, `terraform destroy`; return to
    `default` workspace (`terraform workspace select default`); `terraform
    workspace delete dev` and `delete staging` once both are empty.
12. `terraform destroy` on the imported-container config; `docker ps -a`
    to confirm cleanup. Commit today's backend-declaration pattern and the
    AWS-example placeholder to the project's `terraform/` directory with a
    note for Day 107.

## Definition of done
Explicitly configured and migrated a backend · created isolated
environments via workspaces and proved state isolation by destroying one
without affecting the other · imported a manually-created resource and
iterated HCL until `plan` showed no diff · everything cleanly destroyed and
documented for the Day 107 AWS backend follow-up.
