## Theory (1h)

### A. Custom Resource Definitions — extending the k8s API (20 min)
- Recall Day 61: everything in k8s is an "object" with apiVersion/kind/
  metadata/spec, stored in etcd, reconciled by controllers. A **CRD**
  lets you register a BRAND NEW kind (e.g., `Certificate`, `Backup`) that
  behaves exactly like a built-in object — `kubectl get`/`describe`/
  `apply` all work on it identically, because CRDs plug into the same
  API machinery.
- `kubectl get crd` lists every custom kind registered in a cluster;
  `kubectl explain <customkind>.spec` works on CRDs too, once installed —
  the API is genuinely uniform, not a special case.
- A CRD alone is just a schema — it does NOTHING by itself. It needs an
  **operator** (a controller, usually itself running as a Deployment in
  the cluster) watching instances of that kind and reconciling real
  infrastructure/state to match — the SAME reconciliation-loop pattern
  from Day 61's Deployment controller, generalized to arbitrary domains.

### B. Operators — the pattern, generalized (15 min)
- "Operator pattern" = CRD (the desired-state API) + controller (the loop
  that makes it real) + (usually) deep domain knowledge encoded in the
  controller — e.g., a database operator that knows HOW to safely
  fail over a replica, not just "run N pods."
- Operators exist for almost everything now: databases (Postgres,
  MongoDB), certificates (cert-manager), GitOps (ArgoCD — Day 132),
  service meshes (Istio — Day 135), monitoring (Prometheus Operator —
  Phase 5). Recognizing "this is the operator pattern" is a durable
  mental model across the rest of the curriculum.

### C. cert-manager as the concrete example (15 min)
- cert-manager installs CRDs: `Certificate`, `Issuer`/`ClusterIssuer`,
  `CertificateRequest` — you declare "I want a TLS cert for this host
  from this issuer," and its controller handles the actual
  issuance/renewal, writing the result into a standard
  `kubernetes.io/tls` Secret (the SAME kind of Secret Day 66 used
  manually with self-signed certs) — this closes the loop on the TLS gap
  named back in Day 66's theory.
- For real public certs, an Issuer would talk to Let's Encrypt via ACME
  (needs a real reachable domain — not achievable on kind); today's lab
  uses a `SelfSigned` ClusterIssuer to exercise the FULL mechanism
  (CRD → controller → Secret) without needing real DNS.

### D. When to write your own vs use an existing operator (10 min)
- Use an existing operator whenever the domain is well-trodden (certs,
  databases, ingress, monitoring) — writing a correct, safe reconciliation
  loop is genuinely hard (recall every edge case from Day 73's
  troubleshooting day; operators must handle ALL of them automatically).
- Write your own only when: the domain is genuinely novel to your org, no
  mature operator exists, and the operational complexity of NOT
  automating it exceeds the cost of building/maintaining a controller
  (frameworks like Kubebuilder/Operator SDK lower this cost but it's still
  real ongoing maintenance) — flag this as a judgment call, not a default.

## Lab (2h)

### Part 1 — Install cert-manager and inspect its CRDs (30 min)
1. `kubectl apply -f <cert-manager's official install manifest>` (installs
   its CRDs + controller Deployments into a `cert-manager` namespace).
2. `kubectl get pods -n cert-manager -w` until all 3 components (controller,
   webhook, cainjector) are Running/Ready.
3. `kubectl get crd | grep cert-manager` — list all CRDs it registered;
   `kubectl explain certificate.spec` — confirm it reads exactly like a
   built-in kind's explain output.

### Part 2 — SelfSigned issuer end to end (40 min)
4. Write a `ClusterIssuer` manifest of type `selfSigned`. Apply; `kubectl
   get clusterissuer` — confirm `Ready: True`.
5. Write a `Certificate` resource requesting a cert for `app.local`
   (matching Day 66's host), referencing the ClusterIssuer, naming a
   target `secretName: app-tls-cm`. Apply.
6. `kubectl get certificate -w` — watch it go `Ready: True`; `kubectl get
   secret app-tls-cm -o yaml` — confirm cert-manager auto-created a real
   `kubernetes.io/tls` Secret with populated `tls.crt`/`tls.key`, with NO
   manual `openssl` step this time (contrast directly with Day 66's
   manual process).

### Part 3 — Wire it into the Day 66 Ingress (30 min)
7. Update your `host-ingress.yaml` from Day 66 to reference `app-tls-cm`
   as the TLS secret instead of the manually-created one.
8. `curl -k https://app.local` — confirm it still works, now backed by a
   cert-manager-issued (self-signed, still) certificate managed
   declaratively instead of by hand.

### Part 4 — Reconciliation proof and cleanup (20 min)
9. `kubectl delete secret app-tls-cm` manually — watch `kubectl get secret
   app-tls-cm -w` and confirm cert-manager's controller notices the
   deletion and RECREATES it automatically within seconds — this is the
   reconciliation loop from Day 61, made visible in a completely different
   domain (certificates instead of pods).
10. Clean up the Certificate/ClusterIssuer/cert-manager install if not
    needed going forward; document in the project README (or a new
    `docs/operators.md`) the operator pattern observation from step 9 as
    a concrete example for future reference.

## Definition of done
Installed cert-manager and inspected its CRDs with the same tools used for
built-in kinds · issued a self-signed certificate declaratively and wired
it into the Day 66 Ingress · watched the controller reconcile a manually
deleted Secret back into existence, proving the operator pattern live.
