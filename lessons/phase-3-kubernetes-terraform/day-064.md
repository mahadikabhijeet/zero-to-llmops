## Theory (1h)

### A. From bare Pods to self-healing (15 min)
- A **Deployment** is a higher-level object that manages a **ReplicaSet**,
  which in turn manages Pods. You never hand-manage ReplicaSets — Deployments
  own them.
- Why the extra layer: ReplicaSet guarantees "N replicas running"; Deployment
  adds **rollout history and update strategy** on top (versioned
  ReplicaSets, one per revision).
- `kubectl create deployment nginx --image=nginx:1.27 --replicas=3
  --dry-run=client -o yaml > deploy.yaml` — the fast way to scaffold a
  starting manifest, then hand-edit it (imperative-to-declarative pattern).

### B. Deployment spec anatomy (15 min)
- `spec.replicas`, `spec.selector.matchLabels` (must match
  `spec.template.metadata.labels` — a very common misconfig source),
  `spec.template` (the Pod template — literally a PodSpec nested inside).
- `spec.strategy.type`: `RollingUpdate` (default) with `maxSurge`/
  `maxUnavailable`, or `Recreate` (kill all, then start all — downtime, used
  for apps that can't run two versions concurrently).

### C. Rollouts, history, and rollbacks (20 min)
- Change the image in a Deployment → new ReplicaSet is created, old one scaled
  down gradually (RollingUpdate) — zero-downtime by design if readiness
  probes are correct (Day 69 goes deep on probes).
- `kubectl rollout status deployment/<name>` — blocks until rollout
  completes or fails.
- `kubectl rollout history deployment/<name>` — shows revisions (only if
  `--record` was used or a `kubectl.kubernetes.io/change-cause` annotation is
  set).
- `kubectl rollout undo deployment/<name>` (last good revision) or
  `--to-revision=N` (specific one).
- `kubectl rollout pause`/`resume` — stage multiple template changes before
  triggering the actual rollout.

### D. Scaling and self-healing, demonstrated (10 min)
- `kubectl scale deployment/<name> --replicas=5` — imperative scale
  (Day 69's HPA will do this automatically based on metrics).
- Kill a Pod owned by a Deployment → the ReplicaSet controller notices
  actual < desired and creates a replacement within seconds. This is the
  payoff of Day 61's reconciliation-loop theory made concrete.

## Lab (2h)

### Part 1 — Scaffold and apply a Deployment (25 min)
1. `kind create cluster --name fresher` (if not already up).
2. `kubectl create deployment webapp --image=nginx:1.25 --replicas=3
   --dry-run=client -o yaml > webapp-deploy.yaml`; open it, note
   `selector.matchLabels` and `template.metadata.labels` match automatically.
3. `kubectl apply -f webapp-deploy.yaml`; `kubectl get deploy,rs,pods -o wide`
   — trace the ownership chain: Deployment → ReplicaSet (hashed suffix) →
   Pods (hashed suffix of the ReplicaSet's hash).

### Part 2 — Self-healing, live (20 min)
4. `kubectl get pods -w` in one terminal. In another, `kubectl delete pod
   <one-of-the-three>` — watch a replacement appear within seconds.
5. `kubectl scale deployment/webapp --replicas=5`, then back down to 3 —
   watch Pods created/terminated to match.

### Part 3 — Rolling update and rollback (45 min)
6. Edit `webapp-deploy.yaml`: bump image to `nginx:1.27`, add annotation
   `kubectl.kubernetes.io/change-cause: "bump to 1.27"` under
   `spec.template.metadata.annotations` (or use `kubectl annotate
   deployment/webapp kubernetes.io/change-cause="bump to 1.27"`).
7. `kubectl apply -f webapp-deploy.yaml` then immediately `kubectl rollout
   status deployment/webapp` and `kubectl get rs -w` in another terminal —
   watch the old ReplicaSet scale to 0 while the new one scales to 3.
8. Break it on purpose: edit to `nginx:doesnotexist999`, apply, watch
   `kubectl rollout status` hang/fail, `kubectl get pods` show
   `ImagePullBackOff` on new pods while old (healthy) pods stay serving —
   this IS the safety of RollingUpdate.
9. `kubectl rollout undo deployment/webapp` — confirm it returns to `nginx:1.27`.
10. `kubectl rollout history deployment/webapp` — inspect revisions and
    change-cause annotations.

### Part 4 — Recreate strategy comparison (20 min)
11. Duplicate the manifest as `webapp-recreate.yaml`, rename the Deployment,
    set `strategy.type: Recreate`. Apply, then change the image and apply
    again while watching `kubectl get pods -w` — note ALL pods disappear
    before new ones appear (contrast with RollingUpdate's overlap).
12. Clean up both deployments.

## Definition of done
Deployment→ReplicaSet→Pod ownership chain traced by hash suffixes · watched
self-healing replace a killed pod · performed a rolling update, a rollback,
and can explain the difference from Recreate strategy.
