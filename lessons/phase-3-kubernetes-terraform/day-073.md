## Theory (1h)

### A. A general top-down debugging method (recall Day 19's SELinux method)
(15 min)
- Always the same funnel: **Pod status → Events → container logs → exec
  into the container → check the dependency (Service/DNS/ConfigMap/
  Secret/PVC) it relies on.** Resist guessing before reading Events —
  k8s almost always tells you what's wrong in plain English.
- `kubectl get pods -A` for a fleet-wide sweep (spot the outliers by STATUS
  and RESTARTS columns) before drilling into one Pod.

### B. Reading Pod status and Events precisely (15 min)
- `Pending`: not yet scheduled — check `kubectl describe pod` Events for
  scheduling failures (resource shortage, node selector/affinity mismatch,
  taint without toleration, unbound PVC).
- `ImagePullBackOff`/`ErrImagePull`: bad image name/tag, missing registry
  auth (`imagePullSecrets`), or registry unreachable.
- `CrashLoopBackOff`: container starts then exits repeatedly — the STATUS
  itself doesn't say why; you must read `kubectl logs` (and `--previous`
  for the last crashed instance's output) plus `kubectl describe pod`'s
  Last State/Reason (e.g., `OOMKilled`, `Error`, non-zero exit code).
- `kubectl get events --sort-by=.lastTimestamp -A` — cluster-wide event
  timeline, often faster than per-pod `describe` when you don't know which
  object is the culprit.

### C. DNS failure triage (15 min)
- Symptom: app logs "could not resolve host" for another Service.
- Checklist: is CoreDNS running (`kubectl get pods -n kube-system -l
  k8s-app=kube-dns`)? Does the target Service actually exist and have
  Endpoints (Day 65)? Is the querying Pod's `dnsPolicy` sane (default
  `ClusterFirst`)? Test directly from inside a debug pod with `nslookup`/
  `dig` against the Service name AND against `kubernetes.default` (sanity
  check DNS works at all before assuming the specific Service is broken).

### D. Resource and dependency failures (15 min)
- `Pending` PVC (`kubectl get pvc` shows `Pending` not `Bound`) — usually
  StorageClass mismatch or provisioner not running.
- Config/secret-not-found errors surface as container `CreateContainerConfig
  Error` in `kubectl describe pod` Events — always cross-check the
  ConfigMap/Secret NAME and KEY referenced actually exist
  (`kubectl get configmap/secret`).
- Readiness-vs-liveness confusion (Day 69) as a debugging trap: a Pod stuck
  "Running but 0/1 Ready" is a readiness failure, not a crash — don't chase
  a restart that isn't happening.

## Lab (2h) — break it, then fix it, methodically

### Part 1 — Pending pod scenarios (25 min)
1. Deploy a Pod requesting `resources.requests.memory: 100Gi` (impossible
   on a laptop kind node). `kubectl describe pod` — read the exact
   scheduling-failure Event message. Fix by lowering the request.
2. Deploy a Pod with a `nodeSelector` for a label that doesn't exist on any
   node. Diagnose the same way, then fix by removing/correcting the
   selector.

### Part 2 — ImagePullBackOff and CrashLoopBackOff (30 min)
3. Deploy a Pod with a nonexistent image tag — diagnose via Events, fix the
   tag.
4. Deploy a Pod whose container command deliberately exits non-zero
   immediately (`command: ["sh","-c","exit 1"]`) with default
   `restartPolicy: Always` — watch it enter `CrashLoopBackOff` with rising
   RESTARTS. `kubectl logs <pod> --previous` to see the (empty, in this
   case) last-run output, and `kubectl describe pod` for `Last State:
   Terminated, Reason: Error, Exit Code: 1`. Fix the command to exit 0 and
   confirm it stabilizes (or switch to a real long-running process).

### Part 3 — DNS failure hunt (30 min)
5. Deploy a Pod whose app tries to reach a Service name that doesn't exist
   (e.g., a debug pod running `wget -qO- http://ghost-service` in a loop,
   logging failures). Confirm the failure symptom in logs.
6. Follow the DNS checklist from Theory C: confirm CoreDNS is healthy, then
   `nslookup ghost-service` from a debug pod to reproduce directly, then
   `nslookup kubernetes.default` to confirm DNS itself isn't broken (only
   the specific name is missing). Fix by creating the missing Service (or
   correcting the typo) and re-verify resolution succeeds.

### Part 4 — Dependency and config failures (35 min)
7. Deploy a Pod referencing a ConfigMap key that doesn't exist
   (`envFrom.configMapRef.name: does-not-exist`). Diagnose via `kubectl
   describe pod` Events (`CreateContainerConfigError`); fix by creating the
   correct ConfigMap.
8. Deploy a Pod with a PVC requesting a StorageClass name that doesn't
   exist. `kubectl get pvc` shows `Pending` forever; `kubectl describe pvc`
   for the exact reason. Fix by correcting the StorageClass name or
   removing it to use the cluster default.
9. Wrap-up: write a one-page personal "troubleshooting playbook" cheat
   sheet (in your own notes, not committed to the project) summarizing the
   funnel from Theory A plus the 6 scenarios you just fixed — this becomes
   your go-to reference for the rest of Phase 3 and for CKA drill days
   (85–86).

## Definition of done
Diagnosed and fixed at least 6 distinct failure classes (Pending ×2,
ImagePullBackOff, CrashLoopBackOff, DNS, ConfigMap/PVC dependency) using
Events and logs as primary evidence, not guessing · wrote a personal
troubleshooting cheat sheet.
