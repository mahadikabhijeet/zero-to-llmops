## Theory (1h)

### A. Probes — how k8s knows a container is actually healthy (25 min)
- **Liveness probe**: "is this container alive?" Fails → kubelet **restarts**
  the container. Use for detecting deadlocks/hangs the process can't
  self-recover from.
- **Readiness probe**: "is this container ready to serve traffic?" Fails →
  Pod is removed from Service Endpoints (Day 65) but NOT restarted — use for
  temporary unavailability (warming a cache, waiting on a dependency).
- **Startup probe**: for slow-starting apps — disables liveness/readiness
  checks until startup succeeds, so a legitimately slow boot isn't mistaken
  for a hang. `failureThreshold * periodSeconds` gives it a long total grace
  window.
- Probe mechanisms: `httpGet` (path+port, expects 2xx/3xx), `tcpSocket`
  (port opens), `exec` (command exit code 0 = healthy). Key tuning fields:
  `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds`,
  `failureThreshold`, `successThreshold`.
- Common misconfig: liveness probe too aggressive on a slow-starting app →
  crash-loop from k8s repeatedly restarting something that just needed more
  time — this is why startup probes exist.

### B. Requests and limits — the resource contract (20 min)
- `resources.requests`: what the scheduler guarantees is reserved for this
  container — used for **scheduling decisions** (which node has room).
- `resources.limits`: the hard ceiling — CPU limit gets throttled (CFS
  quota, not killed) if exceeded; memory limit gets the container
  **OOMKilled** if exceeded (no throttling possible for memory).
- Units: CPU in cores or millicores (`500m` = half a core), memory in
  `Mi`/`Gi`. Always set both on real workloads — no requests means the
  scheduler can't reason about fit; no limits means one runaway container
  can starve the node.

### C. QoS classes (10 min)
- **Guaranteed**: requests == limits for every container in the Pod —
  highest priority, last to be evicted under node pressure.
- **Burstable**: requests set, but requests < limits (or limits unset on
  some) — middle priority.
- **BestEffort**: no requests/limits at all — first to be evicted under
  memory pressure. `kubectl describe pod` shows the assigned QoS class.

### D. Horizontal Pod Autoscaler (HPA) and metrics-server (5 min)
- HPA watches a metric (default: CPU utilization %) via **metrics-server**
  and adjusts `replicas` on a Deployment/StatefulSet automatically —
  `kubectl autoscale deployment <name> --cpu-percent=50 --min=1 --max=5`.
- metrics-server must be installed separately (not part of core k8s); on
  kind it needs `--kubelet-insecure-tls` since kind's kubelet certs aren't
  signed for this by default — a known local-cluster quirk worth noting.

## Lab (2h)

### Part 1 — Liveness vs readiness in action (35 min)
1. Deploy an nginx Pod with a **readiness** probe (`httpGet /`, port 80,
   `periodSeconds: 5`). `kubectl get pod -w` and `kubectl get endpoints` on
   its Service (create one) simultaneously.
2. `kubectl exec -it <pod> -- rm /usr/share/nginx/html/index.html` (breaks
   the readiness check's target implicitly if you probe a real path, or
   just `kubectl exec -it <pod> -- nginx -s stop` to kill the nginx
   process) — watch readiness flip to `false` and the Pod drop out of
   Endpoints WITHOUT restarting.
3. Now add a **liveness** probe (`exec`, `pgrep nginx` or similar) to a
   fresh Pod; kill nginx inside it the same way — watch `kubectl get pod -w`
   show a RESTART count increment this time. Compare the two outcomes
   side by side and explain why.

### Part 2 — Startup probe for a deliberately slow container (25 min)
4. Write a Pod whose container command sleeps 20s before starting a simple
   HTTP server (or use `command: ["sh","-c","sleep 20 && <serve-something>"]`
   with busybox+nc, or just simulate with nginx + an init delay).
5. Add a startup probe with enough `failureThreshold * periodSeconds` to
   cover the 20s delay, PLUS a liveness probe with a short
   `initialDelaySeconds` that would have crash-looped it without the
   startup probe. Apply, watch `kubectl describe pod` events show
   `Startup probe failed` (expected, transient) NOT `Liveness probe failed`
   causing a restart during the warm-up window.

### Part 3 — Requests/limits and QoS (30 min)
6. Deploy 3 Pods: Pod A with requests==limits (Guaranteed), Pod B with
   requests<limits (Burstable), Pod C with neither (BestEffort).
7. `kubectl describe pod <each>` and confirm the `QoS Class` line matches
   expectations.
8. Deploy a Pod with a tiny memory limit (e.g. `32Mi`) running something
   that will exceed it (a stress tool, or a script allocating memory);
   watch it get `OOMKilled` via `kubectl describe pod` (Last State:
   Terminated, Reason: OOMKilled).

### Part 4 — metrics-server and HPA (30 min)
9. Install metrics-server on kind with `--kubelet-insecure-tls` patched in
   (per kind's known workaround); `kubectl top nodes` and `kubectl top pods`
   once it's Ready — confirm real metrics flow.
10. Deploy a small CPU-bound Deployment with requests set; `kubectl
    autoscale deployment <name> --cpu-percent=50 --min=1 --max=4`.
11. Generate load against it (a busy-loop container or `kubectl run
    load-gen --image=busybox:1.36 -- sh -c "while true; do wget -q -O-
    <svc>; done"`); `kubectl get hpa -w` — watch replicas scale up, then
    stop the load and watch it scale back down after the cooldown window.

## Definition of done
Demonstrated liveness restarting a container and readiness only pulling it
from Endpoints · startup probe protected a slow-boot container from a
premature liveness restart · confirmed QoS classes and triggered an
OOMKill · HPA scaled replicas up and back down under synthetic load.
