## Theory (1h) — CKA exam domains and time-management method
- The CKA exam is 100% hands-on (no multiple choice), weighted roughly:
  Workloads & Scheduling, Services & Networking, Storage, Troubleshooting,
  and Cluster Architecture/Installation/Configuration — exactly the
  Days 61–73 material, which is why these drills come now, not earlier.
- Exam technique (practice today, not just k8s facts): read the FULL task
  before typing anything; use `kubectl config set-context --current
  --namespace=<ns>` immediately if a task specifies a namespace, so every
  subsequent command defaults correctly; use imperative `kubectl create/
  run --dry-run=client -o yaml` to scaffold fast, then hand-edit — this is
  dramatically faster than writing YAML from scratch under time pressure.
- Bookmark `kubectl explain <kind>.<field>` mentally as your ONLY
  reference tool during a real exam (docs.k8s.io is allowed, but explain
  is faster) — practice using it instead of guessing field names today.
- Time-box discipline: 1 task ≈ 5–10 minutes; if stuck past that, mark it
  and move on — partial credit exists, and easy tasks elsewhere are worth
  more than one perfect answer.

## Lab (2h) — timed task list (set a 15-minute timer per task, work on a
fresh `kind create cluster --name cka-drill`)

1. Create a namespace `cka` and set it as your current context's default.
2. Create a Deployment named `web` in `cka`, image `nginx:1.27`, 3
   replicas, with a resource request of `100m` CPU / `128Mi` memory and a
   limit of `250m` CPU / `256Mi` memory.
3. Expose `web` via a ClusterIP Service on port 80, then create a second
   Service of type NodePort on the same selector using nodePort `30090`.
4. Create a ConfigMap `web-config` with key `LOG_LEVEL=info`, and patch the
   `web` Deployment to consume it via `envFrom` — trigger and verify a
   successful rollout.
5. Add a liveness probe (`httpGet /`, port 80) and a readiness probe
   (same) to the `web` Deployment; verify all 3 pods reach `Running` and
   `Ready 1/1`.
6. Scale `web` to 5 replicas imperatively, then back to 3 declaratively
   (edit the manifest and re-`apply`) — verify the final replica count.
7. Create a PVC `web-data` requesting 1Gi ReadWriteOnce using the cluster's
   default StorageClass; mount it into the `web` Deployment at `/data`;
   verify it's `Bound` and mounted (`exec` in, `df -h /data`).
8. A teammate's Pod spec (write one yourself to simulate this) references
   a Secret key that doesn't exist — diagnose via Events and fix it so the
   Pod reaches `Running`.
9. Create a Job named `report` (image `busybox:1.36`, command prints
   "done" once) with `backoffLimit: 2`; verify it reaches `Completions: 1/1`
   and read its logs.
10. Cordon the (single) node, verify no new pods schedule onto it by
    attempting to scale `web` to 4 (expect `Pending`), then uncordon and
    confirm it schedules successfully.

5. Edit `web.yaml` adding `livenessProbe`/`readinessProbe` blocks with
   `httpGet: {path: /, port: 80}`; apply; `kubectl get pods -w`
6. `kubectl scale deployment/web --replicas=5`; edit `web.yaml`
   `replicas: 3`; `kubectl apply -f web.yaml`; `kubectl get deploy web`
7. `kubectl apply -f web-data-pvc.yaml` (accessModes: ReadWriteOnce,

10. `kubectl cordon <node>`; `kubectl scale deployment/web --replicas=4`;

    confirms `node(s) were unschedulable`; `kubectl uncordon <node>`;
    confirm the pod schedules

## Definition of done
All 10 tasks attempted under a self-imposed timer BEFORE checking
solutions · every failure diagnosed via `kubectl describe`/Events rather
than guessing · cluster torn down after (`kind delete cluster --name
cka-drill`).
