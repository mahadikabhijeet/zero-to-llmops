## Theory (1h)

### A. Why Terraform, and where it fits (10 min)
- Everything through Day 78 assumed a cluster/VM already existed
  (Ansible configured it, Helm deployed onto it). Terraform answers the
  layer BELOW that: **provisioning** the infrastructure itself
  (VMs, networks, even the kind cluster resource) declaratively.
- **Provision vs configure** (this exact boundary gets its own day, 83):
  Terraform creates/destroys infrastructure resources; Ansible/Helm
  configure what runs on/in them. Today we practice Terraform entirely
  against LOCAL providers (docker, kind) — no cloud account needed yet
  (that's Phase 4).

### B. HCL and providers (20 min)
- HashiCorp Configuration Language (HCL): declarative blocks —
  `resource "<type>" "<local_name>" { ... }`, `provider "<name>" { ... }`,
  `variable`, `output`, `data`.
- A **provider** is a plugin translating HCL into API calls for a specific
  system (AWS, Docker, kind, GitHub...). `terraform init` downloads the
  providers referenced in the config into `.terraform/`.
- `required_providers` block in a `terraform {}` block pins provider
  source + version — same discipline as pinning package versions
  (recall Day 9's `dnf` version pinning).

### C. The core workflow (15 min)
- `terraform init` — download providers, set up backend (state storage).
- `terraform plan` — compute the DIFF between current state and desired
  config, WITHOUT changing anything — read every line before ever
  applying; this is Terraform's single most important safety habit.
- `terraform apply` — execute the plan (prompts for confirmation unless
  `-auto-approve`); `terraform destroy` — tear down everything Terraform
  manages in this config (dangerous, mirrors `plan`'s review discipline in
  reverse).
- `terraform fmt` / `terraform validate` — formatting and syntax checks
  (preview of Day 83's CI integration).

### D. State — what it is and why it's dangerous (15 min)
- `terraform.tfstate`: a JSON file mapping your HCL resources to REAL
  infrastructure IDs — Terraform's memory of what it created. Without
  state, Terraform has no way to know what already exists.
- State contains sensitive data in plaintext (resource attributes,
  sometimes secrets) — never commit `.tfstate` to git (add to
  `.gitignore` immediately); local state is fine for today's labs, but
  Day 81 covers remote state + locking for anything shared/real.
- `terraform state list`, `terraform state show <resource>` — inspect
  what Terraform believes exists, without touching the real
  infrastructure.
- Drift: if someone changes real infrastructure OUTSIDE Terraform (e.g.
  manually `docker rm`'d a container Terraform created), the next `plan`
  will show a diff trying to "fix" it back — Day 81 covers `import` and
  drift handling formally.

## Lab (2h)

### Part 1 — Install and first provider (20 min)
1. Install `terraform` CLI; `terraform version`.
2. Create `tf-lab/main.tf` with a `terraform {}` block requiring the
   `kreuzwerker/docker` provider (a well-known community provider for
   local Docker resources), and a `provider "docker" {}` block.
3. `terraform init` — observe it download the provider into
   `.terraform/`; note `.terraform.lock.hcl` (dependency lock file,
   commit THIS one, unlike state).

### Part 2 — Provision a real local resource (35 min)
4. Add a `resource "docker_image" "nginx" { name = "nginx:1.27" }` and a
   `resource "docker_container" "web" { image = docker_image.nginx.
   image_id name = "tf-web" ports { internal = 80 external = 8080 } }`.
5. `terraform plan` — read the full proposed-changes output line by line
   before proceeding.
6. `terraform apply` — confirm interactively; `docker ps` to see the
   container Terraform created; `curl localhost:8080`.
7. `terraform state list` and `terraform state show docker_container.web`
   — confirm Terraform's state matches docker's reality.

### Part 3 — Drift and destroy (30 min)
8. `docker stop tf-web` manually (outside Terraform) — `terraform plan`
   again and observe it detects the drift and proposes to fix it (recreate
   or restart depending on provider behavior). Discuss why this matters:
   Terraform assumes it OWNS anything in its state.
9. `terraform destroy` — confirm and watch it tear down the container and
   image cleanly. `docker ps -a` to confirm removal.

### Part 4 — kind cluster as a Terraform resource (35 min)
10. Explore the `tehcyx/kind` (or equivalent) Terraform provider for
    managing a kind cluster declaratively — add a `resource "kind_cluster"
    "default" { name = "tf-fresher" wait_for_ready = true }` to a new
    config in `tf-lab/kind/main.tf`.
11. `terraform init && terraform plan && terraform apply` — watch it stand
    up a kind cluster; `kubectl get nodes --context kind-tf-fresher` to
    confirm it's real and functional.
12. `terraform destroy` to tear the cluster down. Add `*.tfstate*` and
    `.terraform/` to `.gitignore` in this lab directory (or a project-wide
    `.gitignore`) before committing anything.

## Definition of done
Ran the full init/plan/apply/destroy cycle against a real local Docker
resource · read and understood a `plan` diff before applying · observed and
explained drift detection · stood up and tore down a kind cluster purely
via Terraform · `.tfstate` correctly gitignored, `.terraform.lock.hcl`
correctly NOT gitignored.
