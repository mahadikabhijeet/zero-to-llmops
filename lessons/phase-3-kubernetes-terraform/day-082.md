## Theory (1h)

### A. `count` — replicating a resource N times (15 min)
- `resource "docker_container" "web" { count = 3, name = "web-${count.
  index}" ... }` — creates `docker_container.web[0]`, `[1]`, `[2]`;
  reference all of them via `docker_container.web[*].id` (splat
  expression).
- Weakness: `count` indexes by POSITION — removing item `[1]` from a list
  of 3 shifts indices and can cause Terraform to destroy/recreate items
  that didn't actually change. This is the exact motivation for
  `for_each`.

### B. `for_each` — replicating keyed by identity (20 min)
- `resource "docker_container" "web" { for_each = toset(["a","b","c"])
  name = "web-${each.key}" ... }` (or `for_each = var.some_map` using
  `each.key`/`each.value`) — each instance is tracked by a STABLE key, not
  a position, so removing one item only destroys that one, leaving others
  untouched.
- Rule of thumb taught in the field: prefer `for_each` over `count`
  whenever items have meaningful identity (names, environments); reserve
  `count` for truly identical, order-independent replicas (rare) or the
  0/1 on-off pattern (`count = var.enabled ? 1 : 0`).

### C. Lifecycle meta-arguments (15 min)
- `lifecycle { create_before_destroy = true }` — for resources where
  downtime from destroy-then-create is unacceptable (create the
  replacement first, then destroy the old one).
- `lifecycle { prevent_destroy = true }` — a safety rail on critical
  resources (a real database, in production) that makes `terraform
  destroy` (or a plan that would destroy it) fail outright, requiring
  deliberate removal of this flag first — the closest thing Terraform has
  to an "are you sure" beyond the standard `apply` confirmation.
- `lifecycle { ignore_changes = [tags] }` — tells Terraform to stop
  flagging drift on specific attributes (e.g., a field another system
  manages) — used sparingly and deliberately, since it creates a
  permanent blind spot for that attribute.

### D. Combining the pieces (10 min)
- Real modules commonly combine `for_each` + `lifecycle` +
  variables/locals from Days 79–81 — e.g., a module standing up N kind
  clusters (via `for_each` over a map of cluster configs), each with
  `create_before_destroy` so replacing one doesn't tear down the others.

## Lab (2h)

### Part 1 — count and its footgun (30 min)
1. Write a config creating 3 docker containers via `count = 3` (simple
   nginx containers, distinct names via `count.index`).
2. `terraform apply` — confirm 3 containers exist.
3. Change the underlying image tag for ONLY conceptually "container 1"
   by editing the list count down to 2 (simulate removing a middle item
   if using a list-based name source) — `terraform plan` and observe
   unnecessary destroy/recreate churn on indices that shifted. Document
   this observation explicitly — this IS the lesson.

### Part 2 — Refactor to for_each (35 min)
4. Rewrite the same 3 containers using `for_each = toset(["alpha", "beta",
   "gamma"])`, naming each container `web-${each.key}`.
5. `terraform apply` — confirm 3 containers exist, now keyed by name not
   position.
6. Remove `"beta"` from the set, `terraform plan` — confirm ONLY the beta
   container is proposed for destruction; alpha and gamma show "no
   changes." Apply and confirm.

### Part 3 — Lifecycle meta-arguments (30 min)
7. Add `lifecycle { prevent_destroy = true }` to one container resource.
   `terraform destroy` (or a plan that would remove it) — confirm
   Terraform refuses and explains why. Remove the flag, destroy
   successfully, discuss when this guard is worth the friction (real
   databases, not lab containers).
8. Demonstrate `create_before_destroy` on a resource whose change would
   normally force replacement (e.g., a container's `name` — many
   providers force replacement on name changes) — apply a rename with and
   without the flag, observing the ORDER of destroy/create in the plan
   output each time.

### Part 4 — Combine and clean up (25 min)
9. Build one small config combining `for_each` over a map (key = cluster
   name, value = a small object with a `node_count`-style setting if the
   kind provider supports it, else just distinct labels) to stand up 2
   kind clusters at once via a single resource block, reusing the Day 80
   module if convenient.
10. `terraform apply`, confirm both clusters exist via `kubectl config
    get-contexts`; `terraform destroy` to clean up everything from today
    (containers, images, clusters). `docker ps -a` and `kind get clusters`
    to confirm nothing lingers.

## Definition of done

operation · compared `create_before_destroy` on vs off for a
replacement-forcing change · stood up multiple resources from one block via
`for_each` over a map, then fully cleaned up.
