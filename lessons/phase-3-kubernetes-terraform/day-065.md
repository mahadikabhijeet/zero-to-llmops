## Theory (1h)

### A. The problem Services solve (10 min)
- Pod IPs are ephemeral — every reschedule/rollout gives new IPs. Nothing
  should ever hardcode a Pod IP.
- A **Service** is a stable virtual IP + DNS name that load-balances across
  a dynamic set of Pods matched by a label selector — same idea as
  Deployment's selector, applied to networking instead of scheduling.

### B. Service types (20 min)
- **ClusterIP** (default): stable internal-only IP, reachable from inside the
  cluster only — the default for backend/db services.
- **NodePort**: opens a static port (30000–32767) on every node, forwards to
  the ClusterIP — simplest way to reach a service from outside a cluster
  without a cloud load balancer (what we'll use on kind).
- **LoadBalancer**: asks the cloud provider for an external LB (AWS
  ELB/GCP LB) — on kind this stays `<pending>` unless you install
  MetalLB or use kind's port-mapping tricks; note the gap, don't fake it.
- **ExternalName**: DNS CNAME to an external service — no proxying, just a
  DNS alias (brief mention, rare use case).

### C. Endpoints, kube-proxy, and how traffic actually flows (20 min)
- A Service has no proxying logic itself — it's a spec. The actual work is
  done by:
  - **Endpoints/EndpointSlices** object: auto-populated list of matching Pod
    IPs+ports (`kubectl get endpoints <svc>`).
  - **kube-proxy**: runs on every node, programs iptables (or IPVS) rules so
    traffic to the Service's ClusterIP gets DNAT'd to a real Pod IP,
    round-robin by default.
- If a Pod isn't Ready (Day 69 probes), kube-proxy removes it from Endpoints
  — so unready pods stop receiving traffic even though they're "Running."

### D. Service DNS and NetworkPolicy intro (10 min)
- CoreDNS gives every Service a DNS name:
  `<service>.<namespace>.svc.cluster.local` (short form `<service>` works
  within the same namespace). This is how apps discover each other — never
  hardcode IPs, always use the Service DNS name.
- **NetworkPolicy**: by default, all Pods can reach all Pods (flat network) —
  a NetworkPolicy is an allow-list (deny-by-default once one selects a Pod)
  restricting ingress/egress by label selector. Requires a CNI that
  enforces it (kind's default kindnet does NOT enforce — note this gap,
  deeper NetworkPolicy work resumes when a policy-enforcing CNI is in play).

## Lab (2h)

### Part 1 — ClusterIP and DNS (30 min)
1. Fresh cluster if needed. Apply a Deployment `backend` (nginx:1.27,
   3 replicas, label `app=backend`).
2. Create `backend-svc.yaml`: `kind: Service`, `type: ClusterIP`, selector
   `app=backend`, port 80 → targetPort 80. Apply it.
3. `kubectl get svc,endpoints backend` — confirm 3 Pod IPs appear in
   Endpoints.
4. Run a throwaway debug pod: `kubectl run tmp --rm -it --image=busybox:1.36
   -- sh`, then from inside: `wget -qO- backend` and `nslookup backend` —
   confirm DNS resolution and load-balanced response.

### Part 2 — Watch endpoints track Pod health (25 min)
5. `kubectl delete pod -l app=backend --field-selector=status.phase=Running
   --wait=false` (or just delete one pod by name) while watching `kubectl get
   endpoints backend -w` — confirm the IP list updates as pods are replaced.
6. Scale the deployment to 5, then 1, watching Endpoints track it each time.

### Part 3 — NodePort exposure (30 min)
7. Create `backend-nodeport.yaml`: same selector, `type: NodePort`,
   `nodePort: 30080`. Apply.
8. Because kind runs nodes as Docker containers, the node port isn't
   auto-exposed to your host — recall or check `kind create cluster --config`
   port-mapping; if the current cluster wasn't created with a mapped port,
   delete and recreate it with a config file exposing `30080:30080` on the
   control-plane node, THEN test `curl localhost:30080` from your host.
9. Confirm round-robin: run the curl a few times, or `kubectl logs -l
   app=backend --prefix` to see which pod served each hit (add a distinct
   `hostname` response via a quick ConfigMap-mounted index.html if time
   allows — otherwise just trust the Endpoints list).

### Part 4 — NetworkPolicy exploration (25 min)
10. Write a `deny-all-to-backend.yaml` NetworkPolicy selecting `app=backend`
    with an empty `ingress: []` (deny all ingress once selected).
11. Apply it, retest the debug-pod `wget backend` from Part 1 — on kind's
    default CNI, note whether it still succeeds (likely yes, since kindnet
    doesn't enforce policy) and record this as a known limitation to revisit
    if a policy-enforcing CNI (Calico) is installed later.
12. Clean up all objects from today.
