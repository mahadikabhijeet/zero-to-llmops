## Theory (1h)

### A. Variables — parameterizing configs (15 min)
- `variable "name" { type = string, default = "...", description = "..." }`
  — declared in `variables.tf` by convention (Terraform doesn't enforce
  filenames, but this is universal practice, same spirit as Ansible's
  `defaults/`).
- Supplying values: `-var="name=value"` (CLI), `-var-file="prod.tfvars"`,
  or a `terraform.tfvars` file auto-loaded if present. Precedence: CLI
  `-var` > `*.auto.tfvars` > `terraform.tfvars` > variable defaults.
- Types: `string`, `number`, `bool`, `list(string)`, `map(string)`,
  `object({...})` — Terraform validates types at plan time, catching
  mistakes before touching infrastructure.

### B. Outputs and locals (15 min)
- `output "name" { value = resource.type.name.attribute }` — surfaces a
  resource's computed attribute (e.g., an assigned ID or IP) after apply;
  visible via `terraform output` and consumable by OTHER Terraform
  configs (recall this for Day 81's remote-state data sharing).
- `locals { name = expression }` — named expressions to avoid repeating
  the same computed value across multiple resource blocks (like a
  variable, but computed, not user-supplied) — improves readability the
  same way Bash functions did in Day 23.

### C. Writing a reusable module (20 min)
- A **module** is any directory of `.tf` files — the ROOT module is
  wherever you run `terraform apply`; anything else you `source =` from
  becomes a **child module**.
- Module structure convention: `variables.tf` (inputs), `main.tf`
  (resources), `outputs.tf` (what it exposes) — mirrors a function
  signature: inputs in, outputs out, implementation hidden.
- Calling a module: `module "name" { source = "./modules/mymodule"
  input_var = "value" }`. Referencing its outputs elsewhere:
  `module.name.output_name`.
- Why modules matter: the SAME module (e.g., "a kind cluster with N
  worker nodes") can be instantiated multiple times with different inputs
  (dev cluster, test cluster) — DRY infrastructure, same principle as
  Ansible roles from Day 53.

### D. Data sources (10 min)
- `data "<type>" "<name>" { ... }` — READS existing information without
  managing/owning it (contrast with `resource`, which creates/owns).
  Example: looking up an existing Docker network by name, or (Phase 4)
  looking up the latest AMI ID published by AWS.
- Data sources refresh on every `plan` — useful for referencing
  infrastructure Terraform doesn't manage, without importing it into
  state.

## Lab (2h)

### Part 1 — Variables and outputs (30 min)
1. Take Day 79's docker_container config; refactor hardcoded values
   (image name, container name, ports) into `variables.tf` with sensible
   defaults.
2. Create `terraform.tfvars` overriding at least one variable; `terraform
   plan -var-file="terraform.tfvars"` (or rely on auto-load) — confirm the
   override took effect in the plan output.
3. Add `outputs.tf` exposing the container's ID and the mapped external
   port. `terraform apply` then `terraform output` — confirm both values
   print.

### Part 2 — Locals (15 min)
4. Add a `locals` block computing a `container_name` from a variable
   prefix + a fixed suffix (e.g., `local.container_name =
   "${var.name_prefix}-web"`), and use `local.container_name` in the
   resource instead of a hardcoded string. Re-`plan`/`apply` to confirm no
   unwanted resource replacement (renaming can force recreation —
   observe and explain this if it happens).

### Part 3 — Write a reusable module (45 min)
5. Create `modules/kind-cluster/` with `variables.tf` (`cluster_name`,
   `node_count` or similar — check what the kind provider actually
   supports and scope the module to real capabilities), `main.tf` (the
   `kind_cluster` resource from Day 79), `outputs.tf` (cluster name /
   kubeconfig path if the provider exposes one).
6. In a root `main.tf`, call this module TWICE with different
   `cluster_name` values (e.g., `module "dev" { source =
   "./modules/kind-cluster" cluster_name = "dev" }` and a `staging` one).
7. `terraform init` (re-run — new module requires it), `terraform plan` —
   read carefully, confirm it proposes TWO separate clusters. `terraform
   apply` — confirm both exist via `kubectl config get-contexts`.

### Part 4 — Data source and cleanup (30 min)
8. Add a `data "docker_network" "bridge" {}` (or equivalent read-only
   lookup for whatever provider is in play) referencing an existing
   resource NOT created by this config — print one of its attributes via
   an output, confirming Terraform can read without owning it.
9. `terraform destroy` — tear down both kind clusters and any docker
   resources from this session. Confirm `kubectl config get-contexts` no
   longer lists them.
10. Commit the module + root config structure to a `terraform/` directory
    in the project repo (gitignoring state/`.terraform/` as established
    Day 79), with a short README explaining the module's inputs/outputs.

## Definition of done
Refactored a hardcoded config into variables + outputs + locals · authored
a reusable module and instantiated it twice with different inputs · used a
data source to read (not manage) existing infrastructure · module
structure committed to the project repo with docs.
