## Theory (1h)

### A. What the capstone integrates (15 min)
- Day 78 got the app FULLY on k8s via its own Helm chart, deployed from
  CI — but the kind cluster itself was still created manually
  (`kind create cluster`). Today closes that last gap: the cluster's
  EXISTENCE becomes Terraform-managed too, using the `kind_cluster`
  resource and module practiced on Days 79–82.
- End state: `terraform apply` creates the kind cluster → a follow-up step
  (script or CI job) runs `helm upgrade --install` against it → the full
  app (app+db+ingress+CronJob) comes up — one command (or one CI
  pipeline) taking you from NOTHING to a fully running, observable
  application. This is the complete provision→configure→deploy chain
  named in Day 83, now executed for real, end to end.

### B. Documenting the architecture (15 min)
- A capstone needs an architecture diagram — even ASCII/Mermaid is fine —
  showing every layer: Terraform (provisions kind cluster) → Helm chart
  (deploys app/db/ingress/cronjob onto it) → CI (drives both steps on
  every commit) → GitHub (source of truth, recall Day 33).
- Mermaid syntax (`graph TD; A-->B;`) renders natively in GitHub READMEs —
  a low-effort, high-payoff diagram format worth learning today if not
  already familiar.

### C. What "done" looks like for a portfolio piece (15 min)
- Recall Day 60's Phase 2 capstone standard (public, tested, containerized,
  CI-built, Ansible-deployed) — Phase 3's bar adds: k8s-native (Helm chart,
  not just a container on a VM), infra-as-code for the cluster itself
  (Terraform), and a written narrative (the post) explaining WHY each tool
  was chosen at each layer, not just THAT it works — this is what
  distinguishes a job-ready portfolio entry from a pile of working code.

### D. The public post — job-readiness continuation (15 min)
- Recall Day 41/48/60's pattern of committing/shipping publicly. Today's
  post (LinkedIn/blog, feeding the YouTube channel per the README's
  original motivation) should cover: the problem (manual cluster+deploy
  setup doesn't scale or reproduce), the solution (Terraform+Helm+CI
  chain), one specific hard-won lesson (e.g., a Day 73-style debugging
  war story), and a link to the repo — recruiters and hiring managers
  read these as evidence of communication skill, not just code.

## Lab (2h) — the capstone build

### Part 1 — Terraform-managed cluster (30 min)
1. In `terraform/`, finalize a `kind-cluster` module (or reuse Day 80's)
   that stands up the project's cluster with a name like
   `fresher-capstone`, including the `extraPortMappings`/`ingress-ready`
   node config from Day 66 baked into the module (so Ingress works
   immediately, no manual cluster recreation needed).
2. `terraform init && terraform plan && terraform apply` — confirm the
   cluster comes up; `kubectl config use-context kind-fresher-capstone`;
   `kubectl get nodes`.

### Part 2 — Bootstrap cluster prerequisites (25 min)
3. Install ingress-nginx and (if used) cert-manager onto the new cluster
   — either as a documented manual step or, for extra credit, as
   additional Terraform `helm_release` resources (the Helm Terraform
   provider) if comfortable layering that in per Day 83's noted tradeoff.
4. Confirm both are Running/Ready before proceeding.

### Part 3 — Deploy the full app via Helm (30 min)
5. `helm upgrade --install fresher-project ./fresher-project -f values.
   yaml --wait --timeout 5m` against the Terraform-created cluster.
6. `kubectl get all,ingress,pvc,cronjob -l app.kubernetes.io/instance=
   fresher-project` — confirm every component (app, db, ingress, cronjob)
   is healthy. `curl` the ingress host end to end to confirm the full
   request path works, exactly as validated on Day 78 but now on a
   cluster that exists ONLY because of Terraform.

### Part 4 — Full teardown/rebuild proof, diagram, and post (35 min)
7. `terraform destroy` — tear the ENTIRE cluster down. Confirm `kind get
   clusters` shows nothing. Then `terraform apply` again followed by the
   Part 3 Helm command — time how long "nothing to fully running app"
   takes, and record that number; this number IS the capstone's core
   proof point (reproducibility).
8. Write the architecture diagram (Mermaid, in the project README) showing
   Terraform → cluster → Helm → app/db/ingress/cronjob → CI driving both.
9. Update the CI pipeline (from Day 78) to ALSO run `terraform apply`
   against the kind-cluster module before the Helm step, so the full
   provision-through-deploy chain is automated in one pipeline run, not
   just locally.
10. Draft and (with the instructor's review — this is an outward-facing,
    hard-to-reverse action, flag it rather than auto-posting) prepare the
    public post per Theory D, ready to publish once approved.

## ★ Definition of done (phase capstone — hold this bar)
`terraform apply` provisions the kind cluster from nothing · `helm
upgrade --install` deploys the full app (app+db+ingress+CronJob) onto it ·
a full destroy→apply→deploy cycle was timed and proven reproducible ·
architecture diagram committed to the README · CI runs the full
Terraform+Helm chain on every relevant commit · public post drafted and
held for the instructor's explicit go-ahead before publishing.
