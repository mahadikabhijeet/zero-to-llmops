## Theory (1h)

### A. Why Helm exists (10 min)
- By Day 73 you've hand-written a dozen YAML files per app (Deployment,
  Service, ConfigMap, PVC...) with repeated boilerplate. Helm is the
  package manager for k8s: bundles a set of manifests into a versioned,
  parameterized **chart**, installable/upgradeable/rollback-able as one
  unit. Same motivation as `dnf`/`rpm` from Day 9, one layer up.

### B. Chart anatomy (recall now, author on Day 75) (15 min)
- A chart is a directory: `Chart.yaml` (metadata: name, version,
  appVersion), `values.yaml` (default parameters), `templates/` (Go
  templated YAML manifests), optionally `charts/` (sub-charts/
  dependencies).
- `helm template <chart>` renders manifests locally WITHOUT installing —
  the fastest way to inspect what a chart would actually apply, and your
  primary debugging tool for both consuming and (Day 75) authoring charts.

### C. Install, upgrade, rollback, and releases (20 min)
- `helm repo add <name> <url>` + `helm repo update` — chart repositories
  (like package repos from Day 9).
- `helm install <release-name> <chart> -f custom-values.yaml` — a
  **release** is a named, tracked instance of a chart's installation;
  you can install the same chart multiple times under different release
  names.
- `helm upgrade <release-name> <chart> -f custom-values.yaml` — Helm diffs
  against the current release and applies changes; every upgrade creates a
  new **revision**.
- `helm history <release-name>` / `helm rollback <release-name> <revision>`
  — direct parallel to `kubectl rollout history/undo` from Day 64, but at
  the whole-chart level instead of one Deployment.
- `helm uninstall <release-name>` removes all resources the release
  created (Helm tracks ownership via labels/annotations and a stored
  release manifest in a Secret).

### D. Values — the parameterization mechanism (15 min)
- `values.yaml` provides defaults; override via `-f file.yaml` (merges) or
  `--set key=value` (point overrides, good for one-offs/CI).
- `helm show values <chart>` to see all available knobs before installing.
- Values precedence (lowest to highest): chart's own `values.yaml` →
  `-f` file(s) in order given → `--set` flags (last wins on conflicts) —
  this ordering matters when environments layer dev/staging/prod values
  files.

## Lab (2h)

### Part 1 — Install Helm and explore a real chart (25 min)
1. Install `helm` CLI; `helm version`.
2. `helm repo add bitnami https://charts.bitnami.com/bitnami && helm repo
   update`.
3. `helm search repo bitnami/nginx` and `helm show chart bitnami/nginx`,
   `helm show values bitnami/nginx | less` — survey the available
   configuration surface before touching it.

### Part 2 — Install, inspect, and modify a release (40 min)
4. `helm install my-nginx bitnami/nginx --set service.type=ClusterIP` on
   your kind cluster. `kubectl get all -l app.kubernetes.io/instance=my-
   nginx` — note Helm's standard label conventions tying resources to the
   release.
5. `helm list`, `helm status my-nginx`, `helm get values my-nginx` (see
   only the overrides you set) vs `helm get values my-nginx --all` (full
   effective values).
6. `helm template bitnami/nginx --set service.type=NodePort | less` —
   render what an upgrade WOULD apply before actually doing it. Compare a
   couple of key rendered fields against the current live objects.
7. `helm upgrade my-nginx bitnami/nginx --set replicaCount=3` — confirm
   `kubectl get pods -l app.kubernetes.io/instance=my-nginx` shows 3 pods
   afterward.

### Part 3 — Rollback (25 min)
8. `helm history my-nginx` — see revisions 1 and 2.
9. Make a deliberately bad upgrade: `helm upgrade my-nginx bitnami/nginx
   --set image.tag=doesnotexist999`. Watch pods fail via
   `kubectl get pods -w` (ImagePullBackOff, recall Day 73's playbook).
10. `helm rollback my-nginx 2` — confirm it returns to the last-good
    revision; `kubectl get pods` recovers.

### Part 4 — Values files and a custom install (30 min)
11. Write your own `my-values.yaml` overriding at least 3 settings
    (replicaCount, resources.requests/limits, service.type). `helm upgrade
    my-nginx bitnami/nginx -f my-values.yaml` and confirm all 3 took effect
    via `kubectl describe` on the resulting objects.
12. `helm uninstall my-nginx` — confirm `kubectl get all -l
    app.kubernetes.io/instance=my-nginx` returns nothing (clean teardown).
13. Repeat a fresh install with a DIFFERENT chart from another popular repo
    (e.g., `bitnami/redis` or `ingress-nginx/ingress-nginx`) just to see a
    second chart's values surface and confirm the workflow generalizes.

## Definition of done
Installed, upgraded, and rolled back a real Helm chart on the kind cluster ·
used `helm template` to preview changes before applying · wrote and applied
a custom values file overriding multiple settings · cleanly uninstalled a
release and confirmed all resources were removed.
