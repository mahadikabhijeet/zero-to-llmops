## Theory (1h)

### A. Why externalize config (10 min)
- Recall Day 50's 12-factor intro: config lives in the environment, not
  baked into the image. ConfigMaps/Secrets are k8s's mechanism for this —
  same image, different config per environment (dev/staging/prod) without
  rebuilding.
- ConfigMap = non-sensitive config (key-value pairs, or whole files).
  Secret = same shape, but for sensitive data (passwords, tokens, certs) —
  **base64-encoded, NOT encrypted**, a caveat that trips people up.

### B. Creating and consuming ConfigMaps (20 min)
- Create: `kubectl create configmap app-config --from-literal=LOG_LEVEL=info
  --from-literal=PORT=8080`, or `--from-file=config.properties`, or
  declaratively via `data:` in a manifest.
- Consume as env vars: `envFrom.configMapRef.name` (bulk) or
  `env[].valueFrom.configMapKeyRef` (single key with custom env var name).
- Consume as files: `volumes[].configMap.name` +
  `volumeMounts[].mountPath` — each key becomes a file in that directory,
  useful for whole config files (nginx.conf, application.yaml).
- **Immutability**: `immutable: true` on a ConfigMap prevents updates (must
  delete+recreate) — improves performance at scale (kubelet stops watching
  it) and prevents accidental drift; standard practice is versioning the
  ConfigMap NAME (e.g. `app-config-v2`) and rolling the Deployment forward.

### C. Secrets — creation, consumption, and real caveats (20 min)
- Create: `kubectl create secret generic db-secret
  --from-literal=DB_PASSWORD=changeme`. `kubectl get secret db-secret -o
  yaml` — see the base64 value; `echo <value> | base64 -d` decodes it
  instantly — this IS the caveat: **base64 is encoding, not encryption**.
  Anyone with `get secret` RBAC access reads it in plaintext.
- Built-in types: `Opaque` (generic), `kubernetes.io/tls` (from Day 66),
  `kubernetes.io/dockerconfigjson` (registry pull secrets).
- Real protection comes from: RBAC restricting who can `get`/`list` secrets
  (Day 71), encryption-at-rest for etcd (cluster-admin concern), and
  external secret stores (Vault, sealed-secrets, sops from Day 58) for
  anything truly sensitive — flag this as "the k8s-native mechanism has
  limits" rather than a solved problem.
- Consume identically to ConfigMaps: `envFrom.secretRef` or
  `volumes[].secret.secretName` (mounted files get 0400-ish perms by
  default — more secure than env vars, which leak into `docker inspect`/
  process listings; prefer volume mounts for secrets when practical).

### D. Updates and the restart gap (10 min)
- Mounted ConfigMap/Secret **files** update automatically on the running
  Pod within ~60s (kubelet sync) when the source changes (unless
  `subPath` is used — subPath mounts do NOT auto-update, a common gotcha).
- Env-var-injected values do NOT update on a running Pod — env vars are
  fixed at container start; you must trigger a new rollout to pick up
  changes.

## Lab (2h)

### Part 1 — ConfigMap as env vars (25 min)
1. `kubectl create configmap sysreport-config --from-literal=REPORT_INTERVAL=60
   --from-literal=LOG_LEVEL=debug`.
2. Edit your project's Deployment manifest (or a stand-in nginx Deployment
   if the real app isn't containerized for k8s yet) to add
   `envFrom: [{configMapRef: {name: sysreport-config}}]`.
3. Apply, `kubectl exec -it <pod> -- env | grep -E 'REPORT_INTERVAL|LOG_LEVEL'`
   — confirm both appear.

### Part 2 — ConfigMap as a mounted file (30 min)
4. Create a `nginx-html-config` ConfigMap `--from-file=index.html` (write a
   simple custom HTML file first).
5. Mount it into an nginx Deployment at
   `/usr/share/nginx/html` via `volumes`/`volumeMounts`; apply; `kubectl
   exec` in and `cat` the file, or `curl` the Service to confirm the custom
   page serves.
6. Edit the ConfigMap's `data` value (`kubectl edit configmap
   nginx-html-config`), wait ~60s, re-curl — confirm it updated without a
   pod restart (no subPath used).

### Part 3 — Secret handling (30 min)
7. `kubectl create secret generic sysreport-secret
   --from-literal=API_TOKEN=super-secret-value-123`.
8. `kubectl get secret sysreport-secret -o jsonpath='{.data.API_TOKEN}' |
   base64 -d` — see it decode instantly; discuss why this is a real risk if
   RBAC is loose.
9. Mount it as a volume (not env var) at `/etc/secrets` in your Deployment;
   `kubectl exec` in, `ls -la /etc/secrets` and note file permissions,
   `cat /etc/secrets/API_TOKEN`.

### Part 4 — Project step: configure the app via ConfigMap (35 min)
10. Take your incremental project's containerized app (from Phase 2, e.g.
    `sys_report`) — write a Deployment manifest for it if none exists yet
    (image from your registry, from Day 48). Externalize at least 2 real
    config values (e.g., report interval, log level, output path) into a
    ConfigMap consumed via `envFrom`.
11. Apply to the kind cluster, confirm via `kubectl exec ... env` and via
    the app's actual behavior (e.g., check its output/logs reflect the
    configured interval).
12. Commit the Deployment + ConfigMap manifests to the project repo under
    `k8s/` (or similar), with a README note on how to apply them.

## Definition of done
ConfigMap consumed both as env vars and as a mounted file, with the
auto-update-without-restart behavior demonstrated · Secret created,
decoded to prove base64≠encryption, and mounted as a file · project app now
runs on the kind cluster configured via a real ConfigMap, manifests
committed to the repo.
