## Theory (1h) — etcd backup/restore mechanics and RBAC exam patterns
- **etcd backup**: `etcdctl snapshot save <path>` — requires the correct
  `--endpoints`, `--cacert`, `--cert`, `--key` flags pointing at the
  control-plane's etcd certs (typically under
  `/etc/kubernetes/pki/etcd/`) — this exact flag set is a CKA staple
  worth memorizing the SHAPE of, not the literal paths (they're always
  given in the task).
- **etcd restore**: `etcdctl snapshot restore <path> --data-dir=<new-
  dir>` writes a fresh data directory from the snapshot; you then update
  the etcd static pod manifest (`/etc/kubernetes/manifests/etcd.yaml`) to
  point at the new data dir and let the kubelet pick up the change
  automatically (static pods restart when their manifest file changes —
  recall Day 61's static-pod observation in kube-system).
- RBAC exam pattern: tasks typically give you a ServiceAccount/User and a
  required permission set — `kubectl auth can-i <verb> <resource>
  --as=<subject> -n <namespace>` is the single fastest verification
  command, faster than reasoning through YAML by eye.
- Troubleshooting exam pattern: cluster-component failures (a kubelet
  down, a misconfigured static pod manifest) present as nodes going
  `NotReady` or control-plane pods missing from `kube-system` — the
  funnel from Day 73 applies at the cluster level too: check node status,
  check static pod manifests on the affected node, check
  kubelet/container-runtime service status (`systemctl status kubelet`,
  recall Day 12).

## Lab (2h) — timed task list (15 min/task, fresh `kind create cluster
--name cka-drill-2`)

1. `kubectl auth can-i list pods --as=system:serviceaccount:default:
   default` — record the answer, then create a Role+RoleBinding granting
   exactly `get,list,watch` on `pods` to a NEW ServiceAccount `viewer`,
   and re-run `can-i` with `--as` for that SA to confirm `yes`.
2. Confirm the same `viewer` SA CANNOT delete pods
   (`kubectl auth can-i delete pods --as=...`) — expect `no` without any
   extra config (least privilege by default).
3. Take an etcd snapshot from the kind control-plane node (you'll need
   `docker exec` into the kind node container to reach `etcdctl` and the
   certs, since kind doesn't expose the host filesystem the way a real VM
   would — treat this as the closest local approximation of the real
   exam environment).
4. Create a test resource (a namespace `snapshot-test` with a ConfigMap in
   it) AFTER taking the snapshot, to have something to lose.
5. Restore the etcd snapshot into a new data directory, update the etcd
   static pod manifest to reference it, and confirm (after the etcd pod
   restarts) that `snapshot-test` namespace/ConfigMap is GONE — proving
   the restore rolled back to the pre-snapshot-test state.
6. Break a static pod manifest on purpose (introduce a YAML syntax error
   into a NON-etcd static pod's manifest, e.g. duplicate a key in the
   scheduler's manifest) — observe the pod disappearing from
   `kube-system` within seconds; fix the YAML and confirm it reappears
   automatically (no `kubectl apply` needed for static pods — the kubelet
   watches the manifest directory directly).
7. Simulate a `NotReady` node investigation: `systemctl stop kubelet` on
   the kind node (via `docker exec`), watch `kubectl get nodes` show
   `NotReady` within ~40s, `systemctl start kubelet` to recover, confirm
   `Ready` returns.
8. Diagnose and fix a Pod stuck in `CrashLoopBackOff` due to a wrong
   command (write one deliberately) using ONLY `kubectl describe` and
   `kubectl logs --previous` — no editor guessing.
9. Create a ClusterRole allowing `get,list` on `deployments` across ALL
   namespaces and bind it (ClusterRoleBinding) to the `viewer` SA from
   task 1; verify with `can-i --all-namespaces`.
10. Clean up: delete the practice namespaces/roles/bindings, then `kind
    delete cluster --name cka-drill-2`.
