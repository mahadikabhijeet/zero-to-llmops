## Theory (1h)

### A. A different philosophy: templating vs patching (15 min)
- Helm parameterizes YAML with a templating language (Go templates) — you
  write "holes" and fill them with values.
- **Kustomize** takes the opposite approach: you write plain, valid k8s
  YAML (no template syntax at all) as a **base**, then declare
  **patches** (strategic merge or JSON patch) in **overlays** that
  transform the base for each environment. No new language to learn —
  it's still just YAML plus a `kustomization.yaml` recipe file.
- Kustomize is built INTO `kubectl` (`kubectl apply -k <dir>`) — no
  separate binary required, though the standalone `kustomize` CLI offers
  more (e.g., `kustomize build` to preview, matching Helm's `template`).

### B. Bases and overlays (20 min)
- `base/`: the common, environment-agnostic manifests + a
  `kustomization.yaml` listing them under `resources:`.
- `overlays/dev/`, `overlays/prod/`: each has its own `kustomization.yaml`
  referencing the base via `resources: [../../base]`, plus patches —
  e.g., prod bumps `replicas`, changes `resources.limits`, or adds a
  different ConfigMap value.
- Patch types: `patchesStrategicMerge` (merge by field, most common,
  intuitive), `patchesJson6902` (surgical, exact JSON-patch operations —
  for cases strategic merge can't express, like removing an array
  element), and inline `patches:` (newer unified syntax covering both).
- Generators: `configMapGenerator`/`secretGenerator` in
  `kustomization.yaml` create ConfigMaps/Secrets from files/literals with
  an auto-appended content hash suffix — this hash changes whenever the
  content changes, which AUTOMATICALLY triggers a rolling update on any
  Deployment referencing it (solves the "env var doesn't hot-reload"
  problem from Day 67, by forcing a new Pod generation instead).

### C. Common transformers (10 min)
- `namePrefix`/`nameSuffix`, `namespace:` (override namespace for every
  resource in one place), `images:` (override image tag per overlay
  without a template), `commonLabels`/`commonAnnotations` (stamp every
  resource).

### D. Helm vs Kustomize — decision framework (15 min)
- **Choose Helm** when: distributing a reusable package to others (public
  charts, internal platform team distributing to many teams), need
  conditional logic beyond simple overrides, want versioned releases with
  rollback as a first-class concept, or consuming THIRD-PARTY software
  (Day 74's bitnami/nginx) — you rarely author Kustomize bases for other
  people's software.
- **Choose Kustomize** when: you own both the base and all its
  environments, want to avoid a templating language entirely (plain YAML
  is easier to diff/review in a PR), or are layering GitOps environment
  promotion (a pattern Day 132's ArgoCD will build directly on).
- Common real-world combo: **Helm for third-party/vendored software,
  Kustomize (or plain manifests) for your own app's environment
  variants** — not mutually exclusive; many shops use both.

## Lab (2h)

### Part 1 — Base from your own manifests (30 min)
1. Create `k8s-kustomize/base/` — copy your project's plain Deployment,
   Service, and ConfigMap manifests (the pre-Helm versions from Day 67, or
   re-derive them via `helm template fresher-project . > base-rendered.
   yaml` and split them out) into this directory.
2. Write `base/kustomization.yaml` listing all three under `resources:`.
   `kubectl kustomize base/` (or `kustomize build base/`) — confirm it
   renders exactly your input manifests unchanged (a base alone does
   nothing extra).

### Part 2 — Dev and prod overlays (45 min)
3. Create `overlays/dev/kustomization.yaml`: `resources: [../../base]`,
   `namePrefix: dev-`, a `configMapGenerator` overriding `LOG_LEVEL=debug`,
   and a `patchesStrategicMerge` dropping replicas to 1.
4. Create `overlays/prod/kustomization.yaml`: `resources: [../../base]`,
   `namePrefix: prod-`, `configMapGenerator` with `LOG_LEVEL=warn`, a
   patch bumping replicas to 3 and adding real `resources.limits`.
5. `kubectl kustomize overlays/dev/` and `overlays/prod/` — diff the two
   outputs side by side; confirm names, replica counts, and ConfigMap
   content (and its hash suffix) differ as expected.

### Part 3 — Apply and prove the hash-triggered rollout (30 min)
6. `kubectl apply -k overlays/dev/` onto the kind cluster. `kubectl get
   configmap,deploy -l ...` — note the ConfigMap's generated name includes
   a hash suffix, and the Deployment references that EXACT hashed name.
7. Edit the `configMapGenerator`'s literal value in
   `overlays/dev/kustomization.yaml` (e.g., change `LOG_LEVEL=debug` to
   `LOG_LEVEL=trace`), `kubectl apply -k overlays/dev/` again — confirm a
   NEW ConfigMap (new hash) is created and the Deployment's pod template
   is automatically updated to reference it, triggering a rollout
   (`kubectl rollout status`) — this is Kustomize solving Day 67's
   "env vars don't hot-reload" problem structurally.

### Part 4 — JSON patch and cleanup (15 min)
8. Add one `patchesJson6902` example to the prod overlay (e.g., removing
   or replacing a specific array element the strategic merge patch
   couldn't cleanly express) — even a contrived example is fine, the goal
   is syntax familiarity.
9. `kubectl delete -k overlays/dev/` — confirm clean teardown of
   everything the overlay created. Commit `k8s-kustomize/` to the project
   repo alongside the Helm chart, with a README note explaining which is
   used for what (per the Theory D framework) going into Day 78's project
   milestone.

## Definition of done
Base + two overlays (dev/prod) built and diffed · applied an overlay to the
kind cluster and proved ConfigMap-hash-triggered rollouts work without
manual pod deletion · wrote at least one `patchesJson6902` patch · can
articulate the Helm-vs-Kustomize decision framework from memory.
