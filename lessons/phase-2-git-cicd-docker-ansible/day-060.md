## Theory (1h) — capstone framing, not new tools

### A. What "capstone" means here (10 min)
- No new technical material today. The work is **consolidation and communication**:
  proving, end-to-end, that everything since Day 31 composes into one coherent,
  demonstrable system — and then explaining it publicly, which is its own skill
  (job-readiness, Day 111/148 resume checkpoints will build directly on this habit).

### B. What the finished Phase 2 state must demonstrably include (20 min)
- **Public repo** (Day 33) with a real commit history showing incremental,
  understandable progress (not a single giant dump commit).
- **Tests** (Day 38) that run in CI, with meaningful coverage of the core logic, not
  just a token test.
- **Containerized** (Day 45–48): hardened (non-root, healthcheck), scanned, published
  to GHCR from CI automatically.
- **CI-built**: lint + test + scan + publish, matrix-tested, branch-protected
  (Day 40–41, 48).
- **Ansible-deployed** (Day 51–57): a full-VM playbook, idempotent, wired into CI so a
  merge to `main` results in an updated live deployment, verified against the actual
  artifact (not just green checks).
- **Secrets handled correctly** (Day 58): nothing sensitive in git history, scanning in
  place, a documented rotation procedure that's actually been exercised once.

### C. The pipeline README — writing for an audience who's never seen this (10 min)
- Distinct from the project's functional README (Day 33) — this is a
  `docs/pipeline-overview.md` (or a dedicated section) aimed at a reviewer/recruiter/
  interviewer: what the system does, a diagram of the pipeline stages, what tools were
  used and why (not just what), and what you'd improve next (shows judgment, not just
  execution).
- Include real evidence: link to a specific green Actions run, the GHCR package page,
  the CHANGELOG/tags history — verifiable artifacts beat claims.

### D. The first LinkedIn/blog post (10 min)
- Purpose: visibility (the YouTube channel + LinkedIn feed the same job-readiness
  goal), and articulating what was built forces a final round of consolidation.
- Structure that works for a technical post: what the project is (1-2 sentences) →
  what pipeline it goes through (the diagram) → one specific interesting problem
  solved (e.g., the Day 47 network-by-name gotcha, or the Day 57 SSH-to-VM problem) →
  what's next (Phase 3: Kubernetes). Keep it concrete, avoid generic "excited to share"
  filler.
- **This is an outward-facing action** — draft it today, but actual publishing should
  be a deliberate, reviewed decision by the student/trainer, not automatic.

## Lab (2h) — capstone execution

### Part 1 — Full-system verification pass (40 min)
1. From a completely clean clone of the public repo (`git clone` into a fresh
   directory), run through the ENTIRE workflow as a stranger would: read the README,
   set up the venv, run `pytest` locally, `docker build`, `docker compose up`, confirm
   everything documented actually works with zero tribal knowledge assumed.
2. Trigger the full CI pipeline once more via a real (small, meaningful) PR merge —
   confirm test → scan → publish → deploy all go green in sequence and the target VM
   ends up running the exact new artifact.
3. Fix any documentation gaps or broken steps discovered during this "stranger's eye"
   pass immediately — this IS the capstone work, not a side task.

### Part 2 — Pipeline documentation (30 min)
4. Write `docs/pipeline-overview.md`: architecture diagram (ASCII or a simple
   drawn/exported image referenced from the repo), the 5 pillars from Theory-B each
   with one sentence of evidence (link/reference), and a "what I'd improve next"
   section drawing directly from Day 59's gap list.
5. Update the main `README.md`'s badges/links section to point to this new doc.

### Part 3 — Release and tag the capstone (20 min)
6. Update `CHANGELOG.md` with a `v1.0.0` entry summarizing Phase 2's full arc (git →
   CI/CD → Docker → Ansible → secrets hygiene).
7. `git tag -a v1.0.0 -m "Phase 2 capstone: public, tested, containerized, CI-built,
   Ansible-deployed"`, push tag, create the GitHub Release with the CHANGELOG section
   as notes — this is the version worth pointing recruiters at.

### Part 4 — Draft the LinkedIn/blog post (30 min)
8. Draft the post per the Theory-D structure. Include one real screenshot or link
   (green Actions run, or the GHCR package page).
9. Have the trainer review the draft for accuracy and tone BEFORE any publishing
   decision — publishing itself is a deliberate, separate call, not part of today's
   automatic checklist.
10. `git add -A`, commit: "Phase 2 capstone: pipeline docs, v1.0.0 release, draft
    launch post".

**Definition of done:** ★ a fresh clone of the repo, followed step-by-step with zero
assumed context, successfully builds/tests/runs the project · a real PR merge triggers
the full test→scan→publish→deploy chain end to end against the actual target ·
`docs/pipeline-overview.md` written with verifiable evidence per pillar ·
`v1.0.0` tagged and released · LinkedIn/blog post drafted and reviewed (publish
decision left to student/trainer, not automated).
