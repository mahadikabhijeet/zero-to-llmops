## Theory (1h)

### A. CI/CD anatomy (15 min)
- **Continuous Integration**: every push triggers automated build/lint/test — catch
  breakage immediately, not at release time.
- **Continuous Delivery/Deployment**: CD extends CI to automatically package and (for
  Deployment) ship to an environment — draw the line for this project: CI first
  (Day 40–41), CD arrives Day 46–48 and 57.
- Pipeline anatomy: **trigger** (push, PR, schedule, manual) → **jobs** (units of work,
  can run in parallel) → **steps** (sequential commands inside a job) → **artifacts**
  (files produced, e.g. test reports, built images — passed between jobs or downloaded
  later).
- **Environments**: dev/staging/prod as named targets with their own secrets/protection
  rules (concept today, used for real from Day 57+).

### B. GitHub Actions core model (20 min)
- Workflow file: `.github/workflows/*.yml`, YAML syntax (Day 39 pays off immediately).
- `on:` (triggers: `push`, `pull_request`, `workflow_dispatch` for manual runs,
  `schedule` with cron syntax).
- `jobs:` → each job runs on a fresh VM (`runs-on: ubuntu-latest` is the common free
  runner) unless self-hosted.
- `steps:` → `uses:` (reusable actions from the marketplace, e.g.
  `actions/checkout@v4`) vs `run:` (raw shell commands).
- `actions/checkout` is almost always step 1 — the runner starts with an EMPTY
  filesystem, your repo isn't there until you check it out.

### C. Building the first real workflow (15 min)
- Order of steps for a Python project: checkout → set up Python (`actions/setup-
  python@v5` with a version) → install deps (`pip install -r requirements.txt`) →
  lint (`shellcheck` for bash, `flake8`/`ruff` for python — pick one) → test (`pytest`).
- `requirements.txt` — freeze your venv's deps so CI can reproduce them:
  `pip freeze > requirements.txt` (or a hand-curated minimal list, discuss trade-off).
- Viewing runs: the "Actions" tab on GitHub — green check / red X on commits and PRs is
  the visible payoff.

### D. Why this matters for job-readiness (10 min)
- A green CI badge on a public repo is a credibility signal recruiters actually notice.
- CI on every push forces the discipline of small, working commits (ties back to
  Day 34's trunk-based-development note).
- This is the last "concepts only" day before Day 41 makes CI a required, protected gate.

## Lab (2h)

### Part 1 — First workflow file (30 min)
1. In `/opt/fresher_project`, create `.github/workflows/ci.yml`.
2. Write a minimal workflow: trigger on `push` to `main` and on `pull_request`; one job
   `test` on `ubuntu-latest`; steps: `actions/checkout@v4`, `actions/setup-python@v5`
   (pin a version e.g. `3.12`), `pip install -r requirements.txt` (create this file
   from your venv if it doesn't exist), `pytest`.
3. Commit and push directly to a branch (not `main` yet), open a PR, watch the check
   appear and go green (or red — debug it) in the PR's checks tab.

### Part 2 — Add lint to the pipeline (30 min)
4. `pip install shellcheck-py flake8` (or `ruff`) locally first — run them against your
   code manually, fix any real issues.
5. Add a `lint` job (separate from `test`, so failures are attributed clearly) running
   `shellcheck` against any remaining `.sh` files and `flake8`/`ruff` against the Python
   package.
6. Push, confirm both jobs run and both show status independently in the PR checks.

### Part 3 — Trigger and artifact experiments (35 min)
7. Add `workflow_dispatch:` to `on:` — go to the Actions tab and manually trigger a run
   with the "Run workflow" button; confirm it works without a push.
8. Make `pytest` write a junit-xml report: `pytest --junitxml=report.xml`. Add a step
   using `actions/upload-artifact@v4` to upload `report.xml`. After the run, download
   the artifact from the run's summary page and open it.
9. Deliberately break a test, push, watch the job fail red; read the log output in the
   Actions tab to find exactly which assertion failed; fix it, push again, watch it go
   green.

### Part 4 — Merge and confirm (25 min)
10. Merge your PR into `main` (require the checks to be green first — don't merge red).
11. Push a small follow-up commit directly to a new branch touching an unrelated file;
    confirm CI runs automatically again without you touching the workflow file.
12. `git log --oneline --graph` and review the Actions tab history — narrate what
    happened on each run.

**Definition of done:** `.github/workflows/ci.yml` exists with separate lint and test
jobs · both ran and show status on a real PR · `workflow_dispatch` manual trigger
tested · a broken test was pushed, seen failing in the UI, then fixed and seen passing ·
merged to `main` with green checks.
