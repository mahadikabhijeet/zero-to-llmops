## Theory (1h)

### A. Volumes vs bind mounts (20 min)
- **Named volume**: `docker volume create name`, `-v name:/path` — Docker manages the
  storage location on the host (under `/var/lib/docker/volumes/`); portable, backup-
  able, the right choice for "data a container owns" (databases, Jenkins state from
  Day 43).
- **Bind mount**: `-v /host/absolute/path:/container/path` — you control the exact host
  path; used Day 45 to mount project source into a container. Right choice for "I want
  to see/edit this from the host" (dev workflows, config injection).
- `docker volume ls`, `docker volume inspect`, `docker volume rm` — volumes persist
  independently of any container's lifecycle until explicitly removed.
- Read-only mounts: `-v /host/path:/container/path:ro` — protect a mount from being
  written by the container.

### B. Docker networking model (15 min)
- Default **bridge** network: containers can reach each other by IP but NOT by name
  unless on a user-defined network.
- User-defined bridge network: `docker network create mynet`, then `--network mynet`
  on each container — containers can resolve each other **by container name** via
  Docker's embedded DNS. This is the mechanism that makes multi-container apps work
  without hardcoded IPs.
- `docker network ls`, `docker network inspect`, `docker network connect/disconnect`.
- `host` network mode (container shares host's network stack directly — no port
  mapping needed but no isolation) mentioned as an option, not the default choice.

### C. Docker Compose v2 (25 min)
- Problem: multi-container apps as chained `docker run` commands become unmanageable
  and unrepeatable.
- `compose.yaml` (or `docker-compose.yml`) — declarative multi-service definition:
  `services:`, each with `build:`/`image:`, `ports:`, `volumes:`, `environment:`,
  `depends_on:`.
- Compose automatically creates a shared network for all services in the file — service
  names become hostnames automatically (the payoff of section B, with zero manual
  network commands).
- `docker compose up [-d]`, `docker compose down [-v]` (`-v` also removes volumes —
  know this before running it against real data), `docker compose logs -f
  [service]`, `docker compose ps`, `docker compose build`.
- `docker compose up --build` — rebuild images as part of bringing services up (common
  dev-loop habit).

## Lab (2h)

### Part 1 — Named volumes (25 min)
1. `docker volume create report_data`.
2. `docker run --rm -v report_data:/data python:3.12-slim sh -c "echo hello > /data/
   test.txt"`.
3. `docker run --rm -v report_data:/data python:3.12-slim cat /data/test.txt` — confirm
   the data persisted across two completely separate containers because it lives in the
   volume, not either container's writable layer.
4. `docker volume inspect report_data` — note the `Mountpoint` on the host.

### Part 2 — Networking by name (30 min)
5. `docker network create labnet`.
6. `docker run -d --name db-stub --network labnet python:3.12-slim sleep infinity`.
7. `docker run --rm --network labnet python:3.12-slim python3 -c
   "import socket; print(socket.gethostbyname('db-stub'))"` — confirm name resolution
   works ONLY on the user-defined network (repeat without `--network labnet` to see it
   fail, confirming the default-bridge limitation from theory).
8. `docker network inspect labnet` — see both containers listed with their IPs.
9. Clean up: `docker rm -f db-stub && docker network rm labnet`.

### Part 3 — First Compose file (40 min)
10. In `/opt/fresher_project`, write `compose.yaml` with two services: `app` (build
    from your Dockerfile, depends on `db`) and `db` (use `postgres:16-alpine` or
    similar as a stand-in — even if `sys_report` doesn't use a DB yet, this rehearses
    the pattern for Day 50's real 2-service app), with a named volume for the db's data
    directory and an `environment:` block for db credentials.
11. `docker compose up -d`, `docker compose ps`, `docker compose logs -f db` (Ctrl+C to
    stop following).
12. `docker exec -it <app-container-name> python3 -c "import socket; print(socket.
    gethostbyname('db'))"` — confirm the app service can resolve `db` by name with zero
    manual network setup (Compose did it automatically).
13. `docker compose down` (without `-v` — confirm the named volume survives:
    `docker volume ls`), then `docker compose up -d` again and confirm the db's data
    volume still has the same content as before `down`.

### Part 4 — Bind mount for live dev + cleanup (25 min)
14. Add a bind mount for the `app` service in `compose.yaml`:
    `volumes: - ./src:/app/src:ro` — restart with `docker compose up -d --build` and
    confirm host-side edits to a source file are visible inside the container without
    rebuilding (read-only, so also confirm a write attempt from inside fails).
15. `docker compose down -v` to fully clean up (know that `-v` removes volumes — used
    deliberately here since this is lab data).
16. `git add -A`, commit: "add compose.yaml (app+db pattern), document volumes vs bind
    mounts and network-by-name in README".

**Definition of done:** demonstrated data surviving across containers via a named
volume · confirmed container-name DNS resolution works only on a user-defined network ·
`compose.yaml` brings up app+db with the app able to resolve `db` by name automatically
· confirmed volume data survives `compose down` (without `-v`) but not with it · a
read-only bind mount used for live source editing.
