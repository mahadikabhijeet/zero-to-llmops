## Theory (1h)

### A. Why roles (10 min)
- One giant `playbook.yml` doesn't scale — roles package tasks, handlers, templates,
  vars, and defaults into a reusable, shareable unit (e.g., a "nginx" role you could
  drop into any project).
- Direct parallel to Day 38's `src/` package restructuring for Python — same instinct:
  separate reusable logic from one-off wiring.

### B. Standard role directory layout (15 min)
```
roles/
  nginx/
    tasks/main.yml
    handlers/main.yml
    templates/nginx.conf.j2
    vars/main.yml          # high-priority, role-internal
    defaults/main.yml      # low-priority, override-friendly
    files/
    meta/main.yml          # role metadata, dependencies
```
- `ansible-galaxy init roles/nginx` — scaffolds this structure automatically.
- `defaults/` vs `vars/`: defaults are meant to be overridden by the playbook/inventory
  calling the role (lowest precedence); `vars/` are role-internal constants (higher
  precedence, not meant for casual override) — this distinction trips people up
  constantly, worth internalizing now.
- Using a role in a playbook: `roles: - nginx` under a play, or the newer
  `- name: apply nginx role \n ansible.builtin.include_role: name: nginx`.

### C. Ansible Galaxy (10 min)
- `ansible-galaxy` is the community role/collection registry — `ansible-galaxy install
  geerlingguy.nginx` pulls a battle-tested community role instead of reinventing one.
- Collections (`ansible-galaxy collection install community.general`) bundle modules +
  roles + plugins — know the term, it appears constantly in real-world playbooks.
- `requirements.yml` — declare roles/collections a project needs, install with
  `ansible-galaxy install -r requirements.yml` — same "declare deps in a file" instinct
  as `requirements.txt` (Day 40).

### D. ansible-vault — encrypting secrets (25 min)
- Problem: playbooks/vars often need real secrets (DB passwords, API tokens) that must
  never sit in git in plaintext (ties directly to Day 58's broader secrets-management
  day, previewed here specifically for Ansible).
- `ansible-vault create secrets.yml` (create+encrypt in one step), `ansible-vault edit
  secrets.yml` (decrypt, open in `$EDITOR`, re-encrypt on save), `ansible-vault view
  secrets.yml` (read-only decrypt to stdout).
- `ansible-vault encrypt existing_vars.yml` / `decrypt` — convert existing files.
- Running a playbook that references vault-encrypted vars: `ansible-playbook
  playbook.yml --ask-vault-pass` (prompt) or `--vault-password-file
  .vault_pass` (file, itself must be gitignored and kept out of the repo).
- `ansible-vault encrypt_string 'supersecret' --name 'db_password'` — encrypt a single
  value inline for pasting directly into an otherwise-plaintext vars file (mixed
  plaintext/encrypted vars file — a common real pattern).

## Lab (2h)

### Part 1 — Scaffold and migrate to a role (35 min)
1. `ansible-galaxy init roles/sys_report_nginx` — inspect the generated tree.
2. Move yesterday's nginx-vhost-for-sys_report tasks into
   `roles/sys_report_nginx/tasks/main.yml`, the template into
   `roles/sys_report_nginx/templates/`, and the handler into
   `roles/sys_report_nginx/handlers/main.yml`.
3. Move `nginx_port` into `roles/sys_report_nginx/defaults/main.yml` (so callers can
   override it easily) — note WHY defaults, not vars, per theory.
4. Rewrite `playbook.yml` to simply call the role: `roles: - sys_report_nginx`.
5. Run it — confirm identical behavior to Day 52's monolithic playbook (idempotent,
   handler fires only on real change).

### Part 2 — Galaxy (20 min)
6. `ansible-galaxy search nginx` (or browse galaxy.ansible.com) — pick a well-known
   community role, read its README to see how it structures `defaults/`.
7. Write a `requirements.yml` declaring that role as a dependency (don't need to fully
   integrate it — the exercise is declaring + installing:
   `ansible-galaxy install -r requirements.yml`).

### Part 3 — Vault drill (40 min)
8. `ansible-vault create group_vars/local/vault.yml` — set a vault password (remember
   it or store in a password manager, NOT in the repo). Add `db_password: supersecret`
   inside.
9. `ansible-vault view group_vars/local/vault.yml` — confirm the file on disk is
   encrypted (`cat` it directly — unreadable ciphertext) but `view` decrypts correctly.
10. Reference `{{ db_password }}` from a `debug` task in your playbook; run with
    `ansible-playbook -i inventory.ini playbook.yml --ask-vault-pass` — confirm it
    resolves correctly.
11. Create `.vault_pass` (gitignore it immediately), rerun using
    `--vault-password-file .vault_pass` instead of the interactive prompt — confirm
    both methods work.
12. `ansible-vault encrypt_string 'anothersecret' --name 'api_token'` — paste the
    output into a normal (plaintext) vars file alongside other non-secret vars; confirm
    the playbook can still read `api_token` correctly (mixed file pattern).

### Part 4 — Commit safely (25 min)
13. `git status` — confirm `.vault_pass` is untracked/gitignored and NOT staged; double
    -check `group_vars/local/vault.yml` is genuinely encrypted ciphertext before
    committing it (encrypted vault files ARE safe to commit — that's the whole point).
14. `git add -A`, commit: "restructure nginx config into a role, add Galaxy
    requirements, vault-encrypt secrets used by the playbook".

**Definition of done:** nginx-vhost logic lives in a proper role with `defaults/`
correctly used for overridable values · a community role is declared in
`requirements.yml` and installs · a vault-encrypted vars file is created, viewed,
referenced by the playbook via both `--ask-vault-pass` and `--vault-password-file`, and
committed as ciphertext (never plaintext, never the vault password itself).
