## Theory (1h)

### A. The 12-factor app — a checklist, not a religion (20 min)
- Origin: a set of principles for building software-as-a-service apps that are portable
  and scalable. Cover the ones most relevant now:
  1. **Codebase** — one repo, many deploys (you've had this since Day 33).
  2. **Dependencies** — explicitly declared (`requirements.txt` — Day 40), never
     assumed present on the host.
  3. **Config** — stored in the **environment**, not in code (today's focus).
  4. **Backing services** — treated as attached resources (a database is just a URL/
     connection string, swappable without code changes).
  5. **Processes** — stateless; anything that must persist goes to a backing service or
     volume (Day 47), not the container's local disk.
  6. **Port binding** — the app is self-contained and exports services via a port, not
     dependent on a runtime-injected web server.
  7. **Disposability** — fast startup, graceful shutdown (SIGTERM handling — ties to
     Day 8's signals).
- Not all 12 apply cleanly to a CLI/reporting tool like `sys_report` — the point is
  recognizing the checklist and applying what's relevant, a skill interviewers probe.

### B. Config via environment variables (15 min)
- Recap Day 37's config precedence (default → file → env → CLI flag) — factor III
  formalizes "env" as the primary layer for anything environment-specific (DB host,
  log level, feature flags), leaving files for defaults/structure.
- `os.environ.get("KEY", default)` in Python; `environment:` block in Compose;
  `docker run -e KEY=value`.
- `.env` files + `env_file:` in Compose — convenient for local dev, but Compose reads
  it at `up` time; never commit a `.env` with real secrets (Day 58 goes deeper).

### C. Building a real 2-service Compose app (15 min)
- App service depends on a DB service (recap Day 47's stub, make it real today):
  connection details injected via env vars, not hardcoded.
- `depends_on: db: condition: service_healthy` (using Day 48's healthcheck concept
  applied to the DB container) — ensures the app doesn't start hammering a DB that
  isn't ready yet, a real-world race condition this actually prevents.
- Compose profiles / multiple compose files (`compose.override.yaml`) mentioned as an
  escape hatch for dev-vs-prod variation — concept only today.

### D. Where this leads (10 min)
- This 2-service pattern (app + backing service, config via env, healthcheck-gated
  startup) is the direct ancestor of Phase 3's Kubernetes Deployments+Services and
  Phase 4's RDS-backed apps — the vocabulary doesn't change, only the orchestrator.

## Lab (2h)

### Part 1 — Give sys_report a real backing service (35 min)
1. Extend `sys_report` (or a lab copy) to optionally write report history into a small
   SQLite-compatible or Postgres table instead of only flat files — pick Postgres to
   rehearse the "backing service over network" pattern properly (SQLite is file-based
   and doesn't teach the same lesson).
2. Add a minimal `db.py` module: read `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`,
   `DB_PASSWORD` from environment variables (with sane local defaults), connect (e.g.
   via `psycopg2` or `psycopg[binary]`), create a `reports` table if not exists, insert
   one row per collection run.

### Part 2 — Compose it for real (35 min)
3. Update `compose.yaml`: `db` service uses `postgres:16-alpine` with a named volume
   for `/var/lib/postgresql/data`, environment vars for `POSTGRES_DB/USER/PASSWORD`,
   and a healthcheck (`pg_isready`).
4. `app` service: `depends_on: db: condition: service_healthy`, environment vars
   matching what `db.py` expects, referencing the `db` service by name as `DB_HOST`.
5. `docker compose up -d --build`, `docker compose logs -f app` — confirm the app waits
   for a healthy DB, then connects and inserts successfully.

### Part 3 — Env-based config drill (25 min)
6. Create a `.env` file (add it to `.gitignore` immediately — before committing
   anything) with local values; confirm Compose picks it up via `env_file:`.
7. Override one value at the shell for a single run:
   `DB_NAME=override_test docker compose run --rm app` — confirm the override wins
   (env var precedence check, echoing Day 37/50-A).
8. Verify data persistence: `docker compose down` (no `-v`), `docker compose up -d`,
   query the `reports` table again — confirm prior rows are still there (Day 47 volume
   lesson applied for real this time).

### Part 4 — 12-factor self-audit + commit (25 min)
9. Write a short `docs/12-factor-audit.md`: go through the 7 factors covered in theory,
   one line each on how `sys_report` does or doesn't comply, and what would need to
   change for full compliance (be honest — a CLI tool won't cleanly satisfy "port
   binding," and that's a fine, correct thing to state).
10. `git add -A`, commit: "add Postgres backing service via Compose, env-based DB
    config, 12-factor audit doc". Confirm `.env` is NOT in the commit
    (`git status`/`git show --stat` check).

**Definition of done:** app service waits for a healthy Postgres before connecting ·
DB config comes entirely from environment variables, overridable at run time ·
`reports` table data survives a `compose down`/`up` cycle · `.env` exists locally but is
gitignored · 12-factor audit doc committed.
