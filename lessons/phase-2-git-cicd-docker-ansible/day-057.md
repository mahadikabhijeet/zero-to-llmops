## Theory (1h)

### A. Stitching the whole pipeline together (20 min)
- Recap the pieces already built, in order of when they run: push to `main` (Day 33) →
  GitHub Actions triggers (Day 40) → lint+test matrix (Day 41) → build+scan+publish
  image to GHCR (Day 48) → **NEW today**: a deploy stage that runs Ansible's `site.yml`
  (Day 54) against a target VM, pulling the just-published image/artifact.
- Two trigger patterns for the deploy stage: (1) chained in the SAME workflow as a
  `deploy` job with `needs: [test, scan, publish]`, or (2) a separate `workflow_dispatch`
  / `repository_dispatch` triggered manually or by the first workflow's completion —
  today builds pattern (1), simpler and sufficient for one project/one environment.

### B. How CI reaches a VM it doesn't own (20 min)
- The GitHub Actions runner is ephemeral and has no pre-existing access to your target
  VM — it needs: (a) network reachability (the VM must have a reachable address — for
  a home-lab VM this may mean a Tailscale/VPN address, or simply running the "VM" as
  another container/host reachable from a self-hosted runner; document whichever path
  is actually usable in this training's environment), and (b) SSH credentials.
- SSH key as a GitHub secret: generate a deploy-only keypair, add the PRIVATE key as a
  repo secret (`DEPLOY_SSH_KEY`), add the PUBLIC key to the target's
  `~/.ssh/authorized_keys` — never reuse your personal key for automation.
- In the workflow: write the private key to a file with `0600` perms, point
  `ANSIBLE_HOST_KEY_CHECKING=False` (acceptable for a lab/training target; note this
  would need proper known_hosts handling in a real production pipeline) and
  `ansible_ssh_private_key_file` at it, run `ansible-playbook -i inventory.ini
  site.yml`.
- Alternative if a real reachable VM isn't available in this training setup:
  self-hosted runner registered ON the target VM itself, so `ansible-playbook` runs
  locally against `localhost` — a legitimate, common real-world pattern (not a
  downgrade), document which option was used.

### C. Deploy job design (10 min)
- Only deploy from `main` (never from a feature branch/PR) — `if: github.ref ==
  'refs/heads/main'` guard on the job.
- Pass the freshly-built image tag from the `publish` job to the `deploy` job via
  `needs.publish.outputs.image_tag` (job outputs) so Ansible deploys the EXACT image
  CI just built and scanned — never re-derive or guess the tag.
- Environment protection rule (GitHub `environment: production`) — optional manual-
  approval gate before deploy runs; mention as a maturity step even if not enabled
  today for a solo lab project.

### D. What "done" looks like end-to-end (10 min)
- A single `git push` (via a merged PR) should, unattended, result in: tests pass →
  image scanned clean → image published → Ansible configures/updates the target VM
  with the new image/artifact → the service is verifiably running the new version.
- This IS the portfolio centerpiece the blueprint has been building toward since
  Day 33 — today's lab produces the artifact Day 60's capstone documents.

## Lab (2h)

### Part 1 — Deploy-only SSH key + secret (25 min)
1. Generate a dedicated keypair: `ssh-keygen -t ed25519 -f deploy_key -C
   "ci-deploy@sys-report" -N ""`.
2. Add the public key to the target VM/container's `~/.ssh/authorized_keys` (the same
   target from Day 54's `site.yml` run).
3. Add the PRIVATE key content as a GitHub Actions secret `DEPLOY_SSH_KEY`. Delete the
   local private key file once confirmed added (or keep it secured outside the repo —
   never commit it).

### Part 2 — Wire Ansible into the workflow (40 min)
4. Add a `deploy` job to `.github/workflows/ci.yml`: `needs: [test, scan, publish]`,
   `if: github.ref == 'refs/heads/main'`, `runs-on: ubuntu-latest` (or your self-hosted
   runner if that's the path chosen).
5. Steps: checkout, `pip install ansible`, write `${{ secrets.DEPLOY_SSH_KEY }}` to
   `deploy_key` with `chmod 600`, run
   `ansible-playbook -i inventory.ini site.yml --private-key deploy_key -e
   "image_tag=${{ needs.publish.outputs.image_tag }}"`.
6. Update `site.yml`/the relevant role to accept `image_tag` as a variable and use it
   when pulling/running the published image on the target (rather than hardcoding a
   tag).

### Part 3 — Run it for real (35 min)
7. Merge a small real change via PR (respecting branch protection) and watch the full
   chain execute in the Actions tab: test → scan → publish → deploy, in order, with
   `deploy` waiting on the others.
8. On the target VM, verify the new image/version is actually running (check container
   ID, image digest, or a version string the app reports) — don't just trust green
   checkmarks, confirm the artifact.
9. Deliberately break a test in a PR — confirm `deploy` does NOT run when `test` fails
   (the `needs:` dependency chain protecting production from bad code).

### Part 4 — Document and tag (20 min)
10. Write `docs/pipeline.md`: a short diagram/description of the full chain (commit →
    Actions → build+scan+publish → Ansible deploy), which secrets are involved, and
    which real-world shortcut was taken (VPN/self-hosted runner/etc.) and why.
11. `git tag -a v0.3.0 -m "end-to-end CI-to-deploy pipeline live"`, push tag + create
    GitHub Release. `git add -A`, commit and push: "wire Ansible deploy into CI,
    gated on test+scan+publish; add pipeline docs".

**Definition of done:** ★ a single merged PR triggers test → scan → publish → deploy
unattended, deploying the exact scanned image to the target VM · confirmed the deployed
artifact matches what CI built (not just green checks) · a failing test correctly
blocks deploy · pipeline documented, `v0.3.0` tagged.
