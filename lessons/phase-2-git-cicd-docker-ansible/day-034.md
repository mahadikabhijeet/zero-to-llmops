## Theory (1h)

### A. Rebase vs merge (20 min)
- Merge preserves true history (both branches' commits, plus a merge commit) — honest
  but can get noisy with many small branches.
- Rebase **replays** your branch's commits on top of another branch one at a time,
  producing new commits (new hashes) with linear history — no merge commit.
- `git rebase main` (while on feature branch) — resolve conflicts per-commit if they
  arise (`git rebase --continue` / `--abort` / `--skip`).
- **Golden rule: never rebase commits that have been pushed and others may have pulled**
  — it rewrites history and breaks collaborators' clones.
- When to use which: rebase your own local, not-yet-shared feature branch to keep it
  clean before opening a PR; merge (not rebase) for combining shared/public branches.

### B. Interactive rebase — cleaning up before sharing (15 min)
- `git rebase -i HEAD~3` — opens an editor listing the last 3 commits with actions:
  `pick`, `reword`, `edit`, `squash`, `fixup`, `drop`.
- Common use: squash 5 messy "wip" commits into 1 clean commit before opening a PR.
- Concept only today (do it in the lab) — this is a "understand it exists and is safe on
  local unshared work" day, not mastery.

### C. Reset and reflog — the undo button (15 min)
- `git reset --soft <commit>` (move branch pointer, keep changes staged), `--mixed`
  (default; unstage but keep working-dir changes), `--hard` (DESTROYS uncommitted
  changes and working-dir state — the dangerous one).
- `git reflog` — a local log of every place `HEAD` has pointed, including commits
  "lost" by reset/rebase. This is the safety net: nothing is truly gone until Git's
  garbage collector runs (weeks later, by default).
- Recovery drill: `git reset --hard <bad-target>` "by accident" → `git reflog` → find
  the commit before the mistake → `git reset --hard <that-hash>` to recover.

### D. Tags, releases, and strategy debate (10 min)
- `git tag v1.0.0` (lightweight) vs `git tag -a v1.0.0 -m "message"` (annotated — has
  its own object, author, date; preferred for releases).
- `git push origin v1.0.0` (tags don't push automatically), `git push --tags`.
- GitHub Releases: a tag + release notes + optional binary attachments.
- Trunk-based development (short-lived branches, frequent merges to `main`, feature
  flags for incomplete work) vs Gitflow (long-lived `develop`/`release`/`hotfix`
  branches) — trunk-based is the modern CI/CD-friendly default; Gitflow suits
  slow-release/versioned-product teams. State which this project will use going forward
  (trunk-based, since Day 40+ builds CI on every push to `main`).

## Lab (2h)

### Part 1 — Rebase drill (30 min)
1. In `~/lab31`: `git switch -c feature-rebase`, make 2 commits.
2. Meanwhile `git switch main`, make 1 unrelated commit.
3. `git switch feature-rebase && git rebase main` — observe your commits get new
   hashes replayed on top. `git log --oneline --graph --all` before/after to compare
   against what a `merge` would have produced.
4. Force a conflict during rebase (edit the same line main changed); resolve it,
   `git add`, `git rebase --continue`.

### Part 2 — Interactive rebase cleanup (25 min)
5. On a fresh branch, make 3 sloppy commits ("wip", "wip2", "fix typo").
6. `git rebase -i HEAD~3` — mark the last two as `squash`/`fixup` into the first, write
   one clean commit message. `git log --oneline` to confirm one clean commit remains.

### Part 3 — Reset/reflog rescue drill (35 min)
7. On `main` (in `~/lab31`, NOT the real project), make 3 commits.
8. "Accidentally" run `git reset --hard HEAD~2` — confirm 2 commits appear gone from
   `git log`.
9. `git reflog` — find the entry for the commit before your reset.
10. `git reset --hard <that-hash>` — confirm the "lost" commits are back. State in your
    own words why this worked (the commits were never deleted, just unreferenced).
11. Repeat once more but recover using `git cherry-pick <hash>` onto a fresh branch
    instead of reset — an alternative rescue technique.

### Part 4 — Tags and strategy note (30 min)
12. In `/opt/fresher_project`: `git tag -a v0.1.0 -m "Phase 1 capstone baseline"`.
13. `git push origin v0.1.0`. On GitHub, turn this tag into a Release with short notes
    (what the tool does as of Phase 1).
14. Write a short `docs/branching-strategy.md` (or a README section) stating: this
    project uses trunk-based development — short-lived feature branches, PRs into
    `main`, tags mark milestones. Commit and push it.

**Definition of done:** performed a rebase and resolved a conflict during it · squashed
3 commits into 1 via interactive rebase · recovered "lost" commits twice (reset+reflog,
then cherry-pick) · pushed an annotated tag and created a GitHub Release · branching
strategy documented in the repo.
