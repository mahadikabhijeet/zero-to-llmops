## Theory (1h)

### A. `argparse` deep dive (15 min)
- Recap Day 27 basics; today: subcommands (`add_subparsers()` — e.g. `tool report` vs
  `tool check`), `choices=[...]`, `type=int`, `required=True` for optional-flag-that-
  isn't-optional, `action="store_true"` for boolean flags, `nargs`.
- `-h`/`--help` is generated for free — a CLI without good `--help` text is a support
  burden on your future self.

### B. `click` as an alternative (10 min)
- Decorator-based: `@click.command()`, `@click.option()`, `@click.argument()`.
- Less boilerplate than argparse for complex CLIs with many subcommands; used widely in
  real tooling (e.g., `flask`, `black` are built on click). Compare the same CLI written
  both ways — know both exist, pick one per project and stay consistent.

### C. Logging module done right (20 min)
- Why `print()` doesn't scale: no levels, no timestamps, no easy redirect to file+syslog
  simultaneously, no easy silencing.
- `logging.basicConfig(level=..., format=..., filename=...)` — quick setup.
- Levels: DEBUG < INFO < WARNING < ERROR < CRITICAL — set the threshold once, sprinkle
  calls everywhere, filter by config not by code changes.
- `logger = logging.getLogger(__name__)` — per-module loggers, the standard pattern.
- Handlers: `StreamHandler` (console) + `FileHandler` (file) on the same logger
  simultaneously — echoes Day 2's `tee` idea but structured.
- `logger.exception()` inside an `except` block — logs the message AND the full
  traceback automatically.

### D. Config files (15 min)
- Why: CLI flags for everything gets unwieldy; config files hold defaults, CLI flags
  override them.
- Formats: `.ini`/`configparser` (simple, stdlib), `.env` + `python-dotenv` (secrets/
  env-style), `.yaml`/`.json` (structured, preview of Day 39's deep dive).
- Precedence pattern worth adopting everywhere: defaults → config file → environment
  variable → CLI flag (each layer overrides the previous) — this exact hierarchy
  reappears in Ansible (Day 51+) and Terraform (Day 79+).

## Lab (2h)

### Part 1 — argparse with subcommands (30 min)
1. Rewrite a portion of `sys_report.py`'s CLI (or a scratch copy) to use subcommands:
   `sys_report.py collect` (runs the report) and `sys_report.py show --last`
   (prints the most recent saved report). Use `add_subparsers(dest="command")`.
2. Add a `--format {json,text}` option with `choices=` and a default.
3. Run `sys_report.py -h` and `sys_report.py collect -h` — confirm help text is useful
   without extra work from you.

### Part 2 — click comparison (20 min)
4. `pip install click`. Write a 10-line toy CLI using `@click.command()` +
   `@click.option("--name", default="world")` that prints a greeting — compare line
   count and readability to the equivalent argparse version.

### Part 3 — Logging retrofit (40 min)
5. In `sys_report.py`, replace every `print()` used for status/error messages with
   `logging` calls at the right level (INFO for normal progress, WARNING for the
   internet-unreachable case from Day 36, ERROR for real failures).
6. Configure both a console handler (INFO+) and a file handler writing to
   `/opt/fresher_project/logs/sys_report.log` (DEBUG+, so the file has more detail than
   the screen).
7. Force an error path (e.g., point it at a directory it can't write) and confirm
   `logger.exception()` captures the full traceback in the log file.

### Part 4 — Config file + incremental project step (30 min)
8. Add a `config.ini` (or `.yaml` if you prefer to preview Day 39) with settings like
   `output_dir`, `log_level`, `check_url` (the endpoint from Day 36).
9. Wire config-file reading into `sys_report.py` with the precedence: default → config
   file → CLI flag override (env var layer optional today, full treatment later).
10. Run it three ways — no flags (uses config/defaults), with a CLI override, and with a
    deliberately missing config file (should fall back to defaults, not crash).
11. `git add -p`, commit: "sys_report: subcommands, structured logging, config file with
    override precedence".

**Definition of done:** `sys_report.py` has a subcommand-based CLI with working
`--help` · logs go to console (INFO+) and file (DEBUG+) via the `logging` module, not
`print` · a config file supplies defaults that CLI flags can override · missing config
file doesn't crash the tool · change committed.
