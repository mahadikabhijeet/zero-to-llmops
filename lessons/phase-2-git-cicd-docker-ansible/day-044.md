## Theory (1h)

### A. Agents — solving yesterday's tooling friction (20 min)
- The controller (formerly "master") schedules work; **agents** (formerly "slaves") are
  where builds actually execute — they can have different tooling installed.
- `agent { docker { image 'python:3.12-slim' } }` in a Jenkinsfile — run THIS stage's
  steps inside a fresh container with exactly the tools needed, solving yesterday's
  missing-Python problem cleanly instead of installing Python into the Jenkins
  controller image (bad practice — keep the controller thin).
- Requires the controller to have Docker access: mounting the host's Docker socket into
  the Jenkins container (`-v /var/run/docker.sock:/var/run/docker.sock`) — "Docker
  outside of Docker" — note the security trade-off (mounting the socket gives the
  container root-equivalent power on the host; acceptable for a lab, a real flag for
  production).
- Per-stage agents: different stages can use different images (`Build` in a Python
  image, `Package` in a Docker-in-Docker image) — declarative pipeline supports
  `agent` at both pipeline and stage level.

### B. Credentials management (15 min)
- Jenkins' built-in Credentials store (Manage Jenkins → Credentials) — types: username/
  password, SSH key, secret text, secret file.
- Reference in a Jenkinsfile: `environment { GH_TOKEN = credentials('my-cred-id') }` —
  Jenkins masks the value in console output automatically, same principle as GitHub
  Actions secrets (Day 41).
- Scoping credentials to a folder/job vs globally — least-privilege habit.

### C. Parameterized builds (10 min)
- `parameters { string(name: 'ENV', defaultValue: 'staging', description: '...') 
  choice(name: 'LEVEL', choices: ['debug','info','warn']) }` — Jenkins renders a form
  before each build ("Build with Parameters").
- Use case: same pipeline, different target environment or log verbosity, chosen at
  trigger time — a manual-dispatch analog to GitHub Actions' `workflow_dispatch` inputs.

### D. GitLab CI — a read-only tour (15 min)
- `.gitlab-ci.yml` — YAML-based like GitHub Actions (not Groovy like Jenkins);
  `stages:`, jobs with `script:`, `stage:` — structurally very close to Actions'
  jobs/steps.
- Built-in container registry + integrated CI/CD in one product (vs GitHub Actions +
  separate registry, or Jenkins + separate everything) — a "batteries included" pitch.
- The point of the tour: recognize that pipeline THINKING (trigger → stages → jobs →
  artifacts → secrets) is portable across GitHub Actions, Jenkins, and GitLab CI even
  though syntax differs — this transferability is what interviewers actually probe for.

## Lab (2h)

### Part 1 — Docker-based agent (35 min)
1. Recreate the Jenkins container with Docker socket access:
   `docker run -d --name jenkins -p 8080:8080 -p 50000:50000 -v jenkins_home:/var/
   jenkins_home -v /var/run/docker.sock:/var/run/docker.sock jenkins/jenkins:lts`
   (remove/rename the old container first, confirm the volume preserves your setup).
2. Install the "Docker Pipeline" plugin if not already present (Manage Jenkins →
   Plugins).
3. Update your `Jenkinsfile`: wrap the `Test` stage with
   `agent { docker { image 'python:3.12-slim' } }`, run `pip install -r
   requirements.txt && pytest` inside it.
4. Rebuild via the Pipeline job — confirm Console Output shows Jenkins pulling the
   Python image and running tests inside it successfully (friction from Day 43 solved).

### Part 2 — Credentials (25 min)
5. Add a dummy secret text credential in Manage Jenkins → Credentials (e.g., a fake API
   key, ID `demo-secret`).
6. In the Jenkinsfile, add an `environment { DEMO = credentials('demo-secret') }` block
   and an `echo`/`sh` step referencing `$DEMO` — rebuild, confirm the value is masked
   (`****`) in Console Output.

### Part 3 — Parameterized build (25 min)
7. Add a `parameters` block to the Jenkinsfile: a `choice` parameter for `ENVIRONMENT`
   (`dev`/`staging`/`prod`) and a `string` parameter for a log level.
8. Reference `params.ENVIRONMENT` in an echo step. Trigger via "Build with Parameters"
   in the Jenkins UI twice with different values — confirm the Console Output reflects
   each choice.

### Part 4 — GitLab CI tour + comparison doc (35 min)
9. Without installing GitLab, read through a sample public `.gitlab-ci.yml` (search
   GitLab's own docs example or a well-known open-source project's file) and identify
   its `stages:`, jobs, `script:` blocks, and any `only`/`rules` triggers.
10. Extend yesterday's comparison note into a table: GitHub Actions vs Jenkins vs
    GitLab CI across { config format, hosting, secrets mechanism, parameterization,
    typical use case }. Commit it to `docs/`.
11. `git add -A`, commit: "Jenkinsfile: docker agent for test stage, credentials,
    parameters; add CI tools comparison doc".

**Definition of done:** Test stage runs inside a fresh `python:3.12-slim` container via
`agent { docker {...} }`, solving the missing-tooling problem · a Jenkins credential is
referenced and masked in output · a parameterized build ran twice with different UI-
selected values · GitHub Actions/Jenkins/GitLab CI comparison table committed.
