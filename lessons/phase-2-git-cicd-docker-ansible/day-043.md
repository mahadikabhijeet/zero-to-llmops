## Theory (1h)

### A. Why learn Jenkins alongside GitHub Actions (10 min)
- GitHub Actions is SaaS-hosted, YAML-native, tightly coupled to GitHub. Jenkins is
  self-hosted, plugin-driven, and still dominant in many enterprises (especially
  on-prem/regulated environments) — job-readiness requires knowing both, not preferring
  one dogmatically.
- Jenkins is a general-purpose automation server; "CI/CD tool" undersells how
  pluggable/old/battle-tested it is.

### B. Running Jenkins in a container (15 min)
- Official image: `jenkins/jenkins:lts` — running it in Docker sidesteps installing a
  JVM + Jenkins package directly on the host (cleaner, disposable, matches how it's
  often run in practice today anyway — inside containers/k8s).
- `docker run -d --name jenkins -p 8080:8080 -p 50000:50000 -v jenkins_home:/var/
  jenkins_home jenkins/jenkins:lts` — named volume persists Jenkins state across
  container restarts (preview of Day 47's volumes lab, used here practically first).
- Initial unlock: Jenkins prints an admin password to its logs on first boot —
  `docker logs jenkins` to retrieve it, paste into the setup wizard at
  `localhost:8080`.

### C. UI tour and freestyle jobs (15 min)
- Dashboard → New Item → Freestyle project: point-and-click job config (SCM URL, build
  triggers, build steps as shell commands, post-build actions).
- Freestyle jobs are UI-configured and NOT version-controlled by default — a real
  limitation (config drift, no code review) that Pipeline jobs solve.
- Build history, console output (the log view — your primary debugging tool, same
  instinct as the GitHub Actions log tab).

### D. Pipeline as code — the Jenkinsfile (20 min)
- **Declarative pipeline** syntax (preferred, more structured) vs **scripted pipeline**
  (raw Groovy, more powerful/complex) — learn declarative first.
- Anatomy: `pipeline { agent any stages { stage('Build') { steps { sh '...' } }
  stage('Test') { steps { sh '...' } } } }`.
- `agent any` — run on any available executor; `agent { docker { image '...' } }`
  preview (Day 44 goes deeper on agents).
- Storing the `Jenkinsfile` in the repo root — same "pipeline as code, reviewed via PR"
  philosophy as `.github/workflows/`. Jenkins reads it via a **Pipeline** job type
  pointed at your repo ("Pipeline script from SCM").

## Lab (2h)

### Part 1 — Stand up Jenkins (30 min)
1. `docker volume create jenkins_home`.
2. `docker run -d --name jenkins -p 8080:8080 -p 50000:50000 -v
   jenkins_home:/var/jenkins_home jenkins/jenkins:lts`.
3. `docker logs jenkins` — retrieve the initial admin password. Open `localhost:8080`,
   complete setup wizard (install suggested plugins, create your first admin user).
4. Confirm the container survives a restart with state intact:
   `docker restart jenkins`, log in again, confirm your admin user still exists.

### Part 2 — Freestyle job (30 min)
5. New Item → Freestyle project named `sys-report-freestyle`.
6. Configure it to pull your public GitHub repo (Source Code Management → Git → paste
   the HTTPS clone URL — public repo needs no credentials).
7. Add a Build Step (Execute shell): `pip install -r requirements.txt && pytest`
   (Jenkins container may need Python installed — if `python3`/`pip` are missing inside
   the Jenkins container, note this friction explicitly: it's why agents/containers-per-
   tool matter, foreshadowing Day 44).
8. Build Now, watch Console Output. If Python tooling is missing in the base Jenkins
   image, document the error — this is real-world friction, not a lab bug.

### Part 3 — First Jenkinsfile (40 min)
9. In `/opt/fresher_project`, add a `Jenkinsfile` at the repo root: declarative
   pipeline with `Build` (echo a message or install deps) and `Test` (`sh 'pytest'` or
   an echo placeholder if Python isn't available in this agent) stages.
10. New Item → Pipeline project named `sys-report-pipeline`. Configure "Pipeline script
    from SCM" → Git → your repo URL → script path `Jenkinsfile`.
11. Build Now — watch Jenkins clone your repo and execute the staged pipeline; compare
    the Console Output structure (stage view) to GitHub Actions' job/step view.
12. Commit a small Jenkinsfile change (e.g., add an `echo` step), push, rebuild via
    Jenkins UI — confirm it picks up the change from SCM automatically (pipeline-as-code
    payoff).

### Part 4 — Compare and reflect (20 min)
13. Write a short comparison note (in `docs/` or README): GitHub Actions vs Jenkins —
    hosting model, config format (YAML vs Groovy), where each tends to be used. This
    becomes real interview material (Day 59).

**Definition of done:** Jenkins running in a container with a named volume, admin
account created · a freestyle job built once (even if it hit tooling friction — that's
observed and documented) · a `Jenkinsfile` committed to the repo and run successfully
via a Pipeline job pulling from SCM · comparison notes written.
