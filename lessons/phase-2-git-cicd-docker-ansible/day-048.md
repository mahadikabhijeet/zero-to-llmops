## Theory (1h)

### A. Why images run as root by default, and why that's bad (15 min)
- Without a `USER` instruction, a container's process runs as root INSIDE the
  container — if an attacker escapes the app into the container's OS layer, they're
  root there, one misconfiguration away from host root (via kernel exploits, mounted
  sockets, etc. — ties back to Day 44's Docker-socket security note).
- Fix: create a non-root user in the Dockerfile and switch to it:
  ```
  RUN useradd -r -u 1000 appuser
  USER appuser
  ```
- Caveat: file permissions matter now — anything the app needs to write must be owned
  by/writable by that UID (`COPY --chown=appuser:appuser`).

### B. Healthchecks (15 min)
- `HEALTHCHECK --interval=30s --timeout=3s CMD python3 -c "..." || exit 1` (or `curl
  -f http://localhost/health || exit 1`) — Docker runs this periodically and reports
  `healthy`/`unhealthy`/`starting` in `docker ps`.
- Why it matters beyond cosmetics: orchestrators (Compose `depends_on: condition:
  service_healthy`, and Kubernetes probes in Phase 3) use exactly this signal to decide
  whether to route traffic or restart a container.
- `docker inspect --format='{{.State.Health.Status}}' <name>`.

### C. `.dockerignore` recap + minimal base images (10 min)
- Recap Day 46's `.dockerignore` — reinforce it here as part of the hygiene checklist,
  not a one-off.
- Prefer `-slim`/`-alpine` base images over full ones when practical — smaller attack
  surface AND smaller pull/scan time; know the trade-off (alpine's musl libc can break
  some Python C-extension wheels — slim is often the safer default for Python).

### D. Vulnerability scanning with trivy (20 min)
- `trivy image <image>` — scans OS packages and language dependencies against known
  CVE databases, reports severity (LOW/MEDIUM/HIGH/CRITICAL).
- Run locally first (`brew install trivy` or the official install script / container:
  `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image
  <image>`), understand output, THEN wire into CI.
- `trivy image --severity HIGH,CRITICAL --exit-code 1 <image>` — fail the CI job on
  serious findings; `--exit-code 0` (or omit) to just report without blocking, a
  reasonable starting posture before tightening later.
- Registry push: `docker login ghcr.io` (GitHub Container Registry — reuses your
  GitHub identity, a personal access token with `write:packages` scope), `docker tag
  sys-report:0.1 ghcr.io/<you>/sys-report:0.1`, `docker push ghcr.io/<you>/sys-
  report:0.1`.

## Lab (2h)

### Part 1 — Non-root user (25 min)
1. Edit the project Dockerfile: add a non-root user, `COPY --chown=` for app files, and
   `USER appuser` before the `ENTRYPOINT`.
2. Rebuild, `docker run --rm sys-report:0.1 whoami` (or equivalent) — confirm it's NOT
   root. Confirm the app still runs and can write wherever it legitimately needs to
   (fix any permission errors that surface — this is the realistic friction).

### Part 2 — Healthcheck (25 min)
3. Add a simple healthcheck appropriate to the tool (e.g., a Python one-liner checking
   the last report file's mtime is recent, or just `CMD python3 -c "import sys;
   sys.exit(0)"` as a minimal placeholder if the tool has no long-running process to
   probe — note this honestly rather than inventing a fake HTTP endpoint).
4. Rebuild, run detached (`docker run -d --name sr-health sys-report:0.1 tail -f /dev/
   null` or similar to keep it alive for inspection), `docker ps` — watch the STATUS
   column show `(health: starting)` then `(healthy)`; `docker inspect --format=
   '{{.State.Health.Status}}' sr-health`.

### Part 3 — Trivy scan (35 min)
5. Run trivy against your image locally:
   `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image
   sys-report:0.1`.
6. Read the findings; if any HIGH/CRITICAL are fixable by bumping the base image tag or
   a pinned dependency version, do it and rescan.
7. Add a `scan` step/job to `.github/workflows/ci.yml`: build the image in CI, run
   trivy against it (`aquasecurity/trivy-action` marketplace action, or the raw docker
   command), `exit-code: 1` on HIGH/CRITICAL to make it a real gate.

### Part 4 — ★ Push hardened image from CI (35 min)
8. Add a `GHCR_TOKEN`-equivalent: for GHCR, you can use the automatic `GITHUB_TOKEN`
   with `packages: write` permission set in the workflow — simpler than a new secret;
   document this choice.
9. Add a `publish` job (runs after `test`+`scan` pass, only on push to `main`): login
   to GHCR using `GITHUB_TOKEN`, build, tag with both the git short-SHA and a semantic
   version (or `latest` for now — accept the Day 46 caveat, revisit tagging discipline
   later), push.
10. Push to `main` via a PR merge (respecting Day 41's branch protection), watch CI
    build → scan → publish, and confirm the image lands in your GitHub repo's
    "Packages" tab.
11. `docker pull ghcr.io/<you>/sys-report:<tag>` from your host — confirm you can run
    the exact image CI just built and published.
12. `git add -A`, commit: "harden image (non-root, healthcheck), add trivy scan gate,
    publish to GHCR from CI".

**Definition of done:** ★ image runs as non-root, has a working healthcheck, passes (or
knowingly documents) a trivy scan, and CI builds+scans+publishes it to GHCR on merge to
`main` · pulled and ran the CI-published image locally to confirm it's real.
