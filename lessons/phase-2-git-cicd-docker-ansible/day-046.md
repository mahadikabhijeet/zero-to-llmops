## Theory (1h)

### A. Anatomy of a Dockerfile (15 min)
- `FROM <base-image>` — every image starts from another image (or `scratch` — empty,
  advanced, not today).
- `WORKDIR /app` — sets the working directory for subsequent instructions.
- `COPY src dest` (from build context into image) vs `ADD` (COPY plus URL-fetch/tar-
  extract magic — prefer `COPY` unless you specifically need ADD's extras).
- `RUN` — executes a command AT BUILD TIME, result baked into a new layer.
- `ENV`, `EXPOSE` (documentation of intended port, doesn't actually publish it —
  `-p` at `docker run` time still required), `USER` (preview, full treatment Day 48).

### B. Layers and build cache (20 min)
- Each instruction creates a new layer; Docker caches layers and reuses them if the
  instruction AND everything before it are unchanged (byte-for-byte for `COPY`/`ADD`).
- **Cache-friendly ordering**: copy dependency manifests (`requirements.txt`) and
  install deps BEFORE copying the rest of the source code — code changes shouldn't
  force a dependency reinstall.
  ```
  COPY requirements.txt .
  RUN pip install -r requirements.txt
  COPY . .
  ```
- `docker build -t name:tag .` — the `.` is the **build context** (everything sent to
  the daemon; a `.dockerignore` — full treatment Day 48 — trims this).
- `docker history <image>` — see every layer and its size; a tool for spotting bloat.

### C. Multi-stage builds (15 min)
- Problem: build tools (compilers, full SDKs) bloat the final image if left in.
- Solution: multiple `FROM` blocks in one Dockerfile; a `builder` stage does the heavy
  lifting, the final stage `COPY --from=builder <path> <path>` pulls only the needed
  artifact — final image ships without the build toolchain.
- For a Python project this matters less than for compiled languages, but the pattern
  (e.g., building wheels in one stage, installing only wheels in the final slim stage)
  is worth knowing and interview-relevant.

### D. ENTRYPOINT vs CMD (10 min)
- `CMD` — default command, easily overridden by args passed to `docker run image
  <override>`.
- `ENTRYPOINT` — fixed executable; anything passed to `docker run` becomes ARGS to it,
  not a replacement.
- Common pattern: `ENTRYPOINT ["python3", "-m", "sys_report"]` + `CMD ["collect"]` —
  default subcommand that can still be overridden (`docker run img show --last`).

## Lab (2h)

### Part 1 — First Dockerfile (35 min)
1. In `/opt/fresher_project`, write a `Dockerfile`:
   ```
   FROM python:3.12-slim
   WORKDIR /app
   COPY requirements.txt .
   RUN pip install --no-cache-dir -r requirements.txt
   COPY . .
   ENTRYPOINT ["python3", "-m", "src.sys_report.cli"]
   CMD ["collect"]
   ```
   (adjust the entrypoint module path to your actual `src/` layout from Day 38).
2. `docker build -t sys-report:0.1 .` — watch each instruction become a layer in the
   output.
3. `docker run --rm sys-report:0.1` — confirm it runs the default `collect` subcommand.
4. `docker run --rm sys-report:0.1 show --last` — confirm CMD is overridden correctly
   (ENTRYPOINT stays fixed).

### Part 2 — Cache-order experiment (30 min)
5. Touch a source file (not `requirements.txt`), rebuild — note in the build output
   which layers say "CACHED" and confirm `pip install` was NOT rerun.
6. Now edit `requirements.txt` (add a harmless comment or bump nothing real), rebuild —
   confirm the `pip install` layer AND everything after it reruns, but the `FROM`/
   `WORKDIR` layers stay cached.
7. `docker history sys-report:0.1` — identify the largest layer; discuss whether it's
   reasonable (base image + deps) or bloated.

### Part 3 — .dockerignore and rebuild hygiene (20 min)
8. Add a `.dockerignore` (mirror `.gitignore` mostly: `.git/`, `__pycache__/`,
   `*.pyc`, `logs/`, `.venv/`) so the build context doesn't ship junk.
9. Rebuild, compare build context size/time if noticeably different (`docker build`
   prints "Sending build context to Docker daemon Nx" — compare before/after).

### Part 4 — Multi-stage preview + project step (35 min)
10. Write a second Dockerfile variant (`Dockerfile.multistage`) demonstrating the
    pattern even if the size win is modest for this project: a `builder` stage that
    runs `pip wheel` into `/wheels`, and a final stage that `COPY --from=builder
    /wheels /wheels` and installs from wheels only. Build it, confirm it still runs
    correctly. Compare final image sizes (`docker images`) between the single-stage and
    multi-stage builds.
11. Tag your working single-stage image properly: `docker tag sys-report:0.1
    sys-report:latest` is fine locally, but note that pushing to a registry with a real
    version tag is the Day 48 milestone.
12. `git add -A`, commit: "add Dockerfile (cache-ordered), .dockerignore, multi-stage
    variant — project now containerized".

**Definition of done:** `docker build` produces a working `sys-report` image · CMD
override behavior confirmed against a fixed ENTRYPOINT · cache-order experiment showed
which layers rebuild vs stay cached · `.dockerignore` trims the build context · a
multi-stage variant builds and runs correctly · Dockerfile(s) committed.
