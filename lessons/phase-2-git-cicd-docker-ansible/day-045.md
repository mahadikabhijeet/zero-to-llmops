## Theory (1h)

### A. Images vs containers — the core mental model (15 min)
- An **image** is a read-only, layered filesystem snapshot + metadata (entrypoint, env,
  exposed ports) — it's a template, never runs by itself.
- A **container** is a running (or stopped) instance of an image, with its own writable
  layer on top and its own process namespace — you already used this Day 43–44 without
  the vocabulary (Jenkins itself was a container of the `jenkins/jenkins:lts` image).
- Contrast with a VM: containers share the host kernel (no separate OS boot, much
  lighter/faster); this ties back to Day 1's kernel/process concepts — a container is
  fundamentally Linux namespaces + cgroups, not a mini VM.
- `docker` CLI vs `podman` CLI — Fedora ships Podman by default (daemonless, rootless-
  friendly); the CLI is near-identical. `alias docker=podman` is common; this training
  uses `docker` syntax throughout — assume the alias if using Podman.

### B. Running and inspecting containers (20 min)
- `docker run <image>` (create+start+attach), `docker run -d` (detached), `-it` (
  interactive TTY — for a shell), `--name` (human-readable name instead of random ID),
  `-p host:container` (port mapping — used already Day 43 for Jenkins).
- `docker ps` (running), `docker ps -a` (all, including stopped), `docker logs
  [-f] <name>` (recap the `-f` follow habit from Day 2's `tail -f`).
- `docker exec -it <name> bash` — get a shell INSIDE a running container (different
  from `run`, which starts a NEW container).
- `docker inspect <name>` — full JSON metadata (IP address, mounts, env, config) — pipe
  through `jq` (Day 39 payoff) to extract one field: `docker inspect <name> | jq
  '.[0].NetworkSettings.IPAddress'`.
- `docker stop`/`start`/`restart`/`rm`, `docker rm -f` (force-remove a running
  container).

### C. The container lifecycle (10 min)
- States: created → running → paused → stopped (exited) → removed.
- `docker stats` — live resource usage (CPU/mem) per container.
- Ephemeral by default: `docker run --rm` auto-removes on exit — good habit for
  throwaway test containers.

### D. Registries and image pulls (15 min)
- Docker Hub is the default registry (`docker pull nginx` implicitly means `docker.io/
  library/nginx`); other registries: GHCR (`ghcr.io`), quay.io, private registries
  (previewed Day 48).
- Image naming: `[registry/]repository:tag` — `nginx:1.27`, `python:3.12-slim`;
  `:latest` is a moving tag, NOT a version pin — avoid it in anything you'll rely on
  reproducing.
- `docker pull`, `docker images` (list local images), `docker rmi` (remove an image —
  fails if a container still references it), `docker image prune` (clean up dangling
  layers).
- Image layers and caching preview (full depth Day 46): each Dockerfile instruction is
  a layer; pulling reuses shared layers across images (why `python:3.12-slim` pulls fast
  the second time).

## Lab (2h)

### Part 1 — First containers (25 min)
1. `docker run hello-world` — read the output text carefully, it explains the exact
   pull→create→run→exit sequence that just happened.
2. `docker run -d --name web1 -p 8081:80 nginx:1.27` — `curl localhost:8081` to confirm
   nginx is serving.
3. `docker ps`, `docker ps -a` after stopping it — compare.
4. `docker logs web1`, `docker stats web1` (in another terminal, hit it with a few more
   curls and watch CPU tick).

### Part 2 — exec, inspect, lifecycle (35 min)
5. `docker exec -it web1 bash` — inside, `cat /etc/os-release`, `ls /usr/share/nginx/
   html`, edit `index.html` with `echo "hello from lab" > /usr/share/nginx/html/index.html`,
   exit, `curl localhost:8081` — confirm the change (and understand it's in the
   container's writable layer, not the image).
6. `docker inspect web1 | jq '.[0].NetworkSettings.IPAddress'` and `.Config.Image`.
7. `docker stop web1`, `docker ps -a` (still listed, exited), `docker start web1`,
   `curl` again — confirm your edit survived a stop/start (but ask: would it survive
   `docker rm` + a fresh `docker run`? Answer by testing it — it wouldn't, motivating
   Day 47's volumes).
8. `docker rm -f web1`.

### Part 3 — Ephemeral containers and registries (30 min)
9. `docker run --rm -it python:3.12-slim python3 --version` — confirm the container is
   gone after exit (`docker ps -a` shows nothing for it).
10. `docker pull ubuntu:22.04` and `docker pull ubuntu:latest` — `docker images` — note
    both may resolve to different or same image IDs depending on current `latest`;
    discuss why pinning matters for reproducibility.
11. `docker image prune` after removing a few images — observe reclaimed space.

### Part 4 — Incremental project step (30 min)
12. `docker run --rm -it -v $(pwd):/app -w /app python:3.12-slim bash` — a temporary
    container with your project directory bind-mounted in (preview of Day 47's bind
    mounts, used practically now); inside, `pip install -r requirements.txt && pytest`
    — confirm your project's tests run inside a clean container without installing
    anything on your Fedora host.
13. Note in `docs/`: "project tests now verified runnable in a clean `python:3.12-slim`
    container" — this de-risks tomorrow's Dockerfile work (Day 46 containerizes it for
    real).
14. `git add -A`, commit if any doc changes: "note: sys_report tests verified in clean
    python container".

**Definition of done:** ran, inspected, exec'd into, stopped/started, and removed a
container · explained image vs container and container vs VM in your own words ·
confirmed a container's writable-layer change is lost on `rm` (motivating volumes) ·
ran project tests successfully inside a throwaway `python:3.12-slim` container via a
bind mount.
