## Theory (1h)

### A. Why version control, why Git (10 min)
- The problem: no history, no collaboration, no safe experimentation without VCS.
- Git is distributed — every clone is a full repo with full history (contrast SVN/CVS).
- Three states: working directory → staging area (index) → repository (commits).
- `git config --global user.name`/`user.email` — identity attached to every commit.

### B. The core workflow (15 min)
- `git init` — creates `.git/` in the current directory; a repo is just that hidden dir.
- `git status` — the command you run before and after everything.
- `git add <file>` (stage), `git add -p` (stage hunks interactively — preview).
- `git commit -m "message"` — snapshots the staged tree; `git commit --amend` (careful,
  rewrites the last commit — preview for Day 34).
- `git log` (`--oneline --graph --all`), `git show <hash>`.
- `git diff` (working vs staged), `git diff --staged` (staged vs last commit).

### C. The object model — what a commit actually IS (20 min)
- Git is a content-addressable key-value store. Every object is identified by the
  SHA-1(SHA-256 in newer repos) hash of its content.
- Four object types: **blob** (file content, no filename), **tree** (a directory
  listing — names + modes + object hashes), **commit** (tree hash + parent(s) + author
  + message), **tag** (annotated tags point at a commit with metadata).
- A commit is a pointer to a tree, which is a pointer to blobs/trees. Change one byte →
  new blob hash → new tree hash → new commit hash (this is why history is tamper-evident).
- Branches are just files containing a commit hash: `.git/refs/heads/<branch>`. `HEAD`
  is a pointer to the current branch (or a commit, if "detached").

### D. Peeking under the hood (15 min)
- `git cat-file -p <hash>` — print any object's content.
- `git cat-file -t <hash>` — show its type (blob/tree/commit).
- `git hash-object <file>` — compute a blob hash without committing.
- `.gitignore` preview (full treatment Day 33) — untracked files that should stay untracked.

## Lab (2h)

### Part 1 — First repo, first commits (30 min)
1. `git config --global user.name "..."`, `git config --global user.email "..."`,
   `git config --global init.defaultBranch main`.
2. `mkdir ~/lab31 && cd ~/lab31 && git init`. Inspect `.git/` with `ls -la` and `tree .git`.
3. Create `notes.txt` with one line. `git status` → `git add notes.txt` → `git status`
   again (note the state change) → `git commit -m "first commit"`.
4. Add a second line to `notes.txt`. Run `git diff` (nothing staged yet — see the diff
   against the working copy), then `git add -p` to stage just that hunk, `git diff --staged`,
   `git commit -m "add second line"`.
5. `git log --oneline --graph`.

### Part 2 — Object model excavation (40 min)
6. `git cat-file -p HEAD` — see the tree hash and parent (or lack of one on first commit).
7. `git cat-file -p <tree-hash-from-step-6>` — see the blob entry for `notes.txt`.
8. `git cat-file -p <blob-hash>` — print the raw file content straight from the object
   store.
9. Change one character in `notes.txt`, run `git hash-object notes.txt` — get a hash
   WITHOUT committing. Confirm it differs from the committed blob's hash.
10. `find .git/objects -type f` — count objects; correlate the count with your commits.

### Part 3 — diff and log fluency (30 min)
11. Make 3 more small commits to `notes.txt` (different lines each time).
12. `git diff HEAD~2 HEAD` — diff across two commits.
13. `git log -p -- notes.txt` — full patch history of one file.
14. `git show HEAD~1` vs `git show HEAD~1:notes.txt` (commit metadata+diff vs raw file
    content at that commit).

### Part 4 — Incremental project step (20 min)
15. `cd /opt/fresher_project && git init`. Add a `.gitignore` stub (just `*.log` and
    `__pycache__/` for now — full treatment Day 33).
16. `git add -A && git status` — review what's staged before committing (never blind-add
    on a real project).
17. `git commit -m "initial commit: system_report bash+python tool as of Phase 1 capstone"`.
18. `git log --oneline` and `git cat-file -p HEAD` to confirm the snapshot took.

**Definition of done:** can explain blob→tree→commit chain from a real `cat-file` walk ·
`git diff` vs `git diff --staged` distinction is clear · `/opt/fresher_project` is now a
git repo with one committed baseline snapshot.
