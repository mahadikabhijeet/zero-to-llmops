## Theory (1h)

### A. Consolidating everything learned about secrets so far (15 min)
- Recap the touchpoints already hit: GitHub Actions secrets (Day 41, 57), Jenkins
  credentials (Day 44), `.env` files (Day 50), `ansible-vault` (Day 53) — today unifies
  them into one mental model and fills the remaining gaps.
- Core principle: secrets need to exist SOMEWHERE for automation to work, but that
  somewhere is never git history, never a Dockerfile `ENV`/`ARG` baked into a layer
  (image layers are inspectable — recap Day 46's `docker history`), never a log line.

### B. env vars vs files vs a secrets manager (15 min)
- **Env vars**: simplest, but visible to any process that can read `/proc/<pid>/
  environ` (recall Day 8) on the same host, and easy to accidentally log/echo.
- **Files with tight permissions** (`chmod 600`, owned by the service user from Day 3):
  better for larger secrets (private keys, certs); the pattern used for
  `DEPLOY_SSH_KEY` in Day 57.
- **Dedicated secrets manager** (AWS Secrets Manager/SSM Parameter Store — Phase 4;
  HashiCorp Vault — mentioned, out of scope depth here): fetched at runtime, never
  persisted to disk longer than necessary, access is audited/rotatable — the "grown-up"
  answer for anything beyond a solo lab project.

### C. sops + age — encrypting secrets IN git (20 min)
- Problem `ansible-vault` doesn't fully solve outside Ansible context: what about
  secrets needed by non-Ansible files (Kubernetes manifests in Phase 3, plain YAML
  configs)?
- `sops` (Secrets OPerationS, by Mozilla) — encrypts specific VALUES within a YAML/
  JSON file while leaving structure/keys readable in git diffs, using a key from `age`
  (a modern, simple alternative to GPG) or cloud KMS.
- `age-keygen -o key.txt` — generates a keypair; `sops --age <public-key> -e
  secrets.yaml > secrets.enc.yaml` — encrypt; `sops -d secrets.enc.yaml` — decrypt
  (needs the private key available, e.g. via `SOPS_AGE_KEY_FILE` env var).
- Why this matters beyond Ansible: it's the standard pattern feeding secrets into
  GitOps flows (Phase 5's ArgoCD) where "everything including secrets is a file in
  git" is the whole point, but plaintext secrets in git is never acceptable — sops
  reconciles both.

### D. What NEVER goes in git, and scrubbing when it does anyway (10 min)
- Never: real passwords/tokens/private keys, `.env` files with real values, cloud
  credentials, database connection strings with embedded passwords, TLS private keys.
- If a secret IS accidentally committed: rotating/revoking the secret immediately is
  the FIRST and most important step (a `git filter-branch`/`git filter-repo`/BFG
  history rewrite does NOT undo exposure if anyone already cloned/forked/cached it —
  assume it's compromised the moment it's pushed).
- `git filter-repo` (modern, recommended over `filter-branch`) or BFG Repo-Cleaner —
  tools to purge a file/string from ALL history — mention as the mechanical fix, but
  stress the rotation-first principle above it.
- `.gitignore` prevention (recap) + `git-secrets`/`gitleaks` — scanning tools that can
  run as a pre-commit hook (Day 55!) or CI step to catch secrets BEFORE they're
  committed, the actually-reliable prevention layer.

## Lab (2h)

### Part 1 — Audit what you already have (25 min)
1. Run `git log -p | grep -iE "password|secret|token|BEGIN.*PRIVATE KEY"` across the
   project's full history (harmless grep, not a real leak scanner, but a first gut
   check) — confirm nothing real turns up given the discipline built since Day 33.
2. Install and run `gitleaks detect` (or `gitleaks git -v .`) against the repo —
   compare its findings (if any) to your manual grep; note false positives vs real
   hits.

### Part 2 — Add gitleaks as prevention (30 min)
3. Add a `gitleaks` hook to `.pre-commit-config.yaml` (Day 55's file) so it scans
   staged changes before every commit.
4. Deliberately stage a fake-looking secret (e.g., a string matching an AWS key
   pattern, clearly fake) and attempt to commit — confirm the hook blocks it. Remove
   the fake secret, confirm a normal commit proceeds.
5. Add a `gitleaks` step to `.github/workflows/ci.yml` as a defense-in-depth layer
   (catches anything that slipped past a contributor who skipped pre-commit locally).

### Part 3 — sops + age hands-on (40 min)
6. Install `age` and `sops`. `age-keygen -o key.txt` — note the public key printed.
7. Write a small `secrets.yaml` with a couple of fake key-value secrets (mirroring
   something real you'd actually need, e.g. `db_password`, `api_token`).
8. `sops --age <public-key-from-step-6> -e secrets.yaml > secrets.enc.yaml` — inspect
   `secrets.enc.yaml`: confirm keys are readable but values are ciphertext (the
   diff-friendliness sops advertises).
9. `SOPS_AGE_KEY_FILE=key.txt sops -d secrets.enc.yaml` — confirm decryption works.
   Commit `secrets.enc.yaml` (safe, encrypted) — confirm `key.txt` and the original
   plaintext `secrets.yaml` are gitignored and NOT committed.

### Part 4 — Rotation drill + documentation (25 min)
10. Pick one real secret currently in use (e.g., the Day 57 deploy SSH key) and
    practice the rotation muscle: generate a new keypair, update the target's
    `authorized_keys` and the GitHub secret, confirm the pipeline still deploys
    successfully, THEN remove the old public key from `authorized_keys` — this is what
    "rotate immediately" looks like in practice, done here proactively rather than
    reactively.
11. Write `docs/secrets-policy.md`: what's stored where (GitHub secrets, ansible-
    vault, sops+age), what NEVER goes in git, and the rotation procedure just
    practiced.
12. `git add -A`, commit: "add gitleaks scanning (pre-commit + CI), sops+age secrets
    encryption drill, document secrets policy and rotation procedure".

**Definition of done:** gitleaks blocks a real fake-secret commit attempt locally AND
runs as a CI defense-in-depth layer · a real sops+age encrypt/decrypt round-trip
completed with the encrypted file committed and plaintext/key gitignored · the deploy
SSH key was rotated end-to-end without breaking the Day 57 pipeline · secrets policy
documented.
