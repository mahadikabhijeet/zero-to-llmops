Phase 2 · follows Day 58 (secrets management, gitleaks, sops/age). Distro: RHEL/Fedora.

## Recall warm-up (5 min, from Day 57–58)
1. What does `needs: [test, scan, publish]` guarantee about a deploy job?
2. If a real secret gets committed, what's the FIRST thing to do before any history
   rewrite?
3. Why add secret scanning at both pre-commit AND CI layers?
4. What does `sops` protect that plain `ansible-vault` doesn't structurally address?

## Theory (1h)

### A. How this day is different (10 min)
- No new material — this is a **practice-interview day**. Trainer plays interviewer;
  student answers out loud, then together critique the answer against what a strong
  answer would include. The goal is fluency under mild pressure, not new content.

### B. Git scenario question bank (15 min)
- "Walk me through what happens internally when you run `git commit`." (expects
  blob/tree/commit object chain — Day 31.)
- "A teammate force-pushed and now your branch is broken — what do you do?" (expects
  `reflog`, understanding of why force-push is dangerous — Day 34.)
- "You need to combine 5 messy commits into one clean commit before opening a PR — how?"
  (interactive rebase, squash — Day 34.)
- "Explain fast-forward vs three-way merge and when each happens." (Day 32.)
- "How would you find which commit introduced a bug?" (introduce `git bisect` here as
  NEW-but-small: `git bisect start`, `bad`, `good <hash>`, binary search across
  history, `git bisect run <test-script>` for automation — a genuinely useful tool not
  covered elsewhere in the blueprint, worth a few minutes today.)

### C. CI/CD design question bank (15 min)
- "Design a CI/CD pipeline for a Python web service from scratch — what stages, in
  what order, and why?" (expects: lint → test → build → scan → publish → deploy,
  matches the exact pipeline built since Day 40.)
- "How do you keep secrets out of a CI pipeline's logs?" (masking, secret stores,
  never echo — Day 41, 58.)
- "Your deploy job succeeded but the app is still running the old version — how do you
  debug it?" (image tag mismatch, cache issue, deploy job actually didn't run against
  the right host, container not restarted — practical debugging tree.)
- "When would you choose Jenkins over GitHub Actions, or vice versa?" (Day 44's
  comparison table, argued live.)

### D. Docker debugging question bank (15 min)
- "A container exits immediately after `docker run` — how do you debug it?" (`docker
  logs`, `docker run` without `-d` to see foreground output, check ENTRYPOINT/CMD,
  `docker inspect` exit code meaning.)
- "Two containers can't reach each other by name — what's wrong?" (default bridge
  network, no user-defined network/Compose — Day 47.)
- "The image is 1.2GB and should be 200MB — what do you check?" (`docker history`,
  wrong base image, missing multi-stage build, no `.dockerignore`, layer-cache-busting
  `COPY . .` before deps — Day 46.)
- "A container works locally but fails in CI with a permission error — why?" (non-root
  USER + file ownership mismatch — Day 48.)

## Lab (2h)

### Part 1 — Git scenarios, live (30 min)
1. Trainer poses each Git scenario question cold; student answers verbally first, THEN
   demonstrates on the actual `/opt/fresher_project` repo or `~/lab31` where relevant
   (e.g., actually run `git bisect` against a repo with a deliberately introduced bug
   in one commit).
2. Score each answer 1-3 (needs work / solid / interview-ready) and note the gap for
   any score below 3.

### Part 2 — CI/CD design, whiteboard (30 min)
3. Without looking at the existing `.github/workflows/ci.yml`, student draws (paper or
   a markdown diagram) the pipeline stages from memory, then compares against the real
   file — identify any gaps in either the drawn design or genuine improvements to make
   to the real pipeline.
4. Answer the Jenkins-vs-Actions and secrets-in-logs questions live, referencing
   Day 44 and Day 58 notes only if truly stuck (simulating open-book vs closed-book).

### Part 3 — Docker debugging, hands-on (35 min)
5. Trainer deliberately breaks something for each debugging scenario (e.g., builds an
   image with a bad ENTRYPOINT that exits immediately; spins up two containers on the
   default bridge and asks why they can't reach each other; intentionally removes
   `.dockerignore` and a multi-stage split to bloat an image) — student debugs each
   live using the actual `docker` commands, not just theory.
6. For the "works locally, fails in CI" permission scenario, actually reproduce it:
   build with `USER appuser`, mount a host directory NOT owned by that UID, watch the
   real permission error, then fix it.

### Part 4 — Whiteboard the full pipeline + gap list (25 min)
7. Student whiteboards (or writes in `docs/`) the ENTIRE project pipeline end to end
   from memory: Git workflow → CI (lint/test/scan/publish) → Ansible deploy → what
   runs where — as if explaining it to an interviewer who's never seen the project.
8. Compile a `docs/phase2-gap-list.md`: every question that scored below 3, with a
   one-line plan to close each gap before Phase 3 begins.
9. `git add -A`, commit: "add phase 2 gap list from mock interview".

**Definition of done:** answered git/CI/Docker scenario questions live, with real
command demonstrations where applicable · whiteboarded the full pipeline from memory
without notes · gap list written and committed, ready to revisit before Day 60's
capstone writeup.
