## Theory (1h)

### A. Why automated tests, why pytest (10 min)
- Manual re-running of a script after every change doesn't scale and doesn't catch
  regressions. Tests are executable documentation of expected behavior.
- `pip install pytest`; test files named `test_*.py` or `*_test.py`, functions named
  `test_*` — pytest discovers them with zero config.
- `pytest` (run all), `pytest -v` (verbose), `pytest -k "keyword"` (filter by name),
  `pytest --lf` (rerun last failed).

### B. Writing tests (20 min)
- Plain `assert` statements — pytest rewrites them to show rich failure diffs, no need
  for `self.assertEqual` boilerplate (contrast with `unittest`, mentioned not taught).
- Testing for exceptions: `with pytest.raises(ValueError): ...`.
- **Fixtures** (`@pytest.fixture`) — reusable setup/teardown, e.g. a temp directory or a
  fake config object injected into test functions by name-matching.
- `tmp_path` built-in fixture — a pytest-managed temp dir per test, auto-cleaned.
- **Mocking** external calls: `unittest.mock.patch` — replace `requests.get` in a test
  with a fake that returns canned data, so tests don't hit the real network (ties
  directly to Day 36's `requests` code).

### C. Project layout (15 min)
- Flat layout (fine for tiny scripts) vs `src/` layout: `src/sys_report/__init__.py`,
  `src/sys_report/cli.py`, `src/sys_report/core.py`, `tests/test_core.py` — separates
  importable package code from test code, avoids accidental imports of the working
  directory instead of the installed package.
- `pyproject.toml` basics (preview — full packaging is out of scope for this training,
  but recognize the file and its role: project metadata + build config).
- Why separating "logic" (testable functions) from "CLI glue" (argument parsing, I/O)
  matters: pure functions are trivial to test; `main()` wiring is not.

### D. Type hints intro (15 min)
- `def collect_report(url: str, timeout: int = 5) -> dict:` — hints are documentation +
  editor support, NOT enforced at runtime by default.
- Common hints: `str`, `int`, `bool`, `list[str]`, `dict[str, Any]`, `Optional[str]`
  (or `str | None` in modern Python).
- `mypy` mentioned as the tool that actually checks hints (not installed today — just
  know it exists; ties into CI later as an optional lint step).
- Where hints pay off most: function signatures other people (or future-you) will call
  without reading the implementation.

## Lab (2h)

### Part 1 — First tests (30 min)
1. `pip install pytest`. Create `tests/` next to your project code.
2. Pick a pure function from `sys_report.py` (e.g., something that formats bytes into
   human-readable size, or parses a config value) — if none exists yet, extract one:
   move logic out of `main()` into a small testable function.
3. Write `tests/test_core.py` with 3+ `assert`-based test functions covering normal
   input, an edge case (empty/zero), and a bad-input case using `pytest.raises`.
4. `pytest -v` — confirm all pass; deliberately break the function to confirm a test
   fails with a useful diff, then fix it back.

### Part 2 — Fixtures and mocking (35 min)
5. Write a test that uses the `tmp_path` fixture to write a fake report file and assert
   your "show last report" logic reads it back correctly.
6. Using `unittest.mock.patch`, mock `requests.get` in a test of the Day 36
   internet-reachability check — force it to return a fake 200 response in one test and
   raise `ConnectionError` in another; assert the function returns `True`/`False`
   correctly without touching the real network.

### Part 3 — Restructure to `src/` layout (30 min)
7. Reorganize `/opt/fresher_project` into `src/sys_report/` (package) and `tests/`
   (mirroring module names). Update any imports/entry points accordingly.
8. Confirm `pytest` still discovers and runs tests correctly from the project root after
   the move.

### Part 4 — Type hints + incremental project step (25 min)
9. Add type hints to at least 4 function signatures in the core module (params and
   return types). No new tool run required today — just readable, correct hints.
10. Add a short `tests/README.md` or a section in the main README: "run tests with
    `pytest`", plus what's covered so far.
11. `git add -A`, commit: "add pytest suite (fixtures + mocked requests), restructure to
    src/ layout, add type hints to core functions".

**Definition of done:** `pytest` runs and passes a real suite covering a pure function,
a fixture-based test, and a mocked network call · project uses a `src/`+`tests/` layout
· at least 4 functions have type hints · everything committed.
