## Theory (1h)

### A. Why configuration management, why Ansible (15 min)
- Problem so far: every server-setup step this training has done (users, packages,
  nginx, SELinux contexts, systemd units — Phase 1) was done by hand, one host at a
  time. That doesn't scale past a handful of machines or survive turnover.
- Ansible: agentless (talks over SSH, no daemon to install on managed nodes — unlike
  Puppet/Chef/Salt which need agents) — a genuine adoption advantage worth naming.
- Control node (your machine, has Ansible installed) vs managed nodes (targets, just
  need SSH + Python).
- `pip install ansible` (or `dnf install ansible-core`) in a venv.

### B. Inventory (15 min)
- Inventory = the list of hosts Ansible manages, plus how they're grouped.
- INI-style (`inventory.ini`): `[web]\nweb1 ansible_host=192.168.1.10\n[db]\ndb1 ...`
  or YAML inventory — both valid, INI is more common for small setups.
- Groups and `[group:children]` for nesting; `[all:vars]` for vars applying everywhere.
- `ansible-inventory --list -i inventory.ini` — see how Ansible parses it.
- `ansible_host`, `ansible_user`, `ansible_port`, `ansible_ssh_private_key_file` —
  per-host connection variables.

### C. Ad-hoc commands and modules (15 min)
- `ansible <group> -i inventory.ini -m <module> -a "<args>"` — one-off commands
  without writing a playbook.
- `-m ping` (not ICMP — an Ansible module checking Python+SSH connectivity), `-m
  command`/`-m shell` (run raw commands — shell supports pipes/redirects, command
  doesn't, prefer command when you don't need shell features), `-m copy`, `-m
  package`/`-m dnf` (RHEL-family), `-m service`, `-m user`.
- `--check` (dry-run — show what WOULD change, apply nothing) — foreshadows Day 54's
  check mode.
- `-b`/`--become` (privilege escalation, sudo) — most real config tasks need this.

### D. Idempotency — the core idea (15 min)
- A module is idempotent if running it repeatedly produces the same end state without
  side effects on repeat runs — "ensure nginx is installed" run twice does nothing the
  second time (vs a raw `dnf install` which is technically idempotent too, but a raw
  `useradd` command is NOT — running it twice errors on the second run).
- This is WHY Ansible prefers modules (`user`, `package`, `service`) over raw `shell`/
  `command`: modules check current state first and only act if needed, reporting
  `changed: true`/`false` accordingly.
- `changed`/`ok`/`failed`/`unreachable` — the four outcomes you'll see in every run's
  output, starting today.

## Lab (2h)

### Part 1 — Setup and inventory (30 min)
1. `pip install ansible` in a venv (or `dnf install ansible-core`). `ansible
   --version`.
2. Set up a second target: either a second VM/container reachable over SSH, or (fine
   for this lab) manage `localhost` alongside a container running `sshd` — simplest
   path: use `localhost` with `ansible_connection=local` as one "host" plus one real
   remote/VM host if you have one from Day 17's backup lab.
3. Write `inventory.ini` with a `[local]` group (localhost, `ansible_connection=local`)
   and a `[remote]` group if you have a second host with real SSH details.
4. `ansible all -i inventory.ini -m ping` — confirm both connectivity paths report
   `SUCCESS`.

### Part 2 — Ad-hoc command drills (35 min)
5. `ansible local -i inventory.ini -m command -a "uptime"`.
6. `ansible local -i inventory.ini -m shell -a "uptime | awk '{print \$3}'"` — note why
   this needed `shell` (pipe) not `command`.
7. `ansible local -i inventory.ini -b -m dnf -a "name=htop state=present"` — install a
   package idempotently. Run it AGAIN — confirm `changed: false` the second time (the
   idempotency proof).
8. `ansible local -i inventory.ini -b -m user -a "name=ansibledemo state=present"` —
   run it twice, same idempotency confirmation.
9. `ansible local -i inventory.ini -m copy -a "content='hello from ansible\n'
   dest=/tmp/ansible_test.txt"` — run twice, same idempotency check via `changed`.

### Part 3 — Check mode and the non-idempotent contrast (30 min)
10. `ansible local -i inventory.ini -b -m dnf -a "name=tree state=absent" --check` —
    dry-run a removal, confirm nothing actually changed (`dnf list installed | grep
    tree` before/after).
11. Deliberately run the SAME task via raw shell twice: `ansible local -i inventory.ini
    -m shell -a "useradd rawuser"` — first run succeeds, second run FAILS (user
    exists) — this is the concrete, felt difference between a module and a raw command
    with respect to idempotency. Clean up: `ansible local -i inventory.ini -b -m user
    -a "name=rawuser state=absent"`.

### Part 4 — Incremental project tie-in (25 min)
12. Write an ad-hoc command sequence (not a playbook yet — Day 52) that ensures the
    packages `sys_report` depends on at the OS level (e.g., `python3`, `git`) are
    present on your `local` target, using `-m dnf` for each, run twice to prove
    idempotency both times.
13. Note in `docs/`: "Ansible control node set up, inventory defined, ad-hoc idempotent
    package/user management confirmed" — this becomes the seed for Day 52's first
    playbook.
14. `git add -A`, commit: "add Ansible inventory + ad-hoc command notes".

**Definition of done:** `ansible all -m ping` succeeds against at least one target ·
ran `dnf`/`user`/`copy` modules twice each, confirming `changed: false` on the second
run · demonstrated a raw `shell useradd` failing on its second run as the non-idempotent
contrast · `--check` mode dry-run confirmed with before/after verification.
