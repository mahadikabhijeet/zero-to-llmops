## Theory (1h)

### A. Buckets and objects (15 min)
- S3 is object storage: bucket (globally unique name, region-pinned) holds objects
  (key + value + metadata); no true folders — keys with `/` are a UI convenience over a
  flat namespace.
- Default: all new buckets are **private** with Block Public Access on — making
  something public now requires deliberate, multi-step action (post-2018 hardening
  after many breach headlines).
- Core CLI: `aws s3 mb`, `aws s3 cp/sync`, `aws s3api` (the lower-level, more complete
  API for lifecycle/versioning/policy operations `aws s3` doesn't expose).

### B. Storage classes and lifecycle (15 min)
- Classes trade retrieval speed/cost for storage cost: Standard → Standard-IA →
  One Zone-IA → Glacier Instant Retrieval → Glacier Flexible Retrieval → Glacier Deep
  Archive (cheapest storage, slowest/costliest retrieval).
- Lifecycle rules automate transitions (e.g. "move to IA after 30 days, Glacier after
  90, expire after 365") and expiration — the primary S3 FinOps lever (ties to Day 117).
- Intelligent-Tiering: automatic tier movement based on access patterns, small
  monitoring fee, good default when access patterns are unknown.

### C. Versioning, encryption, and access control (15 min)
- Versioning: once enabled, cannot be disabled (only suspended) — deletes become
  "delete markers," not permanent removal, until a version is explicitly purged. Prevents
  accidental overwrite/delete data loss.
- Encryption: SSE-S3 (AWS-managed keys, default today) vs SSE-KMS (customer-managed key,
  audit trail via CloudTrail, extra cost) — enable "default encryption" at the bucket level.
- Access control layers, cascading: Block Public Access (account/bucket) → bucket
  policy (resource-based JSON, like IAM but attached to the bucket) → IAM policy
  (identity-based) — all must permit for public/cross-account access to work.

### D. Presigned URLs and static hosting (15 min)
- Presigned URL: a time-limited, signed URL granting temporary access to a private
  object without making it public or sharing credentials — generated by whoever holds
  valid credentials with permission on that object.
- Static website hosting: enable on the bucket, set index/error documents; note this
  serves HTTP only and needs Block Public Access relaxed + a bucket policy — CloudFront
  (Day 101) is the production-correct way to add HTTPS + caching in front of it.

## Lab (2h)

### Part 1 — Bucket basics and versioning (30 min)
1. `aws s3 mb s3://fresher-lab-<unique-suffix>` (bucket names are globally unique — use
   your account id or a random suffix).
2. Enable versioning: `aws s3api put-bucket-versioning --bucket <bucket> --versioning-
   configuration Status=Enabled`.
3. Upload a file, overwrite it, then `aws s3api list-object-versions --bucket <bucket>`
   — see both versions. Delete the object (`aws s3 rm`), then list versions again —
   confirm it's a delete marker, not a purge; restore by deleting the delete marker.

### Part 2 — Lifecycle and encryption (30 min)
4. `aws s3api put-bucket-encryption --bucket <bucket> --server-side-encryption-
   configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":
   "AES256"}}]}'`.
5. Write a lifecycle JSON (`lifecycle.json`): transition objects with prefix `logs/` to
   `STANDARD_IA` after 30 days, expire after 180. Apply: `aws s3api put-bucket-
   lifecycle-configuration --bucket <bucket> --lifecycle-configuration file://lifecycle.json`.
6. Verify: `aws s3api get-bucket-lifecycle-configuration --bucket <bucket>`.

### Part 3 — Presigned URLs and static site (40 min)
7. Upload a private object; generate a presigned URL: `aws s3 presign
   s3://<bucket>/private-file.txt --expires-in 300`; open it in a browser within and
   after the 5-minute window — confirm expiry works.
8. Create a second bucket for static hosting; upload a simple `index.html`; enable
   website hosting (`aws s3api put-bucket-website`); relax Block Public Access on this
   bucket only, and attach a bucket policy allowing `s3:GetObject` to `*`.
9. Fetch the website endpoint URL (`aws s3api get-bucket-website` + the standard
   `<bucket>.s3-website-<region>.amazonaws.com` pattern) and `curl` it — confirm the
   page loads over plain HTTP (no TLS yet — Day 101 fixes that).

### Part 4 — Cleanup (mandatory, 20 min)
10. Empty and delete both buckets: `aws s3 rm s3://<bucket> --recursive` (must also
    remove all versions for a versioned bucket — `aws s3api delete-objects` looping
    over `list-object-versions` output, or use `aws s3 rb --force` where supported),
    then `aws s3 rb s3://<bucket>`.
11. Confirm: `aws s3 ls` shows neither bucket.

**Definition of done:** versioning + delete-marker behavior demonstrated · lifecycle
rule applied and verified · presigned URL expiry proven · static site served
successfully · both buckets fully emptied and deleted.
