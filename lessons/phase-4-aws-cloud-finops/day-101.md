## Theory (1h)

### A. DNS and Route 53 (15 min)
- Recall Day 16's DNS client-side view; today is the authoritative/hosting side.
  Route 53 = AWS's DNS service: hosted zones (public/private) hold record sets.
- Record types you'll actually use: A/AAAA (address), CNAME (alias to another name,
  can't coexist with other records at the same name), and Route 53's special **Alias**
  record — points at AWS resources (CloudFront, ALB, S3 website) at the zone apex,
  which plain CNAME cannot do, at no extra query cost.
- Registering a domain is optional for this course (cost); a **free** alternative for
  the lab is to skip real registration and demonstrate the mechanics with a subdomain
  of a domain you already own, or a hosted zone without external delegation.

### B. ACM certificates (15 min)
- AWS Certificate Manager issues free public TLS certs for use with CloudFront, ALB,
  API Gateway — cannot be used directly on a raw EC2 instance (no private key export).
- Validation methods: DNS validation (add a CNAME record — automatable, preferred) vs
  email validation (manual, avoid).
- **Region matters**: a cert for CloudFront must be requested in `us-east-1` regardless
  of where your other resources live — a classic gotcha.

### C. CloudFront (15 min)
- CDN: caches content at edge locations close to users, reduces origin load/latency,
  and is the standard way to add HTTPS in front of an S3 static site (S3 website
  endpoints are HTTP-only, as seen Day 99).
- Origin types: S3 (via Origin Access Control — OAC — so the bucket stays private and
  only CloudFront can read it) vs custom origin (ALB, EC2, any HTTP server).
- Cache behavior basics: TTLs, cache keys (query strings/headers/cookies), invalidations
  (`aws cloudfront create-invalidation`) — invalidations cost money at volume, so
  versioned filenames are the cheaper cache-busting pattern in practice.

### D. Tying it together (15 min)
- Full chain for today's lab: S3 bucket (private, OAC) → CloudFront distribution (with
  ACM cert) → Route 53 Alias record → custom subdomain, all HTTPS.
- Order of operations matters: request the cert first (validation takes minutes), then
  the distribution (references the cert), then the DNS record (references the
  distribution) — building out of order means waiting on each dependency anyway.

## Lab (2h)

### Part 1 — Private bucket + OAC (30 min)
1. Recreate a static-site bucket (Day 99 pattern) but keep Block Public Access **fully
   on** this time — no public bucket policy.
2. Note the bucket's ARN and region; you'll wire it to CloudFront next, which will
   generate the bucket policy for you via OAC.

### Part 2 — ACM certificate (25 min)
3. If you have a real domain available: `aws acm request-certificate --domain-name
   lab.yourdomain.com --validation-method DNS --region us-east-1`; retrieve the
   validation CNAME (`aws acm describe-certificate`) and add it to your Route 53 hosted
   zone (or your registrar if the zone lives elsewhere).
4. If no real domain is available: skip real validation and instead document the exact
   steps and commands in `docs/aws-network/dns-tls-notes.md` — the CLI syntax and
   ordering is the learning objective either way.
5. Wait for `Status: ISSUED` (`aws acm describe-certificate --query
   'Certificate.Status'`) before proceeding.

### Part 3 — CloudFront distribution (35 min)
6. Create a distribution with the S3 bucket as origin, Origin Access Control enabled,
   and (if you have a validated cert) the custom domain + ACM cert attached; otherwise
   use the default `*.cloudfront.net` domain to complete the mechanics.
   `aws cloudfront create-distribution --distribution-config file://dist-config.json`.
7. Confirm the bucket policy CloudFront generated (`aws s3api get-bucket-policy`) —
   grants `cloudfront.amazonaws.com` read access scoped to this specific distribution's
   ARN via a condition, not a blanket public grant.
8. `curl -I https://<distribution-domain>.cloudfront.net` — confirm HTTPS works and
   TLS is served by CloudFront, not S3.

### Part 4 — Route 53 record (20 min, if using a real domain)
9. Create/confirm a hosted zone; add an Alias A record pointing your subdomain at the
   CloudFront distribution: `aws route53 change-resource-record-sets --hosted-zone-id
   <zone-id> --change-batch file://alias-record.json` (Alias target = the distribution's
   domain name, hosted zone id `Z2FDTNDATAQYW2` — CloudFront's fixed alias zone id).
10. `dig lab.yourdomain.com` and `curl -I https://lab.yourdomain.com` — confirm
    end-to-end resolution and HTTPS.

### Part 5 — Teardown (mandatory, 20 min)
11. Delete the Route 53 record (if created), disable then delete the CloudFront
    distribution (`update-distribution` to set `Enabled: false`, wait for
    `Deployed`, then `delete-distribution` with matching ETag), delete the ACM
    certificate, empty and delete the S3 bucket.
12. Confirm `aws cloudfront list-distributions` and `aws acm list-certificates` show no
    lab resources remaining.

**Definition of done:** static content served over HTTPS via CloudFront with a private
(OAC-only) S3 origin · ACM cert requested in `us-east-1` regardless of other resource
regions · (if applicable) custom domain resolves via Route 53 Alias · full teardown
verified, including the disable-before-delete CloudFront sequence.
