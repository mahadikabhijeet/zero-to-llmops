## Theory (1h)

### A. GCP's organizing structure (15 min)
| AWS | Azure | GCP | Notes |
|---|---|---|---|
| Account | Subscription | Project | GCP's Project is the *primary* billing+resource boundary, more granular than an AWS account — teams often have dozens of projects |
| Organization | Management Group | Organization | same multi-tenant-governance idea, one level up from Project |
| Resource Group | Resource Group | (no strong equivalent) | GCP resources belong directly to a Project; there's no mandatory sub-grouping layer like Azure's RG |
| IAM Role/Policy | RBAC Role Assignment | IAM Role Binding | GCP IAM is resource-hierarchy-based (Org→Folder→Project→Resource), policies inherit downward by default |

- Free tier: GCP's "Always Free" tier (small persistent amounts, e.g. one f1-micro VM in
  specific regions) differs structurally from AWS's mostly 12-month-limited free tier —
  worth noting for anyone actually choosing a learning cloud on budget grounds.

### B. IAM differences worth knowing (15 min)
- GCP IAM roles are three-tiered: **Basic** (Owner/Editor/Viewer — broad, legacy,
  avoid in real work), **Predefined** (service-specific, like AWS managed policies), and
  **Custom** (like AWS customer-managed policies).
- Policy inheritance flows down the resource hierarchy automatically (Org→Folder→
  Project→Resource) — there's no equivalent automatic inheritance in AWS IAM (AWS
  Organizations SCPs are a *ceiling*, not additive inheritance the same way).
- Service Accounts in GCP are themselves both an identity *and* a resource you can grant
  access to — conceptually close to an IAM role, but usable more like a user identity
  for workloads (a subtlety worth a sentence, not a deep dive today).

### C. GKE vs EKS/AKS (15 min)
| AWS (EKS) | Azure (AKS) | GCP (GKE) | Notes |
|---|---|---|---|
| Managed control plane (paid) | Managed control plane (free) | Managed control plane (free tier eligible; Autopilot mode fully managed nodes too) | GKE originated Kubernetes itself (Google open-sourced it) — historically the most mature managed offering |
| Managed node group | Node pool | Node pool | same term as Azure, coincidentally |
| IRSA | Workload Identity | Workload Identity | GCP's is literally called the same name Azure borrowed — same OIDC-federation pattern all three clouds converged on |
| Standard mode | — | **Autopilot mode** | GKE Autopilot manages nodes entirely (pay per pod resource, not per node) — no direct AWS/Azure equivalent yet, worth knowing as GCP's differentiator |

### D. When-which-cloud decision framework (15 min)
- Not "which is best" — "which fits this constraint": existing team skillset, existing
  enterprise agreement/spend commitment, specific managed-service needs (e.g. BigQuery
  for GCP-shop analytics, deep AWS-native service breadth for AWS shops), and regulatory/
  data-residency requirements.
- BigQuery (mention only): serverless data warehouse, SQL over massive datasets,
  pay-per-query-scanned pricing — GCP's most commonly cited "reason to pick GCP"
  differentiator in job postings; know the name and one sentence, not the internals.
- The honest fresher answer in an interview: "I'm AWS-deep with working fluency in
  Azure/GCP core concepts, and I can ramp on either quickly because the underlying
  patterns — IAM, VPC/VNet, managed k8s, object storage — are the same shape everywhere."

## Lab (2h)

### Part 1 — Project + IAM (25 min)
1. Create a GCP free-tier account/project (if not already done): `gcloud projects
   create fresher-project-<suffix>`; `gcloud config set project fresher-project-<suffix>`.
2. `gcloud iam service-accounts create fresher-sa --display-name "fresher lab SA"`;
   `gcloud projects add-iam-policy-binding fresher-project-<suffix> --member
   "serviceAccount:fresher-sa@fresher-project-<suffix>.iam.gserviceaccount.com" --role
   "roles/viewer"` — a predefined role, mirroring Day 93's least-privilege habit.

### Part 2 — GKE cluster + the same Helm chart, again (55 min)
3. Enable required APIs: `gcloud services enable container.googleapis.com`.
4. Create a small Autopilot cluster (simplest free-tier-friendly path, no node-pool
   sizing needed): `gcloud container clusters create-auto fresher-gke --region
   <region>`.
5. `gcloud container clusters get-credentials fresher-gke --region <region>`;
   `kubectl get nodes`.
6. `helm upgrade --install fresher-project ./charts/fresher-project --set
   image.repository=<accessible-registry>/fresher-project --set image.tag=latest` —
   third cloud, same unmodified chart (this is the punchline of Days 113–115).
7. `kubectl expose deployment fresher-project --type=LoadBalancer --port=80`; wait for
   external IP; `curl` it.

### Part 3 — Workload Identity glance + BigQuery mention (20 min)
8. `gcloud container clusters describe fresher-gke --region <region> --format
   "value(workloadIdentityConfig.workloadPool)"` — confirm Workload Identity is enabled
   by default on Autopilot; compare to Day 104/114's federation pattern (name only,
   don't build the binding today).
9. `bq ls` (if the BigQuery CLI is available) or just read the console's BigQuery
   sandbox page for 5 minutes — note one query example from the public datasets in your
   docs file, no analysis required.

### Part 4 — Decision-framework writeup and final table (15 min)
10. Complete `docs/cloud-mapping/decision-framework.md`: the four-column comparison
    table (extend Day 113/114's tables with GKE's row), plus 3–4 sentences on when
    you'd pick each cloud given a hypothetical constraint (team skill, cost model,
    specific managed service need).

### Part 5 — Teardown (mandatory, 5 min)
11. `gcloud container clusters delete fresher-gke --region <region> --quiet`; delete the
    service account; confirm `gcloud container clusters list` is empty.

**Definition of done:** GKE Autopilot cluster created and the unmodified Helm chart
deployed successfully — third cloud, zero chart changes · IAM policy binding created
using a predefined role · decision-framework doc completed with the full 3-cloud table ·
cluster and service account deleted and confirmed gone.
