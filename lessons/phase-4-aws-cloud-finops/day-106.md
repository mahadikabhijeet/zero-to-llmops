## Theory (1h)

### A. CloudWatch Metrics (15 min)
- Every AWS service publishes metrics automatically (namespace + metric name +
  dimensions, e.g. `AWS/EC2`, `CPUUtilization`, dimension `InstanceId`); custom metrics
  via `aws cloudwatch put-metric-data` for anything app-specific.
- Metric math and statistics (avg/sum/min/max/percentiles) over a period — percentiles
  (p99) matter more than averages for latency (recall: an average hides tail pain, a
  concept Phase 5's SLO work will lean on hard).
- Retention: 1-minute granularity metrics keep detail for 15 days, then progressively
  coarsen — design dashboards knowing old data loses resolution.

### B. CloudWatch Logs and Alarms (15 min)
- Log groups (one per source, e.g. `/aws/lambda/<fn>`, `/ecs/<service>`) → log streams;
  retention is *infinite by default* until you set it — an easy forgotten-cost trap.
- CloudWatch Logs Insights: a query language over log groups (`fields`, `filter`,
  `stats`) — faster than grepping raw log exports for ad-hoc investigation.
- Alarms: metric + threshold + comparison + evaluation periods → state (OK/ALARM/
  INSUFFICIENT_DATA) → action (SNS notification, Auto Scaling action). Composite alarms
  combine multiple alarms with AND/OR logic.

### C. Dashboards (10 min)
- A dashboard is just a JSON layout of widgets (metric graphs, log-insights queries,
  text) — version it (`aws cloudwatch put-dashboard --dashboard-body file://
  dash.json`) instead of clicking it together by hand, same "infra as data" instinct as
  Terraform.

### D. CloudTrail and Config (20 min)
- CloudTrail: an audit log of **every API call** made in the account (who, what, when,
  from where) — Management events (control-plane, e.g. "who created this bucket") are
  free/on by default for 90 days in Event History; a Trail persists everything to S3
  long-term.
- This answers "who deleted my instance" — the first thing you check in a security
  incident or a mystery-teardown investigation.
- AWS Config: continuously records resource *configuration* (not just API calls) and
  evaluates it against rules (e.g. "is any S3 bucket public?") — compliance-as-code,
  distinct from CloudTrail's who-did-what focus. Mention only today (has its own cost
  per config item — don't leave it running past the lab).

## Lab (2h)

### Part 1 — Metrics and a custom metric (30 min)
1. Launch one small EC2 instance (Day 94 pattern, restricted SSH SG, teardown planned).
2. `aws cloudwatch get-metric-statistics --namespace AWS/EC2 --metric-name
   CPUUtilization --dimensions Name=InstanceId,Value=<id> --start-time <1h-ago>
   --end-time <now> --period 300 --statistics Average Maximum`.
3. Publish a custom metric from inside the instance: `aws cloudwatch put-metric-data
   --namespace FresherApp --metric-name RequestCount --value 1` (repeat a few times),
   then retrieve it back with `get-metric-statistics`.

### Part 2 — Logs and Insights (30 min)
4. Reuse a Lambda from Day 102 (or redeploy `fresher-hello`); invoke it a few times to
   generate log entries; set retention explicitly: `aws logs put-retention-policy
   --log-group-name /aws/lambda/fresher-hello --retention-in-days 7`.
5. Run a Logs Insights query: `fields @timestamp, @message | filter @message like /START/
   | sort @timestamp desc | limit 20` via `aws logs start-query` / `get-query-results`.

### Part 3 — Alarms and dashboard (35 min)
6. Create an SNS topic and email subscription for alerts (confirm the subscription via
   the emailed link).
7. Create an alarm: `aws cloudwatch put-metric-alarm --alarm-name high-cpu
   --metric-name CPUUtilization --namespace AWS/EC2 --dimensions
   Name=InstanceId,Value=<id> --statistic Average --period 300 --threshold 70
   --comparison-operator GreaterThanThreshold --evaluation-periods 1
   --alarm-actions <sns-topic-arn>`.
8. Stress the instance briefly (`yes > /dev/null &` for a minute, then kill it) to
   trigger ALARM state; confirm the email/notification arrives; then let it return to OK.
9. Build a small dashboard JSON with the CPU widget + the custom metric widget;
   `aws cloudwatch put-dashboard --dashboard-name fresher-dash --dashboard-body
   file://dash.json`.

### Part 4 — CloudTrail lookback (15 min)
10. `aws cloudtrail lookup-events --lookup-attributes
    AttributeKey=EventName,AttributeValue=RunInstances --max-results 5` — find the
    event for the instance you launched in Part 1; note the `userIdentity` field.

### Part 5 — Teardown (mandatory, 10 min)
11. Delete the alarm, dashboard, SNS topic/subscription, log group (or let retention
    expire — deleting is faster for lab hygiene), and terminate the EC2 instance.
12. Confirm `aws cloudwatch describe-alarms` and `aws ec2 describe-instances
    --filters "Name=instance-state-name,Values=running"` are empty.

**Definition of done:** custom metric published and retrieved · Logs Insights query run
successfully · alarm fired and notified on real threshold breach · dashboard JSON
version-controllable and applied · CloudTrail used to answer "who launched this" · all
lab resources deleted.
