## Theory (1h)

### A. EKS architecture (15 min)
- EKS = AWS-managed control plane (API server, etcd, scheduler) — you don't see or
  patch it; you bring/manage the **data plane** (worker nodes).
- Compare to Phase 3's kind cluster: same Kubernetes API and `kubectl` you already
  know — the control plane being managed is the only structural difference at this
  layer; your Helm chart doesn't change.
- `aws eks update-kubeconfig --name <cluster> --region <region>` wires `kubectl` to the
  EKS API server using your IAM identity (EKS maps IAM principals to Kubernetes RBAC
  via the `aws-auth` ConfigMap or, on newer clusters, EKS access entries).

### B. Node groups (15 min)
- Managed node group: AWS handles the ASG of worker EC2 instances (patching AMI
  versions, draining on update) — the free-tier-friendliest way to run compute-backed
  EKS nodes for learning.
- Fargate profiles: an alternative data plane with no nodes to manage at all
  (namespace/label-selector based) — mention as the serverless option, use managed
  nodes today since Day 103 already covered Fargate mechanics.
- Node group sizing directly drives cost — this is an always-on EC2 fleet even when
  idle; teardown discipline is non-negotiable here more than almost anywhere else in
  this phase.

### C. IRSA — IAM Roles for Service Accounts (15 min)
- Problem: pods need AWS permissions (e.g. read S3) without embedding long-lived keys
  or over-granting the whole node's role to every pod on it.
- IRSA: OIDC identity provider tied to the cluster + an IAM role with a trust policy
  scoped to a specific Kubernetes ServiceAccount (namespace + name) → pods using that
  ServiceAccount get temporary, scoped AWS credentials automatically via projected
  tokens.
- This is the cloud-native evolution of the EC2-instance-profile pattern from Day 94/103
  — same least-privilege idea, now scoped to pod identity instead of node identity.

### D. Connecting Phase 3 skills (15 min)
- Everything from Days 61–90 (Deployments, Services, Ingress, ConfigMaps/Secrets,
  probes, Helm) applies unchanged — EKS is just a different `kubectl` context.
- New pieces specific to cloud: the AWS Load Balancer Controller (turns Kubernetes
  `Ingress`/`Service type=LoadBalancer` into real ALBs/NLBs) and the EBS CSI driver (for
  PVCs backed by real EBS volumes) — both installed as one-time cluster add-ons, often
  via Helm themselves.

## Lab (2h)

### Part 1 — Cluster creation (30 min)
1. Reuse Day 96/97's VPC (or a fresh minimal one with public+private subnets across 2
   AZs — EKS requires this topology).
2. `aws eks create-cluster --name fresher-eks --role-arn <cluster-role-arn>
   --resources-vpc-config subnetIds=<priv-a>,<priv-b>,<pub-a>,<pub-b>`; poll
   `describe-cluster` until `ACTIVE` (this takes ~10-15 min — read ahead while waiting).
3. `aws eks update-kubeconfig --name fresher-eks --region <region>`; `kubectl get
   nodes` (empty — no node group yet).

### Part 2 — Node group (25 min)
4. `aws eks create-nodegroup --cluster-name fresher-eks --nodegroup-name fresher-ng
   --node-role <node-role-arn> --subnets <priv-a> <priv-b> --instance-types t3.small
   --scaling-config minSize=1,maxSize=2,desiredSize=1`.
5. Poll until `ACTIVE`; `kubectl get nodes` — confirm 1 node Ready.

### Part 3 — IRSA setup (25 min)
6. `eksctl utils associate-iam-oidc-provider --cluster fresher-eks --approve` (or the
   equivalent `aws eks` OIDC-provider commands if not using eksctl).
7. Create an IAM role with a trust policy scoped to `system:serviceaccount:default:
   fresher-sa`; attach a narrow S3-read policy; create the matching Kubernetes
   ServiceAccount annotated with the role ARN
   (`eks.amazonaws.com/role-arn`).
8. Run a debug pod using `fresher-sa`; from inside it, confirm `aws sts
   get-caller-identity` resolves to the IRSA role, and `aws s3 ls` works without any
   mounted static credentials.

### Part 4 — Deploy the project's Helm chart (30 min)
9. `helm upgrade --install fresher-project ./charts/fresher-project --set
   image.repository=<ecr-repo-uri> --set image.tag=latest` (reuse the ECR image pushed
   Day 103, and the chart authored Day 75).
10. `kubectl get pods,svc,ingress` — confirm rollout healthy; if an Ingress is defined,
    check whether the AWS Load Balancer Controller add-on is needed (note it, install
    only if time allows — otherwise document as a follow-up).
11. Port-forward or use a NodePort/temporary LB to confirm the app responds.

### Part 5 — Teardown (mandatory, 20 min)
12. `helm uninstall fresher-project`; delete the node group
    (`aws eks delete-nodegroup`, wait for completion); then delete the cluster
    (`aws eks delete-cluster`); delete the IRSA role and ServiceAccount.
13. Confirm `aws eks list-clusters` and `aws eks list-nodegroups` show nothing left
    running.

**Definition of done:** EKS cluster + node group reached Active/Ready · IRSA proven (pod
gets scoped AWS creds with zero static keys) · Phase 3 Helm chart deployed successfully
onto EKS with the Day 103 image · full teardown verified.
