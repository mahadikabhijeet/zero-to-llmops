## Theory (1h)

### A. Rightsizing (15 min)
- Rightsizing = matching provisioned capacity to actual utilization — the single
  highest-leverage, lowest-risk optimization, and usually the first thing a FinOps
  practitioner checks before touching commitments.
- CloudWatch (Day 106) is the data source: sustained low CPU/memory/network on an
  instance is the signal; Compute Optimizer (AWS's own recommendation engine, reads
  14+ days of CloudWatch history) automates this analysis instead of eyeballing graphs.
- Rightsizing isn't just "make smaller" — it also catches *undersized* resources
  causing performance problems that get worked around with more instances instead of
  correctly sized ones (a subtler, often-missed waste pattern).

### B. Reserved Instances, Savings Plans, Spot (20 min)
- **Reserved Instances (RIs)**: commit to a specific instance family/region for
  1 or 3 years for a discount (up to ~72%); Standard RIs are cheaper but inflexible,
  Convertible RIs allow instance-family changes at a smaller discount.
- **Savings Plans**: commit to a $/hour spend level (not a specific instance) for
  1 or 3 years — Compute Savings Plans apply across instance family/region/even
  Fargate/Lambda; more flexible than RIs, now the generally preferred commitment
  vehicle for new workloads.
- **Spot Instances**: bid on spare capacity for up to ~90% discount; can be reclaimed
  with a 2-minute warning — fits stateless, interruption-tolerant workloads (CI
  runners, batch jobs, some Kubernetes worker nodes) but never a database or anything
  stateful without careful architecture.
- The FinOps decision rule: **on-demand for unpredictable/spiky, commitments for
  known-steady baseline, spot for interruption-tolerant** — most real workloads are a
  deliberate mix of all three, not one choice.

### C. Storage tiering as a cost lever (10 min)
- Recall Day 99's S3 lifecycle rules — today reframes them explicitly as a FinOps
  lever: the cost delta between Standard and Glacier Deep Archive can be 20x+ for cold
  data nobody's accessed in months.
- EBS volumes attached to stopped instances (Day 94's gotcha) and orphaned snapshots
  are classic "silent leak" costs — a recurring FinOps audit line item, not a one-time
  fix.
- gp3 vs gp2 EBS: gp3 decouples IOPS/throughput from size and is usually cheaper for
  the same performance — a rightsizing opportunity specific to storage, not just compute.

### D. Kubernetes cost visibility (15 min)
- The hard problem: a node's cost is easy to see (it's an EC2 instance), but
  *attributing* that cost to the namespace/deployment/team consuming it requires
  understanding requests/limits and actual usage per pod — plain CloudWatch/Cost
  Explorer stop at the node boundary.
- Kubecost (or OpenCost, its open-source core) ingests cluster metrics (Prometheus —
  foreshadowing Phase 5) and cloud billing data to show cost per namespace/deployment/
  label — the k8s-native equivalent of Day 117's tagging-based allocation.
- Idle/unallocated cost in a cluster (requested-but-unused capacity, recall Day 69's
  requests/limits) is usually the single biggest visible waste once Kubecost is
  running — a direct callback to getting resource requests right in Phase 3.

## Lab (2h)

### Part 1 — Rightsizing pass (30 min)
1. If any EC2/RDS resources are running from recent labs, pull CloudWatch utilization
   (Day 106 pattern) for the last few hours; otherwise use Compute Optimizer's
   recommendations page (works off historical account data even with nothing currently
   running) — screenshot or note 2–3 real recommendations for `docs/finops/rightsizing.md`.
2. Audit for orphaned resources: `aws ec2 describe-volumes --filters
   "Name=status,Values=available"` (unattached EBS — pure waste), `aws ec2
   describe-snapshots --owner-ids self` (check ages), `aws ec2 describe-addresses`
   (Elastic IPs not attached to a running instance — billed while idle). Delete/release
   anything found and log it in the doc.

### Part 2 — Commitment modeling (30 min)
3. Using AWS's public pricing pages or the Pricing Calculator, model three scenarios
   for a hypothetical steady `t3.medium` workload running 24/7 for a year: on-demand
   cost, 1-year Compute Savings Plan cost, 1-year Standard RI cost — build the
   comparison table in `docs/finops/commitments.md` with real numbers and % savings.
4. Write the decision: at what utilization/steadiness threshold would you actually
   recommend a commitment vs staying on-demand for this course's project workload today
   (be honest — a learning project running a few hours a week should stay on-demand;
   explain why).

### Part 3 — Storage cost audit (20 min)
5. Revisit the Day 99/117 S3 lifecycle rules; add a Glacier Deep Archive transition
   tier for anything older than 365 days to the lifecycle JSON; recompute the
   theoretical storage cost delta for a 100GB bucket under Standard-only vs the full
   tiered lifecycle.
6. If any gp2 volumes exist, note the gp3 migration path (`aws ec2 modify-volume
   --volume-type gp3`) as a no-downtime cost win; log the expected % savings.

### Part 4 — Kubecost on the cluster (30 min)
7. On a kind cluster (Day 61) or a small live EKS cluster if still available, install
   Kubecost via Helm: `helm repo add kubecost https://kubecost.github.io/cost-analyzer/
   && helm upgrade --install kubecost kubecost/cost-analyzer --namespace kubecost
   --create-namespace`.
8. Port-forward the UI (`kubectl port-forward -n kubecost svc/kubecost-cost-analyzer
   9090:9090`); explore cost-by-namespace and cost-by-deployment views for the
   project's Helm-deployed workload (Day 78/104).
9. Identify one pod with requests set much higher than actual usage (Kubecost flags
   this directly) and right-size its `resources.requests` in the chart's `values.yaml`
   — log the before/after in `docs/finops/kubecost-findings.md`.

### Part 5 — Teardown + synthesis (10 min)
10. `helm uninstall kubecost -n kubecost`; delete any test cluster/instances used.
11. Commit `docs/finops/` with all four sub-documents from today plus Day 117's.

**Definition of done:** rightsizing/orphan audit performed with real findings logged ·
commitment cost comparison table built with real numbers and an honest recommendation ·
storage tiering delta computed · Kubecost installed, cost-by-namespace explored, and one
real right-sizing fix applied to the chart · everything torn down and documented.
