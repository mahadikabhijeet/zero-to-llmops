## Theory (1h)

### A. Why modularize now (15 min)
- Recall Day 80: a module is a reusable, parameterized Terraform package (inputs via
  `variables.tf`, outputs via `outputs.tf`) — yesterday's flat stack becomes tomorrow's
  reusable building blocks.
- Boundary principle: one module per *concern that changes independently* — network
  rarely changes shape, database schema/sizing changes more often, compute
  (ECS/EKS-facing) changes with every deploy. Separate state per module (or careful use
  of `terraform_remote_state` data sources between them) limits blast radius.
- This is also how a real team divides ownership — network/platform team owns the
  network module, app teams consume its outputs.

### B. Module design for this project (15 min)
- `modules/network`: VPC, subnets (public/private ×2 AZ), IGW, NAT, route tables —
  Day 107's resources, parameterized (CIDR, AZ count, project name).
- `modules/compute`: ECS cluster + task definition + service (Day 103) OR an EKS
  cluster + node group (Day 104) — pick one as the "live" target per the project's
  actual choice; document the other as an alternate module stub.
- `modules/database`: RDS instance + subnet group + SG (Day 100), parameterized
  engine/size/credentials (via variables, never hardcoded).
- `modules/storage`: the project's S3 bucket(s) (Day 99) with lifecycle/versioning/
  encryption baked in as sensible defaults, overridable via variables.

### C. Composing modules in a root (15 min)
- Root `main.tf` calls each module, passing outputs from one as inputs to another
  (e.g. `modules.network.private_subnet_ids` into `modules.database.subnet_ids`) —
  this is how Terraform expresses the dependency graph declaratively.
- `terraform graph` visualizes this dependency chain; use it once to sanity-check no
  accidental coupling exists.
- Versioning modules: today they live in the same repo (local path modules,
  `source = "../modules/network"`); mention registry/git-sourced modules with version
  pins as the next step once modules are shared across projects.

### D. State strategy for a module set (15 min)
- Options: one state file for the whole root (simplest, what we do today) vs one state
  per module (more isolation, more `terraform_remote_state` plumbing) — start simple,
  split later if team size or blast-radius concerns justify it.
- `terraform state list` to inspect what's tracked; `terraform state mv` for
  refactoring resource addresses without destroy/recreate (useful when moving resources
  *into* a module from a flat config, exactly today's situation).

## Lab (2h)

### Part 1 — Carve out the network module (35 min)
1. Create `terraform/modules/network/{main,variables,outputs}.tf`; move the VPC/subnet/
   IGW/route-table resources from Day 107's root into it, parameterizing CIDR and AZ
   list.
2. In the root, replace those resources with a `module "network" { source =
   "./modules/network" ... }` block. Use `terraform state mv` to re-point existing
   state entries to the new module addresses instead of destroy/recreate:
   `terraform state mv aws_vpc.main module.network.aws_vpc.main` (repeat per resource).
3. `terraform plan` — confirm **zero changes** (proof the refactor didn't touch real
   infrastructure, just its representation in state).

### Part 2 — Compute, database, storage modules (55 min)
4. Create `modules/compute` wrapping Day 103's ECS cluster/task-def/service (or Day
   104's EKS+node-group, per your project's chosen path) as a module with variables for
   image URI, desired count, and instance/task sizing.
5. Create `modules/database` wrapping Day 100's RDS instance + subnet group + SG,
   variables for engine, instance class, and credentials (reference an
   `aws_secretsmanager_secret` or a variable marked `sensitive = true` — never a literal
   password in `.tf` files).
6. Create `modules/storage` wrapping the project's S3 bucket with lifecycle/versioning/
   encryption defaults.
7. Wire the root: `module "compute"` consumes `module.network.private_subnet_ids`;
   `module "database"` consumes the same plus a DB security group referencing
   `module.compute`'s SG (SG-to-SG, recall Day 97/100).

### Part 3 — Validate the whole graph (20 min)
8. `terraform fmt -recursive && terraform validate`. `terraform graph | dot -Tpng >
   graph.png` (or paste into any Graphviz viewer) — visually confirm network → database
   and network → compute edges, no compute↔database coupling that shouldn't exist.
9. `terraform plan` against the full module set — review carefully; `terraform apply`
   if you're keeping this environment running into Day 109–110 (otherwise plan-only
   today and apply fresh next session — note your choice).

### Part 4 — Documentation (10 min)
10. Write `terraform/README.md`: module list, what each owns, the dependency graph
    image, and the state strategy decision (single root state, documented reasoning).
11. Commit everything except `.tfstate`/`.terraform/` (confirm `.gitignore` covers
    both): `git add terraform/ && git commit -m "feat: modularize project infra
    (network/compute/database/storage)"`.

**Definition of done:** four modules exist with clean variable/output contracts ·
`state mv` refactor produced a zero-diff plan · dependency graph reviewed and matches
intent · README documents the module set and state strategy · committed (state files
excluded).
