## Theory (1h)

### A. AKS vs EKS (15 min)
| AWS (EKS) | Azure (AKS) | Notes |
|---|---|---|
| Managed control plane | Managed control plane | AKS control plane is **free** (no hourly charge), unlike EKS's per-hour control-plane fee — a real cost difference worth naming |
| Managed node group | Node Pool | same idea — a scaled set of VMs as workers |
| IRSA (OIDC + IAM role trust) | Workload Identity (Entra Workload ID) | same underlying pattern: federated OIDC trust between a Kubernetes ServiceAccount and a cloud identity |
| `aws eks update-kubeconfig` | `az aks get-credentials` | both just populate `~/.kube/config` — `kubectl` itself is identical after that |

- The headline insight for a fresher: **`kubectl`, Helm, and your chart don't change at
  all** — everything from Phase 3 is portable. Only the cluster-creation and
  identity-federation commands differ per cloud.

### B. Azure DevOps glance (15 min)
- Azure DevOps = Boards (work tracking) + Repos (git, alternative to GitHub) + Pipelines
  (CI/CD, YAML-based like GitHub Actions) + Artifacts + Test Plans — a full suite vs
  GitHub's more unbundled ecosystem.
- Pipeline YAML shape is conceptually identical to GitHub Actions (recall Day 40–41):
  triggers → stages → jobs → steps; the vocabulary differs, the mental model doesn't.
- This course stays on GitHub Actions as the primary tool (already built, already
  public per Day 33) — today is recognition-level familiarity only, not a rebuild.

### C. Networking AKS vs EKS (10 min)
- AKS defaults to "kubenet" or "Azure CNI" networking (Azure CNI assigns pods real
  VNet IPs, closer to EKS's `awsvpc`-style pod networking); mention only — not a
  hands-on distinction today.
- Both clouds' managed k8s need a load-balancer-capable ingress path (Azure Load
  Balancer / AWS ALB Controller) to expose services externally — same shape as Day 104's
  add-on requirement.

### D. Closing the "one cloud deep, others mapped" thesis (20 min)
- The point of Days 113–115 is not competence in three clouds — it's proving that AWS
  depth (Days 92–111) *transfers*. A hiring manager cares whether you can ramp on
  whatever cloud their company uses; today's lab is the proof-of-transfer exercise.
- Recall the concept-mapping tables built Day 113 — today extends the same table with
  the container-orchestration row, and the lab proves it by actually deploying the same
  artifact (the Helm chart) with zero changes to the chart itself.

## Lab (2h)

### Part 1 — AKS cluster (35 min)
1. `az group create --name fresher-aks-rg --location <region>` (fresh RG for easy
   single-command teardown, per Day 113's pattern).
2. `az aks create --resource-group fresher-aks-rg --name fresher-aks --node-count 1
   --node-vm-size Standard_B2s --generate-ssh-keys` — note this takes several minutes;
   read ahead while waiting.
3. `az aks get-credentials --resource-group fresher-aks-rg --name fresher-aks`;
   `kubectl get nodes` — confirm Ready.

### Part 2 — Deploy the unchanged Helm chart (35 min)
4. `helm upgrade --install fresher-project ./charts/fresher-project --set
   image.repository=<any-public-or-accessible-registry>/fresher-project --set
   image.tag=latest` — reuse the exact chart from Day 75/104, no edits.
5. `kubectl get pods,svc` — confirm rollout healthy; if the image lives in ECR
   (private), either push a copy to Docker Hub/GHCR for this cross-cloud lab or note
   the cross-cloud registry-auth gap explicitly rather than spending the lab solving it.
6. Expose it: `kubectl expose deployment fresher-project --type=LoadBalancer --port=80`
   (Azure provisions an Azure Load Balancer automatically); poll `kubectl get svc` for
   an external IP; `curl` it.

### Part 3 — Workload Identity glance (20 min)
7. `az aks show --resource-group fresher-aks-rg --name fresher-aks --query
   oidcIssuerProfile.issuerUrl` — confirm OIDC issuer exists (enable it if not:
   `--enable-oidc-issuer` at creation or via update); compare mentally to Day 104's
   IRSA OIDC provider association — same mechanism, different vendor.
8. Do **not** build the full federated-identity credential chain today (time-boxed) —
   note the steps in `docs/cloud-mapping/aks-vs-eks.md` as "next if this becomes the
   primary cloud."

### Part 4 — Azure DevOps glance (10 min)
9. Log into Azure DevOps (free tier); create one organization/project; open the
   Pipelines section and read (don't build) one sample YAML pipeline template — note 3
   structural parallels to GitHub Actions in the docs file.

### Part 5 — Teardown + close the thesis (10 min, mandatory)
10. `az group delete --name fresher-aks-rg --yes --no-wait`; poll until gone.
11. Write the closing paragraph of `docs/cloud-mapping/aks-vs-eks.md`: what proved
    portable (chart, `kubectl` commands) vs what didn't (cluster creation syntax,
    registry auth, identity federation specifics) — this paragraph is today's real
    deliverable.

**Definition of done:** AKS cluster created and Helm chart deployed with zero chart
changes · service reachable via Azure's LoadBalancer · OIDC issuer confirmed present ·
Azure DevOps pipeline structure recognized and compared · full teardown via RG deletion
confirmed · closing "what transferred vs what didn't" paragraph written.
