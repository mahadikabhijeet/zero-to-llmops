## Theory (1h)

### A. RDS fundamentals (15 min)
- RDS = managed relational database (Postgres/MySQL/MariaDB/etc.) — AWS handles patching,
  backups, and (optionally) Multi-AZ failover; you manage schema, queries, and access.
- DB Subnet Group: RDS needs ≥2 subnets across ≥2 AZs even for a single-AZ instance —
  required for Multi-AZ upgrade later, no exceptions.
- Free tier: `db.t3.micro`, 20GB storage, single-AZ — always check current free-tier
  terms before choosing an engine/size.

### B. Networking a database correctly (15 min)
- RDS should live in **private subnets**, never internet-facing — connect only from
  application instances or a bastion, via SG-to-SG reference (same pattern as Day 97's
  bastion→private-instance rule).
- "Publicly accessible" flag at creation time is a hard gate — leave it `No`; combined
  with an SG that only allows the app tier's SG, this is the standard secure pattern.
- Parameter groups (engine config) and option groups (engine features) vs the instance
  itself — config lives outside the instance so it survives replacement.

### C. Backups, snapshots, and restore (15 min)
- Automated backups: point-in-time recovery within a retention window (1–35 days);
  manual snapshots: explicit, retained until you delete them, usable to restore into a
  **new** instance (RDS restore is always to a new endpoint, never in-place).
- Snapshot copy across regions/accounts is how DR plans work at this layer — mention
  only, not built today.

### D. DynamoDB basics (15 min)
- DynamoDB = managed NoSQL key-value/document store; no servers to size — you define a
  partition key (+ optional sort key) and it scales automatically.
- Capacity modes: on-demand (pay per request, good for unpredictable/learning workloads)
  vs provisioned (pay for reserved RCU/WCU, cheaper at steady high volume).
- Core CLI: `aws dynamodb create-table`, `put-item`, `get-item`, `query` (uses key
  conditions — efficient) vs `scan` (reads the whole table — expensive, avoid at scale).

## Lab (2h)

### Part 1 — Network prep (20 min)
1. Reuse or rebuild a VPC with ≥2 private subnets across 2 AZs (Day 96/97 script).
2. Create a DB subnet group: `aws rds create-db-subnet-group --db-subnet-group-name
   fresher-db-subnets --db-subnet-group-description "lab" --subnet-ids <priv-a> <priv-b>`.
3. Create a DB security group allowing inbound 5432 (Postgres) only from the app-tier
   SG (create a placeholder app SG if not reusing one).

### Part 2 — RDS provisioning and connection (50 min)
4. `aws rds create-db-instance --db-instance-identifier fresher-db --db-instance-class
   db.t3.micro --engine postgres --master-username fresheradmin --master-user-password
   <strong-password> --allocated-storage 20 --db-subnet-group-name fresher-db-subnets
   --vpc-security-group-ids <db-sg-id> --no-publicly-accessible --backup-retention-
   period 1`.
5. Poll `aws rds describe-db-instances --db-instance-identifier fresher-db --query
   'DBInstances[0].DBInstanceStatus'` until `available`; note the endpoint.
6. Launch an EC2 instance in a **public** subnet with the app-tier SG (needed to reach
   the private DB and be SSH-reachable); install a Postgres client (`dnf install -y
   postgresql15`); `psql -h <rds-endpoint> -U fresheradmin -d postgres` — confirm
   connectivity, run `\l` and `SELECT version();`.

### Part 3 — Snapshot + restore drill (30 min)
7. Create a table, insert a row. Take a manual snapshot: `aws rds create-db-snapshot
   --db-instance-identifier fresher-db --db-snapshot-identifier fresher-db-snap1`.
8. Restore it into a **new** instance: `aws rds restore-db-instance-from-db-snapshot
   --db-instance-identifier fresher-db-restored --db-snapshot-identifier
   fresher-db-snap1 --db-subnet-group-name fresher-db-subnets --vpc-security-group-ids
   <db-sg-id>`; once available, connect and confirm the row is present.

### Part 4 — DynamoDB quick tour (20 min)
9. `aws dynamodb create-table --table-name fresher-table --attribute-definitions
   AttributeName=id,AttributeType=S --key-schema AttributeName=id,KeyType=HASH
   --billing-mode PAY_PER_REQUEST`.
10. `put-item` two rows, `get-item` by key, `query` vs `scan` (time both mentally —
    note query needs a key condition, scan doesn't).

### Part 5 — Teardown (mandatory, 20 min)
11. Delete both RDS instances (skip final snapshot for the lab, but note in production
    you'd take one): `aws rds delete-db-instance --db-instance-identifier fresher-db
    --skip-final-snapshot`, same for `-restored`.
12. Delete the manual snapshot, DB subnet group, DynamoDB table, and terminate the EC2
    instance. Confirm `aws rds describe-db-instances` and `aws dynamodb list-tables`
    return empty/no lab resources.

**Definition of done:** RDS reachable only from the app-tier SG in a private subnet ·
snapshot restored successfully into a working new instance · DynamoDB query vs scan
demonstrated · all RDS/DynamoDB/EC2 resources deleted and verified.
