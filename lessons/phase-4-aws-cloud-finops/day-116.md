## Theory (1h)

### A. The "write once, run anywhere" myth (15 min)
- Kubernetes gives you workload portability (Days 113–115 proved the *chart* moves
  unchanged) — it does not give you infrastructure portability. Every Terraform
  provider block, every IAM model, every managed-database API is cloud-specific.
- Abstraction layers that promise full portability (some multi-cloud PaaS tools, generic
  Terraform "modules" claiming cross-cloud) typically hide complexity rather than remove
  it — you still hit cloud-specific edge cases the abstraction didn't anticipate, now
  with an extra layer to debug through.
- The honest framing: **applications** (containerized, cloud-agnostic APIs) can be
  portable; **infrastructure** rarely is without deliberate, costly abstraction
  investment most teams don't need.

### B. Egress economics (20 min)
- All three clouds: ingress (data coming in) is free; egress (data leaving to the
  internet or to another cloud) is billed, often the least-visible line item on a bill
  until it's large.
- Cross-cloud egress is typically *more* expensive than same-cloud cross-region
  transfer — a genuine cost argument against casual multi-cloud architectures ("just
  put the DB in GCP and the app in AWS" sounds flexible, costs real money at any scale).
- CDN/caching (recall Day 101's CloudFront) exists partly *because* egress is expensive
  — caching at the edge reduces origin egress, a cost lever as much as a performance one.
- Data gravity: large datasets (data warehouses, ML training sets) create inertia —
  moving them is expensive and slow, which quietly locks in cloud choice for
  data-heavy workloads more than compute choice ever does.

### C. Abstraction costs beyond money (10 min)
- Every abstraction layer (multi-cloud Terraform wrappers, generic PaaS) adds a
  debugging hop: when something breaks, you now troubleshoot the abstraction *and* the
  underlying cloud API — recall Day 73's troubleshooting playbook, which gets harder
  with more layers between symptom and cause.
- Team cognitive load: maintaining fluency across 3 clouds' IAM/networking/CLI quirks
  is real ongoing cost, not a one-time learning cost — this is why most companies pick
  one primary cloud and treat others as acquisition-driven exceptions, not strategy.

### D. Hybrid patterns worth knowing (15 min)
- On-prem + cloud (true hybrid): AWS Outposts / Azure Arc / GCP Anthos extend the
  cloud's control plane onto owned hardware — relevant for regulated/latency-sensitive
  workloads, not something this course builds.
- Multi-cloud-for-resilience (rare, expensive, usually only justified at extreme scale
  or extreme regulatory pressure) vs multi-cloud-by-accident (a company acquires
  another company already on a different cloud) — the second is far more common in
  practice than the first.
- DR-across-clouds vs DR-across-regions: recall Day 100/107's Multi-AZ mentions — most
  DR requirements are satisfiable with multi-region-same-cloud, which is dramatically
  simpler and cheaper than genuine multi-cloud DR.

## Lab (2h) — analysis and writing lab, not hands-on cloud today

### Part 1 — Cost-model comparison (35 min)
1. Look up current egress pricing (per-GB, first-tier bracket) for AWS, Azure, and GCP
   to the public internet; build a small table in `docs/cloud-mapping/multi-cloud-
   reality.md`.
2. Estimate: for a hypothetical 500GB/month egress workload, what's the annual cost
   difference between "all traffic same-cloud" vs "50% of traffic crosses to a second
   cloud for a dependency"? Show the arithmetic.

### Part 2 — Portability audit of your own project (40 min)
3. Walk the incremental project's stack (Terraform modules from Day 108, the Helm chart
   from Day 75/104) and classify every component as: **Portable as-is** (the Helm
   chart), **Portable with rework** (Terraform — same resources exist elsewhere, syntax
   differs), or **Cloud-locked** (anything using a fully proprietary managed service
   with no equivalent, e.g. a deeply AWS-specific serverless integration from Day 102).
4. Write one paragraph: if forced to migrate this project to Azure or GCP next month,
   what would take a day vs a week vs be a genuine redesign?

### Part 3 — Hybrid pattern scenarios (25 min)
5. Write short (3–4 sentence) answers to three scenario prompts: (a) a healthcare
   company needs on-prem data residency but wants cloud burst capacity — which pattern
   fits? (b) a startup acquires a company running on a different cloud — what's the
   pragmatic near-term move (migrate everything immediately vs run both for now)? (c)
   a company wants DR — is multi-region-same-cloud or multi-cloud the right first
   answer, and why?

### Part 4 — Synthesis (20 min)

7. Commit: `git add docs/cloud-mapping/ && git commit -m "docs: multi-cloud reality
