## Theory (1h)

### A. From manual VPC to Terraform (15 min)
- Everything built by hand on Days 96–97 (VPC, subnets, route tables, IGW) is
  expressible as `aws_vpc`, `aws_subnet`, `aws_route_table`, `aws_internet_gateway`
  resources — today converts muscle memory into code.
- Recall Day 79's HCL basics and Day 80's variables/outputs/modules — today's stack is
  the first "real" (non-toy) Terraform applied against a live account.
- `terraform import` exists for adopting hand-created resources into state, but today
  we build fresh and destroy — avoids state/reality drift from Days 96–97's leftovers.

### B. Remote state in S3 (15 min)
- Local state (`terraform.tfstate` on disk) doesn't work for teams or CI — it must live
  somewhere shared: an S3 bucket configured as the backend.
- Backend config (`backend "s3"` block): bucket, key (path within bucket), region;
  since Terraform 1.6+, native S3 state locking via `use_lockfile = true` is available
  as an alternative to a separate DynamoDB lock table — mention both, use whichever your
  installed Terraform version supports, document which one in the module README.
- State contains **sensitive values** (e.g. DB passwords) in plaintext by default —
  encrypt the state bucket (Day 99's SSE) and never commit `.tfstate` to git.

### C. Locking and why it matters (10 min)
- Without locking, two concurrent `apply` runs can corrupt state (race condition on the
  same resources) — locking makes `apply` wait or fail loudly instead of corrupting.
- `terraform force-unlock <lock-id>` exists for genuinely stuck locks (crashed process)
  — a manual escape hatch, not a routine command.

### D. Structuring the stack (20 min)
- Recall Day 80's module pattern: even a "flat" stack benefits from `variables.tf`,
  `outputs.tf`, `main.tf` separation — today is still single-root, full modularization
  is Day 108.
- `terraform fmt` / `validate` / `tflint` (Day 83) run before every commit — today makes
  that a habit against a real cloud target, not just kind/docker providers.
- Tagging every resource via a shared `default_tags` provider block (or a `locals.tags`
  map merged in) — sets up Day 117's FinOps tagging strategy early.

## Lab (2h)

### Part 1 — Bootstrap the backend (25 min)
1. Create the state bucket and (if using DynamoDB locking) the lock table manually,
   once, outside Terraform (a well-known chicken-and-egg exception — recall Day 81):
   `aws s3 mb s3://fresher-tfstate-<suffix>` + `aws s3api put-bucket-versioning
   ...Enabled` + `aws s3api put-bucket-encryption ...`; optionally `aws dynamodb
   create-table --table-name tf-locks --attribute-definitions
   AttributeName=LockID,AttributeType=S --key-schema AttributeName=LockID,KeyType=HASH
   --billing-mode PAY_PER_REQUEST`.
2. Document this bootstrap step in `terraform/aws-stack/README.md` — it's the one thing
   that can never itself be Terraform-managed on first run.

### Part 2 — Write the stack (55 min)
3. `terraform/aws-stack/main.tf`: provider block with a default tags map; `aws_vpc`
   (Day 96's CIDR plan), 2 public + 2 private `aws_subnet`, `aws_internet_gateway`,
   `aws_route_table` + `aws_route_table_association` for public.
4. Add `aws_security_group` (SSH restricted to your IP via a variable), and one
   `aws_instance` (free-tier type, latest Amazon Linux via an `aws_ami` data source —
   recall Day 80's data sources) with user-data installing nginx.
5. `variables.tf` for CIDR, instance type, allowed SSH CIDR; `outputs.tf` for instance
   public IP and VPC id.
6. Backend block: `backend "s3" { bucket = "fresher-tfstate-<suffix>" key =
   "aws-stack/terraform.tfstate" region = "<region>" dynamodb_table = "tf-locks" }`
   (or `use_lockfile = true` if on Terraform 1.6+ without DynamoDB).

### Part 3 — Init, plan, apply (25 min)
7. `terraform fmt && terraform validate`. `terraform init` — confirm it reports using
   the S3 backend.
8. `terraform plan -out=tfplan` — read every line; confirm resource count matches
   expectations before applying.
9. `terraform apply tfplan`; `curl http://$(terraform output -raw instance_public_ip)`
   confirms nginx is live.

### Part 4 — Prove locking works (10 min)
10. In a second terminal, run `terraform plan` while the first terminal holds an
    `apply` mid-flight (or manually run `terraform apply` twice back-to-back quickly) —
    observe the lock error message; then confirm normal operation resumes once the
    first completes.

### Part 5 — Teardown (mandatory, 15 min)
11. `terraform destroy` — confirm the plan removes everything before typing `yes`.
12. Manually empty and delete the state bucket and lock table (Terraform can't destroy
    its own backend) once you're fully done with this phase's Terraform work — or leave
    the backend live if Day 108 will reuse it (state your choice in the README).

**Definition of done:** VPC+subnets+SG+EC2 stack applied entirely via Terraform ·
state stored in S3 with locking proven to block a concurrent write · nginx reachable at
the instance's public IP · `destroy` run cleanly and confirmed via `aws ec2
describe-instances`.
