## Theory (1h)

### A. Why one cloud deep, others mapped (10 min)
- Recall the README's stated thesis: three clouds "in depth" in one course is
  unrealistic and not how freshers get hired. The goal here is fluency in the *concept*
  so a new cloud's docs become readable, not memorized service names.
- Every cloud solves the same problems (identity, compute, network isolation, storage,
  managed k8s) — today's method is deliberate: for each AWS concept already mastered,
  find and name its Azure counterpart.

### B. Account/organization structure (15 min)
| AWS | Azure | Notes |
|---|---|---|
| AWS Account | Subscription | billing + resource boundary |
| Organizations | Management Groups | multi-subscription governance |
| Resource (loose, tagged) | Resource Group | Azure **requires** grouping resources into an RG at creation — no equivalent-strength requirement in AWS |
| Region | Region | same concept; Azure also has "Availability Zones" within a region, same idea |

- Azure's Resource Group is a stronger organizing primitive than anything in AWS —
  deleting an RG deletes everything inside it, a genuinely useful and genuinely
  dangerous single command (`az group delete`).

### C. Identity: Entra ID vs IAM (15 min)
| AWS | Azure | Notes |
|---|---|---|
| IAM User | Entra ID user | Entra ID (formerly Azure AD) is org-directory-first, unlike IAM's account-scoped users |
| IAM Role | Managed Identity | system- or user-assigned identity for a resource, no keys — same idea as an EC2 instance profile |
| IAM Policy (JSON) | Azure RBAC Role Assignment | scope (subscription/RG/resource) + role definition, conceptually parallel to IAM's Resource+Action |
| Root account | Global Administrator (Entra ID role) | more org-directory flavored than AWS root |

- Key structural difference: Azure's identity system (Entra ID) is a full directory
  service by default (like on-prem Active Directory) — AWS IAM is deliberately *not* a
  directory service (that's what AWS SSO/IAM Identity Center bolts on separately).

### D. Networking, compute, storage (20 min)
| AWS | Azure | Notes |
|---|---|---|
| VPC | Virtual Network (VNet) | same CIDR/subnet model from Day 96 applies directly |
| Security Group | Network Security Group (NSG) | NSG applies at subnet **or** NIC level — AWS SG is instance/ENI-level only |
| Internet Gateway | (implicit — Public IP resource) | Azure has no separate IGW object; a Public IP attached to a resource is the whole story |
| EC2 | Virtual Machine (VM) | same instance-type-family idea (B-series ≈ t-series burstable) |
| EBS | Managed Disk | same snapshot concept |
| S3 | Blob Storage (Storage Account) | Storage Account is the parent resource; containers hold blobs — one more nesting level than S3's flat bucket model |

## Lab (2h)

### Part 1 — Account and RG setup (25 min)
1. Create an Azure free-tier account (if not already done); note the Subscription ID:
   `az account show --query id -o tsv` (after `az login`).
2. Create a resource group: `az group create --name fresher-rg --location <region>`.
3. `az account list-locations -o table` — compare naming to AWS regions (e.g.
   `centralindia` vs AWS's `ap-south-1`).

### Part 2 — Identity mapping drill (25 min)
4. `az ad signed-in-user show` — inspect your own Entra ID identity object.
5. Create a resource-group-scoped role assignment for a test user or your own account
   using a built-in role (`Reader`): `az role assignment create --assignee <user-or-sp>
   --role Reader --resource-group fresher-rg`; `az role assignment list --resource-group
   fresher-rg -o table` — compare mentally to an IAM policy attached at a scope.

### Part 3 — Small hands-on: one VM + storage (55 min)
6. Create an NSG allowing SSH from your IP only (mirror Day 94's SG discipline):
   `az network nsg create --resource-group fresher-rg --name fresher-nsg`;
   `az network nsg rule create --nsg-name fresher-nsg --resource-group fresher-rg
   --name allow-ssh --priority 100 --source-address-prefixes <your-ip>/32
   --destination-port-ranges 22 --access Allow --protocol Tcp`.
7. Create a free-tier-eligible VM: `az vm create --resource-group fresher-rg --name
   fresher-vm --image Ubuntu2204 --size Standard_B1s --admin-username azureuser
   --generate-ssh-keys --nsg fresher-nsg`.
8. SSH in using the generated key; `curl ifconfig.me` to confirm outbound works; exit.
9. Create a Storage Account + Blob container: `az storage account create --name
   <uniquename> --resource-group fresher-rg --sku Standard_LRS`; `az storage container
   create --account-name <uniquename> --name fresher-container`; upload one file with
   `az storage blob upload`.
10. Write `docs/cloud-mapping/azure-vs-aws.md` capturing the four tables above plus one
    observation from hands-on ("RG deletion is more dangerous/convenient than anything
    in AWS because...").

### Part 4 — Teardown (mandatory, 15 min)
11. Delete everything in one shot via the Resource Group: `az group delete --name
    fresher-rg --yes --no-wait`; poll `az group exists --name fresher-rg` until `false`.
12. Confirm: `az resource list --resource-group fresher-rg` errors (RG gone) or returns
    empty.

**Definition of done:** four comparison tables written and committed · VM reachable via
SSH with NSG restricted to your IP · blob uploaded successfully · entire environment
torn down via a single RG deletion, confirmed gone.
