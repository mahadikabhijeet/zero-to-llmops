## Theory (1h)

### A. Disks and partitions (20 min)
- Block devices: `/dev/sda`, `/dev/nvme0n1`, etc. Partitions: `/dev/sda1`, `/dev/sda2`
  (or `/dev/nvme0n1p1` for NVMe). `lsblk` (tree view of disks/partitions/mounts, add
  `-f` for filesystem type + UUID).
- Partition tables: **MBR** (legacy, 4 primary partition limit, ties back to Day 1's
  BIOS discussion) vs **GPT** (modern, needed for UEFI, many more partitions, checksum-
  protected).
- Tools: `fdisk` (MBR-focused but handles GPT too, interactive), `parted` (both
  table types natively, can be scripted). `fdisk -l` / `parted -l` to list.

### B. Filesystems (15 min)
- **xfs**: RHEL's default since RHEL 7 — good for large files, cannot be shrunk (only
  grown) once created.
- **ext4**: still common, well understood, can be both grown and shrunk (unmounted).
- Creating: `mkfs.xfs /dev/sdb1`, `mkfs.ext4 /dev/sdb1`. Checking: `blkid` (shows
  UUID + TYPE for every block device — the canonical source for fstab entries).

### C. Mounting (15 min)
- Manual: `mount /dev/sdb1 /mnt/data`, `umount /mnt/data` (or `umount /dev/sdb1`).
  `umount` fails with "target busy" if something has an open file/cwd there — pairs
  with Day 8's `lsof +D <dir>` for finding the culprit.
- Persistent: `/etc/fstab` — one line per mount: `<device-or-UUID> <mountpoint>
  <fstype> <options> <dump> <pass>`. **Always use UUID, not `/dev/sdX`** — device names
  can shift across reboots, UUIDs don't.
- Test before trusting a reboot: `mount -a` (mounts everything in fstab that isn't
  already mounted — errors here mean you'd have booted into a broken system).

### D. UUIDs and options (10 min)
- `blkid /dev/sdb1` or `lsblk -f` to get a UUID. Common mount options: `defaults`,
  `noatime` (skip access-time updates, minor perf win), `ro` (read-only), `nofail`
  (don't block boot if this device is missing — important for removable/network
  storage).

## Lab (2h)

### Part 1 — Inspect existing storage (25 min)
1. `lsblk` and `lsblk -f` — map every disk, partition, filesystem type, and mountpoint
   on your VM.
2. `df -h` — compare against `lsblk` output; identify which partition backs `/`.
3. `blkid` — list UUIDs for everything, cross-reference with `lsblk -f`.
4. `cat /etc/fstab` — identify at least one entry, confirm it uses UUID not `/dev/sdX`.

### Part 2 — Add a new disk (if your VM allows attaching one) (40 min)
If your hypervisor lets you attach a second virtual disk, do the real thing; otherwise
simulate with a loopback device (see step 5b).
5a. Attach a new virtual disk in your hypervisor UI, then `lsblk` to confirm it
    appears (e.g. `/dev/sdb`, unpartitioned).
5b. **No spare disk available:** create a loopback file instead:
    `dd if=/dev/zero of=~/lab10/diskfile.img bs=1M count=512`, then
    `sudo losetup -fP ~/lab10/diskfile.img` and `losetup -a` to find its `/dev/loopN`
    name — use that in place of `/dev/sdb` below.
6. `sudo parted /dev/sdb mklabel gpt`, then `sudo parted /dev/sdb mkpart primary
   xfs 0% 100%` — create one partition filling the disk.
7. `lsblk` to confirm the new partition (`/dev/sdb1`), `sudo mkfs.xfs /dev/sdb1`.
8. `sudo mkdir -p /mnt/data`, `sudo mount /dev/sdb1 /mnt/data`, `df -h /mnt/data` to
   confirm.

### Part 3 — Persist it in fstab (30 min)
9. `sudo blkid /dev/sdb1` — copy the UUID exactly.
10. `sudo umount /mnt/data` first (test clean), then edit `/etc/fstab` (use a text
    editor, back it up first: `sudo cp /etc/fstab /etc/fstab.bak`):
    `UUID=<uuid-here>  /mnt/data  xfs  defaults,nofail  0  2`
11. `sudo mount -a` — confirms fstab syntax is correct and mounts it. `df -h /mnt/data`
    to verify. **This is the step that saves you from a boot-failure surprise.**
12. Deliberately break it (educational): change the UUID to a wrong value, run
    `sudo mount -a`, observe the error, then fix it back from your `fstab.bak` value.

### Part 4 — Busy-target troubleshooting (25 min)
13. `cd /mnt/data && touch testfile`, keep that shell's cwd there, open a second
    terminal and try `sudo umount /mnt/data` — expect "target is busy."
14. `sudo lsof +D /mnt/data` — find what's holding it open (your first shell's cwd).
    `cd ~` in the first shell, retry `umount` — should succeed now.
15. Re-mount with `mount -a`, confirm `/opt/fresher_project` is untouched by any of
    today's work (sanity check — no project step today, but verify state is stable).

**Definition of done:** created a partition and xfs filesystem on a new (or
loopback) disk · mounted it manually, then persisted via UUID in `/etc/fstab` and
verified with `mount -a` · reproduced and resolved a "target busy" umount failure using
`lsof +D`.
