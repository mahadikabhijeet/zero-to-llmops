## Theory (1h)

### A. Unit file anatomy (20 min)
- A `.service` unit has three sections: `[Unit]` (metadata + dependencies: `Description`,
  `After`, `Requires`, `Wants`), `[Service]` (how to run it: `Type`, `ExecStart`,
  `ExecStop`, `Restart`, `User`, `Group`), `[Install]` (how it hooks into targets:
  `WantedBy`).
- `Type=` values: `simple` (default, main process is the service), `oneshot` (runs and
  exits, used for scripts — pairs naturally with timers), `forking` (daemonizes itself).
- Unit file locations: `/usr/lib/systemd/system/` (vendor-shipped, don't edit
  directly), `/etc/systemd/system/` (admin-created/overrides — **this is where ours
  goes**). `systemctl cat <unit>` shows the effective merged file.

### B. Targets and dependencies (15 min)
- Targets group units and replace old runlevels: `multi-user.target` (non-GUI,
  networked — our default), `graphical.target`, `reboot.target`. `systemctl
  list-dependencies multi-user.target` shows what's pulled in.
- Ordering (`After=`, `Before=`) vs requirement (`Requires=`, `Wants=`) are separate
  axes — ordering alone doesn't guarantee something starts; you need both for a real
  dependency. `Wants=` is a soft dependency (failure doesn't block); `Requires=` is
  hard.

### C. Timers vs cron (15 min)
- Cron (`crontab -e`, `/etc/cron.d/`) still works and is simpler for a one-liner, but
  systemd timers integrate with journald logging, dependency ordering, and
  `systemctl status` visibility.
- A timer is a separate `.timer` unit paired with a same-named `.service`
  (`OnCalendar=`, `OnBootSec=`, `OnUnitActiveSec=` for relative schedules).
  `systemctl list-timers` shows all active timers and next-run times.
- `OnCalendar=*-*-* *:00:00` (hourly, on the hour) syntax — `systemd-analyze calendar
  "<expr>"` lets you test an expression before deploying it.

### D. Writing and reloading units (10 min)
- After creating/editing a unit file in `/etc/systemd/system/`, you **must** run
  `sudo systemctl daemon-reload` before systemd sees the change.
- `systemctl enable <unit>` (symlinks it into the target's `.wants/` dir — starts at
  boot) vs `systemctl start <unit>` (starts it now) — they're independent; you often
  want both (`enable --now`).

## Lab (2h)

### Part 1 — Read existing units (25 min)
1. `systemctl cat sshd.service` (or another running service) — identify all three
   sections.
2. `systemctl list-dependencies multi-user.target | head -20`.
3. `systemctl list-timers --all` — find at least one existing timer (e.g.
   `logrotate.timer` if present) and its paired service:
   `systemctl cat logrotate.timer` and `systemctl cat logrotate.service`.

### Part 2 — Write a oneshot service for boot_logger (35 min)
4. Create `/etc/systemd/system/boot-logger.service`:
   ```ini
   [Unit]
   Description=Fresher project boot logger
   After=network.target

   [Service]
   Type=oneshot
   User=svc_fresher
   Group=devops-trainees
   WorkingDirectory=/opt/fresher_project
   ExecStart=/opt/fresher_project/boot_logger.sh

   [Install]
   WantedBy=multi-user.target
   ```
5. `sudo systemctl daemon-reload`, `sudo systemctl start boot-logger.service`,
   `systemctl status boot-logger.service` — confirm `Active: inactive (dead)` with
   exit status 0 (expected for a oneshot that finished).
6. `journalctl -u boot-logger.service --no-pager` — confirm the script's stdout landed
   in the journal (systemd captures it automatically — no more manual `tee` needed for
   this path, though the script's own file logging stays for the project's own
   `logs/` directory).

### Part 3 — Add a timer (35 min)
7. Create `/etc/systemd/system/boot-logger.timer`:
   ```ini
   [Unit]
   Description=Run fresher project boot logger every 15 minutes

   [Timer]
   OnBootSec=2min
   OnUnitActiveSec=15min
   Unit=boot-logger.service

   [Install]
   WantedBy=timers.target
   ```
8. `sudo systemctl daemon-reload`, `sudo systemctl enable --now boot-logger.timer`.
9. `systemctl list-timers | grep boot-logger` — confirm next-run time is scheduled.
10. `systemd-analyze calendar "*-*-* *:00:00"` — practice reading a calendar
    expression's next-elapse output (unrelated to our timer, just the syntax drill).

### Part 4 — ★ Project milestone: verify end to end (25 min)
11. `sudo systemctl status boot-logger.timer boot-logger.service` — both should show
    healthy state.
12. Manually trigger early: `sudo systemctl start boot-logger.service` again, confirm
    `logs/` gains a new entry and the awk summary line count increases.
13. Reboot the VM if permitted (`sudo reboot`), log back in, `systemctl list-timers` —
    confirm the timer re-armed automatically after boot (this is the actual milestone:
    the project now self-runs without a human invoking the script).

**Definition of done:** ★ `boot-logger.service` and `boot-logger.timer` both exist in
`/etc/systemd/system/`, are enabled, and survive a reboot · `journalctl -u
boot-logger.service` shows successful runs · `systemctl list-timers` shows the next
scheduled run · you can explain `Wants=` vs `Requires=` and `enable` vs `start`.
