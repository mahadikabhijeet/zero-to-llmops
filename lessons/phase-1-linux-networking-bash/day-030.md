## Theory (1h)

### A. What "capstone" means here (10 min)
- No new commands today — this is integration work: wiring together everything from
  Days 1–29 (boot logging, users/perms, systemd, logging/logrotate, networking/
  firewalld/SELinux, nginx/TLS, robust bash, and Python) into one coherent,
  documented, self-running tool. This is exactly the shape of a real junior-DevOps
  first project and the centerpiece of the portfolio going into Phase 2.

### B. Architecture of `system_report` (25 min)
- **Collector** (`boot_logger.sh`, bash): gathers boot/systemd/log-level facts,
  writes text logs, triggers the formatter.
- **Formatter** (`sys_report.py`, Python): gathers deeper numeric snapshots (CPU load,
  memory, disk, boot-error count) and emits structured JSON — Python's strengths
  (data structures, JSON) doing what bash is clumsy at.
- **Presentation layer**: an HTML report combining both collector and formatter
  output, served by nginx over HTTP and HTTPS.
- **Scheduling**: a systemd `.timer` runs the whole pipeline on a schedule without a
  human invoking anything — the "self-running" property that makes this a real
  system, not just a script.
- **Documentation**: a README so the tool is legible to someone who isn't you — the
  actual bar for a portfolio piece.

### C. Integration points to verify (15 min)
- Bash calls Python: `boot_logger.sh` should invoke `sys_report.py` as one of its
  steps (via `subprocess`-equivalent in bash: just calling the script directly with
  the right interpreter/venv).
- Python output feeds HTML: the HTML report should embed both the bash log tail and
  the JSON snapshot (pretty-printed) so a viewer sees the full picture in one page.
- Permissions/SELinux/firewalld must all agree: `svc_fresher` must be able to run
  both scripts, write to `www/`, and nginx must be able to read `www/` with correct
  context, and the firewall must allow HTTP/HTTPS — every prior day's security work
  has to hold together simultaneously, not just individually.

### D. What "documented" means for a README (10 min)
- Minimum bar: what the tool does, how to run it manually, how the automation
  (systemd timer) works, where the output lives, and one "how to extend this" note —
  this is the first artifact that would survive contact with a stranger (or Phase 2's
  GitHub push on Day 33).

## Lab (2h) — Build the capstone

### Part 1 — Wire bash → Python (30 min)
1. Edit `boot_logger.sh`: after the existing text-log and awk-summary sections, add a
   call to the Python formatter using the project's venv interpreter (create
   `/opt/fresher_project/venv` if you haven't set up a project-local venv yet:
   `python3 -m venv /opt/fresher_project/venv`, then
   `/opt/fresher_project/venv/bin/pip install --quiet --upgrade pip` — no third-party
   packages needed since `sys_report.py` is stdlib-only, but this establishes the
   convention for Phase 2):
   ```bash
   echo "--- Running sys_report.py ---"
   /opt/fresher_project/venv/bin/python3 /opt/fresher_project/sys_report.py \
       -o /opt/fresher_project/logs/sys_report.json -v || true
   ```
2. Run `boot_logger.sh` end to end — confirm both the text log and
   `logs/sys_report.json` update together in one invocation.

### Part 2 — Merge into one HTML report (35 min)
3. Update `generate_html_report()` in `boot_logger.sh` to embed the JSON snapshot
   alongside the log tail:
   ```bash
   generate_html_report() {
       {
         echo "<html><head><title>system_report — $(hostname)</title></head><body>"
         echo "<h1>System Report — $(date)</h1>"
         echo "<h2>Boot log tail</h2><pre>"
         cat logs/boot_$(date +%F).log 2>/dev/null
         echo "</pre><h2>System snapshot (JSON)</h2><pre>"
         cat logs/sys_report.json 2>/dev/null
         echo "</pre></body></html>"
       } > /opt/fresher_project/www/report.html
   }
   ```
4. Run `boot_logger.sh` again, `curl -I http://localhost/report.html` and view the
   page contents via `curl http://localhost/report.html` — confirm both sections
   render.

### Part 3 — Confirm the full automation chain (30 min)
5. `sudo systemctl restart boot-logger.timer`, `systemctl list-timers | grep
   boot-logger` — confirm scheduled.
6. `sudo systemctl start boot-logger.service`, `journalctl -u boot-logger.service
   --no-pager | tail -20` — confirm both bash and Python ran without errors and the
   report updated.
7. Re-verify SELinux/firewalld haven't drifted: `restorecon -Rv
   /opt/fresher_project/www`, `firewall-cmd --list-services` (confirm `http` present),
   `curl -vk https://localhost/report.html` (confirm TLS still works from Day 20).

### Part 4 — Write the README (25 min)
8. Create `/opt/fresher_project/README.md`:
   ```markdown
   # system_report

   Automated system-health snapshot tool. Bash collector (`boot_logger.sh`) gathers
   boot/systemd log facts and calls the Python formatter (`sys_report.py`), which adds
   CPU/memory/disk/error-count data as JSON. Both are merged into an HTML report
   served by nginx.

   ## Run manually
   `sudo -u svc_fresher /opt/fresher_project/boot_logger.sh -v`

   ## Automated schedule
   `boot-logger.timer` (systemd) runs the full pipeline every 15 minutes.
   Check with: `systemctl list-timers | grep boot-logger`

   ## Output
   - Text logs: `/opt/fresher_project/logs/`
   - JSON snapshot: `/opt/fresher_project/logs/sys_report.json`
   - HTML report: `https://<host>/report.html`

   ## Extending this
   Add new metrics to `sys_report.py`'s `build_report()` function; they'll
   automatically appear in the next HTML report without touching `boot_logger.sh`.
   ```
9. Final full regression: reboot the VM if possible, confirm the timer re-arms, the
   service runs successfully, and `curl` to the report page succeeds — this is the
   real capstone test, not just "it worked when I ran it by hand."

**Definition of done:** ★ `boot_logger.sh` calls `sys_report.py` via the project venv
every run · the HTML report at `/report.html` shows both the log tail and the JSON
snapshot · the systemd timer runs the whole pipeline unattended and survives a reboot ·
SELinux and firewalld both confirmed still correctly configured · `README.md` exists
and accurately describes how to run, automate, and extend the tool.
