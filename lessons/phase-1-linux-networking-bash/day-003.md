## Theory (1h)

### A. The user/group model (15 min)
- Every process runs as a **UID** (user) and one primary **GID** plus optional
  supplementary groups. `id`, `id -Gn <user>`, `whoami`, `groups`.
- UID ranges: 0 = root, 1–999 typically system/service accounts, 1000+ regular human
  users on RHEL/Fedora (`/etc/login.defs` defines the exact cutoffs).
- Files: `/etc/passwd` (username:x:UID:GID:GECOS:home:shell — password field is `x`,
  meaning "look in shadow"), `/etc/shadow` (hashed password + aging fields, root-only
  readable), `/etc/group` (groupname:x:GID:member-list).

### B. Managing users and groups (20 min)
- Create: `useradd -m -s /bin/bash -c "comment" <name>` (`-m` makes home dir),
  `groupadd <name>`.
- Modify: `usermod -aG <group> <user>` (**always `-a` with `-G`** — without it you wipe
  existing supplementary groups), `usermod -s /sbin/nologin <user>` for service accounts.
- Passwords: `passwd <user>`, `chage -l <user>` (aging info), `chage -M 90 <user>`
  (max password age).
- Delete: `userdel -r <user>` (`-r` removes home dir too — be careful).
- Inspect: `getent passwd <user>`, `getent group <group>` (works with any nsswitch
  source, not just local files).

### C. su vs sudo vs sudoers (15 min)
- `su - <user>` switches user entirely (needs target's password), full login shell
  (`-` reloads their environment).
- `sudo <cmd>` runs one command as another user (default root) using **your own**
  password, governed by `/etc/sudoers` (never edit directly — use `visudo`, which
  syntax-checks before saving).
- Sudoers syntax basics: `user ALL=(ALL) ALL`; group form `%wheel ALL=(ALL) ALL`
  (RHEL/Fedora convention: members of `wheel` get sudo).
- `sudo -l` (what can I run?), `sudo -u <user> <cmd>` (run as a specific non-root user).

### D. Password policy (10 min)
- PAM (`/etc/pam.d/`) enforces policy at login/auth time — just know it exists as the
  plumbing (deep dive not this course's focus).
- `/etc/login.defs`: `PASS_MAX_DAYS`, `PASS_MIN_LEN`, UID_MIN/UID_MAX ranges.
- Locking accounts: `passwd -l <user>` / `-u` to unlock; `usermod -L`/`-U` equivalent.

## Lab (2h)

### Part 1 — Read the account files (25 min)
1. `cat /etc/passwd | column -t -s:` — identify your own line, root's line, and one
   system account (e.g. `daemon` or `sshd`). Note UID and shell for each.
2. `sudo cat /etc/shadow | head -5` — identify the hash field vs the aging fields
   (colon-separated: lastchange:min:max:warn:inactive:expire).
3. `cat /etc/group | grep wheel` — who's in it? `groups $USER` to confirm your own
   memberships.
4. `getent passwd 1000` (or your own UID) — confirm it matches `/etc/passwd`.

### Part 2 — Create users and groups (35 min)
5. `sudo groupadd devops-trainees`.
6. `sudo useradd -m -s /bin/bash -c "Fresher trainee" -G devops-trainees fresher01`.
7. Set a password: `sudo passwd fresher01`. Confirm with `id fresher01`.
8. `su - fresher01`, run `whoami`, `id`, `exit` back to your own shell.
9. `sudo chage -l fresher01` — read the aging report. Set a 90-day max:
   `sudo chage -M 90 fresher01`, confirm with `chage -l` again.

### Part 3 — sudo and sudoers (30 min)
10. `sudo visudo` — find the `%wheel ALL=(ALL) ALL` line (don't change it yet, just
    locate it).
11. `groups $USER` — are you in `wheel`? If not, `sudo usermod -aG wheel $USER`, then
    log out/in (or `newgrp wheel`) and confirm `sudo -l` now shows privileges.
12. Test the trap: `sudo usermod -G devops-trainees $USER` (no `-a`) then
    `groups $USER` — did you lose `wheel`? Fix it back with `-aG wheel`.
13. `sudo -u fresher01 whoami` — run a single command as another user without a full
    `su`.

### Part 4 — Incremental project step (30 min)
Create the service account the project will run under from now on:
14. `sudo useradd -r -s /sbin/nologin -d /opt/fresher_project -c "Fresher project service account" svc_fresher`
    (`-r` = system account, no login shell — it should never be an interactive login).
15. `sudo chown -R svc_fresher:svc_fresher /opt/fresher_project`.
16. Run `boot_logger.sh` as that account: `sudo -u svc_fresher /opt/fresher_project/boot_logger.sh`.
    It should still work (reading `/proc`, journald — all world-readable). Note any
    permission errors you hit and why (we fix perms properly on Day 4).

**Definition of done:** can explain passwd/shadow/group fields from memory · created
`fresher01` and `devops-trainees` · `wheel` membership confirmed via `sudo -l` ·
`svc_fresher` system account exists, owns `/opt/fresher_project`, and can run
`boot_logger.sh`.
