## Theory (1h)

### A. rwx and octal (15 min)
- Three permission classes: **owner (u), group (g), other (o)**; three bits each:
  **r**ead, **w**rite, e**x**ecute. On a directory, `x` means "can traverse/enter,"
  `r` means "can list," `w` means "can create/delete entries inside."
- Octal shorthand: r=4, w=2, x=1, summed per class — `rwxr-xr--` = 754.
- `chmod 750 file`, `chmod u+x,g-w file` (symbolic form), `chmod -R` for recursive.
- `chown user:group file`, `chgrp group file`.

### B. umask (10 min)
- The mask **subtracted** from the default max (666 for files, 777 for dirs) when a
  new file/dir is created. Default `umask 022` → new files get 644, new dirs 755.
- Check: `umask`; set for a session: `umask 027`; persistent per-user: add to
  `~/.bashrc`; persistent system-wide: `/etc/profile` or `/etc/bashrc`.

### C. Special bits — SUID, SGID, sticky (20 min)
- **SUID** (4000, shows as `s` in owner's x slot): executable runs with the *file
  owner's* privileges, not the caller's. Classic example: `/usr/bin/passwd` (must write
  root-owned `/etc/shadow` on your behalf). `ls -l $(which passwd)`.
- **SGID** (2000, `s` in group's x slot): on a file, runs with the file's group
  privileges; on a **directory**, new files inherit the directory's group (huge for
  shared team directories).
- **Sticky bit** (1000, `t` in other's x slot): on a directory, only the file's owner
  (or root) can delete/rename files inside, even if others have write on the dir.
  Classic example: `/tmp` — `ls -ld /tmp`.
- Setting: `chmod 4755 file` (SUID), `chmod 2775 dir` (SGID), `chmod 1777 dir` (sticky),
  or symbolic `chmod u+s`, `g+s`, `+t`.

### D. ACLs and chattr (15 min)
- Standard rwx only supports one owner + one group. **ACLs** (Access Control Lists) let
  you grant specific permissions to additional users/groups on the same file.
- `getfacl <file>` (view), `setfacl -m u:fresher01:rx <file>` (grant),
  `setfacl -x u:fresher01 <file>` (remove), `setfacl -b <file>` (strip all ACLs).
  A `+` after the mode in `ls -l` signals an ACL is present.
- `chattr +i file` (immutable — even root can't modify/delete without unsetting first),
  `lsattr file` to view. Useful for protecting critical configs from accidental change.

## Lab (2h)

### Part 1 — rwx and octal drills (25 min)
1. `touch testfile; ls -l testfile` — read the default mode (644, from umask 022).
2. `chmod 640 testfile; ls -l testfile` — verify. Then `chmod u+x,o-r testfile` and
   verify again, converting the result back to octal by hand.
3. `mkdir testdir; chmod 700 testdir` — confirm only you can `cd` into it or `ls` it
   as `fresher01` (`sudo -u fresher01 ls testdir` should fail).

### Part 2 — umask (15 min)
4. `umask` — note current value. `umask 027; touch f1; mkdir d1; ls -l f1; ls -ld d1` —
   confirm 640 and 750 respectively. Reset with `umask 022`.

### Part 3 — SUID/SGID/sticky (35 min)
5. `ls -l /usr/bin/passwd` — confirm the `s` bit. `ls -ld /tmp` — confirm sticky `t`.
6. Create a shared group scenario: `sudo mkdir /srv/shared`, `sudo chgrp
   devops-trainees /srv/shared`, `sudo chmod 2775 /srv/shared` (SGID). As `fresher01`,
   create a file inside; confirm (`ls -l`) it inherited group `devops-trainees` even
   though `fresher01`'s primary group differs.
7. Test sticky yourself: `sudo mkdir /srv/stickytest; sudo chmod 1777 /srv/stickytest`.
   As two different users, each create a file, then try deleting the *other's* file —
   confirm it's denied even though the directory is world-writable.

### Part 4 — ACLs (25 min)
8. `touch acltest; chmod 600 acltest` (owner-only). `getfacl acltest`.
9. `setfacl -m u:fresher01:r acltest` — grant read to just that user without touching
   group/other. `getfacl acltest` again — note the `+` you'll now see in `ls -l acltest`.
10. `sudo -u fresher01 cat acltest` — should now succeed. `setfacl -x u:fresher01
    acltest` to revoke, confirm it fails again.

### Part 5 — Incremental project step (20 min)
Lock down `/opt/fresher_project` properly, replacing yesterday's quick `chown -R`:
11. `sudo chown -R svc_fresher:devops-trainees /opt/fresher_project`.
12. `sudo chmod 750 /opt/fresher_project` (owner rwx, group rx, other nothing).
13. `sudo chmod 2750 /opt/fresher_project/logs` if it exists (SGID so new logs inherit
    `devops-trainees` group even when created by `svc_fresher`).
14. Grant yourself read access via ACL without joining the group:
    `sudo setfacl -m u:$USER:rx /opt/fresher_project`. Verify with `getfacl`.
15. Evolve the script with today's material: add `umask 027` as line 2 of
    `boot_logger.sh` (right under the shebang) so every log it writes is created `640`
    instead of world-readable `644`. This is the day's umask lesson applied to the project.
16. Re-run `sudo -u svc_fresher /opt/fresher_project/boot_logger.sh` — confirm it still
    works end to end under the new perms, and that `ls -l /opt/fresher_project/logs` shows
    the new log as `svc_fresher:devops-trainees`, mode `640`.

**Definition of done:** can convert any `rwx` string to octal and back · SGID directory
demo showed group inheritance · sticky-bit demo showed only-owner-deletes · ACL grant/
revoke verified with `getfacl` · `/opt/fresher_project` is 750, owned by
`svc_fresher:devops-trainees`, boot_logger still runs clean under `svc_fresher`.
