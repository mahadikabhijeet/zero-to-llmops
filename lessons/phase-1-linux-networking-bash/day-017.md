## Theory (1h)

### A. SSH keys and ssh-agent (20 min)
- Asymmetric keypair: private key stays on your machine (never share, protect with a
  passphrase), public key goes on servers you want to access. `ssh-keygen -t ed25519
  -C "comment"` (ed25519 preferred over older RSA for speed/security; use `-b 4096` if
  forced to use RSA).
- Deploy: `ssh-copy-id user@host` (appends your public key to their
  `~/.ssh/authorized_keys`) — or manually `cat id_ed25519.pub | ssh user@host 'cat >>
  ~/.ssh/authorized_keys'`.
- `ssh-agent` holds decrypted keys in memory for the session so you don't retype your
  passphrase every connection: `eval $(ssh-agent)`, `ssh-add ~/.ssh/id_ed25519`,
  `ssh-add -l` to list loaded keys.

### B. SSH client config and sshd hardening (20 min)
- `~/.ssh/config` lets you alias connections:
  ```
  Host secondvm
      HostName 192.168.1.60
      User fresher01
      IdentityFile ~/.ssh/id_ed25519
      Port 22
  ```
  Then just `ssh secondvm`.
- Server-side hardening in `/etc/ssh/sshd_config` (always `sudo sshd -t` to
  syntax-check before restarting — a bad config can lock you out):
  `PermitRootLogin no`, `PasswordAuthentication no` (key-only, once keys are confirmed
  working — never disable passwords before testing key login succeeds), `Port` change
  (security-through-obscurity, minor value but common), `AllowUsers <list>`.
- `sudo systemctl reload sshd` after validating with `sshd -t`.

### C. Tunnels (10 min)
- Local port forward: `ssh -L 8080:localhost:80 user@remotehost` — forwards your local
  8080 to the remote's port 80, tunneled through SSH. Useful for reaching a
  remote-only web UI securely.
- `-N` (no remote command, tunnel only), `-f` (background after auth).

### D. scp and rsync (10 min)
- `scp file user@host:/path/` (simple copy over SSH) vs **rsync** (`rsync -avz
  source/ user@host:/dest/`) — rsync only transfers *differences* (delta algorithm),
  supports resuming, and is the right tool for repeated backups. `-a` (archive: recurse
  + preserve perms/times/links), `-v` (verbose), `-z` (compress in transit), trailing
  slash on source matters (contents vs the directory itself).
- `rsync --dry-run` to preview what would transfer before committing.

## Lab (2h)

### Part 1 — Generate and deploy keys (25 min)
1. `ssh-keygen -t ed25519 -C "fresher-training"` — accept default path, set a
   passphrase.
2. `eval $(ssh-agent)`, `ssh-add ~/.ssh/id_ed25519`, `ssh-add -l` to confirm loaded.
3. Provision (or confirm access to) a second VM for the rest of this lab. `ssh-copy-id
   fresher01@<secondvm-ip>` (create `fresher01` there first if needed, mirroring
   Day 3's setup).
4. `ssh fresher01@<secondvm-ip>` — confirm passwordless (or passphrase-only, no
   remote password) login works.

### Part 2 — SSH config and hardening (35 min)
5. Add a `Host secondvm` block to `~/.ssh/config` per Theory B; test with
   `ssh secondvm`.
6. On the second VM, `sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak`, then set
   `PermitRootLogin no`. `sudo sshd -t` to validate, `sudo systemctl reload sshd`.
7. **Before** disabling password auth, confirm key login still works from a *fresh*
   terminal (`ssh secondvm` in a brand-new window, not reusing an already-open
   session). Only then set `PasswordAuthentication no`, `sshd -t`, `reload sshd`.
8. Attempt `ssh -o PreferredAuthentications=password fresher01@<secondvm-ip>` — should
   now fail, confirming the hardening took effect.

### Part 3 — Tunnels (20 min)
9. On the second VM: `python3 -m http.server 9090 &` (a throwaway web server).
10. From your first VM: `ssh -L 8081:localhost:9090 secondvm -N -f`.
11. `curl http://localhost:8081` — confirm you reach the second VM's web server
    through the tunnel. `kill` the backgrounded ssh tunnel process when done (find it
    via `ps aux | grep 8081`).

### Part 4 — Incremental project step: rsync backup (40 min)
12. On the second VM: `sudo mkdir -p /opt/fresher_project_backup`,
    `sudo chown fresher01:fresher01 /opt/fresher_project_backup`.
13. From the first VM, dry-run first:
    `rsync -avz --dry-run /opt/fresher_project/ secondvm:/opt/fresher_project_backup/`
    — read the plan.
14. Run it for real: `rsync -avz /opt/fresher_project/ secondvm:/opt/fresher_project_backup/`.
15. Confirm on the second VM: `ls -la /opt/fresher_project_backup/` matches the
    source's contents (script, logs/, unit files won't transfer since they live in
    `/etc/systemd/system/` — note that as a known gap, not a bug).
16. Wrap it as a reusable one-liner: create `~/lab17/backup_project.sh`:
    ```bash
    #!/bin/bash
    rsync -avz /opt/fresher_project/ secondvm:/opt/fresher_project_backup/
    ```
    `chmod +x` it, run it again — confirm a second run transfers almost nothing (rsync
    delta at work — only genuinely changed files move).

**Definition of done:** key-based login working to a second VM · sshd hardened
(`PermitRootLogin no`, `PasswordAuthentication no`) with password auth confirmed
disabled only after key auth was verified · local port-forward tunnel demonstrated ·
`rsync` backup of `/opt/fresher_project` running to the second VM, second run showing
minimal transfer.
