## Theory (1h)

### A. Why SELinux exists and the top-down method (15 min)
- Standard permissions (Day 4) are **discretionary** (DAC) — the owner decides access.
  SELinux is **mandatory** (MAC) — even root is constrained by policy; a compromised
  process running as root still can't touch files outside its labeled scope.
- General troubleshooting method for "it should work but doesn't": (1) check DAC perms
  first (Day 4 skills), (2) check the service is actually running/listening (Day 8/16
  skills), (3) check firewalld (Day 18), (4) **only then** suspect SELinux — it's
  usually the last, not first, thing to blame, though it's often the actual cause once
  the obvious layers check out.

### B. Booleans (15 min)
- Booleans are named on/off switches for common policy exceptions, avoiding the need
  to write custom policy for routine cases. `getsebool -a | grep <keyword>` to find
  relevant ones, `getsebool httpd_can_network_connect`.
- Set: `setsebool httpd_can_network_connect on` (session-only) vs `setsebool -P
  httpd_can_network_connect on` (`-P` = persistent across reboot — almost always what
  you want in practice, but always set +test with the non-persistent form first).

### C. File contexts: fcontext and restorecon (20 min)
- Every file has a **type** in its SELinux context (e.g. `httpd_sys_content_t` for web
  docroots). Moving/copying files can carry the *wrong* type if copied from an
  unlabeled location — the #1 cause of "permissions look fine but it still fails."
- `semanage fcontext -a -t httpd_sys_content_t "/opt/mydir(/.*)?"` defines a **policy
  rule** for a path pattern (persists across relabels) — but it does NOT apply it to
  existing files by itself.
- `restorecon -Rv /opt/mydir` **applies** the defined context to files that already
  exist — you need both commands, in that order, for existing files.
- `chcon -t httpd_sys_content_t file` changes a context immediately but is NOT
  persistent — a `restorecon` or relabel will revert it. Use `semanage fcontext` +
  `restorecon` for anything that should stick.

### D. audit2why and audit2allow (10 min)
- SELinux denials are logged to the audit log (`/var/log/audit/audit.log`) and
  surfaced via `ausearch -m avc -ts recent`.
- `audit2why < /var/log/audit/audit.log` (or piped from `ausearch`) translates a raw
  denial into a plain-English explanation and often suggests the exact boolean or
  fcontext fix.
- `audit2allow` can generate a *custom policy module* from denials — powerful but
  risky (it can over-grant); prefer booleans/fcontext fixes first, treat
  `audit2allow -M` as a last resort your trainer should sign off on.

## Lab (2h)

### Part 1 — Reproduce a real denial (30 min)
1. Confirm `getenforce` is `Enforcing`. Move nginx's content to a non-standard
   location to trigger a real problem: `sudo mkdir -p /srv/webcontent`,
   `echo "<h1>Fresher Project</h1>" | sudo tee /srv/webcontent/index.html`.
2. Point nginx at it (edit `/etc/nginx/nginx.conf`'s `root` directive, or add a simple
   server block — coordinate with Day 20's fuller nginx setup; for now just change
   `root` under the default server block to `/srv/webcontent`), then
   `sudo systemctl restart nginx`.
3. `curl http://localhost/` — expect a 403 Forbidden despite correct DAC permissions
   (`ls -l /srv/webcontent/index.html` looks fine).

### Part 2 — Diagnose with audit2why (25 min)
4. `sudo ausearch -m avc -ts recent` — find the denial entry for nginx trying to read
   `/srv/webcontent`.
5. `sudo ausearch -m avc -ts recent | audit2why` — read the plain-English explanation;
   it should point at a context mismatch (`default_t` instead of
   `httpd_sys_content_t`).
6. `ls -Zd /srv/webcontent` and `ls -Z /srv/webcontent/index.html` — confirm the wrong
   type directly.

### Part 3 — Fix it properly with fcontext + restorecon (30 min)
7. `sudo semanage fcontext -a -t httpd_sys_content_t "/srv/webcontent(/.*)?"`
   (install `policycoreutils-python-utils` first if `semanage` is missing:
   `sudo dnf install -y policycoreutils-python-utils`).
8. `sudo restorecon -Rv /srv/webcontent` — confirm output shows the context change.
9. `ls -Z /srv/webcontent/index.html` — confirm it's now `httpd_sys_content_t`.
10. `curl http://localhost/` — should now succeed (200 with your HTML).
11. Compare against the anti-pattern: what would `chcon -t httpd_sys_content_t
    /srv/webcontent/index.html` alone have achieved, and why would it not survive a
    relabel? (Answer from Theory C — write it down.)

### Part 4 — Booleans (25 min)
12. `getsebool -a | grep httpd | head -15` — skim available httpd-related booleans.
13. `getsebool httpd_can_network_connect` — note current value (off by default; this
    boolean matters when a web app needs to make outbound connections, e.g. to a
    database on another host).
14. `sudo setsebool httpd_can_network_connect on`, confirm with `getsebool`, then
    `sudo setsebool -P httpd_can_network_connect on` for persistence, then optionally
    turn it back off if not actually needed for your setup:
    `sudo setsebool -P httpd_can_network_connect off`.

**Definition of done:** reproduced a real SELinux denial (not a manufactured example) ·
diagnosed it with `ausearch`/`audit2why` · fixed it correctly with `semanage fcontext`
+ `restorecon` (not `chcon`) and verified the fix persists conceptually · toggled a
boolean both session-only and persistently and explained the difference.
