## Theory (1h)

### A. What's actually different about LLMs (15 min)
- Everything from Days 151–158 (lifecycle, tracking, serving, monitoring) still
  applies — an LLM is still a model with a train/serve split. What's new: the model
  is enormous (billions of parameters), usually **not trained from scratch** by
  you, and the serving workload is fundamentally different (sequential token
  generation, not one-shot classification).
- Ops framing for this whole sub-track: you will almost never train an LLM; you
  will **serve, wrap, and operate** one someone else trained. That's the DevOps/SRE
  angle, and why this fits the phase.

### B. Tokens and context (15 min)
- Text is broken into **tokens** (sub-word units, not whole words) before being fed
  to the model — roughly ~4 characters/token in English as a rule of thumb.
- **Context window**: the max number of tokens (input + output combined) a model
  can attend to in one request. Exceeding it means truncation or a hard error —
  this is a real operational limit, like a request body size limit.
- Cost and latency both scale with token count — token counting is the LLM
  equivalent of "watch your payload size."

### C. Inference vs training, and GPU basics (15 min)
- Training an LLM from scratch needs massive GPU clusters (out of scope for this
  course and for the fresher's first job). **Inference** (serving) is what you'll
  operate — still often GPU-bound for large models, but small/quantized models can
  run acceptably on CPU, which is what this course uses throughout.
- GPU basics worth knowing conversationally: VRAM is the hard constraint (a model
  must fit in GPU memory to run efficiently there); quantization (Day 164) shrinks
  a model's memory footprint at some quality cost; CPU inference trades latency for
  zero GPU dependency — the right call for low-traffic, cost-sensitive, or
  commodity-hardware environments (exactly the fresher's home lab).

### D. Latency/cost levers — the ops surface (15 min)
- Bigger model = better quality, worse latency/cost — the first lever an ops
  engineer tunes is "which model size actually meets the requirement," not "use the
  biggest model available."
- Output length dominates latency (tokens are generated one at a time,
  sequentially) — capping `max_tokens` is a direct latency control.
- Preview of Day 164's deeper dive: caching repeated prompts, batching concurrent
  requests, and quantization are the three big cost/perf levers; today just names
  them so Day 160's lab makes sense.

## Lab (2h)

### Part 1 — Token counting (30 min)
1. Install a tokenizer library appropriate to a small open model you'll use Day 160
   (e.g., a `tiktoken`-style or Hugging Face `tokenizers` package — follow that
   library's own quickstart rather than guessing at an API).
2. Tokenize a handful of real strings (a short sentence, a paragraph, a code
   snippet) and print token counts. Compare the "~4 chars/token" rule of thumb
   against your actual counts. Note where it breaks down (code, non-English text).

### Part 2 — Context window math (30 min)
3. Pick a documented context window size for a small open model (check that
   model's model card/docs — do not guess a number). Compute: given that window,
   roughly how many pages of English text (assume ~500 words/page) fit as input
   context alongside a 500-token expected output.
4. Write a one-paragraph answer to: "a user pastes a 50-page document and asks a
   question — what are the operational options?" (truncate, chunk+retrieve —
   preview of Day 162's RAG, summarize first, or reject with a clear error).

### Part 3 — CPU vs GPU decision exercise (30 min)
5. Research (docs, not invented numbers) the approximate parameter-count range
   where small open models comfortably run on CPU vs where GPU becomes practically
   necessary for acceptable latency. Write 3–4 bullet points citing what you found
   and where (model card, project docs) — practice sourcing real numbers instead of
   guessing, a habit worth keeping for the rest of the phase.
6. Decide, in writing, which class of model this course will use for hands-on labs
   (small, CPU-friendly) and why — this becomes the standing assumption for Days
   160–166.

### Part 4 — Cost lever brainstorm (30 min)
7. Given a hypothetical: "our LLM feature costs 3x what we budgeted" — list every
   lever you could pull (smaller model, cap output tokens, cache repeated queries,
   batch requests, quantize, move to CPU for low-traffic paths, rate-limit). Rank
   the top 3 by expected impact vs effort. Keep this list; Day 164 builds on it
   directly.

**Definition of done:** can explain tokens/context window with a real number from
a real model's docs (not invented) · CPU-vs-GPU decision documented with sourced
reasoning · a ranked cost-lever list produced for later reuse.
