# Day 176 — Capstone Build 7: Chaos Test + Load Test + Hardening

Phase 6 · Capstone build sprint, day 7 of 7 (final build day; Day 177 is docs/demo).

---

## Recall warm-up (5 min)
1. What did Day 175's buffer close out — was any checkpoint still open?
2. What are the capstone's two SLOs?
3. Is the anomaly-detection coverage for the capstone service still confirmed live?

## Objectives (today)
1. Run at least one chaos experiment (Day 137 muscle — chaos-mesh/Litmus) against
   the capstone service and observe SLO impact.
2. Run a k6 load test (Day 138 muscle) to find the saturation point.
3. Fix whatever the experiments reveal — this day is about **finding and closing**
   a real weakness, not just observing one.

## Deliverables
- One chaos experiment executed (pod-kill or network-delay) with results recorded:
  did SLOs hold, did the `AnomalyDetected` or SLO burn-rate alert fire correctly,
  did the service recover automatically or need intervention.
- A k6 load test report: request rate at which latency/error-rate SLOs start to
  degrade, i.e., the saturation point, with the test script committed.
- At least one concrete hardening fix applied as a result of either test (e.g., a
  corrected resource limit, an added retry/timeout per Day 144's reliability
  patterns, a PDB to protect against the chaos scenario tested).
- A short "what we found, what we fixed" note for Day 177's docs.

## Suggested time-box (3h)
- **0:00–0:20** — Recap chaos engineering's blast-radius principle (Day 137) and
  k6's ramping-VU pattern (Day 138) before running anything against a live system.
- **0:20–1:10** — Run the chaos experiment against the capstone namespace; watch
  the SLO dashboard and alerting live during the experiment.
- **1:10–2:00** — Run the k6 load test, ramping until an SLO is visibly violated;
  record the exact saturation point.
- **2:00–2:40** — Apply the hardening fix chosen from the findings; rerun the
  relevant test to confirm the fix actually helped (not just "looks better").
- **2:40–3:00** — Checkpoint review and write the findings note.

## Checkpoint (trainer confirms before Day 177 starts)
- Chaos experiment results recorded, including whether alerting behaved correctly.
- Load test saturation point identified with a committed test script and report.
- At least one hardening fix applied and verified with a rerun, not just theorized.

## Trainer-review questions
1. During the chaos experiment, did the SLO burn-rate alert or the anomaly alert
   fire — which, and was that the correct behavior?
2. What was the load test's saturation point, and what resource was the
   bottleneck (CPU, memory, connections, downstream dependency)?
3. Walk through the fix you applied — how do you know it actually helped, versus
   assuming it did?
4. If you had one more day, what's the next-highest-risk weakness you'd test?

## Definition of done
One chaos experiment run with recorded results, one k6 load test with an
identified saturation point, at least one hardening fix applied and verified,
findings note written, checkpoint confirmed.
