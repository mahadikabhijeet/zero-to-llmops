## Theory (1h)

### A. Alert fatigue — the problem AIOps targets (10 min)
- Real incidents often produce a storm of correlated alerts (one root cause,
  dozens of downstream symptoms) — this is the "alert noise" problem Day 125's
  Alertmanager grouping/routing already partially addresses with rules; AIOps adds
  a data-driven layer on top.

### B. Log clustering concepts (15 min)
- Raw logs are unstructured text with huge cardinality (timestamps, request IDs,
  changing values) that makes exact-match grouping useless. **Log clustering**
  groups structurally similar log lines (e.g., "connection timeout to db-01" and
  "connection timeout to db-02" cluster together) so an operator sees "1 cluster of
  500 events" instead of 500 individual lines.
- Common technique at exposure level: template extraction (replace variable tokens
  like IDs/numbers/IPs with placeholders) then group by the resulting template —
  conceptually similar to how you already grep/sed logs into patterns (Day 5–6),
  now automated. Full algorithms (e.g., Drain) are named for awareness; implementing
  one from scratch is out of scope — a simple regex-based templating pass is enough
  for today's lab.

### C. Alert-noise reduction concepts (15 min)
- Deduplication: collapse repeated identical alerts into one with a count (partly
  what Alertmanager's grouping already does).
- Correlation: if metric-anomaly and log-cluster-spike happen in the same window
  for the same service, surface them as one incident signal, not two separate
  pages — reduces the on-call cognitive load from Day 131's incident-management
  material.
- Suppression: known noisy/flaky alerts get a documented, time-boxed silence
  (Day 125's silencing, applied more systematically) rather than being ignored by
  habit — the ops discipline that keeps AIOps trustworthy instead of "the thing
  everyone mutes."

### D. Wiring the anomaly model into Alertmanager (20 min)
- Alertmanager doesn't know about your custom model — the standard integration
  path is the same one Prometheus itself uses: expose anomaly results as
  **Prometheus metrics** (e.g., a Gauge `anomaly_score` and a binary
  `anomaly_detected`), scrape them, and write a normal Prometheus **alerting
  rule** on top (Day 123 skill) — this reuses 100% of existing alerting
  infrastructure rather than inventing a parallel pipeline.
- Alternative path (also legitimate, named for completeness): the detection job
  posts directly to Alertmanager's HTTP API — more custom, less consistent with
  the rest of the stack; today's lab uses the Prometheus-metrics path for
  consistency with everything built since Phase 5.
- Runbook discipline (Day 125): every new alert needs a runbook — "what does an
  anomaly alert mean, what should the on-call do first" — write it today, don't
  defer it.

## Lab (2h)

### Part 1 — Expose anomaly results as metrics (35 min)
1. Extend `ml/anomaly/detect.py` (Day 165) to run as a small long-lived process
   (or have the CronJob write to a `/metrics`-exposing sidecar/small Flask/FastAPI
   app) exposing `anomaly_score` (Gauge, latest score) and `anomaly_detected`
   (Gauge, 0/1) via `prometheus-client`.
2. Add a scrape target for this endpoint on the project's Prometheus.

### Part 2 — Alerting rule (25 min)
3. Write a Prometheus alerting rule: fire `AnomalyDetected` when
   `anomaly_detected == 1` for at least N consecutive scrapes (avoid firing on a
   single noisy blip — same debounce reasoning as any other alert rule).
4. Route it in Alertmanager (Day 125 config) to a distinct receiver/label (e.g.,
   `team: aiops`) so it's visibly distinguishable from standard threshold alerts.

### Part 3 — Minimal log clustering (40 min)
5. Pull a sample of the project's application logs (from Loki, Day 127–128).
   Write `ml/anomaly/log_cluster.py`: a regex-based templating pass (replace
   numbers, UUIDs, IPs with placeholders), group log lines by resulting template,
   count occurrences per template over a time window.
6. Print the top 5 templates by count — discuss which look like "normal noise"
   vs a genuine emerging problem.

### Part 4 — Runbook and correlation note (20 min)
7. Write `ml/anomaly/runbook.md`: what the `AnomalyDetected` alert means, first
   diagnostic steps (check the Grafana "Model Health" dashboard from Day 158,
   check log-cluster output for a correlated spike), and escalation criteria.
8. Trigger a real anomaly (e.g., synthetic load spike via k6, Day 138 skill) and
   confirm the full path: metric anomaly → Prometheus alert fires → Alertmanager
   routes it → runbook's first step actually helps diagnose it.

**Definition of done:** anomaly scores exposed as Prometheus metrics and scraped ·
alerting rule fires correctly on a real triggered anomaly and is routed distinctly
in Alertmanager · basic log clustering groups a real log sample into templates ·
runbook written and validated against the end-to-end drill.
