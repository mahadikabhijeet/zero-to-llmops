# Day 169 — Capstone Build 1: Repo Scaffold (Backstage Template) + Infra (Terraform)

Phase 6 · Capstone build sprint, day 1 of 7 (per `capstone-spec.md` from Day 167).
Format: **build sprint**, not a tutorial — objectives, deliverables, checkpoints.

---

## Recall warm-up (5 min)
1. What is the capstone's scope decision from Day 167 (second service via golden
   path, or standalone utility)?
2. What are the 8 success criteria, in one phrase each?
3. Why does the capstone reuse existing cluster/GitOps/ML infra?

## Objectives (today)
1. Scaffold the capstone repo through the Backstage software template built on
   Day 142, proving the golden path works for a new service end to end.
2. Provision the capstone's infra needs (if any beyond the shared cluster) via
   Terraform — no manual console/CLI steps.
3. Confirm CI is green from the very first commit.

## Deliverables
- A new git repo (or a new directory in the existing monorepo, per the Day 167
  scope decision) created via the Backstage template, pushed to GitHub, public.
- `terraform/` directory with any capstone-specific infra (e.g., a dedicated
  namespace, a DNS record, an S3 bucket for artifacts) — `terraform plan`/`apply`
  run and state stored per Day 81's remote-state discipline.
- A passing CI run (lint + test, even if the test suite is a placeholder) visible
  on the very first commit — non-negotiable per success criterion 1.
- `capstone-spec.md` copied/linked into the new repo so it's self-documenting.

## Suggested time-box (3h total: 1h theory recap + 2h build, same shape as content days)
- **0:00–0:20** — Recap the Backstage template mechanics from Day 142 (what it
  generates: repo structure, CI workflow, catalog registration) before touching it.
- **0:20–0:40** — Recap Terraform module-writing discipline from Day 80/83
  (variables/outputs, fmt/validate, remote state) before writing new HCL.
- **0:40–1:00** — Confirm the scope decision is final; write the one-paragraph
  purpose statement into the new repo's README before scaffolding (forces clarity
  before code).
- **1:00–1:50** — Run the Backstage template, review every generated file rather
  than accepting it blindly, push to GitHub, confirm CI goes green.
- **1:50–2:40** — Write and apply the Terraform for any capstone-specific infra;
  confirm `terraform plan` is clean (no drift) on a second run.
- **2:40–3:00** — Checkpoint review against today's deliverables list.

## Checkpoint (trainer confirms before Day 170 starts)
- Repo is public on GitHub, CI is green, `capstone-spec.md` is present.
- Terraform state is remote (not local-only) and `terraform plan` shows no drift
  after apply.
- **Go/no-go**: if either is not true, Day 170 does not start on new work — fix
  first. This is the hard gate named in Day 167's spec.

## Trainer-review questions
1. Show me the Backstage-generated CI workflow — what does it actually run?
2. Why does Terraform state need to be remote rather than a local `.tfstate` file?
3. What would you do differently if the Backstage template had generated
   something you didn't need?
4. What's the blast radius if today's Terraform apply had a mistake — what's
   protecting the rest of the platform from it?

## Definition of done
Public repo scaffolded via the golden path, CI green on commit 1, capstone-specific
infra applied via Terraform with clean remote state, checkpoint confirmed by
trainer.
