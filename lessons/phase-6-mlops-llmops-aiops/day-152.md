## Theory (1h)

### A. Why tracking matters (10 min)
- A model trained once with no record of params/data/metrics is unreproducible and
  undebuggable — same failure mode as a hand-run deployment with no CI log.
- **MLflow Tracking** solves this: every training run is logged with its
  hyperparameters, metrics, and output artifacts, queryable later. Think of it as
  `git log` + CI build history, but for training runs.

### B. MLflow Tracking core concepts (20 min)
- **Run**: one execution of a training script. **Experiment**: a named group of
  runs (e.g., "anomaly-detector").
- Logging API: `mlflow.start_run()`, `mlflow.log_param(k, v)`,
  `mlflow.log_metric(k, v)`, `mlflow.log_artifact(path)`.
- Local tracking server: MLflow can run with a local file-based backend
  (`mlruns/` directory) with zero infra — no server needed for this exercise.
  Launch the UI locally with `mlflow ui` to browse runs in a browser.
- Comparing runs: the UI table sorts/filters by metric — this is how you pick the
  best of N training attempts, the ML equivalent of comparing CI build results.

### C. Model Registry (15 min)
- The registry sits on top of tracking: promote a specific run's model to a **named,
  versioned registry entry** (e.g., `anomaly-detector` v1, v2…) with a **stage**
  (`Staging`, `Production`, `Archived`).
- This is directly analogous to a container registry + environment promotion
  (dev → staging → prod tags) that you already do with Docker/Helm.
- Promotion is a deliberate, auditable step — never silently swap the "production"
  model.

### D. What "the project's metrics data" means here (15 min)
- From Phase 5, the project already emits Prometheus metrics (CPU, request rate,
  error rate, etc.) scraped and stored in the TSDB.
- Today we pull a slice of that historical data out via PromQL / the HTTP API
  (`/api/v1/query_range`) into a CSV — this becomes the first real (not synthetic)
  dataset the fresher trains on, foreshadowing Day 165's anomaly detector.

## Lab (2h)

### Part 1 — Install and first tracked run (30 min)
1. `pip install mlflow` (in `~/ml-lab`). Confirm with `mlflow --version`.
2. Rewrite yesterday's `train.py` to wrap training in
   `with mlflow.start_run():` and log: params (`n_estimators`, `random_state`),
   metrics (`accuracy`), and the artifact (`mlflow.sklearn.log_model(model, "model")`).
3. Run it 3 times varying `n_estimators` (e.g., 10, 50, 200). Run `mlflow ui`
   (default `http://127.0.0.1:5000`) and compare the three runs' accuracy.

### Part 2 — Pull real project metrics (40 min)
4. On the project's Prometheus, query a metric with history, e.g.
   `curl -G 'http://localhost:9090/api/v1/query_range' --data-urlencode 'query=rate(http_requests_total[5m])' --data-urlencode 'start=...' --data-urlencode 'end=...' --data-urlencode 'step=60s'`.
5. Write a small Python script to flatten the JSON response into a CSV
   (`timestamp,value`) using `pandas`. Save as `ml/data/request_rate.csv`.
6. Eyeball the data: `pandas.read_csv(...).describe()` — note mean, std, min, max.
   This is the dataset Day 165's anomaly model will build on.

### Part 3 — Registry promotion drill (30 min)
7. From the MLflow UI, pick the best of your 3 runs by accuracy; register its model
   as `anomaly-detector-poc` in the Model Registry.
8. Transition it to stage `Staging` via the UI or
   `mlflow models transition-model-version-stage`. Load it back with
   `mlflow.pyfunc.load_model("models:/anomaly-detector-poc/Staging")` and predict.
9. Discuss: what would "promote to Production" mean operationally here (who
   approves it, what gate must pass)? Write one sentence per gate.

### Part 4 — Project scaffold (20 min)
10. In `/opt/fresher_project/ml/`, add `data/`, `mlruns/` (gitignored — it's a local
    tracking store, treat like build output), and a `pull_metrics.py` script
    combining steps 4–5. Commit the script and directory structure (not the data
    dump or `mlruns/`).

**Definition of done:** 3 tracked runs visible in `mlflow ui` · one model registered
and promoted to `Staging` and successfully re-loaded · real Prometheus data pulled
into a CSV and inspected · `pull_metrics.py` committed with `mlruns/`/data gitignored.
