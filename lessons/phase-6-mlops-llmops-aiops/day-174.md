# Day 174 — Capstone Build 6: ML/AIOps Component Integration

Phase 6 · Capstone build sprint, day 6 of 7. This day closes success criterion 6
from `capstone-spec.md`: the anomaly-detection component must be visibly
integrated with this capstone service's own telemetry, not a second disconnected
model.

---

## Recall warm-up (5 min)

   anything was found)?
2. Show, in one sentence, how the Gatekeeper constraint rejects a bad manifest.
3. Where does the anomaly-detection model (Day 165) currently pull its metrics from?

## Objectives (today)
1. Point the Day 165 anomaly-detection pipeline (or a second, purpose-fit instance
   of the same approach) at the capstone service's own Prometheus metrics.
2. Confirm the resulting `AnomalyDetected` alert path (Day 166) is live for this
   service specifically and routed through the same Alertmanager/runbook pattern.

## Deliverables
- Either: the existing `anomaly-detector` CronJob extended to also score a metric
  from the capstone service, or a second, clearly-named instance of the same
  detection code pointed at the capstone's metric — decide and document which,
  and why (reuse vs isolation tradeoff, same reasoning as any shared-vs-dedicated
  infra decision).
- The `anomaly_score`/`anomaly_detected` metrics for this service exposed and
  scraped, with the existing Prometheus alerting rule (or a service-labeled
  variant of it) covering it.
- A runbook update noting this service is now covered by anomaly detection.
- A demonstrated end-to-end drill: synthetic anomalous traffic against the
  capstone service triggers a real `AnomalyDetected` alert routed correctly.

## Suggested time-box (3h)
- **0:00–0:20** — Recap Day 165's model training/serving shape and Day 166's
  Alertmanager wiring before touching code — decide reuse-vs-second-instance here.
- **0:20–1:30** — Wire the capstone service's metric into the anomaly pipeline
  (retrain if the metric's statistical properties differ meaningfully from the
  original project's metric — don't assume the same trained model transfers).
- **1:30–2:00** — Expose and scrape the resulting anomaly metrics; extend/label
  the Prometheus alerting rule.
- **2:00–2:40** — Run the end-to-end drill: generate synthetic anomalous traffic,
  confirm detection, confirm the alert fires and routes.
- **2:40–3:00** — Checkpoint review.

## Checkpoint (trainer confirms before Day 175 starts)
- The anomaly model is demonstrably scoring the capstone service's own metric
  data, not just the original project's.
- The end-to-end drill (synthetic anomaly → alert fired → routed correctly) was
  observed live by the trainer, not just described.
- Runbook updated to reflect the new coverage.
