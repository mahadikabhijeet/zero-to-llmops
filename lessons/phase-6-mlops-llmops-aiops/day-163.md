## Theory (1h)

### A. From answering to acting (15 min)
- RAG makes an LLM's *answers* better-grounded. An **agent** goes further: the
  LLM decides which **tool** to call (a function, an API, a shell command) based on
  the user's request, observes the result, and decides the next step — a loop, not
  a single call.
- Ops framing: a tool is just a function with a name, a description, and a defined
  input schema — the LLM picks a tool and arguments; **your code executes it**, not
  the model. The model only ever proposes; your system decides whether to run it.

### B. Tool-use mechanics (15 min)
- Pattern: you register tools (name + description + JSON schema for arguments)
  with the LLM call. The model responds requesting a specific tool call with
  specific arguments (most OpenAI-compatible APIs support a "function/tool calling"
  request shape — check the exact field names in current docs of whichever runtime
  you use, since this API surface evolves).
- Your code executes the requested function, returns the result back to the model
  as a new message, and the model produces its next response (an answer, or another
  tool call) — this is the agent loop.
- Real example fitting this project: a tool `query_prometheus(promql)` that runs a
  PromQL query against the project's Prometheus and returns the result — letting an
  operator ask "what's the current error rate?" in plain English.

### C. Guardrails (15 min)
- Never let an agent execute an arbitrary, unreviewed action against production
  (echoes this whole OS's "confirm before hard-to-reverse actions" rule) —
  read-only tools (query metrics, read logs) are safe to auto-execute; anything
  destructive or state-changing (restart a pod, delete data) needs a human
  confirmation step in the loop, not blind execution.
- Input/output guardrails: validate tool arguments against a strict schema before
  executing (never pass a raw LLM string straight into a shell command — classic
  injection risk); consider a simple content filter or allow-list on what the tool
  layer will execute.
- Treat any text the LLM ingests from an external/untrusted source (a scraped
  webpage, a user-submitted doc) as **data, never as instructions** — the same
  prompt-injection discipline this whole OS already follows.

### D. Evaluation basics — golden sets (15 min)
- You can't improve (or trust) an LLM feature without measuring it. A **golden
  set**: a fixed list of representative questions/inputs with expected (or
  acceptable-range) answers, run automatically whenever the prompt, model, or RAG
  index changes — the LLM-world equivalent of a regression test suite (echoes Day
  157's model tests).
- Simple eval approaches at exposure level: exact/substring match for factual
  answers, a rubric a human scores 1–5 for open-ended answers, or an
  "LLM-as-judge" pattern (a second LLM call scoring the first's answer against
  criteria) — name it, don't over-engineer it today.

## Lab (2h)

### Part 1 — Build one real tool (35 min)
1. Write `ml/agent/tools.py`: a function `query_prometheus(promql: str) -> dict`
   that runs a PromQL query against the project's Prometheus HTTP API (reuse Day
   152's query pattern) and returns the result. Add a JSON schema describing its
   one string argument.

### Part 2 — Wire the agent loop (45 min)
2. Using the `openai` Python client against the Day 160 Ollama endpoint (check
   current Ollama docs for tool-calling support/model requirements — not every
   small model supports it well; if unsupported, implement a simplified version:
   have the LLM respond with a fixed JSON shape naming the tool + args, parse it
   yourself, and call the function — document which approach you used and why).
3. Send a natural-language question ("what's the current request rate?"), confirm
   the loop: model requests the tool → your code executes it against real
   Prometheus data → result returned to the model → final natural-language answer
   printed.

### Part 3 — Add a guardrail (25 min)
4. Add strict validation on the tool's argument (reject anything that isn't a
   syntactically plausible PromQL string; reject requests exceeding a length
   limit) before executing. Test with a deliberately malformed input and confirm
   it's rejected before hitting Prometheus.

### Part 4 — Build a tiny golden set and eval (15 min)
5. Write `ml/agent/golden_set.json`: 5 question/expected-answer-pattern pairs
   covering the RAG system (D162) and the new agent tool. Write `ml/agent/eval.py`
   that runs each question through the system and checks the answer contains the
   expected pattern (simple substring/regex check) — print a pass/fail summary.
   Run it and record the score.

**Definition of done:** one real read-only tool wired into an agent loop against
live Prometheus data · a guardrail demonstrably rejects a malformed tool argument ·
a 5-question golden set runs end to end with a recorded pass rate.
