## Theory (1h)

### A. The gap MLflow doesn't close (10 min)
- MLflow versions runs, params, metrics, and model artifacts — but not the raw
  **data** feeding a run. If `request_rate.csv` changes silently, your tracked runs
  become unreproducible even though MLflow "looks" fine.
- Git itself is a poor fit for large/binary data files (bloats the repo, no diffing
  value). **DVC (Data Version Control)** solves exactly this — it's "git for data."

### B. DVC core mechanics (20 min)
- `dvc init` — adds `.dvc/` to a git repo (DVC layers on top of git, doesn't replace it).
- `dvc add data/request_rate.csv` — moves the real file into DVC's cache, replaces
  it in the working tree with a small `.dvc` pointer file (hash + size) that IS
  committed to git. This is exactly like Git LFS but with pluggable storage.
- `dvc push` / `dvc pull` — sync actual data to/from a **remote** (local dir, S3,
  GDrive, etc.); git only ever stores pointers.
- Versioning data = `git commit` the `.dvc` file after each `dvc add`; `git checkout`
  an old commit + `dvc checkout` restores the matching data version.

### C. DVC pipelines (20 min)
- `dvc.yaml` defines a **pipeline**: stages with `cmd`, `deps` (inputs), `outs`
  (outputs) — e.g., stage `pull_metrics` (deps: none, outs: raw CSV), stage `train`
  (deps: CSV + train.py, outs: model.joblib, metrics: accuracy).
- `dvc repro` re-runs only stages whose dependencies changed (hash-based, like
  Make/Terraform's dependency graph) — this is the reproducibility payoff: one
  command rebuilds the whole pipeline deterministically.
- `dvc dag` visualizes the pipeline graph.

### D. Remotes and reproducibility discipline (10 min)
- A **local remote** (just another directory, e.g., `/opt/dvc-remote`) is enough for
  this course — same pattern scales to S3 later with zero code change, only a
  `dvc remote add` config change.
- Discipline: never `dvc add` output files by hand if a pipeline stage produces them
  — let `dvc.yaml` own outputs; only `dvc add` raw/source data.

## Lab (2h)

### Part 1 — Init and first data version (30 min)
1. `pip install dvc`. In `/opt/fresher_project/`, run `dvc init`; commit the
   resulting `.dvc/` and `.dvcignore` to git.
2. Set up a local remote: `dvc remote add -d localremote /opt/dvc-remote`; commit
   `.dvc/config`.
3. `dvc add ml/data/request_rate.csv`; inspect the generated `.dvc` file; `git add`
   it plus the updated `.gitignore`; commit; `dvc push`.

### Part 2 — Version a second cut of data (25 min)
4. Re-run `pull_metrics.py` with a wider time range to produce a bigger CSV
   (overwrite the file). `dvc add` again; commit the new `.dvc` pointer with a clear
   message ("widen metrics window").
5. `git log -p -- ml/data/request_rate.csv.dvc` — show the hash changed between
   commits. `git checkout <old-commit> -- ml/data/request_rate.csv.dvc && dvc checkout`
   — confirm the old (smaller) CSV comes back. Then return to the latest commit.

### Part 3 — Build a pipeline (45 min)
6. Write `dvc.yaml` with two stages: `pull_metrics` (cmd: `python ml/pull_metrics.py`,
   outs: `ml/data/request_rate.csv`) and `train` (cmd: `python ml/train.py`, deps:
   `ml/data/request_rate.csv`, `ml/train.py`, outs: `ml/model.joblib`, metrics:
   a small `metrics.json` with accuracy — use `--metrics-no-cache` for the metrics file).
7. `dvc repro` — confirm both stages run. Run it again immediately — confirm DVC
   reports "nothing to reproduce" (nothing changed). Touch `train.py` (no real
   change) and rerun — confirm only `train` reruns, not `pull_metrics`.
8. `dvc dag` — view and explain the stage graph aloud.

### Part 4 — Project commit (20 min)
9. Commit `dvc.yaml`, `dvc.lock` (the generated lockfile — DVC's equivalent of a
   dependency lockfile), and the pipeline scripts to git. `dvc push` the data/model
   to the local remote.

**Definition of done:** two data versions tracked with working `dvc checkout` time
travel · local remote push/pull works · `dvc.yaml` pipeline reproduces end-to-end
with `dvc repro` and correctly skips unchanged stages.
