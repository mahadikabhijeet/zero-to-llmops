## Theory (1h)

### A. The problem RAG solves (15 min)
- An LLM only "knows" what was in its training data plus what's in its context
  window right now. It has no live access to your project's docs, runbooks, or
  private data unless you put that text into the prompt.
- **RAG (Retrieval-Augmented Generation)**: retrieve the most relevant chunks of
  your own documents at query time, and inject them into the prompt as context —
  the model then answers grounded in real, current, private text instead of
  guessing from training data.
- Ops framing: this is a *retrieval pipeline* feeding a *serving* step you already
  built (Day 160) — no retraining, no fine-tuning required.

### B. Embeddings and chunking (20 min)
- An **embedding** is a vector (list of floats) representing a piece of text's
  meaning — similar-meaning text produces vectors close together in that space.
  An embedding model is a separate (usually much smaller) model from the LLM doing
  generation.
- **Chunking**: documents are split into smaller passages (a few hundred tokens
  each, often with slight overlap) before embedding — because embedding models
  have their own context limits and because retrieval precision improves with
  smaller, topic-coherent chunks. Naive fixed-size chunking is the exposure-level
  approach; smarter (semantic) chunking exists but is out of scope today.

### C. Vector databases (15 min)
- A **vector DB** stores embeddings + their source text and supports fast
  similarity search (nearest-neighbor by vector distance) — the retrieval half of
  RAG.
- Lightweight, easy local options: **Chroma** or **Qdrant** — both run embedded/
  locally with no cluster required, good fits for CPU-only commodity hardware and
  for this course. Follow each tool's own quickstart for the exact client API;
  don't assume method names.
- Core operations regardless of tool: `add`/`upsert` (store chunk + embedding +
  metadata), `query`/`search` (given a query embedding, return top-K nearest chunks).

### D. The RAG request flow, end to end (10 min)
1. User asks a question → 2. Embed the question with the same embedding model used
for indexing → 3. Query the vector DB for top-K similar chunks → 4. Build a prompt:
system instructions + retrieved chunks + the question → 5. Send to the LLM (Day
160's Ollama server) → 6. Return the grounded answer, ideally citing which chunks
were used.

## Lab (2h)

### Part 1 — Index the project's docs (40 min)
1. Install a lightweight vector DB client (`pip install chromadb` or `pip install
   qdrant-client` — pick one and follow its official quickstart).
2. Install an embedding model runtime — either a small sentence-embedding model via
   `sentence-transformers` (CPU-friendly, well-documented) or Ollama's own
   embedding-model support (`ollama pull <embedding-model>` if one is available in
   its library) — check current docs rather than assuming.
3. Write `ml/rag/index.py`: walk the project's markdown docs (READMEs, runbooks
   from Day 125, this curriculum's day files are a good large corpus too), chunk
   each file (~300–500 tokens, simple fixed-size splitting), embed each chunk, and
   upsert into the vector DB with metadata (source file, chunk index).

### Part 2 — Query and retrieve (30 min)
4. Write `ml/rag/query.py`: takes a question, embeds it with the same model, queries
   the vector DB for top-3 chunks, prints the retrieved chunks with their source
   file — verify by eye that retrieval looks relevant before adding generation.

### Part 3 — Wire in generation (35 min)
5. Extend `query.py`: build a prompt combining the retrieved chunks + the question,
   send it to the Day 160 Ollama server via the OpenAI-compatible client, print the
   answer.
6. Ask 3–4 real questions about the project (e.g., "what alerting rules exist for
   the anomaly detector?" or "how is the model server deployed?") and sanity-check
   the answers against the actual docs.

### Part 4 — Failure-mode check (15 min)
7. Ask a question with no good answer in the docs (e.g., about something never
   documented) — observe whether the model hallucinates a plausible-sounding wrong
   answer or admits it doesn't know. Add an explicit instruction to the prompt
   ("only answer from the provided context; say 'not in the docs' if unsure") and
   retest — note the difference.

**Definition of done:** project docs indexed into a local vector DB · retrieval
returns relevant chunks for real questions · generation grounded in retrieved
context produces sane answers · a no-answer case tested and mitigated with an
explicit prompt instruction.
