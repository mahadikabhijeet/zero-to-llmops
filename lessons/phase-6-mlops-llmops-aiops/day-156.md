## Theory (1h)

### A. What today's DIY stack already gives you (10 min)
- By Day 155 you have, hand-assembled: tracking (MLflow), data/pipeline versioning
  (DVC), serving (FastAPI+Docker+Helm+CI). That's a real, working MLOps stack — just
  not automated end to end or multi-tenant.
- Today is about naming the platforms that automate/glue these pieces together and
  knowing when reaching for one is the right call — this is a **map, not a
  hands-on build** (no lab-heavy install of a full platform).

### B. Kubeflow concepts (20 min)
- Kubeflow = an ML platform **on top of Kubernetes** (fits everything you know from
  Phase 3). Core idea: **Pipelines** — a DAG of containerized steps (data prep →
  train → evaluate → deploy), each step is just a container, orchestrated like
  Argo Workflows under the hood.
- Other components you'll see named in the wild: Katib (hyperparameter tuning),
  KServe (model serving with autoscaling-to-zero, canary rollouts for models —
  directly analogous to Day 136's Istio canary work).
- Why it's heavy: real operational cost (its own control plane, upgrades, RBAC) —
  worth it at team/org scale with many models and pipelines, not for one fresher's
  one model.

### C. Managed platforms — SageMaker as the archetype (15 min)
- AWS SageMaker: managed notebooks, managed training jobs (spin up GPU instances on
  demand, pay per job), a managed Model Registry, and managed endpoints (serving)
  with built-in autoscaling and A/B/canary traffic splitting.
- The pattern is the same shape as Kubeflow's, but AWS runs the control plane —
  trade DIY control for less ops burden (echoes the whole Phase 4 build-vs-buy
  conversation, e.g., EKS vs ECS/Fargate).
- Equivalent managed options exist per cloud (Vertex AI on GCP, Azure ML) — same
  concept-mapping instinct from Days 113–115 applies here: know one deeply,
  recognize the shape everywhere else.

### D. Platform vs DIY — a decision framework (15 min)
- Signals to reach for a platform: many models/teams sharing infra, need for
  managed GPU scheduling, need built-in experiment UI/governance, compliance
  requirements for audit trails.
- Signals DIY is enough (today's case): single model, small team, infra you already
  operate (k8s cluster + registry + CI) — a platform would add ops burden without
  removing enough toil to be worth it.
- This mirrors the IDP conversation from Day 141: a platform is worth building/
  adopting only when it removes more toil than it adds.

## Lab (2h)

### Part 1 — Read the docs, don't install (40 min)
1. Read the Kubeflow Pipelines overview and the KServe overview (official docs) —
   focus on: what is a "pipeline component," how is a trained model served, how
   does canary/traffic-split work for a KServe `InferenceService`.
2. Read the SageMaker "how it works" overview — identify the equivalents of:
   MLflow tracking, MLflow registry, and your FastAPI/Helm serving setup.

### Part 2 — Build the mapping table (40 min)
3. Produce a table (Markdown, save into the project docs) mapping: DIY component
   (MLflow tracking / MLflow registry / DVC / FastAPI+Helm) → Kubeflow equivalent
   → SageMaker equivalent. Leave a "notes" column for what's genuinely different,
   not just renamed.

### Part 3 — Decision framework applied (30 min)
4. Write a one-page decision memo: "Should the fresher project migrate to Kubeflow
   or SageMaker?" Answer with a clear no-for-now, backed by the signals from
   Theory D — this is a job-interview-shaped answer ("when would you NOT use a
   platform") worth rehearsing out loud.

### Part 4 — Optional stretch (10 min)
5. If time allows, spin up a Kubeflow Pipelines quickstart (many offer a
   local/lightweight try-it sandbox in their docs) just to see the pipeline UI —
   purely exposure, not required for the project.

**Definition of done:** mapping table committed to project docs · decision memo
written with a defended recommendation · can explain, unscripted, when a platform
earns its complexity vs when DIY wins.
