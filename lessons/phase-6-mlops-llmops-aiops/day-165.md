## Theory (1h)

### A. Why anomaly detection, and why here (10 min)
- Traditional alerting (Day 125) is threshold-based: "fire if error rate > 5%."
  That misses anomalies with no fixed threshold — a metric behaving unusually for
  its *own* normal pattern (e.g., request rate at 3am that's fine for weekdays but
  never happens on Sundays). Anomaly detection catches "unusual for this metric,"
  not "over a fixed line."
- This closes the DevOps-skills-to-ML-skills loop that's run through the whole
  phase: same Prometheus data (Phase 5), same alerting destination (Alertmanager,
  Day 166), one small model in between.

### B. Anomaly detection approaches — pick the simplest that works (20 min)
- Exposure-level goal: **unsupervised, univariate** anomaly detection on a single
  time series — no labeled "this was an anomaly" dataset required (rare in
  practice anyway).
- Two well-known, well-documented approaches suitable for CPU and scikit-learn:
  - **Statistical**: rolling mean/std, flag points beyond N standard deviations
    (a "z-score" approach) — simple, explainable, a good baseline.
  - **Isolation Forest** (`sklearn.ensemble.IsolationForest`): an unsupervised
    model that isolates outliers by random partitioning — handles more complex
    patterns than a fixed z-score threshold, still CPU-cheap, still a
    scikit-learn `.fit()`/`.predict()` interface you already know from Day 151.
- Start with the statistical baseline to build intuition, then compare against
  Isolation Forest — a real engineering habit: always have a simple baseline
  before reaching for a fancier model.

### C. Data prep specifics for time series (15 min)
- Reuse Day 152's PromQL pull pattern to get a longer historical window of a
  meaningful metric (e.g., request rate, error rate, or latency p99 from the
  project's app).
- Feature engineering stays minimal at exposure level: the raw value, and
  optionally a rolling-window statistic (rolling mean, rolling std) as extra
  features for Isolation Forest — resist the urge to over-engineer.
- Train/test split for time series must respect **time order** (train on earlier
  data, evaluate on later data) — never randomly shuffle time series, unlike Day
  151's iris dataset.

### D. From "is this an anomaly" to "should this alert" (15 min)
- A model's anomaly score is not automatically an alert — apply a decision
  threshold (score above X → anomaly) tuned to an acceptable false-positive rate,
  same tuning conversation as Day 125's alert-routing thresholds.
- Output contract for Day 166: the model needs to run continuously (or on a
  schedule) against live metrics and emit something Alertmanager can consume —
  today builds the detection logic and validates it; Day 166 does the wiring.

## Lab (2h)

### Part 1 — Pull a real, longer time series (30 min)
1. Reuse/extend `ml/pull_metrics.py` (Day 152) to pull a longer historical window
   (as much history as your project's Prometheus retains) of one metric — pick
   one with visible variation (e.g., request rate or latency p99). Save as
   `ml/data/anomaly_source.csv` and `dvc add` it (Day 153 discipline).

### Part 2 — Statistical baseline (30 min)
2. Write `ml/anomaly/baseline.py`: compute a rolling mean/std (e.g., 1-hour
   window via `pandas.rolling`), flag points where
   `abs(value - rolling_mean) > 3 * rolling_std` as anomalies.
3. Plot the series with anomalies marked (matplotlib or just print flagged
   timestamps) — eyeball whether flagged points look genuinely unusual.

### Part 3 — Isolation Forest model (45 min)
4. Write `ml/anomaly/train.py`: build features (raw value + rolling mean/std),
   respect time-ordered train/test split, train
   `IsolationForest(contamination=0.01, random_state=42)` (start with a low
   contamination estimate — the expected anomaly rate — and justify the number in
   a comment).
5. Wrap in MLflow (Day 152 pattern): log params, log a chosen evaluation summary
   (e.g., count and rate of flagged anomalies, compared against the statistical
   baseline's flags — how much do they agree?), log the model artifact.
6. Save the trained model via `mlflow.sklearn.log_model` and register it as
   `anomaly-detector` in the registry, promoted to `Staging`.

### Part 4 — ★ Project step: wire it as a scheduled job (15 min)
7. Write `ml/anomaly/detect.py`: loads the registered model, pulls the latest
   window of live metrics, scores them, and prints/writes any detected anomalies
   with timestamps and scores.
8. Add this as a Kubernetes CronJob (Day 72 skill) on the project's cluster,
   running every N minutes, writing output to a location Day 166 will consume.
   Commit the CronJob manifest, scripts, and DVC-tracked data pointer.

**Definition of done:** longer metric history pulled and DVC-tracked · statistical
baseline and Isolation Forest both implemented and compared · model tracked in
MLflow and registered/promoted to Staging · `detect.py` runs as a scheduled
CronJob producing anomaly output ready for Day 166's Alertmanager wiring.
