## Objectives (today)
1. Implement the capstone's actual core logic (not placeholder code) — whatever
   the Day 167 scope decision named.
2. Harden CI beyond the scaffold's defaults: real tests, dependency/SAST scanning
   (Day 143 muscle), and a build artifact (container image) produced and pushed.

## Deliverables
- Working core service(s) with a real, if small, feature set — enough to be
  meaningfully exercised by later days' observability, chaos, and load tests.
- A test suite (`pytest` or equivalent) covering at least the core logic paths,
  running in CI.
- CI pipeline stages: lint → test → build image → scan (trivy/grype, Day 143) →
  push to registry — all green, all real (no skipped steps).
- A README section describing what the service does and how to run it locally.

## Suggested time-box (3h)
- **0:00–0:20** — Recap 12-factor app principles (Day 50) and the testing pyramid
  (Day 38) before writing new code — keep config out of code, keep tests fast.
- **0:20–2:00** — Implement the core feature(s). Write tests alongside, not after
  (or at minimum, immediately after each function, not at the end of the day).
- **2:00–2:30** — Wire the hardened CI pipeline: add the scan step, confirm it
  actually fails the build on a high-severity finding (test this by deliberately
  adding a vulnerable dependency, then removing it once confirmed).
- **2:30–3:00** — Checkpoint review: run the full CI pipeline once more end to end
  from a clean commit.

## Checkpoint (trainer confirms before Day 171 starts)
- CI pipeline has all five stages (lint/test/build/scan/push) and all are green.
- The scan step was proven to actually catch something (not silently passing
  because it isn't really wired in).
- Core service runs locally per the README instructions, verified by the trainer
  running them cold.

## Trainer-review questions
1. Walk through one test in the suite — what specifically does it protect against?
2. Show me the scan step catching a real finding — how do you know it isn't a no-op?
3. What's still a placeholder or a shortcut in today's build, and what's the
   plan to close it before Day 177's demo?
4. If this service needed a second core feature next sprint, where would it go
   architecturally, and why?

## Definition of done
Core service(s) implemented with real logic, test suite green in CI, five-stage CI
pipeline fully wired and verified (including a proven scan-catch), README updated,
checkpoint confirmed.
