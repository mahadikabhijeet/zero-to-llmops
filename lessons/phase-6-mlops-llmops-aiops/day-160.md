# Day 160 — LLMOps I: Serving a Small OSS Model (CPU-Friendly), OpenAI-Compatible API

Phase 6 · follows Day 159 (LLM fundamentals: tokens, context, GPU basics, cost levers).

**Hardware note:** vLLM is the industry-standard high-throughput LLM server, but it
is built around GPU batching and is not a good CPU fit for a home-lab machine.
Today uses **Ollama** (backed by llama.cpp) instead — it runs small quantized
models acceptably on CPU-only commodity hardware and exposes both its own API and
an OpenAI-compatible `/v1/chat/completions` endpoint, so the serving contract you
learn today transfers directly to a GPU-backed vLLM deployment later in your
career without relearning the client side.

## Theory (1h)

### A. Why a runtime matters, not just a model file (15 min)
- An LLM "model" is just weights — you need a **runtime** to load them and run
  inference efficiently. Runtimes differ hugely in hardware assumptions: vLLM
  (GPU, high-throughput serving), llama.cpp (CPU-first, quantized formats),
  Ollama (a friendly wrapper around llama.cpp with model pulling, a REST API, and
  an OpenAI-compatible layer).
- Ops takeaway: the same conceptual serving contract (chat completion request in,
  completion out) can sit on very different runtimes — pick the runtime for your
  hardware, not the other way around.

### B. Quantization, briefly (10 min)
- Quantization reduces the numeric precision of model weights (e.g., 16-bit down
  to 4-bit) to shrink memory footprint and speed up CPU inference, at some quality
  cost. Ollama models are typically distributed already quantized (e.g., GGUF
  format) — you'll consume this, not build it, today. Day 164 revisits quantization
  as a cost lever in more depth.

### C. The OpenAI-compatible API pattern (20 min)
- Because OpenAI's chat completion API became a de facto standard, most serving
  tools (Ollama, vLLM, and many others) expose a compatible endpoint
  (`/v1/chat/completions`) accepting the same request shape: a `model` name and a
  `messages` array of `{role, content}` objects, returning a `choices[].message`.
- Operational upside: your client code, load-testing scripts, and observability
  wrapper (Day 164) don't need to change when you swap the underlying runtime —
  same reason an ALB doesn't care which app server is behind it.

### D. What "serving" means operationally here (15 min)
- Ollama runs as a local daemon (`ollama serve`) exposing HTTP; a model is "pulled"
  once (downloaded, cached locally) then loaded on first request.
- Cold start matters: the first request after starting the daemon (or after the
  model is evicted from memory) is slower — same cold-start conversation as
  serverless (Day 102) or Kubernetes pod startup.
- Resource limits apply exactly like any other containerized workload — CPU/memory
  requests and limits matter even more here since inference is CPU-hungry.

## Lab (2h)

### Part 1 — Install and pull a small model (30 min)
1. Install Ollama per its official docs for your OS.
2. `ollama pull <small-model>` — choose the smallest well-known instruction-tuned
   model documented in Ollama's model library as suitable for CPU-only use (check
   Ollama's library page for current recommendations rather than assuming a name;
   sizes in the low single-digit billions of parameters are the CPU-friendly range).
3. `ollama run <model>` — have a short interactive conversation; note the response
   latency on your CPU.

### Part 2 — Use the OpenAI-compatible endpoint (35 min)
4. With `ollama serve` running, `curl` its OpenAI-compatible endpoint directly:
   `curl http://localhost:11434/v1/chat/completions -d '{"model": "<model>",
   "messages": [{"role": "user", "content": "..."}]}'` (confirm exact port/path in
   Ollama's docs — it has changed across versions).
5. Write a small Python client using the official `openai` Python package pointed
   at Ollama's base URL (`base_url="http://localhost:11434/v1"`) — this is the
   whole point: OpenAI-shaped client code, local CPU-served model.

### Part 3 — Containerize the runtime (35 min)
6. Run Ollama as a container instead (official image) with a persistent volume for
   pulled models; confirm the same client from step 5 works unchanged against the
   containerized endpoint.
7. Set explicit CPU/memory limits on the container (Day 47/69 skills) and observe
   the effect on response latency with `time curl ...`.

### Part 4 — Latency measurement (20 min)
8. Send 10 sequential requests with a fixed prompt; record response time for each
   (first request vs steady-state) — confirm the cold-start effect from Theory D.
9. Note down: model name, quantization level (from `ollama show <model>`), and
   average steady-state latency — this becomes your baseline for Day 164's
   cost/perf tuning lab.

**Definition of done:** small model pulled and running locally on CPU · direct curl
against the OpenAI-compatible endpoint succeeds · Python client using the `openai`
package works against the local endpoint · containerized version works with
resource limits set and a recorded latency baseline.
