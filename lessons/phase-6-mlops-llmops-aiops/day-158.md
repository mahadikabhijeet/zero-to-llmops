## Theory (1h)

### A. A model can fail silently — that's the whole problem (10 min)
- Unlike a crashed pod, a model that's gotten worse keeps returning HTTP 200 with
  confident-looking wrong answers. There's no exception to alert on — this is why
  model monitoring is its own discipline, not just "reuse your existing alerts."

### B. Drift — the core concept (20 min)
- **Data drift**: the distribution of incoming inputs shifts away from what the
  model was trained on (e.g., request patterns change after a product change).
- **Concept drift**: the relationship between inputs and the correct output
  changes, even if input distribution looks the same (the real world's rules
  shifted).
- **Prediction drift**: a cheap proxy signal — the distribution of the model's
  *outputs* shifts over time, often detectable without needing ground-truth labels.
- Detecting drift without labels: compare recent input feature distributions
  against the training-set baseline (e.g., simple statistical distance measures
  like population stability index, or just tracking mean/std over time) — exposure-
  level, not a deep stats course.

### C. Performance tracking (15 min)
- When ground truth eventually arrives (labels, or a proxy like "did the
  operator override the model's alert"), track accuracy/precision/recall over time
  as a **metric**, not a one-off number — this is exactly a Prometheus gauge/counter,
  scraped and graphed like any other SRE metric (Day 122–124 skills, reused).
- Emit model-specific metrics from the FastAPI server: prediction count, prediction
  latency histogram, class distribution of predictions, and (when available)
  rolling accuracy — expose via `/metrics` using the same client library pattern
  as Day 122's exporters.

### D. Feedback loops (15 min)
- A feedback loop closes the lifecycle: monitoring signals (drift, degraded
  accuracy) should be able to **trigger retraining** — wiring today's monitoring
  into yesterday's CI/CD pipeline (e.g., an Alertmanager webhook that kicks off the
  `ml-retrain.yml` workflow, or simply a scheduled retrain that's frequent enough
  to absorb drift).
- Danger to flag: a feedback loop that retrains on the model's own (possibly wrong)
  predictions without ever seeing real ground truth can reinforce its own errors —
  always prefer a real label source when one exists.

## Lab (2h)

### Part 1 — Instrument the model server (40 min)
1. `pip install prometheus-client` (or `prometheus-fastapi-instrumentator`). Add a
   `/metrics` endpoint to `app.py` from Day 155 exposing: `predictions_total`
   (Counter, labeled by predicted class), `prediction_latency_seconds`
   (Histogram), and a Gauge for the last-computed mean of a key input feature
   (proxy for input drift).
2. Add a scrape config entry for the model-server Service on your project's
   Prometheus (same pattern as any other target from Day 122).

### Part 2 — Simulate drift (40 min)
3. Write a small script that sends a batch of "normal" requests (sampled near the
   training distribution) then a batch of "shifted" requests (deliberately
   out-of-range feature values). Watch the input-feature Gauge move in Grafana/
   Prometheus.
4. Build a simple PromQL alerting rule: fire if the mean input-feature Gauge
   deviates more than N standard deviations from a fixed baseline value over a
   5-minute window (reuse Day 123's alerting-rule syntax).

### Part 3 — Dashboard (25 min)
5. Add a "Model Health" row to the project's Grafana dashboard (Day 124 skill):
   prediction rate, prediction latency, class distribution over time, drift gauge.

### Part 4 — Close the loop (15 min)
6. Document (in `ml/README.md`) how the drift alert *would* trigger the Day 157
   retraining workflow (e.g., Alertmanager webhook → GitHub Actions
   `repository_dispatch` trigger) — describe the wiring; full Alertmanager
   integration is Day 166's job for the anomaly detector specifically.

**Definition of done:** `/metrics` endpoint live and scraped · drift simulation
visibly moves the Gauge and the dashboard · a PromQL alert rule fires on simulated
drift · feedback-loop wiring documented.
