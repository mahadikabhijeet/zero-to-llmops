## Theory (1h)

### A. Why this day exists — the instructor's differentiator (10 min)
- Everything so far made the LLM feature *work*. Today makes it *affordable and
  fast at scale* — the same FinOps discipline from Days 117–120, now applied to
  AI workloads. This is explicitly a differentiator for the fresher's resume:
  most DevOps/SRE candidates can deploy an LLM; fewer can explain its unit
  economics.

### B. Caching (15 min)
- **Exact-match caching**: identical prompt → return the stored response instead of
  re-running inference. Simple key-value cache (e.g., a hash of the prompt as key)
  — cheap, high win-rate for repeated/templated queries (a support bot answering
  the same FAQ repeatedly).
- **Semantic caching**: cache by *meaning* (embed the query, check for a
  near-duplicate previous query above a similarity threshold, reuse its answer) —
  higher hit rate, more complexity and a real risk of returning a stale/wrong
  answer for a subtly different question; use conservatively.
- Cost framing: cache hit rate directly cuts your token spend and latency
  proportionally — the single highest-leverage lever for repetitive workloads.

### C. Batching and quantization (20 min)
- **Batching**: serving multiple requests' inference together shares the sequential
  generation cost more efficiently — this is exactly why GPU-based servers like
  vLLM get their throughput advantage (continuous batching); on CPU with Ollama,
  concurrency is much more limited, which is precisely why Day 160 flagged this
  hardware tradeoff explicitly.
- **Quantization** (recap from Day 160): using a lower-precision (e.g., 4-bit)
  version of a model trades some answer quality for a smaller memory footprint and
  faster CPU inference — check the specific quantized model's documented quality
  benchmarks before assuming "good enough" rather than guessing.
- Rule of thumb for this course: on CPU, the biggest wins come from (1) picking the
  smallest model that meets the quality bar, and (2) capping output length — GPU-
  style batching gains are a "when you eventually have a GPU" lever, name it, don't
  chase it on this hardware.

### D. GPU utilization and cost levers, tied together (15 min)
- On GPU, the ops-relevant metric is **utilization** — an idle or underused GPU is
  pure waste (same "rightsizing" idea from Day 118, applied to accelerators).
  Autoscaling-to-zero for bursty LLM workloads (as KServe/managed platforms offer,
  Day 156) avoids paying for idle GPU time.
- Full lever list, now measured instead of brainstormed (Day 159 built the
  unranked list): model size selection, `max_tokens` capping, exact/semantic
  caching, batching (GPU), quantization, and — the FinOps classic — right-sizing
  the serving instance/pod to actual load, verified with real numbers not guesses.

## Lab (2h)

### Part 1 — Measure the baseline (25 min)
1. Reuse Day 160's baseline: 10 requests to the Ollama server, recorded latency and
   (from `ollama show` / model docs) approximate token throughput.
2. Add token counting to `ml/rag/query.py` (Day 162) or `ml/agent` (Day 163): log
   input tokens, output tokens, and wall-clock latency per request to a CSV.

### Part 2 — Implement exact-match caching (35 min)
3. Add a simple cache layer in front of the RAG or agent query function: hash the
   final prompt (post-retrieval), check an in-memory (or SQLite-backed) dict before
   calling the LLM; store the response on a miss.
4. Run the same 5 questions from Day 163's golden set twice through the cached
   path; measure and compare latency for the first pass (cold) vs second pass
   (cached) — record the speedup and the "cost" (zero tokens spent) explicitly.

### Part 3 — Cap output length and measure the effect (30 min)
5. Re-run the golden set with `max_tokens` set to a small vs generous value (e.g.,
   64 vs 512); compare latency and, by eye, whether answer quality/completeness
   suffered. Document the tradeoff in a short table.

### Part 4 — Write the FinOps-for-AI memo (30 min)
6. Produce `ml/finops-ai-memo.md`: given the measured baseline, project a rough
   monthly cost estimate for two scenarios — (a) this workload run on a small
   always-on CPU instance, and (b) the same workload on a GPU instance sized for a
   documented small-model inference benchmark (cite a real cloud instance type and
   its published on-demand price; do not invent a number). State clearly which
   levers (cache hit rate, output cap, model size) matter most for cost in each
   scenario, and your recommendation.

**Definition of done:** per-request token/latency logging in place · caching
demonstrably cuts latency to near-zero on a repeat query · output-cap tradeoff
measured and documented · FinOps-for-AI memo written with sourced (not invented)
cost figures.
