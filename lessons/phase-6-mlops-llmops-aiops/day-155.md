## Theory (1h)

### A. From `.predict()` to an HTTP endpoint (15 min)
- Serving = wrapping `model.predict()` behind an API so other systems can call it
  without knowing Python or scikit-learn exists.
- **FastAPI** is a natural fit here: you already know Python (Phase 1), and FastAPI
  gives typed request/response models, auto-generated OpenAPI docs at `/docs`, and
  an ASGI server (`uvicorn`) — no new paradigm, just a thin HTTP layer.
- Load the model **once at startup** (not per-request) — a request-time model load
  is a classic ML-serving latency bug.

### B. Designing the serving contract (15 min)
- Define a Pydantic request model matching your feature columns; a response model
  with the prediction (+ optionally a confidence/probability).
- Add a `/health` endpoint (liveness) separate from `/predict` — same probe
  discipline as Day 69's liveness/readiness split, now applied to a model server.
- Version the API path or response (`/v1/predict`) so a future model change doesn't
  silently break callers — same discipline as any other API you've built.

### C. Containerizing a model server (15 min)
- Dockerfile shape: base Python image → copy `requirements.txt` → `pip install` →
  copy `model.joblib` (or pull it from the MLflow registry at build/start time) →
  copy app code → `CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]`.
- Multi-stage build (Day 46 skill) keeps the final image lean — no need for
  training-only packages in the serving image.
- Bake the model artifact into the image for now (simplest, most reproducible);
  discuss the tradeoff vs pulling it at container start (faster iteration, but a new
  runtime dependency on the registry being reachable).

### D. Deploying with skills you already have (15 min)
- This is not new infrastructure — it's the Day 45–48/74–78 Docker+Helm+CI muscle
  pointed at a new kind of workload.
- CI pipeline addition: build the serving image → scan (trivy, Day 48) → push to
  registry → Helm upgrade on the cluster, identical shape to the app pipeline.
- A model server is "just another microservice" from the platform's point of view —
  that reframing is the whole point of today.

## Lab (2h)

### Part 1 — Build the FastAPI app (35 min)
1. `pip install fastapi uvicorn[standard]` in `~/ml-lab`.
2. Write `app.py`: load `model.joblib` at import time; define a Pydantic
   `PredictRequest` matching your feature schema; `POST /v1/predict` returns the
   prediction; `GET /health` returns `{"status": "ok"}`.
3. Run locally: `uvicorn app:app --reload`; hit `/docs` in a browser; `curl` a
   sample prediction from `/v1/predict`.

### Part 2 — Containerize (35 min)
4. Write a Dockerfile (multi-stage: builder installs deps, final stage copies venv
   + app + `model.joblib`). Build: `docker build -t model-server:v1 .`
5. Run it: `docker run -p 8000:8000 model-server:v1`; re-run the same `curl` from
   step 3 against the container.
6. `trivy image model-server:v1` — review findings, note any you'd fix vs accept.

### Part 3 — Push and deploy (35 min)
7. Tag and push to your registry (same one used in Phase 2/3): `docker tag ... &&
   docker push ...`.
8. Add a minimal Helm template (reuse the project chart's structure from Day 75) for
   a `model-server` Deployment + Service, with liveness probe on `/health`.
   `helm upgrade --install model-server ./chart -n <ns>`.
9. `kubectl port-forward` to the service; confirm `/v1/predict` responds from
   inside the cluster's Helm-managed deployment.

### Part 4 — CI wiring (15 min)
10. Add a CI job (GitHub Actions) that builds, scans, and pushes the `model-server`
    image on changes to `ml/` — do not wire the Helm deploy step into GitOps yet;
    that's Day 166's job for the anomaly-detector specifically. Commit.

**Definition of done:** FastAPI app serves predictions locally and in a container ·
image passes a reviewed trivy scan · deployed via Helm to the cluster and reachable
via port-forward · CI builds/scans/pushes on `ml/` changes.
