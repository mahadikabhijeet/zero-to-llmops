## Theory (1h)

### A. Why manual promotion (Day 152) doesn't scale (10 min)
- Manually eyeballing MLflow's UI and clicking "promote to Staging" works for one
  demo. In a real pipeline, retraining should be **triggered** (new data, schedule,
  or code change) and **gated** (only promote if the new model is actually better/
  safe) — the ML equivalent of a CI pipeline gating a merge.

### B. Anatomy of an ML CI/CD pipeline (20 min)
- Trigger: cron (nightly retrain), or a CI trigger on `ml/` path changes (same
  GitHub Actions trigger patterns from Day 40–41).
- Stage 1 — **reproduce**: `dvc repro` pulls latest data, retrains, produces a new
  `model.joblib` + `metrics.json`.
- Stage 2 — **gate**: automated checks before promotion is even considered:
  - Accuracy/metric threshold (don't promote a model worse than a fixed floor).
  - Comparison against the current Production model's metric on the same
    evaluation set (don't regress).
  - Basic sanity/unit tests on the model (e.g., predict on a few known inputs,
    check output shape/type) — same spirit as `pytest` from Day 38, applied to a
    model artifact.
- Stage 3 — **register**: if gates pass, register the new model version in MLflow's
  registry (Day 152 mechanics, now automated).
- Stage 4 — **promote**: move the new version to `Staging` automatically; promotion
  to `Production` stays a **human-approved step** (same "hard-to-reverse action
  needs a human" principle you already apply everywhere else) — e.g., a manual
  GitHub Actions approval gate (`environment:` protection rules, familiar from
  earlier deploy pipelines).

### C. Model tests worth writing (15 min)
- Schema test: input/output shape and types match the contract.
- Invariance test: a small perturbation that shouldn't change the prediction,
  doesn't (e.g., irrelevant feature noise).
- Regression test: a fixed set of "golden" inputs with known expected outputs,
  checked every run — catches silent behavior drift.
- These live in the repo as real test files, run by the same CI runner as your
  existing `pytest` suite.

### D. Rollback (15 min)
- Because the registry keeps every version, rollback = re-point serving at the
  previous `Production`-tagged version — no retraining needed, same instant-rollback
  property as a Helm rollback (Day 64) or ArgoCD rollback (Day 134).
- Discuss: what would trigger an automatic rollback in production (e.g., a drift/
  performance alert from Day 158's monitoring) vs a manual one.

## Lab (2h)

### Part 1 — Write model tests (35 min)
1. Create `ml/tests/test_model.py` with `pytest`: a schema test (predict on a
   correctly-shaped input, check output type), a regression test (2–3 fixed inputs
   with expected outputs from the current model), and one invariance test.
2. Run `pytest ml/tests/` locally against the current `model.joblib`; confirm green.

### Part 2 — Build the gate script (40 min)
3. Write `ml/gate.py`: loads `metrics.json` from the latest `dvc repro`, compares
   accuracy against (a) a fixed floor (e.g., 0.85) and (b) the currently-registered
   `Production` model's logged accuracy (query via MLflow client). Exit non-zero if
   either check fails.
4. Run it once against your current model to confirm it exits 0 (passes).

### Part 3 — Wire the CI pipeline (35 min)
5. Add a GitHub Actions workflow `ml-retrain.yml`: on schedule (nightly cron) or on
   push to `ml/data/**`, run `dvc repro`, `pytest ml/tests/`, then `python
   ml/gate.py`. If all pass, register the new model version via a script calling
   the MLflow client and transition it to `Staging`.
6. Add a manual approval step (GitHub Environments with required reviewers) before
   a separate job transitions `Staging` → `Production`.

### Part 4 — Break it on purpose (10 min)
7. Intentionally lower the accuracy floor's data (e.g., corrupt a training row) and
   confirm the gate fails and blocks promotion — the whole point of the exercise.

**Definition of done:** model tests pass locally and in CI · gate script correctly
blocks a deliberately-worsened model · CI pipeline auto-registers and promotes to
Staging, with a human-approval gate before Production.
