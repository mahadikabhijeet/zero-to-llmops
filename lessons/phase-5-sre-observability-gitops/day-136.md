## Theory (1h)

### A. mTLS in the mesh (20 min)
- Mutual TLS: both client and server sidecars present certificates —
  service-to-service traffic is encrypted and authenticated without any
  app-level TLS code.
- `PeerAuthentication` CR sets the mesh-wide or per-namespace mode:
  `PERMISSIVE` (accepts both plaintext and mTLS — safe default during
  migration) vs `STRICT` (mTLS only — refuses plaintext).
- Istio's `istiod` acts as the certificate authority, auto-rotating
  workload certs — no manual cert management, unlike Day 20's self-signed
  nginx cert.

### B. Canary releases using traffic splitting (15 min)
- A canary release ships a new version to a small traffic slice, watches
  its **SLO/error-rate/latency** (Days 121–130's instrumentation is exactly
  what makes this safe to judge), and ramps up only if healthy — the direct
  payoff of everything built this phase.
- Progressive delivery pattern: 5% → watch 10 min → 25% → watch → 50% →
  watch → 100%, with an automatic or manual abort (revert weights to 0%)
  if error rate/latency breaches threshold at any step.
- Contrast with Day 64's Kubernetes rolling update: that shifts traffic by
  replacing pods gradually (coupled to replica count); Istio's canary
  decouples "how many pods" from "how much traffic" entirely.

### C. Kiali — mesh observability (15 min)
- Kiali visualizes the mesh's live service graph: which services talk to
  which, request volume/error rate/latency per edge, mTLS status per
  connection — a topology view that Grafana's per-service dashboards don't give.
- Complements, doesn't replace, Days 122–130's stack — Kiali reads from
  the same Prometheus and adds the Istio-specific traffic-graph lens.

### D. Fault injection (10 min)
- Istio can inject synthetic delays/aborts via `VirtualService.http.fault`
  — useful for testing whether the app's timeout/retry logic (relevant
  again on Day 144) actually degrades gracefully, without needing chaos-mesh.

## Lab (2h)

### Part 1 — Enable mTLS (25 min)
1. Apply a `PeerAuthentication` in `PERMISSIVE` mode for the `default`
   namespace; confirm existing traffic still works.
2. Switch to `STRICT`; re-test — confirm mesh traffic still works (both
   sides have sidecars) but a plain `curl` from a non-mesh pod (no sidecar)
   now fails — this demonstrates what mTLS actually enforces.

### Part 2 — Run a real canary of v2 (50 min)
3. Using Day 135's v1/v2 subsets, start the canary at 5% weight to v2.
4. Generate load and watch the Day 124 RED dashboard filtered to `v2` pods
   (or add a `version` label filter) — confirm error rate/latency look healthy.
5. Ramp: 5% → 25% → 50%, pausing ~2 minutes at each step to watch the
   dashboard and Prometheus alerts (Day 123/130) for any breach.
6. At 50%, deliberately inject a fault into v2 via
   `VirtualService.http.fault.abort.percentage: 50, httpStatus: 500` on
   the v2 route — watch `HighErrorRate` fire, then immediately abort the
   canary (weights back to 100/0 on v1) — this is the "abort on signal" drill.

### Part 3 — Kiali (30 min)
7. Install Kiali (`istioctl` addon or `kiali-operator` Helm chart);
   port-forward and open the UI.
8. View the live graph during a load-generation run; identify the v1/v2
   split visually, check the mTLS padlock icons on each edge.

### Part 4 — Project step (15 min)
9. Document the canary procedure (ramp steps, watch dashboard, abort
   condition) as `/opt/fresher_project/docs/canary-runbook.md`.
10. Commit the `PeerAuthentication` manifest and the canary runbook.

**Definition of done:** STRICT mTLS enforced and verified; a canary ramp
from 5% to 50% performed with dashboard monitoring; an abort executed
correctly after an injected fault; Kiali graph observed during load.
