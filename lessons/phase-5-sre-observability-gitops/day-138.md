## Theory (1h)

### A. Why load-test deliberately, not just observe production (15 min)
- Chaos (Day 137) answers "does it survive failure"; load testing answers
  "how much traffic can it survive *before* failure" — the missing half
  of capacity planning. Both use the same SLO lens to judge results.

### B. k6 concepts (20 min)
- Test script in JavaScript defines **virtual users (VUs)** and **stages**
  (ramp-up/steady/ramp-down): `options.stages = [{duration: '2m', target: 50}, ...]`.
- Built-in metrics: `http_req_duration`, `http_req_failed`, `vus`,
  `iterations` — exportable to Prometheus via a remote-write output
  (`k6 run --out experimental-prometheus-rw script.js`) so load-test
  results land in the same Grafana dashboards as everything else.
- **Thresholds**: `thresholds: {http_req_duration: ['p(95)<500'],
  http_req_failed: ['rate<0.01']}` — k6 exits non-zero if breached, making
  load tests usable as a CI gate, not just a manual exercise.

### C. Load-test types (15 min)
- **Smoke test**: 1 VU, verify the script itself works.
- **Load test**: expected normal traffic, confirm SLOs hold.
- **Stress test**: ramp well past expected traffic to find the breaking point.
- **Soak test**: sustained moderate load for a long duration — surfaces
  memory leaks and slow resource exhaustion that short tests miss.

### D. Capacity math (10 min)
- Saturation point: the load level where latency/error rate starts
  degrading nonlinearly — read it off the dashboard as the knee of the curve.
- Simple headroom math: if the saturation point is 200 req/s and expected
  peak traffic is 80 req/s, headroom = 2.5x — connects directly to Day
  139's autoscaling and Day 118's FinOps rightsizing (over-provisioned
  headroom costs money; under-provisioned headroom breaches SLOs).

## Lab (2h)

### Part 1 — Install k6 and write a smoke test (25 min)
1. Install `k6` (binary or `docker run grafana/k6`).
2. Write `smoke.js`: 1 VU, 1 iteration, hits the project app's main
   endpoint, asserts `status === 200`.
3. `k6 run smoke.js` — confirm it passes before scaling up.

### Part 2 — Load test with thresholds (40 min)
4. Write `load.js`: stages ramping 0→30 VUs over 2m, hold 30 VUs for 5m,
   ramp down over 1m; thresholds `p(95)<500ms`, `http_req_failed rate<0.01`.
5. Run it while watching the Day 124 RED dashboard live; confirm
   thresholds pass and the dashboard shows a clean rate/latency profile.
6. Export results to Prometheus (`--out experimental-prometheus-rw`) if
   remote-write is enabled on the kube-prometheus-stack instance;
   otherwise note results from k6's summary output.

### Part 3 — Stress test to find saturation (45 min)
7. Write `stress.js`: ramp 0→200 VUs over 5m (well beyond expected load).
8. Run it, watching the dashboard for the point where p99 latency spikes
   and/or error rate rises — note the approximate VU count / req/s at
   that knee.
9. Confirm the Day 130 burn-rate alerts fire once the SLO is actually
   breached during the stress test — this is chaos-mesh's sibling drill,
   using load instead of fault injection as the stressor.

### Part 4 — Project step: capacity math + gate (10 min)
10. Compute headroom: saturation req/s ÷ expected peak req/s; write the
    result and the raw numbers to `/opt/fresher_project/docs/capacity.md`.
11. Add `load.js` as a CI job (manual trigger or scheduled, not on every
    push — load tests are slow) so the threshold gate is repeatable;
    commit all three k6 scripts and `capacity.md`.

**Definition of done:** smoke, load, and stress scripts run; saturation
point identified from the dashboard; headroom computed and documented;
load test wired into CI as a repeatable job.
