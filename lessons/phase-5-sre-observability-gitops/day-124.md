## Theory (1h)

### A. USE and RED — the two dashboard methods (20 min)
- **USE** (per resource: CPU, memory, disk, network): **U**tilization,
  **S**aturation, **E**rrors. Good for infrastructure/host-level panels.
- **RED** (per service): **R**ate, **E**rrors, **D**uration. Good for
  request-driven services — maps directly onto the SLIs drafted Day 121.
- Rule of thumb: USE for nodes/hardware, RED for services/APIs. A good
  project dashboard has one row of each.

### B. Grafana building blocks (20 min)
- Data source: Prometheus (already provisioned by kube-prometheus-stack).
- Panel types: time series, stat (single number), gauge, table, heatmap
  (nice for latency distributions).
- **Variables**: `$namespace`, `$pod` — templated dropdowns built from a
  PromQL query (`label_values(kube_pod_info, pod)`) so one dashboard serves
  many instances without duplication.

### C. Dashboards as code (10 min)
- Export dashboard JSON, store it in the repo (`dashboards/project.json`);
  provision via a `ConfigMap` labeled `grafana_dashboard: "1"` that the
  Grafana sidecar auto-loads — dashboards become git-versioned, not
  click-ops artifacts.

### D. Grafana-native alerting (10 min)
- Grafana can alert directly off any data source query, not just Prometheus
  rules — useful for cross-datasource alerts (Day 128's Loki, Day 129's traces).
- Contact points + notification policies mirror Alertmanager's routing/
  grouping concepts (Day 125) but live inside Grafana; the project will use
  Alertmanager as the source of truth and Grafana mainly for visualization.

## Lab (2h)

### Part 1 — Access Grafana and connect Prometheus (15 min)
1. `kubectl -n monitoring port-forward svc/kps-grafana 3000:80`; log in
   (default admin creds from the Helm chart's secret — retrieve with
   `kubectl -n monitoring get secret kps-grafana -o jsonpath='{.data.admin-password}' | base64 -d`).
2. Confirm the Prometheus data source is pre-provisioned (Connections → Data sources).

### Part 2 — Build the RED row for the project app (45 min)
3. New dashboard → add panel: **Rate** = `sum(rate(requests_total[5m]))`.
4. Add panel: **Errors** = `sum(rate(requests_total{code=~"5.."}[5m])) / sum(rate(requests_total[5m]))`,
   format as percentage.
5. Add panel: **Duration** = p50 and p99 from `histogram_quantile` (two series,
   one panel), using the recording rules from Day 123.
6. Add a `$pod` variable (`label_values(kube_pod_info{namespace="default"}, pod)`)
   and apply it to the Rate panel's query so it filters by selection.

### Part 3 — Build the USE row for the node (30 min)
7. Add panel: **Utilization** = `100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)`.
8. Add panel: **Saturation** = `node_load1` compared against CPU core count.
9. Add panel: **Errors** = `rate(node_network_receive_errs_total[5m])`.

### Part 4 — Project step: version and alert (30 min)
10. Export the dashboard JSON (Share → Export → Save to file); commit it to
    `/opt/fresher_project/dashboards/project.json`.
11. Wrap the JSON in a `ConfigMap` with label `grafana_dashboard: "1"`, apply
    it, and confirm Grafana auto-loads it from the sidecar on next refresh.
12. Add one Grafana alert rule on the Errors panel (>5% for 5m) as a
    cross-check against the Prometheus `HighErrorRate` alert from Day 123.

**Definition of done:** dashboard with RED row (app) + USE row (node) live,
`$pod` variable working, JSON committed and auto-provisioned via ConfigMap.
