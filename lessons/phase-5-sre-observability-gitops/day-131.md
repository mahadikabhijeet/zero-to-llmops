## Theory (1h)

### A. Severity levels (15 min)
- A simple SEV scale (SEV1–SEV4) maps impact to response urgency:
  SEV1 (full outage / data loss, all hands, page immediately), SEV2
  (major feature down / SLO burning fast, on-call + lead), SEV3 (degraded,
  minor user impact, business hours fix), SEV4 (cosmetic, backlog).
- Severity should map directly to the burn-rate alerts from Day 130 —
  `ErrorBudgetBurnFast` = candidate SEV2, `ErrorBudgetBurnSlow` = SEV3/ticket.

### B. Incident roles and communication (15 min)
- Minimum roles even on a small team: **Incident Commander** (IC — drives
  the process, not necessarily the fix), and whoever is actively debugging.
  On a two-person team the learner plays both, but naming the roles out
  loud is the habit that scales.
- A single **status channel** (or a shared doc) is the source of truth
  during an incident — no side-channel decisions. Timestamped updates:
  what's known, what's being tried, what's next, ETA for next update.
- Declare, then communicate, then fix — resist the urge to silently debug
  a SEV1/2 for 20 minutes before telling anyone.

### C. The postmortem template (20 min)
- Blameless, focused on systems and process, not people. Core sections:
  **Summary** (what happened, impact, duration), **Timeline** (timestamped,
  detection → mitigation → resolution), **Root cause** (the technical why —
  often multiple contributing factors, not one), **What went well / what
  didn't**, **Action items** (owner + due date, tracked to closure — an
  action item nobody owns doesn't happen).
- Detection time and time-to-mitigate are the two numbers worth trending
  over successive incidents — they measure whether observability investment
  (Days 121–130) is actually paying off.

### D. Tabletop exercises (10 min)
- A tabletop incident is a **verbal walkthrough**, not a live break: someone
  presents a scenario ("Prometheus shows ErrorBudgetBurnFast firing"), the
  responder narrates diagnosis steps and decisions without touching a
  keyboard — cheap way to rehearse the process before Day 145's live game day.

## Lab (2h)

### Part 1 — Define severities and write the postmortem template (30 min)
1. Write `/opt/fresher_project/docs/incident-severity.md` mapping SEV1–4 to
   the alerts and dashboards built in Days 122–130.
2. Write `/opt/fresher_project/docs/postmortem-template.md` with the five
   sections above as headers and one-line prompts under each.

### Part 2 — Tabletop incident #1 (50 min)
3. Instructor presents scenario: "at 14:32, `ErrorBudgetBurnFast` fires. Grafana
   RED row shows error rate at 18%." The learner narrates, out loud, exactly
   which dashboard/query/log/trace he'd check first, second, third — no
   live terminal, this is a verbal/decision exercise.
4. Instructor injects a twist mid-scenario (e.g. "the dashboard itself is slow
   to load" or "logs show nothing unusual") to test adaptability.
5. Debrief: did the responder start with the SLO dashboard row before
   drilling into logs/traces? Did they consider declaring severity before
   fully diagnosing?

### Part 3 — Tabletop incident #2, then write it up (40 min)
6. Run a second scenario rooted in a different failure mode (e.g. a
   dependency — DB — going slow, surfacing as `HighLatency` not
   `HighErrorRate`).
7. Immediately after, fill out the postmortem template *for the tabletop
   scenario itself* as if it were real — timeline, root cause, action items.
   This is the actual skill: writing a clear postmortem under time pressure.

### Part 4 — Project step (10 min)
8. Commit `incident-severity.md`, `postmortem-template.md`, and the two
   tabletop postmortem write-ups to `/opt/fresher_project/docs/postmortems/`.

**Definition of done:** severity doc and postmortem template committed; two
tabletop scenarios run with a completed postmortem write-up for at least one.
