## Theory (1h)

### A. Why a service mesh (15 min)
- As services multiply, cross-cutting concerns (mTLS, retries, timeouts,
  traffic shaping, fine-grained observability) get duplicated in every
  app's code. A mesh moves those concerns into the infrastructure layer —
  applications stay unaware, the mesh handles it uniformly.
- Istio's model: a **sidecar proxy** (Envoy) injected into every pod
  intercepts all inbound/outbound traffic; the **control plane** (`istiod`)
  configures every sidecar's routing/security rules.

### B. Sidecar injection (15 min)
- Enabled per-namespace via a label: `kubectl label namespace default
  istio-injection=enabled` — new pods in that namespace automatically get
  an Envoy sidecar container added by Istio's mutating webhook.
- `kubectl get pod <pod> -o jsonpath='{.spec.containers[*].name}'` shows
  two containers where there was one — the app and `istio-proxy`.
- Every network call in/out of the pod now flows through Envoy — this is
  what makes mesh-wide mTLS (Day 136) and traffic rules possible without
  touching app code.

### C. VirtualService and DestinationRule (20 min)
- **DestinationRule**: defines **subsets** of a service (e.g. `version: v1`,
  `version: v2`) based on pod labels — the mesh's way of distinguishing
  "which deployment is this."
- **VirtualService**: defines **routing rules** — which subset gets what
  percentage of traffic, path-based routing, retries/timeouts per route.
  `http: - route: - destination: {host: project-app, subset: v1} weight: 90
  - destination: {host: project-app, subset: v2} weight: 10` — the exact
  mechanism Day 136's canary release will use.
- Gateway: Istio's ingress entry point (parallel to Day 66's nginx-ingress,
  but mesh-native) — needed if traffic should enter the mesh from outside
  the cluster.

### D. Traffic splitting vs Kubernetes-native approaches (10 min)
- A plain Kubernetes Service load-balances by pod count only — 3 pods of
  v1 + 1 pod of v2 gives roughly 25% to v2, coarse and hard to tune.
- Istio's weighted routing is **independent of pod count** — 90/10 traffic
  split regardless of how many replicas each subset runs — this precision
  is what makes controlled canaries (Day 136) practical.

## Lab (2h)

### Part 1 — Install Istio (30 min)
1. Install `istioctl`; `istioctl install --set profile=demo -y` on the
   kind cluster (demo profile includes ingress gateway, good for labs).
   AWS-prod equivalent: same Istio, or a managed mesh (App Mesh/EKS
   add-on) — the concepts transfer directly.
2. `kubectl label namespace default istio-injection=enabled`.
3. Restart the project-app deployment (`kubectl rollout restart deployment
   project-app`) and confirm the pod now shows 2 containers.

### Part 2 — Deploy a v2 subset (35 min)
4. Build/tag a `v2` image of the project app with a trivial visible
   difference (e.g. a version string in a response header or log line).
5. Deploy it as a second Deployment (`project-app-v2`) with label
   `version: v2`, alongside the existing `project-app` (label it `version: v1`
   if not already).
6. Create a `DestinationRule` defining subsets `v1` and `v2` on the
   `project-app` Service host, keyed by the `version` label.

### Part 3 — VirtualService traffic splitting (40 min)
7. Create a `VirtualService` routing 100% to `v1` initially; confirm all
   traffic (via `curl` in a loop) hits v1 only (check the version header/log).
8. Change the weights to 80/20 (v1/v2); re-run the loop (~50 requests) and
   count how many hit each version — confirm roughly proportional.
9. Change to 0/100 — confirm a full cutover with zero code changes to the
   app, just a manifest edit.

### Part 4 — Project step (15 min)
10. Revert the `VirtualService` to 100% v1 (v2 becomes tomorrow's canary
    candidate); commit the `DestinationRule`, `VirtualService`, and v2
    deployment manifests to the project repo (managed by ArgoCD per Day 134).

**Definition of done:** sidecar injection confirmed (2 containers per pod);
DestinationRule with v1/v2 subsets created; VirtualService traffic split
demonstrated at 100/0, 80/20, and 0/100.
