## Theory (1h)

### A. Shifting security left — where DevSecOps fits (15 min)
- DevSecOps means security checks run **in the pipeline**, before merge/
  deploy, not as a separate audit after the fact — cheaper to fix a
  vulnerable dependency at PR time than after it's running in prod.
- Three checkpoints covered today: code (SAST), dependencies (SCA), and
  runtime cluster policy (admission control) — defense in depth, not one gate.

### B. SAST and dependency scanning (20 min)
- **SAST** (Static Application Security Testing): scans source code for
  known bad patterns (hardcoded secrets, injection risks) without running
  it — `bandit` for Python, or language-appropriate linters with security rules.
- **SCA/dependency scanning**: checks third-party packages/images against
  known-CVE databases — `trivy` (already used Day 48 for image hygiene)
  and `grype` both do this; run against both the app's dependency
  manifest (`requirements.txt`, `package.json`) and the built container image.
- CI gate pattern: fail the build on `CRITICAL`/`HIGH` severity findings,
  warn (don't block) on `MEDIUM`/`LOW` — a blanket "zero findings" gate
  usually just gets bypassed under deadline pressure.

### C. SBOM — Software Bill of Materials (10 min)
- An SBOM is a machine-readable manifest of every component (direct and
  transitive) in a build — `trivy` or `syft` can generate one
  (`syft <image> -o cbom-json`/SPDX format).
- Purpose: when a new CVE drops (e.g. another Log4Shell), an SBOM lets you
  answer "are we affected?" in minutes by searching manifests instead of
  re-scanning everything from scratch — increasingly a compliance
  requirement (US federal software supply-chain rules), worth knowing even
  for a fresher's resume.

### D. OPA/Gatekeeper — policy at admission time (15 min)
- Open Policy Agent (OPA) + Gatekeeper enforce policy **as Kubernetes
  admission control** — a manifest that violates policy is rejected before
  it's ever scheduled, closing the gap between "CI scanned it" and
  "someone `kubectl apply`'d something unscanned anyway."
- Policies written in Rego; common examples: require resource
  requests/limits on every pod (ties back to Day 69), disallow
  `:latest` image tags, require non-root `securityContext` (ties to Day 48).
- `ConstraintTemplate` (the Rego rule) + `Constraint` (where/how it
  applies) — same two-layer pattern as CRDs in general (Day 88).

## Lab (2h)

### Part 1 — Add SAST + dependency scanning to CI (40 min)
1. Add a CI job running `bandit -r .` (or the app's language's SAST tool)
   on every PR; confirm it catches at least one seeded issue (e.g.
   temporarily hardcode a fake "secret" string to test detection, then
   remove it).
2. Add a `trivy fs .` step scanning dependency manifests, and a
   `trivy image <project-image>` step scanning the built container;
   configure `--severity CRITICAL,HIGH --exit-code 1` to fail the build,
   `MEDIUM,LOW` to warn only.

### Part 2 — Generate an SBOM (25 min)
3. Run `syft <project-image> -o spdx-json > sbom.json` (or `trivy image
   --format spdx-json`) locally or as a CI artifact.
4. Inspect `sbom.json` — find one transitive dependency you didn't know
   was in the build; discuss why SBOMs matter for incident response speed.

### Part 3 — Install and configure Gatekeeper (40 min)
5. `helm repo add gatekeeper https://open-policy-agent.github.io/gatekeeper/charts && helm install gatekeeper gatekeeper/gatekeeper -n gatekeeper-system --create-namespace`.
6. Write a `ConstraintTemplate` requiring container resource
   requests/limits be set; write the matching `Constraint` scoping it to
   the `default` namespace.
7. Attempt to apply a Pod manifest with no resource limits — confirm
   Gatekeeper rejects it at admission time with a clear violation message.
8. Add a second constraint disallowing the `:latest` tag; test similarly.

### Part 4 — Project step (15 min)
9. Confirm `project-app`'s existing manifests already satisfy both
   constraints (fix if not); commit the CI scanning steps, the
   `ConstraintTemplate`/`Constraint` manifests, and the SBOM generation
   step to the project repo.

**Definition of done:** SAST and dependency scanning run in CI with a
severity-based fail/warn gate; SBOM generated and inspected; Gatekeeper
rejects a non-compliant manifest for both constraints tested.
