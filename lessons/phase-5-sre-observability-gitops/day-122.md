## Theory (1h)

### A. Prometheus architecture (15 min)
- Pull-based model: Prometheus server **scrapes** HTTP `/metrics` endpoints on an
  interval — contrast with push-based systems.
- Core pieces: TSDB (time-series storage, local disk), scrape config, PromQL
  query engine, optional Alertmanager (Day 125) for firing alerts.
- Metric types: **counter** (only increases — requests_total), **gauge**
  (goes up/down — memory_bytes), **histogram** (buckets of observations —
  latency), **summary** (client-side quantiles, less flexible than histograms).

### B. Exporters — getting metrics out of things that don't speak Prometheus (15 min)
- `node_exporter`: host-level metrics (CPU, memory, disk, network) — the
  first thing installed on any box.
- Application metrics: instrument code directly with a client library
  (`prometheus_client` for Python) and expose `/metrics`.
- Exporter pattern: sidecar or standalone process translating a
  third-party system's stats into Prometheus format (e.g. `postgres_exporter`).

### C. Scrape config (10 min)
- `scrape_configs` in `prometheus.yml`: `job_name`, `static_configs` (targets
  list) or `kubernetes_sd_configs` (service discovery — what we'll use on kind).
- `scrape_interval`, `scrape_timeout`, relabeling basics (`__meta_*` labels).

### D. PromQL basics (20 min)
- Instant vector: `up`, `node_cpu_seconds_total{mode="idle"}`.
- Label matching: `{job="node-exporter"}`, `{instance=~"10.*"}` (regex).
- Basic arithmetic and aggregation: `sum(...)`, `avg(...)`, `sum by (instance) (...)`.
- Range vector as input to `rate()` (previewed, deep dive Day 123):
  `rate(node_cpu_seconds_total[5m])`.

## Lab (2h)

### Part 1 — Install kube-prometheus-stack on kind (40 min)
1. `helm repo add prometheus-community https://prometheus-community.github.io/helm-charts && helm repo update`.
2. `helm install kps prometheus-community/kube-prometheus-stack -n monitoring --create-namespace`.
   (AWS-prod equivalent: same chart on EKS, or managed AMP — one line, no cluster to babysit.)
3. `kubectl get pods -n monitoring` — identify Prometheus, Alertmanager, Grafana,
   node-exporter (DaemonSet), kube-state-metrics pods.
4. Port-forward: `kubectl -n monitoring port-forward svc/kps-kube-prometheus-stack-prometheus 9090`.

### Part 2 — Explore targets and PromQL (40 min)
5. In the Prometheus UI, go to Status → Targets; confirm node-exporter and
   kube-state-metrics are `UP`.
6. Run these in the Graph tab: `up`, `node_memory_MemAvailable_bytes`,
   `sum(kube_pod_status_phase{phase="Running"})`.
7. Try a broken query on purpose: `up{job="doesnotexist"}` — confirm empty result,
   not an error.

### Part 3 — Instrument the project app (30 min)
8. Add `prometheus_client` (or the app's language equivalent) to the project app;
   expose `/metrics` with a counter (`requests_total`) and a histogram
   (`request_duration_seconds`).
9. Add a `ServiceMonitor` (or `PodMonitor`) CR pointing at the app's `/metrics`
   port so kube-prometheus-stack's Prometheus Operator picks it up automatically.
10. Confirm the app shows up under Status → Targets in Prometheus.

### Part 4 — Project step (10 min)
11. Commit the `/metrics` instrumentation code and the `ServiceMonitor` manifest
    to the project repo.

**Definition of done:** kube-prometheus-stack running on kind; node-exporter and
app targets both `UP` in Prometheus; app exposes a counter and a histogram.
