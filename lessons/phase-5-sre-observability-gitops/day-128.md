## Theory (1h)

### A. LogQL beyond filtering — parsing and metrics from logs (20 min)
- LogQL has two stages: a **log stream selector** (`{app="x"}`, label-based,
  cheap) piped into **line filters and parsers** (`|= "error"`, `| json`,
  `| logfmt`, `| pattern`) that operate on content.
- `| json` parses a JSON log line into fields usable downstream:
  `{app="project-app"} | json | status_code >= 500`.
- Loki can also produce **metrics from logs**:
  `sum(count_over_time({app="project-app"} |= "error" [5m]))` — an
  error-count time series derived purely from log content, gap-filling
  what an app that doesn't yet export a Prometheus counter can't show.

### B. Structured logging — why JSON beats free text (15 min)
- Free-text logs (`"User 42 failed login"`) are hard to parse reliably at
  scale; structured logs (`{"event":"login_failed","user_id":42,"ts":"..."}`)
  are queryable, filterable, and correlate cleanly with traces (Day 129).
- Minimum fields for every log line: `timestamp`, `level`, `message`,
  and — once tracing is added — `trace_id`/`span_id` for correlation.
- Python: `python-json-logger` or a small custom `logging.Formatter`
  emitting JSON to stdout (never write to files inside a container —
  stdout is the Kubernetes/promtail contract).

### C. Retention and cost control (15 min)
- Loki retention configured via `limits_config.retention_period` and the
  compactor's deletion job — set a retention window (e.g. 7–14 days) so
  disk doesn't grow unbounded; the AWS-prod equivalent ships older chunks
  to S3 lifecycle tiers instead of deleting.
- Cardinality discipline (Day 127's label rule) is the biggest cost lever —
  more than retention length, in practice.

### D. Correlating logs with metrics (10 min)
- Grafana's **derived fields** on a Loki data source can turn a `trace_id`
  found in a log line into a clickable link to Jaeger (Day 129) or to a
  Prometheus query for the same time window — this is the "click log →
  jump to trace/metric" workflow real SRE teams live in.

## Lab (2h)

### Part 1 — Add structured logging to the app (40 min)
1. Replace the app's ad-hoc `print`/plain logging calls with a JSON logger
   emitting `timestamp`, `level`, `message`, `path`, `status_code`,
   `duration_ms` on every request.
2. Redeploy; confirm in Grafana Explore that `{app="project-app"} | json`
   now exposes those fields as filterable columns.

### Part 2 — Parsed LogQL drills (40 min)
3. `{app="project-app"} | json | status_code >= 500` — errors only.
4. `sum(count_over_time({app="project-app"} | json | status_code >= 500 [5m]))`
   — an error-rate-from-logs metric; compare it against the Prometheus
   `requests_total{code=~"5.."}` rate from Day 123 (should roughly agree).
5. `{app="project-app"} | json | duration_ms > 500` — slow-request log lines,
   cross-checking Day 123's latency alert.

### Part 3 — Retention config (20 min)
6. Edit the Loki Helm values to set `limits_config.retention_period: 336h`
   (14 days) and enable the compactor's `retention_enabled: true`; upgrade
   the release (`helm upgrade loki grafana/loki-stack -f values.yaml -n monitoring`).
7. Confirm the config took via `kubectl -n monitoring get cm loki -o yaml`
   (or the equivalent generated ConfigMap) — look for the retention block.

### Part 4 — Project step (20 min)
8. Add a derived field on the Loki data source in Grafana matching a
   `trace_id` regex in log lines to a placeholder Jaeger link
   (`http://localhost:16686/trace/${__value.raw}`) — it won't resolve
   until Day 129 wires tracing, but the plumbing is ready.
9. Commit the structured-logging code change and the updated Loki
   `values.yaml` to the project repo.

**Definition of done:** app emits structured JSON logs; `| json` filters
work in Grafana Explore; retention period set and confirmed; derived field
for trace correlation configured (even if not yet resolving).
