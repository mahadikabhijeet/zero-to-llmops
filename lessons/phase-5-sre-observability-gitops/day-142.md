## Theory (1h)

### A. Software templates — codifying the golden path (20 min)
- A Backstage **template** is a `kind: Template` entity that, when run,
  asks a developer a few questions (service name, owner, description) and
  then generates a new repo pre-wired with: the right directory structure,
  a starter CI pipeline, a `catalog-info.yaml`, a Helm chart skeleton, and
  optionally an ArgoCD `Application` manifest — everything a new service
  needs to be observable, deployable, and cataloged from commit #1.
- Template anatomy: `spec.parameters` (the input form), `spec.steps`
  (actions: `fetch:template` to copy/templatize files, `publish:github`
  to create the repo, `catalog:register` to register it).
- This is the concrete payoff of "platform engineering": what took the
  learner 30+ days to build by hand (Phases 1–5) becomes a 5-minute
  self-service action for the *next* engineer.

### B. Templating mechanics (15 min)
- Templates use `nunjucks`-style placeholders (`${{ values.name }}`) inside
  **skeleton files** that get rendered with the form's answers — same
  mental model as Ansible's Jinja2 (Day 52) or Helm's `values.yaml`
  (Day 74), applied one layer up at "generate a whole repo" scope.

### C. TechDocs — docs-as-code (15 min)
- TechDocs renders Markdown docs (living in the repo, under `docs/`, with
  an `mkdocs.yml`) directly inside the Backstage entity page — docs stay
  next to code, versioned and reviewed the same way, but are discoverable
  from the catalog without hunting through the repo.
- This is where all of this phase's `docs/*.md` files (SLOs, runbooks,
  postmortems, canary/chaos notes) belong once the catalog exists — one
  click from `project-app`'s Backstage page to all of it.

### D. Where golden paths cap out (10 min)
- Templates encode the *common* case; teams with a real reason to deviate
  should be able to (a template is a strong default, not a mandate) — the
  platform engineering failure mode is templates so rigid that any
  deviation requires fighting the platform.

## Lab (2h)

### Part 1 — Build a software template (50 min)
1. Create a `templates/service-template/` directory with `template.yaml`
   (`kind: Template`), a `skeleton/` folder containing a minimal
   Dockerfile, a starter CI workflow, a `catalog-info.yaml` skeleton (with
   `${{ values.name }}`, `${{ values.owner }}` placeholders), and a
   one-line `docs/index.md`.
2. Define `spec.parameters` for `name`, `description`, `owner`.
3. Define `spec.steps`: `fetch:template` (render the skeleton),
   `publish:github` (create the new repo — use a test/throwaway repo or
   local git init if avoiding real GitHub org sprawl), `catalog:register`.

### Part 2 — Run the template (30 min)
4. Register the template in Backstage (`app-config.yaml` catalog
   locations); go to Create → find the template → fill the form → run it.
5. Confirm the generated repo has correctly rendered placeholders (no
   literal `${{ values.name }}` left anywhere) and appears in the catalog
   automatically after `catalog:register`.

### Part 3 — TechDocs for the project (30 min)
6. Add an `mkdocs.yml` to the project repo referencing the existing
   `docs/` folder (SLOs, runbooks, postmortems, canary/chaos notes,
   capacity/autoscaling notes from this phase).
7. Add `backstage.io/techdocs-ref: dir:.` annotation to `catalog-info.yaml`;
   rebuild/refresh TechDocs in Backstage and confirm the docs render
   inside the `project-app` entity page.

### Part 4 — Project step (10 min)
8. Commit `templates/service-template/`, the updated `catalog-info.yaml`
   annotation, and `mkdocs.yml` to the appropriate repos.

**Definition of done:** template successfully scaffolds a new repo with
rendered placeholders and auto-registers it in the catalog; TechDocs
renders the project's existing docs inside its Backstage entity page.
