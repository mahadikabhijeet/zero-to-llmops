## Theory (1h)

### A. What platform engineering is (15 min)
- Platform engineering builds an **Internal Developer Platform (IDP)** —
  a self-service layer so application developers get infrastructure,
  CI/CD, observability, and standards *without* needing deep expertise in
  every tool covered in Phases 3–5 — the platform team absorbs that
  complexity once, centrally.
- This whole training so far has been "become the platform team"; today
  is where that expertise gets packaged into something *other* developers
  can consume without repeating the journey.

### B. Golden paths (15 min)
- A golden path is the **paved, supported way** to do something common
  (spin up a new service, deploy to the mesh, wire up dashboards) —
  opinionated defaults that are easy to follow and hard to get wrong,
  while still allowing deviation for teams with real reasons to.
- Golden paths reduce cognitive load and toil (Day 121's definition)
  platform-wide — the ROI of platform engineering is measured in developer
  time saved and consistency gained, not in tool count.

### C. Backstage core concepts (20 min)
- Backstage (CNCF project, originally Spotify): a portal unifying a
  **software catalog** (every service, its owner, its dependencies,
  its links to dashboards/runbooks), **software templates** (Day 142's
  scaffolding), and **TechDocs** (docs-as-code rendered in the portal).
- `catalog-info.yaml`: the file every repo carries describing itself
  (kind: Component, owner, lifecycle, links) — Backstage's catalog is
  built by scanning repos for these files, git-native, not a separate
  database to hand-maintain.

### D. Where this sits relative to everything built so far (10 min)
- Backstage doesn't replace ArgoCD, Prometheus, or Grafana — it's the
  **front door** linking to all of them from one place per service: "here's
  project-app's dashboard, its runbooks, its ArgoCD app, its on-call owner."

## Lab (2h)

### Part 1 — Install Backstage (40 min)
1. Scaffold a new Backstage app: `npx @backstage/create-app@latest`
   (creates a local Backstage instance — this runs outside the kind
   cluster initially, as a Node app, which is the standard way to bootstrap).
2. `yarn dev` (or the generated start command) and confirm the default
   Backstage UI loads locally.
3. AWS-prod equivalent: Backstage deployed to the cluster via its own
   Helm chart/container image, same catalog concepts — local dev mode is
   sufficient for cataloging today.

### Part 2 — Write catalog-info.yaml for the project (35 min)
4. In the project repo root, write `catalog-info.yaml`: `kind: Component`,
   `metadata.name: project-app`, `spec.type: service`,
   `spec.lifecycle: production` (or `experimental`), `spec.owner:
   <team-or-username>`.
5. Add `metadata.links`: entries for the Grafana dashboard URL, the
   ArgoCD app URL, the runbooks doc, and the GitHub repo itself.

### Part 3 — Register and browse the catalog (30 min)
6. In Backstage's `app-config.yaml`, add the project repo's
   `catalog-info.yaml` under `catalog.locations`.
7. Restart Backstage, navigate to the Catalog, find `project-app`, and
   confirm all the links (dashboard, ArgoCD, runbooks) resolve correctly
   from the entity page.
8. Explore the entity's relationships tab (even with just one component,
   note where dependencies/APIs would show up as the catalog grows).

### Part 4 — Project step (15 min)
9. Add a second catalog entry for one platform component already running
   (e.g. the kube-prometheus-stack or ArgoCD itself) as `kind: Resource`
   or `kind: Component`, linked as a dependency of `project-app` via
   `spec.dependsOn`.
10. Commit `catalog-info.yaml` and any Backstage config changes worth
    versioning to the project repo.

**Definition of done:** Backstage running locally; `project-app` cataloged
with working links to dashboard, ArgoCD, and runbooks; at least one
dependency relationship modeled.
