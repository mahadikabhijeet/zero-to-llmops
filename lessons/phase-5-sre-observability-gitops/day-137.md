## Theory (1h)

### A. Chaos engineering principles (20 min)
- Definition: the discipline of experimenting on a system to build
  confidence in its capability to withstand turbulent conditions —
  deliberately, safely, with a hypothesis.
- The scientific method applied to production reliability: (1) define
  **steady state** using the SLIs from Day 121, (2) hypothesize the steady
  state holds under a specific failure, (3) inject the failure, (4)
  measure whether the hypothesis held, (5) fix the gap if it didn't.
- Chaos engineering is not "randomly break things" — every experiment has
  a scope, a hypothesis, and a rollback plan defined *before* it starts.

### B. Blast radius (15 min)
- Start every experiment with the smallest possible blast radius (one pod,
  one replica, off-peak, non-prod-like traffic) and expand only after
  confidence builds — never start with "kill the whole cluster."
- A **kill switch**: know in advance how to abort the experiment
  immediately if steady state breaks worse than hypothesized (this is
  exactly the canary "abort on signal" muscle from Day 136).

### C. Common experiment types (15 min)
- **Pod kill**: terminate a pod, verify the Deployment/ReplicaSet
  self-heals and traffic reroutes without user-visible impact (tests
  Kubernetes self-healing + readiness probes from Day 69).
- **Network delay/loss**: inject latency or packet loss between services,
  verify timeouts/retries (Day 144 territory) degrade gracefully instead
  of cascading.
- **Resource stress**: CPU/memory pressure on a pod, verify HPA/limits
  (Day 69) behave as designed instead of the node evicting everything.

### D. Tying experiments to SLOs (10 min)
- The pass/fail criterion for every experiment should be **the SLO**, not
  a vague "did it seem okay" — did the error budget burn stay within
  tolerance during the experiment? This is why chaos engineering sits in
  Phase 5 *after* Days 121–130's instrumentation, not before it.

## Lab (2h)

### Part 1 — Install chaos-mesh (25 min)
1. `helm repo add chaos-mesh https://charts.chaos-mesh.org && helm repo update`.
2. `helm install chaos-mesh chaos-mesh/chaos-mesh -n chaos-mesh --create-namespace --set chaosDaemon.runtime=containerd --set chaosDaemon.socketPath=/run/containerd/containerd.sock`
   (adjust runtime/socket path to match the kind node's container runtime).
3. `kubectl get pods -n chaos-mesh` — confirm controller-manager and daemon
   pods running. AWS-prod equivalent: same chaos-mesh on EKS, or AWS Fault
   Injection Simulator for managed-service-level faults.

### Part 2 — Experiment 1: pod-kill against steady state (40 min)
4. Define steady state: watch the Day 124 RED dashboard for 2 minutes with
   normal load — note baseline error rate (~0%) and p99 latency.
5. Write a `PodChaos` manifest: `action: pod-kill`, selector targeting one
   `project-app` pod, no schedule (one-shot).
6. Apply it while generating continuous load; watch the dashboard —
   confirm error rate stays near baseline (readiness probes + multiple
   replicas absorbing the kill) and the pod recovers via ReplicaSet.
7. Check whether `HighErrorRate` or the Day 130 burn-rate alerts fired —
   if they did, that's a finding: the app isn't tolerating single-pod loss
   as well as hypothesized.

### Part 3 — Experiment 2: network delay (40 min)
8. Write a `NetworkChaos` manifest: `action: delay`, `latency: 300ms`,
   targeting traffic between the app and its dependency (DB or an
   internal call), duration 5 minutes.
9. Apply it; watch the p99 latency panel and the `HighLatency` alert from
   Day 123 — confirm it fires as expected (it should, given a 300ms
   injected delay against a 500ms threshold plus baseline).
10. Let the experiment expire naturally; confirm latency and alerts
    return to baseline.

### Part 4 — Project step (15 min)
11. Write `/opt/fresher_project/docs/chaos-experiments.md`: for each
    experiment, record hypothesis, blast radius, result, and any gap found
    (e.g. "single-pod-kill briefly breached SLO — investigate readiness
    probe timing").
12. Commit both `PodChaos`/`NetworkChaos` manifests and the findings doc.

**Definition of done:** pod-kill and network-delay experiments run against
real load; dashboard/alert behavior observed and recorded against the
SLO/error-budget lens; findings documented.
