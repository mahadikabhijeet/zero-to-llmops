# Day 145 — Game Day: Live Incident Simulation (Facilitator Session)

Phase 5 · follows Day 144 (reliability patterns).
Format: this is a **session-plan day**, not a lecture+lab — the instructor runs
a live incident against the real project stack while the learner is on-call.

2. Why must a timeout be shorter than the calling path's SLO latency?
3. What's the difference between liveness and readiness probes?
4. What tools from Days 122–139 will you rely on to diagnose an incident

## Pre-session setup (instructor prep, do the night before)
- Pick **one** injected failure from the menu below — don't tell the
  learner which one in advance.
- Confirm dashboards (Day 124/130), alerts (Day 123/125/130), logs (Day
  127/128), traces (Day 129), and ArgoCD (Day 132/134) are all reachable
  and healthy *before* the session starts — a game day tests the
  responder, not broken tooling.
- Have a rollback/fix ready for the chosen scenario so the incident can be
  resolved within the session, not left broken afterward.

### Scenario menu (pick one)
1. **Bad deploy**: push a config change via git that breaks a downstream
   call (reuses Day 137/144 fault-injection muscle) — surfaces as
   `HighErrorRate`/burn-rate alert.
2. **Resource exhaustion**: apply a `PodChaos` CPU-stress experiment
   (Day 137) against `project-app` — surfaces as latency degradation and
   possibly HPA thrash.
3. **Dependency slowness**: inject a `NetworkChaos` delay (Day 137) or
   Istio fault (Day 136) against the DB call — surfaces as `HighLatency`
   with a confusing "app looks fine, DB looks fine" red herring until
   traces are checked.

## Session plan (2h, timed)

### Block 1 — Inject and wait for detection (0:00–0:15)
- Instructor silently triggers the chosen scenario. Do not announce it.
- Start a stopwatch. The learner should be working normally (or on a
  distractor task) until an alert fires — record **detection time** from
  injection to alert-fire (or to the learner noticing, if alerts fail —
  that's itself a finding).

### Block 2 — Live response (0:15–1:15)
- The learner works the incident live: checks dashboard → alert →
  logs/traces → forms a hypothesis → attempts mitigation, narrating
  decisions out loud the whole time.
- Instructor plays "on-call backup" only if truly stuck for 10+ minutes — the
  point is independent diagnosis, not instructor-led debugging.
- Instructor may inject one twist at the 30-minute mark (e.g. a red herring
  metric, or "a stakeholder is asking for an ETA") to test comms under pressure.
- Record **time-to-mitigate** (service healthy again) separately from
  **time-to-root-cause** (actual understanding, which may come later).

### Block 3 — Live postmortem (1:15–1:50)
- Immediately after mitigation, fill out the Day 131 postmortem template
  together while memory is fresh: timeline (from the stopwatch notes),
  root cause, what went well, what didn't, action items with owners/dates.
- Be blameless and specific — "the runbook didn't mention checking traces
  first" is a better finding than "I was slow."

### Block 4 — Debrief and close (1:50–2:00)
- Compare detection/mitigation times against the SLO error budget (Day
  121/130) — did the incident burn a meaningful fraction of the 30-day
  budget? Would a faster response have mattered?
- Assign the top 1–2 action items to be done before Day 150's capstone
  (e.g. "add a runbook step", "tighten an alert threshold").

## Evaluation rubric
| Dimension | Weak | Solid | Strong |
|---|---|---|---|
| Detection | Missed alert / found by luck | Alert noticed within minutes | Alert acted on immediately with correct triage |
| Diagnosis | Guessed / thrashed | Used dashboard→logs→traces in order | Used correlation triangle efficiently, ruled out red herring fast |
| Communication | Silent, no status updates | Gave periodic updates | Clear timestamped updates, ETA given under twist |
| Mitigation | Fixed by luck or full rollback only | Targeted fix or rollback | Used the least disruptive effective fix |
| Postmortem | Vague, blame-adjacent | Complete template, generic action items | Specific, owned, dated action items tied to real gaps |

**Definition of done:** incident injected and detected; live response
narrated end-to-end; postmortem completed with dated action items; times
recorded and compared against the error budget.
