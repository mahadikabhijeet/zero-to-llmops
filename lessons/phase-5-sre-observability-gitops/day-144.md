## Theory (1h)

### A. Timeouts — the first line of defense (15 min)
- Every network call needs an explicit timeout — without one, a slow
  dependency holds a thread/connection indefinitely, and enough of those
  exhaust the caller's own resources, turning one slow dependency into a
  full outage (this is the failure mode Day 137's network-delay chaos
  experiment was rehearsing for).
- Timeout budget should be shorter than the SLO's latency target for the
  calling path — a 10s timeout on a call inside a 500ms-p99 endpoint is
  effectively no timeout at all.

### B. Retries and backoff (15 min)
- Naive immediate retries amplify load on an already-struggling
  dependency (a "retry storm") — use **exponential backoff with jitter**
  (`base * 2^attempt + random_jitter`) to spread retries out and avoid
  synchronized thundering herds across many clients.
- Only retry **idempotent** operations safely (GET, PUT are generally
  safe; POST that creates a resource is not, unless idempotency keys are used).
- Cap retry attempts and total time spent retrying — a retry loop with no
  ceiling just delays the inevitable failure while burning the error budget.

### C. Circuit breakers (15 min)
- A circuit breaker tracks failure rate to a dependency; past a threshold
  it "opens" — stops calling the dependency for a cooldown period and
  fails fast instead, protecting both the caller (no more wasted timeouts)
  and the struggling dependency (no more load piling on while it recovers).
- States: **closed** (normal, calls flow), **open** (failing fast, no
  calls), **half-open** (a trial call after cooldown decides whether to
  close again or reopen) — directly analogous to the canary "abort on
  signal" pattern from Day 136, but automated at the call level.

### D. Graceful degradation and health-check design (15 min)
- Graceful degradation: when a non-critical dependency fails, serve a
  reduced but still-useful response (cached data, a default value, a
  disabled feature flag) instead of failing the whole request.
- Health checks should distinguish **liveness** (is the process alive —
  restart if not) from **readiness** (can it serve traffic right now —
  remove from load balancing if not) — this is Day 69's probe design,
  revisited with the reliability-pattern lens: a readiness check that
  pings a struggling downstream dependency can itself cause a cascading
  failure if not careful (don't couple readiness to every dependency's health).

## Lab (2h)

### Part 1 — Add timeouts and backoff-retry to the app (45 min)
1. Identify one outbound call in the project app (DB query, HTTP call to
   another service) that currently has no explicit timeout; add one,
   sized against the SLO's latency budget.
2. Implement exponential backoff with jitter around that call (a small
   retry wrapper, or a library like `tenacity` for Python), capped at 3
   attempts and a total retry budget (e.g. 2 seconds).
3. Use Day 136's Istio fault injection (or Day 137's chaos-mesh
   `NetworkChaos`) to simulate the dependency being slow; confirm the
   timeout fires and the retry/backoff behaves as coded (not as a
   retry storm — check logs for spacing between attempts).

### Part 2 — Implement a simple circuit breaker (35 min)
4. Add a circuit-breaker library (or hand-roll a minimal one: track
   consecutive failures, open after N, cooldown timer, half-open trial) around
   the same outbound call.
5. Force enough consecutive failures (via fault injection again) to trip
   the breaker to `open`; confirm subsequent calls fail fast (near-zero
   latency) instead of waiting out the timeout each time.
6. Let the cooldown expire; confirm a half-open trial call occurs and the
   breaker closes again once the fault injection is removed.

### Part 3 — Graceful degradation (25 min)
7. Pick one non-critical piece of the response (e.g. a "related items"
   section, a decorative stat) and make it fail gracefully — if that
   sub-call fails or times out, return the main response without it
   (log a warning, don't 500 the whole request).
8. Verify with the same fault injection: main request still returns 200
   with degraded content when the non-critical dependency is down.

### Part 4 — Project step: revisit health checks (15 min)
9. Audit the app's liveness and readiness probes (Day 69) against
   today's lens — confirm readiness doesn't transitively depend on a
   downstream service's health in a way that could cascade; adjust if it does.
10. Commit the timeout/retry/circuit-breaker code and any probe adjustments.

**Definition of done:** timeout + backoff-retry demonstrated under
simulated slowness; circuit breaker observed opening and half-opening
correctly; graceful degradation verified returning 200 with reduced
content; readiness probe reviewed for cascade risk.
