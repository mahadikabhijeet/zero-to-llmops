## Theory (1h)

### A. From error budget to burn-rate alert (25 min)
- A **burn rate** of 1 means "consuming the budget exactly on schedule to
  exhaust it right at the end of the window." A burn rate of 14.4 means
  "at this rate, the entire 30-day budget is gone in ~2 days (30d / 14.4)."
  14.4x is the SRE-workbook fast-burn threshold because it equals consuming
  **2% of the monthly budget in 1 hour** — page-immediately territory.
- Naive alerting ("fire if error rate > X for 5m") either pages too late
  for fast burns or too often for slow-but-real ones. The fix: **multi-window,
  multi-burn-rate alerts** (the Google SRE workbook pattern):
  - Fast burn: short window (5m/1h) + high burn-rate threshold (e.g. 14.4x)
    → page immediately: budget is burning at 2%/hour, gone in ~2 days.
  - Slow burn: long window (6h/3d) + lower threshold (e.g. 1x–6x) → ticket,
    not page; budget exhausts in days.
- PromQL shape:
  `( sum(rate(requests_total{code=~"5.."}[1h])) / sum(rate(requests_total[1h])) ) > (14.4 * (1 - 0.995))`
  paired with a second condition over a 5m window for confirmation
  (short + long window together avoids both false pages and slow detection).

### B. Wiring SLOs into the dashboard (15 min)
- Add an "SLO" row to the Day 124 dashboard: current 30-day availability
  vs target, error budget remaining (as a percentage and as minutes),
  and burn-rate over 1h/6h windows — the at-a-glance "are we OK" panel.

### C. What "fully instrumented" means for the milestone (10 min)
- Every request produces a metric (Day 122), a structured log with
  trace context (Day 128), and a trace (Day 129) — no user-facing path is
  a blind spot. This is the bar for the milestone, not "more tools."

### D. Reliability review meta-point (10 min)
- Multi-window burn-rate alerting is the single highest-leverage SRE
  pattern in this phase — cheap to implement once the pillars exist,
  and it's the kind of interview answer ("how would you alert on an SLO?")
  that signals real depth versus tutorial-level knowledge.

## Lab (2h)

### Part 1 — Compute burn-rate thresholds (30 min)
1. From `docs/slo.md`'s 99.5% availability SLO, compute the fast-burn
   threshold (14.4x) and slow-burn threshold (~2x) as documented in the
   SRE workbook's standard table for a 30-day window.
2. Write both as PromQL expressions using the app's `requests_total` metric.

### Part 2 — Implement multi-window alerts (40 min)
3. Add a `PrometheusRule` with two alerts: `ErrorBudgetBurnFast` (1h+5m
   windows, high threshold, `severity: page`) and `ErrorBudgetBurnSlow`
   (6h+30m windows, lower threshold, `severity: ticket`).
4. Add `runbook_url` annotations pointing at a new
   `docs/runbooks/error-budget-burn.md` (write it: symptom, "check the SLO
   dashboard row first", escalation).
5. Trigger the fast-burn alert on purpose (loop 500s again) and confirm it
   fires within the expected short window — much faster than the plain
   `HighErrorRate` alert from Day 123 would have without the multi-window logic.

### Part 3 — Build the SLO dashboard row (30 min)
6. Add panels: 30-day availability vs target (stat panel, threshold-colored),
   error budget remaining % (gauge), and 1h/6h burn-rate (time series with
   the 14.4x / 2x reference lines).
7. Confirm the panels reflect the drills above; commit the updated dashboard JSON.

### Part 4 — ★ Milestone verification (20 min)
8. Walk the full instrumentation checklist and confirm each item:
   - [ ] Every app request emits a Prometheus metric.
   - [ ] Every app request emits a structured JSON log with `trace_id`.
   - [ ] Every app request produces a Jaeger trace.
   - [ ] SLO dashboard row live with real burn-rate data.
   - [ ] Multi-window burn-rate alerts fire correctly (tested above).
9. Write `/opt/fresher_project/docs/milestone-d130.md` summarizing the
   instrumentation state with a screenshot/description of the SLO row;
   commit and tag the repo (`git tag d130-instrumented`).

**Definition of done:** all five milestone checklist items verified; burn-rate
alerts tested firing at the expected pace; tag `d130-instrumented` pushed.
