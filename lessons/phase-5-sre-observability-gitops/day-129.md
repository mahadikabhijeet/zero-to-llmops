## Theory (1h)

### A. Why tracing — the third pillar (15 min)
- Metrics say *something* is slow; logs say *what* happened on one node;
  tracing says *where in the call chain* time was spent across services —
  essential once a request crosses more than one hop (app → db, app → cache).
- A **trace** is a tree of **spans**; each span has a name, start/end time,
  parent span ID, and attributes (tags) — e.g. `db.query` span nested under
  an `http.request` span.

### B. OpenTelemetry (OTel) concepts (20 min)
- OTel is the vendor-neutral standard: SDKs (auto-instrumentation +
  manual spans), the **Collector** (receives/processes/exports telemetry),
  and exporters (Jaeger, Prometheus, Loki, cloud vendors) — instrument once,
  export anywhere, which is why it replaced vendor-specific SDKs industry-wide.
- **Context propagation**: trace ID and span ID travel across process/
  network boundaries via headers (`traceparent`, W3C Trace Context) so a
  trace spans multiple services, not just one process.
- Sampling: tracing everything at scale is expensive; head-based sampling
  (decide at trace start, e.g. 10%) is the simple default; tail-based
  sampling (decide after seeing the whole trace, e.g. "keep all errors")
  is the production-grade approach — mention, don't implement both today.

### C. Jaeger — visualizing traces (15 min)
- Jaeger UI: search by service/operation, view a trace's waterfall (span
  durations stacked), inspect tags/logs attached to a span.
- Simple deployment mode (`allInOne`) bundles collector, query, and storage
  (in-memory or Badger) for a training cluster — production uses Elasticsearch/
  Cassandra/Tempo-style backends for durability and scale.

### D. Closing the correlation triangle (10 min)
- Metric spikes → find the time window → query logs for that window/service
  → find a `trace_id` in the log line → jump to Jaeger → see exactly which
  downstream call was slow. This full loop is the day's real deliverable —
  more valuable than any single tool.

## Lab (2h)

### Part 1 — Deploy Jaeger (25 min)
1. `helm repo add jaegertracing https://jaegertracing.github.io/helm-charts && helm repo update`.
2. `helm install jaeger jaegertracing/jaeger -n monitoring --set allInOne.enabled=true --set provisionDataStore.cassandra=false --set storage.type=memory`.
3. `kubectl -n monitoring port-forward svc/jaeger-query 16686` and open the UI.

### Part 2 — Instrument the app with OpenTelemetry (50 min)
4. Add the OTel SDK for the app's language (Python:
   `opentelemetry-distro`, `opentelemetry-exporter-otlp`) and auto-instrument
   the web framework (`opentelemetry-instrument python app.py`) plus any
   DB client in use.
5. Configure the OTLP exporter endpoint to point at the Jaeger collector
   (`jaeger-collector.monitoring.svc.cluster.local:4317`).
6. Manually add one custom span around a business-logic function (e.g. the
   report-generation step) with an attribute (`report.rows_processed`).
7. Redeploy, generate traffic, and confirm traces show up in the Jaeger UI
   under the app's service name.

### Part 3 — Correlate trace_id into logs (25 min)
8. Update the structured logger (Day 128) to pull the active span's
   `trace_id`/`span_id` from OTel context and include them in every log line.
9. Re-verify the Day 128 derived field: click a `trace_id` from a Loki log
   line in Grafana Explore and confirm it now jumps to the matching Jaeger trace.

### Part 4 — Project step (20 min)
10. Pick one real slow-ish path in the app, look at its trace waterfall,
    identify the span consuming the most time, and note the finding in
    `/opt/fresher_project/docs/observability-notes.md`.
11. Commit the OTel instrumentation code and updated logger.

**Definition of done:** Jaeger deployed; app traces visible with at least
one custom span; `trace_id` present in structured logs; at least one
successful log→trace jump in Grafana.
