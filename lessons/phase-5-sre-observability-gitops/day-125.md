## Theory (1h)

### A. Alertmanager's job (15 min)
- Prometheus rules decide **when** something's wrong (Day 123); Alertmanager
  decides **who hears about it, how, and how often** — it sits between rule
  evaluation and a human's phone/inbox.
- Pipeline: alert fires in Prometheus → sent to Alertmanager → routed →
  grouped → deduplicated → sent to a receiver (Slack, email, webhook, PagerDuty).

### B. Routing (15 min)
- `route` tree: a root route with `receiver`, `group_by`, `group_wait`,
  `group_interval`, `repeat_interval`, and nested `routes` matched by labels
  (`match` / `match_re`) — e.g. `severity: page` → PagerDuty-style receiver,
  `severity: warning` → Slack channel.
- Routes are evaluated top-down; child routes inherit parent settings unless
  overridden — first matching route in the tree wins (unless `continue: true`).

### C. Grouping and silencing (15 min)
- `group_by: [alertname, cluster]` — bundles related alerts into one
  notification instead of a flood (10 pods crashlooping = 1 message, not 10).
- `group_wait` (initial delay to batch), `group_interval` (time between
  updates to an existing group), `repeat_interval` (resend cadence for
  still-firing alerts).
- **Silences**: time-boxed mute by label matcher — for planned maintenance;
  always set an expiry, never silence indefinitely.
- **Inhibition**: suppress a lower-severity alert when a related higher-severity
  one is already firing (e.g. suppress `HighLatency` when `ServiceDown` fires).

### D. Runbooks — the payoff of a good alert (15 min)
- Every alert's `annotations` should include a `runbook_url` — a page telling
  the on-call person: what this alert means, likely causes, first three
  diagnostic commands, and escalation path if unresolved in N minutes.
- An alert without a runbook is a future 3am mystery — write the runbook
  *before* you consider the alert done, not after the first incident.

## Lab (2h)

### Part 1 — Configure routing (40 min)
1. Edit the Alertmanager config (via the kube-prometheus-stack `Secret` or
   its `AlertmanagerConfig` CR): add a root route with `group_by:
   ['alertname']`, `group_wait: 30s`, `group_interval: 5m`,
   `repeat_interval: 4h`.
2. Add a child route matching `severity: page` → a "page" receiver (use a
   webhook receiver pointed at a local test endpoint, e.g. `webhook.site`
   or a simple `nc -l` listener, since no real pager is wired up).
3. Add a child route matching `severity: warning` → a "notify" receiver
   (Slack webhook if available, else the same test webhook with a
   different label to distinguish it in logs).
4. Apply and confirm via the Alertmanager UI (Status → Config) that routes loaded.

### Part 2 — Trigger, group, and silence (40 min)
5. Fire `HighErrorRate` again (as in Day 123) and confirm it lands on the
   "page" route in Alertmanager's UI.
6. Fire two different alerts at once (e.g. also breach `HighLatency`) and
   observe them grouped into one notification if they share `group_by` labels.
7. Create a silence for `HighLatency` with a 15-minute expiry via the UI or
   `amtool silence add alertname=HighLatency --duration=15m`; confirm it
   stops notifying but the alert still shows as firing (silenced ≠ resolved).

### Part 3 — Inhibition rule (20 min)
8. Add an inhibition rule: if `alertname: ServiceDown` is firing, suppress
   `alertname: HighLatency` and `HighErrorRate` for the same service (they're
   symptoms of the same root cause).

### Part 4 — Project step: runbooks (20 min)
9. Write `/opt/fresher_project/docs/runbooks/high-error-rate.md` and
   `high-latency.md`: symptom, likely causes (deploy? dependency? resource
   exhaustion?), 3 diagnostic commands (`kubectl logs`, PromQL query to run,
   dashboard link), escalation note.
10. Add `runbook_url` annotations pointing at these files to both
    `PrometheusRule` alerts; commit everything.

**Definition of done:** routing tree separates page vs warning severities;
a silence was created and expired correctly; two runbooks committed and
linked from alert annotations.
