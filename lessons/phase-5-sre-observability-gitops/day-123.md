## Theory (1h)

### A. `rate()` and `increase()` — the counter-reading functions (20 min)
- Counters only go up (and reset to 0 on restart) — you never read a counter's
  raw value for "how much happened"; you use `rate()` or `increase()`.
- `rate(http_requests_total[5m])`: per-second average rate over the last 5
  minutes — handles counter resets automatically.
- `increase(http_requests_total[5m])`: total increase over the window
  (`rate() * window_seconds`, roughly) — better for "how many errors in 5m."
- Rule of thumb: window should be **≥ 4x the scrape interval** to avoid noise.

### B. `histogram_quantile()` — turning buckets into percentiles (20 min)
- Histograms expose `_bucket{le="..."}` cumulative counts, `_sum`, `_count`.
- Pattern: `histogram_quantile(0.99, sum(rate(request_duration_seconds_bucket[5m])) by (le))`
  — the p99 latency over 5 minutes.
- Why `sum by (le)` matters: aggregating across pods requires preserving the
  `le` (less-than-or-equal) label; dropping it breaks the quantile math.
- Caveat: bucket boundaries determine quantile accuracy — a `histogram_quantile`
  is an interpolation, not exact.

### C. Recording rules — precomputing expensive queries (10 min)
- `groups: - name: ... rules: - record: job:request_latency_p99:5m
  expr: histogram_quantile(0.99, ...)` — saved as a new time series,
  queried cheaply later (dashboards, alerts).
- Naming convention: `level:metric:operations` (e.g. `job:http_errors:rate5m`).

### D. Alerting rules — defining "this needs a human" (10 min)
- `groups: - name: ... rules: - alert: HighErrorRate expr: ... for: 5m
  labels: {severity: page} annotations: {summary: "..."}`.
- `for:` prevents flapping — the condition must hold continuously before firing.
- Alerting rules live in Prometheus; **routing** those alerts (who gets paged,
  when, how grouped) is Alertmanager's job — Day 125.

## Lab (2h)

### Part 1 — rate/increase drills (30 min)
1. On the app's `requests_total` counter, run
   `rate(requests_total[5m])` and `increase(requests_total[5m])` — generate
   load first (`for i in {1..50}; do curl -s localhost:PORT/ >/dev/null; done`).
2. Compare a 1m window vs 5m window on a bursty load pattern — discuss noise.

### Part 2 — histogram_quantile drills (30 min)
3. Run `histogram_quantile(0.50, sum(rate(request_duration_seconds_bucket[5m])) by (le))`
   and `histogram_quantile(0.99, ...)` — compare p50 vs p99.
4. Artificially slow one request path in the app (add `time.sleep(0.6)` on a
   test route), redeploy, regenerate load, and watch p99 shift while p50 stays flat.

### Part 3 — Recording + alerting rules (45 min)
5. Write a `PrometheusRule` CR with a recording rule
   `job:request_latency_p99:5m` for the app.
6. Write an alerting rule `HighLatency`: fires when the recorded p99 exceeds
   500ms for 5 minutes, `severity: warning`.
7. Write a second alert `HighErrorRate`: error ratio
   `sum(rate(requests_total{code=~"5.."}[5m])) / sum(rate(requests_total[5m])) > 0.05`
   for 5m, `severity: page`.
8. Apply the `PrometheusRule`; confirm both rules appear in Prometheus →
   Alerts, in `Inactive` state.

### Part 4 — Project step (15 min)
9. Trigger `HighErrorRate` on purpose (make the test route return 500s in a
   loop) and watch it go `Pending` → `Firing`. Screenshot or note the timing.
10. Commit the `PrometheusRule` manifest to the project repo.

**Definition of done:** recording rule visible under Prometheus → Rules;
both alerts defined and at least one observed transitioning to `Firing`.
