## Theory (1h)

### A. SLI, SLO, SLA — the vocabulary that runs SRE (20 min)
- **SLI** (indicator): a measured signal — e.g. request latency p99, error rate,
  availability ratio (good events / total events).
- **SLO** (objective): the internal target for an SLI over a window — e.g.
  "99.5% of requests succeed over 30 days."
- **SLA** (agreement): the external, often contractual promise — usually looser
  than the SLO, with a penalty. SLO is the tripwire before you breach the SLA.
- Pick SLIs that measure user-facing experience, not internal implementation
  (a healthy pod count is not an SLI).

### B. Error budgets — the mechanism that makes SLOs actionable (20 min)
- Error budget = 100% − SLO. A 99.9% SLO over 30 days = ~43 minutes of budget.
- Budget spent → freeze risky releases, prioritize reliability work over features.
- Budget healthy → ship faster, take more risk. This is the negotiation tool
  between dev velocity and operational stability — the core SRE contract.
- **Burn rate**: how fast you're consuming the budget (multi-window burn-rate
  alerts are Day 130's payoff — flag it now).

### C. Toil and on-call philosophy (15 min)
- Toil: manual, repetitive, automatable, no enduring value work. Google's SRE
  book caps toil at ~50% of an SRE's time — the rest goes to engineering it away.
- On-call is a rotation with a **budget of interruptions**, not a punishment;
  page only on symptoms that need a human *now* (user-facing SLO burn), not
  every internal warning.
- Blameless culture underpins all of this — Day 131 goes deeper on postmortems.

## Lab (2h)

### Part 1 — Inventory today's project (30 min)
1. List every user journey the project currently serves (e.g. "GET /report",
   "static site load", "DB write path").
2. For each journey, write down what "good" and "bad" look like from a user's
   perspective (not from a server's perspective).

### Part 2 — Draft SLIs (40 min)
3. For the top 2 journeys, define one availability SLI (successful / total
   requests) and one latency SLI (e.g. "requests under 500ms").
4. Decide the measurement window (30-day rolling is the SRE-book default).
5. Write these down in `/opt/fresher_project/docs/slo.md`.

### Part 3 — Project step: draft SLOs (50 min)
6. Turn each SLI into a target: e.g. "99.5% availability over 30 days",
   "95% of requests under 500ms over 30 days."
7. Compute the error budget in minutes for the 30-day window for each SLO.
8. Add a "toil log" section to `slo.md`: list 3 manual tasks done during the
   project's life so far (log pruning, redeploys, cert renewal) as toil
   candidates for future automation.
9. Commit `docs/slo.md` — this file is the seed for Day 124's dashboard and
   Day 130's burn-rate alerts.

**Definition of done:** at least 2 SLIs with numeric SLOs and computed error
budgets committed to `docs/slo.md`; toil log started.
