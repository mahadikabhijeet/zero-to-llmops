## Session plan (2h, timed)

### Block 1 — Inventory what's new since Checkpoint #1 (0:00–0:20)
- Walk Days 91–147 together and list every concrete, resume-worthy
  capability added: SLO definition, Prometheus/Grafana/Loki/Jaeger stack,
  GitOps via ArgoCD, Istio canary releases, chaos engineering, k6 load
  testing, Backstage platform work, DevSecOps scanning/policy, reliability
  patterns, and a live incident response (Day 145).
- Group into resume-line candidates: each should be an **achievement with
  a number or outcome**, not a tool list (e.g. "Reduced mean detection
  time from ~15min to <2min by implementing multi-window burn-rate
  alerting" beats "used Prometheus").

### Block 2 — Rewrite the resume's project section (0:20–1:00)
- Apply the standard resume-bullet formula: **action verb + what + how +
  measurable result**. Draft 4–6 new bullets from Block 1's inventory.
- Cut anything from Checkpoint #1 that's now superseded (e.g. "deployed to
  EC2" is subsumed by "GitOps-managed, meshed, SLO'd platform on AWS").
- Sanity check every bullet against the actual repo — nothing on the
  resume should be unverifiable by a reviewer clicking through to GitHub.

### Block 3 — Architecture diagram (1:00–1:30)
- Produce one current architecture diagram showing: the app, the mesh
  (Istio), the GitOps flow (ArgoCD), the observability stack (Prometheus/
  Grafana/Loki/Jaeger), and the AWS deployment target — a single picture
  an interviewer can screen-share understanding from in 30 seconds.
- Tool-agnostic: hand-drawn + photographed, draw.io, or Mermaid in the
  README — whichever the learner can actually produce and maintain; commit
  it to the repo as `docs/architecture.png` (or `.md` with a Mermaid block).

### Block 4 — README audit, pin repos, LinkedIn rewrite (1:30–2:00)
- README audit: confirm it has — what the project does (one paragraph),
  the architecture diagram, a "how to run it" section, and links to the
  SLO doc, runbooks, and dashboards (leveraging Day 141/142's Backstage
  catalog links as the source list).
- GitHub profile: pin the project repo and any template/platform repos
  from Days 142–143; confirm all commit history looks consistent with a
  real working project (no single giant "final commit" dump).
- LinkedIn: rewrite the headline and one post/summary line to reflect the
  SRE/platform-engineering skill set now demonstrated, not just "learning DevOps."

## Evaluation rubric
| Dimension | Weak | Solid | Strong |
|---|---|---|---|
| Resume bullets | Tool lists, no outcomes | Outcomes stated | Outcomes with numbers, verifiable in repo |
| Architecture diagram | Missing or outdated | Present, covers main components | Present, accurate, explains data/control flow at a glance |
| README | Missing setup or links | Has setup + links | Has setup + links + is what a hiring manager would actually read fully |
| LinkedIn | Unchanged since Checkpoint #1 | Headline updated | Headline + summary + at least one artifact-linked post |

**Definition of done:** resume project section rewritten with 4–6
outcome-based bullets; architecture diagram committed; README passes the
audit checklist; LinkedIn headline/summary updated.
