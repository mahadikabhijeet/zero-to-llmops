## Theory (1h)

### A. Why logs, when we already have metrics (10 min)
- Metrics tell you **that** something's wrong (error rate spiked); logs tell
  you **why** (the actual stack trace, the offending request ID). Traces
  (Day 129) tell you **where** in a distributed call chain. All three
  correlate around the same timestamp/request — that's the goal by Day 130.

### B. EFK vs Loki — the tradeoff (20 min)
- **EFK** (Elasticsearch + Fluentd/Fluent Bit + Kibana): full-text indexing
  of every log line — powerful free-text search, but Elasticsearch is
  resource-hungry (heap, disk, JVM tuning) — heavy for a training cluster.
- **Loki**: indexes only **labels** (like Prometheus does for metrics), not
  log content — dramatically cheaper to run and operate. Query language
  (LogQL) mirrors PromQL, which is why it's the pedagogically and
  operationally lighter choice here.
- Tradeoff: Loki's lack of full-text indexing means broad `|=` greps over
  large volumes are slower than Elasticsearch's — acceptable at this scale;
  a real production call weighs log volume and search patterns.
- Decision for this project: **Loki**, per README's cost/complexity stance.

### C. Loki architecture at a glance (15 min)
- Components: distributor (receives writes), ingester (chunks + flushes to
  storage), querier, and (for scale) a compactor — the Helm chart's
  single-binary mode collapses these for a training cluster.
- Log shipping agent: **promtail** (or Grafana Agent) runs as a DaemonSet,
  tails container logs from `/var/log/pods`, attaches Kubernetes labels
  (namespace, pod, container) automatically, ships to Loki.

### D. Labels — the design decision that matters most (10 min)
- Loki labels should be **low-cardinality** (namespace, app, container,
  level) — high-cardinality labels (request_id, user_id) blow up the index
  the same way they would in Prometheus. Put high-cardinality data in the
  **log line content**, query it with LogQL filters instead (Day 128).

## Lab (2h)

### Part 1 — Deploy Loki + promtail (40 min)
1. `helm repo add grafana https://grafana.github.io/helm-charts && helm repo update`.
2. `helm install loki grafana/loki-stack -n monitoring --set promtail.enabled=true`
   (bundles Loki + promtail in one chart). AWS-prod equivalent: same chart
   pointed at an S3-backed Loki config, or managed Grafana Cloud Loki — one
   values-file change, no cluster rearchitecture.
3. `kubectl get pods -n monitoring | grep -E 'loki|promtail'` — confirm the
   Loki pod and the promtail DaemonSet (one pod per node) are running.

### Part 2 — Wire Loki into Grafana (20 min)
4. In Grafana, add a new data source: Loki, URL
   `http://loki.monitoring.svc.cluster.local:3100`.
5. Go to Explore, select the Loki data source, and browse available labels
   (`namespace`, `pod`, `app`) via the label browser.

### Part 3 — First LogQL queries (40 min)
6. `{namespace="default"}` — raw log stream for the app's namespace.
7. `{app="project-app"} |= "error"` — filter to lines containing "error".
8. `{app="project-app"} != "healthcheck"` — exclude noisy healthcheck lines.
9. Generate an error in the app (hit the same test route from Day 123) and
   watch it appear live in Explore within a few seconds.

### Part 4 — Project step (20 min)
10. Confirm the project app's pod logs are being scraped by promtail with
    correct `app`/`namespace` labels (no manual config needed if the app
    just logs to stdout — the Kubernetes convention).
11. Add a "Logs" panel to the Day 124 Grafana dashboard using the Loki
    data source, filtered to `{app="project-app"}`; commit the updated
    dashboard JSON.

**Definition of done:** Loki + promtail running; Loki wired as a Grafana
data source; app logs queryable via LogQL; Logs panel added to the
project dashboard.
