## Theory (1h)

### A. Push vs pull deployment (15 min)
- **Push**: CI pipeline runs `kubectl apply` / `helm upgrade` directly
  against the cluster — CI needs cluster credentials, and the cluster's
  actual state can drift silently if someone runs a manual `kubectl edit`.
- **Pull**: an agent *inside* the cluster (ArgoCD) continuously watches a
  git repo and reconciles cluster state to match it — the cluster never
  hands out its credentials to CI, and drift is detected/auto-corrected.
- GitOps principle: **git is the single source of truth for desired state**;
  the cluster state is a function of what's in git, always reconcilable.

### B. ArgoCD core concepts (20 min)
- `Application` CR: points at a git repo path + target cluster/namespace;
  ArgoCD diffs live state vs the repo and shows `Synced`/`OutOfSync`,
  `Healthy`/`Degraded`.
- Sync can be manual (click "Sync" — good for learning) or automated
  (`syncPolicy.automated` — good once trust is built; Day 134 goes deeper
  on auto-prune/self-heal).
- Sources ArgoCD renders: plain YAML, Helm charts (with values), Kustomize
  overlays — it understands all three natively.

### C. App-of-apps pattern (15 min)
- One root `Application` whose "source" is a directory of *other*
  `Application` manifests — bootstrap the whole cluster's app set from a
  single `argocd app create` or `kubectl apply` of the root. Scales from
  "one app" to "N apps + platform tooling" without N manual `argocd app create` calls.

### D. Where CI still fits in a GitOps world (10 min)
- CI still builds, tests, and pushes the image + updates the manifest/values
  file in git (new image tag) — CI's job ends at "git now says version X
  should run"; ArgoCD's job is making the cluster actually run version X.
  This split is the answer to "doesn't GitOps replace CI?" (no, it replaces
  CD's *deployment* step, not build/test).

## Lab (2h)

### Part 1 — Install ArgoCD (25 min)
1. `kubectl create namespace argocd`.
2. `kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml`.
3. `kubectl -n argocd port-forward svc/argocd-server 8080:443`; get the
   initial admin password:
   `kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d`.
4. Install the `argocd` CLI; `argocd login localhost:8080`.

### Part 2 — Deploy a first app via ArgoCD (40 min)
5. Ensure the project's k8s manifests (or Helm chart, from Phase 3) live in
   a git path ArgoCD can reach.
6. `argocd app create project-app --repo <repo-url> --path <chart-or-manifest-path> --dest-server https://kubernetes.default.svc --dest-namespace default`.
7. `argocd app sync project-app`; watch it go `OutOfSync` → `Synced`,
   `Progressing` → `Healthy` in the UI or `argocd app get project-app`.
8. Make a trivial change in git (bump a label or replica count), commit,
   `argocd app diff project-app` to see drift detected, then sync.

### Part 3 — Manual drift and self-correction (30 min)
9. `kubectl scale deployment project-app --replicas=5` directly (bypassing
   git) — watch ArgoCD flag `OutOfSync` immediately without auto-syncing
   yet (manual sync policy).
10. Manually re-sync and confirm ArgoCD reverts to git's declared replica
    count — this is the drift-correction behavior that makes push-based
    hotfixes dangerous under GitOps (they get silently reverted).

### Part 4 — App-of-apps + project step (25 min)
11. Create an `apps/` directory in the repo containing an `Application`
    manifest for `project-app` and one for `kps` (kube-prometheus-stack,
    Day 122) or `loki` (Day 127) — anything already running.
12. Create one root `Application` pointing at `apps/`; `argocd app sync`
    the root and confirm both child apps register and sync.
13. Commit the `apps/` directory and root manifest to the project repo.

**Definition of done:** ArgoCD running; `project-app` deployed and synced
via ArgoCD; manual drift observed and corrected; app-of-apps root
successfully registers at least two child applications.
